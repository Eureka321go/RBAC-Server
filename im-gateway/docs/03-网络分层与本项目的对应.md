# 网络分层与本项目的对应

> 网络分层是学网络绕不开的地基。好消息是:本项目**几乎每一层都能找到真实代码**,是绝好的教材。
> 本文先讲分层,再把每一层映射到 RBAC-Server / im-gateway 的具体组件和代码。
> 关联阅读:`01-im-gateway架构与源码精读.md`(pipeline、心跳)、`02-为什么是Netty...md`(epoll)。

---

## 一、两套模型:先分清 OSI 和 TCP/IP

网络分层有两套说法,别被搞混:

| OSI 七层(教科书理论) | TCP/IP 四层(工程实际) | 一句话职责 |
|---|---|---|
| 7 应用层 Application | 应用层 | **你的业务数据长什么样**(HTTP/WebSocket/Redis 协议…) |
| 6 表示层 Presentation | (并入应用层) | 编码、加密、压缩(TLS、JSON、UTF-8) |
| 5 会话层 Session | (并入应用层) | 会话的建立/维持(实际很模糊) |
| 4 传输层 Transport | 传输层 | **进程到进程**,可靠传输(TCP / UDP) |
| 3 网络层 Network | 网络层 | **主机到主机**,寻址与路由(IP) |
| 2 数据链路层 Data Link | 网络接口层 | 相邻设备间传帧(以太网、MAC、ARP) |
| 1 物理层 Physical | 网络接口层 | 电信号/光信号/网线电波 |

- **OSI 七层**是理论模型,用来教学、分析问题时分层定位。
- **TCP/IP 四层**是真实互联网跑的模型,把 OSI 的上三层(会话/表示/应用)合并成一个"应用层"。
- 日常沟通两套混着用:讲"应用层""传输层"用 TCP/IP 的叫法;讲"这属于表示层的加密"又借 OSI 的词。知道它们对得上就行。

### 记忆钥匙:层与层之间是"封装"关系

**上层的整包数据,是下层的"货物(payload)"。** 发数据时像套娃,一层层往外包:

```
你的消息 {"op":"SEND","text":"hi"}          ← 应用层数据
  └─ 塞进 TCP 段:[TCP头 | 上面那坨]           ← 传输层加"端口"
       └─ 塞进 IP 包:[IP头 | TCP段]           ← 网络层加"IP地址"
            └─ 塞进以太网帧:[帧头|IP包|帧尾]   ← 链路层加"MAC地址"
                 └─ 变成电信号发出去           ← 物理层
```

收数据时反着拆。**每一层只关心自己那层的头,不管里面装的是啥** —— 这就是分层解耦的威力:TCP 不需要懂 HTTP,IP 不需要懂 TCP,各修各的路。

## 二、四个关键层各干嘛(挑项目用得到的深讲)

物理层、链路层云厂商和操作系统全包了,这里从网络层往上讲。

### 网络层(IP):负责"到哪台机器"

- 核心是 **IP 地址**,解决"茫茫互联网里,数据发给哪台主机"。
- 只管"尽力送到",**不保证送达、不保证顺序、不保证不重复** —— 这些是上层 TCP 的事。
- 项目里的体现:`106.15.89.180`(阿里云那台机器的公网 IP)、Docker 容器之间的 `172.x` 内网 IP。

### 传输层(TCP / UDP):负责"到哪个进程"+"可靠"

这一层项目重度依赖,必须讲清。

**端口:定位进程。** IP 找到机器,端口找到机器上的具体程序:

| 端口 | 谁在听 |
|------|--------|
| 8080 | RBAC backend(HTTP,context-path `/api`) |
| 9001 | im-gateway 的 WebSocket |
| 8090 | 网关 actuator(配了但暂未启 web,见 `01` 文档) |
| 3306 | MySQL |
| 6379 | Redis |
| 9092 | Kafka |
| 27017 | MongoDB |
| 9000 | MinIO |

**TCP 的核心价值 = 把不可靠的 IP 变可靠:**

- 三次握手建连接、四次挥手关连接
- 数据分段、编号、丢了重传、乱序重排 → **保证按序到达、不丢不重**
- 流量控制(别把慢的接收方冲垮)、拥塞控制(别把网络堵死)

**UDP 则相反:** 不保证送达、不保证顺序,但快、开销小(视频通话、DNS、游戏用它)。本项目全程走 TCP。

> **"长连接"到底是什么?**
> 就是**一条建好之后一直不关闭的 TCP 连接**。普通 HTTP 请求用完就关 TCP;IM 建好之后一直留着,消息随时双向流动。所谓"维持 50 万在线",就是一台/几台机器上同时挂着 50 万条不关闭的 TCP 连接 —— 这也是为什么瓶颈是**文件描述符(FD)和内存**,每条 TCP 连接都占一个 FD 和两个内核缓冲区。

### 应用层:负责"数据的语义"

TCP 只负责把一堆字节可靠送到,**但这堆字节是什么意思,由应用层协议定义**。同样走 TCP,可以是不同"方言":

| 应用层协议 | 模型 | 项目里谁在用 |
|-----------|------|-------------|
| HTTP | 请求/响应,一问一答 | RBAC 所有 `/api/**` 接口(Spring MVC) |
| WebSocket | 全双工,双方随时主动发 | im-gateway 的 `/im` 长连接 |
| RESP | Redis 自定义 | session、路由表、seq |
| Kafka wire protocol | Kafka 自定义 | `im-inbound` / `im-outbound` |
| MySQL protocol | MySQL 自定义 | 会话/成员/群(MyBatis-Plus) |
| MongoDB wire protocol | MongoDB 自定义 | 消息正文 |
| S3 (HTTP 之上) | 对象存储 | MinIO 富媒体 |

**同一种传输层(TCP),承载完全不同的应用层协议。** 传输层不关心方言内容,只负责可靠送达。

### 表示层的现实存在:TLS / 加密

理论归表示层,工程上它夹在 TCP 和应用层之间:

- `https://` = HTTP + **TLS**;`wss://` = WebSocket + TLS
- 项目 `docs/ops/02-域名与HTTPS配置.md` 配的就是这个。**Nginx 终结 TLS** —— 把加密的外部流量解密后,转发给内部的明文 HTTP/WS。所以 backend 和网关内部只处理明文,不用自己管证书。

## 三、本项目对应哪几层(重点)

**结论:本项目是彻头彻尾的应用层项目,但 im-gateway 和传输层贴身肉搏。**

```
┌─────────────────────────────────────────────────────────────┐
│ 应用层   ★★★ 项目主战场                                       │
│   • HTTP        RBAC REST 接口 /api/**(Spring MVC)          │
│   • WebSocket   im-gateway 长连接 /im(Netty)                │
│   • RESP        Redis:session、路由表、seq                   │
│   • Kafka 协议  im-inbound / im-outbound                     │
│   • MySQL 协议  会话/成员/群(MyBatis-Plus)                  │
│   • MongoDB 协议 消息正文                                     │
│   • TLS/HTTPS   Nginx 终结,wss://                            │
├─────────────────────────────────────────────────────────────┤
│ 传输层   ★★★ 网关贴身操作                                     │
│   • TCP:所有连接。Netty 直接操作 TCP socket                 │
│     SO_BACKLOG / SO_KEEPALIVE 就是 TCP 层参数                │
├─────────────────────────────────────────────────────────────┤
│ 网络层   ☆ 不写代码,但要懂                                    │
│   • IP:阿里云公网 IP、Docker 容器内网 IP                    │
├─────────────────────────────────────────────────────────────┤
│ 链路层 / 物理层  ☆ 云厂商 & 操作系统全包,你完全不碰          │
└─────────────────────────────────────────────────────────────┘
```

### 传输层 —— im-gateway 比 RBAC backend "更底层"的地方

`NettyWebSocketServer.java` 里这几行,全是**直接拨弄 TCP**:

```java
.channel(NioServerSocketChannel.class)              // 我要一个 TCP 服务端 socket
.option(ChannelOption.SO_BACKLOG, 1024)             // TCP 三次握手完成、等 accept 的队列长度
.childOption(ChannelOption.SO_KEEPALIVE, true)      // 开启 TCP 层保活探测
```

- **`SO_BACKLOG`**:TCP 层面,握手已完成但程序还没来得及 `accept` 的连接排队上限。高并发瞬时建连时太小会**丢连接**。
- **`SO_KEEPALIVE`**:TCP 协议自带的保活探测(和应用层心跳是两回事,见下一节)。

> **关键对比:为什么说网关"更底层"?**
> 普通 Spring Boot 后端(RBAC)**看不到这些参数** —— 因为 Tomcat 把整个传输层封装好了,你只跟 HTTP 对象打交道。而 im-gateway 直接站在 TCP 上自己搭 WebSocket,所以必须亲手管这些 socket 参数。**这层封装被捅破,正是网关的技术含量所在。**

### 应用层 —— WebSocket 的"混血"身世

WebSocket 是从 HTTP **升级**而来的。回看网关的 pipeline(`WebSocketChannelInitializer.java`):

```
HttpServerCodec           ← 先按 HTTP 协议解析(此刻应用层 = HTTP)
  → HandshakeAuthHandler  ← 还在 HTTP 阶段,验 token(身份认证)
  → WebSocketServerProtocolHandler ← 发一个"协议升级"握手
  → (升级完成后)           ← 应用层从此变成 WebSocket
  → ImFrameHandler        ← 收发 WebSocketFrame
```

**同一条 TCP 连接,应用层协议在握手瞬间从 HTTP 变成了 WebSocket。** 这就是为什么客户端连的是 `ws://.../im`(URL 形式脱胎于 HTTP),连上后却能双向自由收发。

> 呼应 `01` 文档"两个握手 handler"的区分:`HandshakeAuthHandler` 做的是**身份认证(token)**,`WebSocketServerProtocolHandler` 做的是**协议升级(HTTP→WS)** —— 前者认证完自拆,后者留守完成升级。本质就是"HTTP 阶段"和"WebSocket 阶段"的分界线。

### 一个必须澄清的点:两种"心跳"分属两层(面试常考)

项目里 `IdleStateHandler` 和上面的 `SO_KEEPALIVE` 都叫"保活",但**不在同一层**:

| | 属于哪层 | 谁做的 | 探测什么 | 灵敏度 |
|---|---|---|---|---|
| `SO_KEEPALIVE` | **传输层**(TCP) | 操作系统内核 | TCP 连接底层通道是否还通 | 默认约 2 小时才探,极迟钝 |
| `IdleStateHandler` + PING 帧 | **应用层** | 你的 Netty 代码 | 对端**应用**是否还活着、还响应 | 项目设 60 秒,灵敏 |

**为什么两个都要?** TCP KEEPALIVE 太慢太粗,发现不了"TCP 还连着、但应用假死/卡住"的情况。IM 必须自己做应用层心跳(`IdleStateHandler`),才能及时踢掉僵尸连接、回收 FD。`01` 文档那个 60 秒 idle 关连接,就是应用层心跳。

## 四、一条消息穿越所有层(把知识串起来)

用户 A 发 "hi",从上到下封装、传输、再从下到上解封:

```
【A 客户端】自上而下封装
  应用层:  {"op":"SEND","text":"hi"}  按 WebSocket 帧格式打包
  表示层:  TLS 加密(wss)
  传输层:  切成 TCP 段,加端口(→ 9001)
  网络层:  加 IP(→ 网关机器 IP)
  链路层:  加 MAC,变电信号
             │  ~~~ 穿过互联网,沿途路由器一跳跳转发 ~~~
             ▼
【网关机器】自下而上解封
  链路层 → 网络层 → 传输层(TCP 重组、按序、去重)→ TLS 解密
             ▼
  应用层:  Netty pipeline 收到完整 WebSocketFrame → ImFrameHandler
             ▼
  之后是你熟悉的业务链路:
    Kafka(又一次跨网络到 backend)→ 定序 → MongoDB → 扇出 → 再跨网络推回 B
```

**关键认知:A→网关、网关→Kafka、Kafka→backend、backend→Redis/Mongo,每一跳都是一次完整的"多层封装 + 解封"。** 项目里那么多 `localhost:端口`,每一个背后都是一次传输层握手 + 应用层协议交互。**分布式系统的性能开销,很大一部分就来自这些反复的跨网络封装/解封** —— 这也是为什么"把网关和业务拆开"虽然换来可扩展性,却要付出多一跳 Kafka 网络往返的代价。

## 五、一句话总结

> 本项目主体活在**应用层**(HTTP / WebSocket / 各种中间件协议)。
> RBAC backend 靠 Tomcat 把传输层封装掉了,只碰应用层;
> 而 **im-gateway 的技术价值,恰恰在于它捅破了这层封装,直接站到传输层(TCP)上** ——
> 自己管 socket 参数(`SO_BACKLOG`/`SO_KEEPALIVE`)、自己把 HTTP 升级成 WebSocket、自己做应用层心跳。
> 网络层及以下,阿里云和操作系统全替你包了。
