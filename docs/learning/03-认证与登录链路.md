# 阶段 3 — 认证与登录链路【核心吃透 1】

> 目标：一个用户从"输账号密码"到"拿到令牌、以后每次请求都被系统认成已登录"，中间到底发生了什么。
> 这是全项目最精彩的部分之一。读完你要能**对着流程图，用自己的话把登录讲一遍**。

## 零、先建立一个大心智模型

传统网站用 **Session**：登录后服务器在自己内存里记「张三已登录」，发给浏览器一个 sessionId 饼干。缺点：服务器要存状态，多台机器难共享。

本项目用 **JWT + Redis 会话**的混合方案，核心思想：

- **JWT（令牌）**：一张「盖了防伪章的通行证」，本身就写着「我是用户 3、这张证 access 类型、几点过期」，服务器**不用查库**光验章就知道真假。
- **但纯 JWT 有个死穴**：签发出去就收不回，没到期之前你没法让它失效（改密/登出/强踢都做不到）。
- **本项目的解法**：令牌只管「证明身份」，真正「这张证还有效吗」去 **Redis 会话**里查一把。**登出/改密 = 删掉 Redis 里那条会话**，令牌当场作废——这是本项目认证设计最聪明的一笔，务必记住。

一句话：**JWT 证明"你是谁"，Redis 会话决定"你还算不算登录中"。两者缺一不可。**

## 一、登录全流程（AuthController.login → AuthService.login）

### 1.1 入口：`AuthController`

```java
@PostMapping("/login")
public Result<LoginVO> login(@Valid @RequestBody LoginRequest request, HttpServletRequest servletRequest) {
    String userAgent = servletRequest.getHeader("User-Agent");
    return Result.success(authService.login(request, clientIp(servletRequest), userAgent));
}
```

- `@RequestBody LoginRequest`：把前端发来的 JSON `{username, password}` 装进 `LoginRequest` 对象。
- `@Valid`：先校验 `LoginRequest` 上的规则（`@NotBlank` username/password），空的直接被挡回，进不了 Service。
- `clientIp(...)` / `User-Agent`：顺手抓来源 IP 和浏览器信息，为了**写登录日志**。
- 真正干活的是 `authService.login(...)`，Controller 只是「收快递、转交」。

### 1.2 大脑：`AuthService.login`（逐段精读）

```java
public LoginVO login(LoginRequest request, String loginIp, String userAgent) {
    try {
        // ① 按用户名查用户
        SysUser user = userMapper.selectOne(Wrappers.<SysUser>lambdaQuery()
                .eq(SysUser::getUsername, request.getUsername()));
        // ② 用户不存在 或 密码不对 → 同一个错（不告诉坏人到底哪错了）
        if (user == null || !passwordEncoder.matches(request.getPassword(), user.getPassword())) {
            throw new BusinessException("auth.badCredentials");
        }
        // ③ 账号被禁用 → 拒绝
        if (!"ENABLED".equals(user.getStatus())) {
            throw new BusinessException("auth.disabled");
        }

        // ④ 装配"登录用户上下文"：查出角色、权限码、部门、数据范围
        LoginUser loginUser = loginUserAssembler.assemble(user);
        // ⑤ 签发令牌 + 写 Redis 会话
        LoginVO loginVO = issueTokens(loginUser);

        // ⑥ 记录本次登录的时间和 IP
        SysUser update = new SysUser();
        update.setId(user.getId());
        update.setLastLoginAt(LocalDateTime.now());
        update.setLastLoginIp(loginIp);
        userMapper.updateById(update);

        // ⑦ 写"登录成功"日志
        logService.recordLogin(request.getUsername(), true, "登录成功", loginIp, userAgent);
        return loginVO;
    } catch (BusinessException e) {
        // 只要上面任何一步抛错，都写一条"登录失败"日志，再把错抛出去
        logService.recordLogin(request.getUsername(), false, e.getMessage(), loginIp, userAgent);
        throw e;
    }
}
```

**几个必须理解的点：**

- **② 密码怎么校验的？** 库里存的**不是明文密码**，是 BCrypt 哈希（阶段 2 见过 `data.sql` 里那串 `$2a$10$...`）。`passwordEncoder.matches(明文, 哈希)` 把用户输入的明文用同样算法哈希后比对。**数据库泄露了也拿不到原始密码**——这是安全底线。
- **② 为什么"用户不存在"和"密码错"报同一个错？** 安全考虑：如果分开报错，坏人就能靠「这个提示」判断哪些用户名真实存在（用户枚举攻击）。统一成 `auth.badCredentials`，堵住这个信息泄露。
- **④ `assemble` 干了啥？** 见下面第二节——把「一个用户」变成「带角色、权限、数据范围的完整登录上下文」。
- **⑦ 登录日志 try/catch 的巧思**：成功走 `try` 尾部记「成功」；任何一步抛 `BusinessException` 都落到 `catch` 记「失败」再重新抛出。**成功失败都留痕**，安全审计要的就是这个。

## 二、装配登录上下文（LoginUserAssembler.assemble）

登录校验通过后，光有一个 `SysUser` 还不够——系统还需要知道「这人有哪些角色、能点哪些按钮、能看哪个范围的数据」。这就是 `assemble` 干的：

```java
public LoginUser assemble(SysUser user) {
    LoginUser loginUser = new LoginUser();
    loginUser.setUserId(user.getId());
    loginUser.setUsername(user.getUsername());
    // ...昵称、头像、部门 id...

    // 查部门名
    if (user.getDeptId() != null) {
        SysDept dept = deptMapper.selectById(user.getDeptId());
        if (dept != null) loginUser.setDeptName(dept.getDeptName());
    }

    // ① 查这个用户的所有【启用】角色
    List<SysRole> roles = roleMapper.selectRolesByUserId(user.getId()).stream()
            .filter(r -> "ENABLED".equals(r.getStatus()))
            .collect(Collectors.toList());
    List<String> roleCodes = roles.stream().map(SysRole::getRoleCode).collect(Collectors.toList());
    loginUser.setRoleCodes(roleCodes);

    // ② 是不是超管？
    boolean isSuper = roleCodes.contains(SUPER_ADMIN);   // "super_admin"
    // ③ 超管拿【全部】权限码；普通用户按"用户→角色→菜单"链路查出自己的权限码
    List<String> perms = isSuper
            ? menuMapper.selectAllPermissionCodes()
            : menuMapper.selectPermissionCodesByUserId(user.getId());
    loginUser.setPermissions(new HashSet<>(perms));

    // ④ 数据范围：超管=ALL；普通用户取其多个角色里"范围最大"的那个
    loginUser.setDataScope(isSuper ? "ALL" : mergeDataScope(roles));
    return loginUser;
}
```

**这里把阶段 2 讲的"权限链"真正跑通了：**

```
user.id ──selectPermissionCodesByUserId──▶ 顺着 sys_user_role → sys_role_menu
                                          → 查出这个用户所有 BUTTON 菜单的 permission_code
                                          ──▶ 一堆权限码字符串（如 system:user:add）
```

- **③ 超管走捷径**：`super_admin` 不查链路，直接 `selectAllPermissionCodes()` 拿全站权限——所以超管什么按钮都能点。这也是阶段 2 说的 `admin → super_admin → 全部权限` 那条链的代码落点。
- **④ 多角色数据范围取并集里最大的**：`mergeDataScope` 按 `ALL > CUSTOM_DEPT > OWN_DEPT_CHILD > OWN_DEPT > SELF` 的优先级，挑范围最大的。一个人若同时是「部门经理(OWN_DEPT)」和「区域总监(ALL)」，最终按 ALL 算。**数据范围的细节留到阶段 4 详讲**，这里只需知道：登录时就把 `dataScope` 算好、塞进 `LoginUser`。

装配完的 `LoginUser` 长这样（`security/model/LoginUser.java`）：

```java
public class LoginUser implements UserDetails, Serializable {
    private Long userId;
    private String username;
    private List<String> roleCodes;
    private Set<String> permissions;   // 权限码集合 = Spring Security 的 authorities
    private String dataScope;          // 合并后的数据范围
    // ...
}
```

**两个关键身份：**
- `implements UserDetails`：它是 Spring Security 认识的「当前用户」标准类型。`getAuthorities()` 把 `permissions` 变成 Security 的权限对象——**这就是 `@PreAuthorize("hasAuthority('system:user:add')")` 能生效的原因**（阶段 4 详讲）。
- `implements Serializable`：它要被**存进 Redis**（序列化成 JSON），所以必须可序列化。注意 `getPassword()` 打了 `@JsonIgnore` 且返回 `null`——**密码绝不进会话缓存**，安全红线。

## 三、签发令牌 + 写会话（issueTokens）

```java
private LoginVO issueTokens(LoginUser loginUser) {
    String accessJti  = JwtTokenProvider.newJti();   // 给 access 证一个唯一编号
    String refreshJti = JwtTokenProvider.newJti();   // 给 refresh 证一个唯一编号
    String accessToken  = tokenProvider.createAccessToken(accessJti, loginUser.getUserId(), loginUser.getUsername());
    String refreshToken = tokenProvider.createRefreshToken(refreshJti, loginUser.getUserId(), loginUser.getUsername());
    // ★ 把会话写进 Redis，并设过期时间
    sessionService.saveAccessSession(accessJti, loginUser, tokenProvider.getAccessTtlSeconds());
    sessionService.saveRefreshSession(refreshJti, loginUser.getUserId(), tokenProvider.getRefreshTtlSeconds());
    return new LoginVO(accessToken, refreshToken, tokenProvider.getAccessTtlSeconds());
}
```

### 3.1 什么是 access + refresh 双令牌？为什么要两个？

| | access token（访问令牌） | refresh token（刷新令牌） |
|---|---|---|
| 干嘛的 | 每次请求都带上它，证明「我已登录」 | 专门用来「换一张新的 access」 |
| 有效期 | **短**（本项目 7200 秒 = 2 小时） | **长**（604800 秒 = 7 天） |
| 带在哪 | 每个请求头 `Authorization: Bearer xxx` | 只在调 `/auth/refresh-token` 时用 |

**为什么不干脆发一个长期 access 就好？** 因为 access 到处在网络里跑，暴露面大，所以让它**短命**——就算被偷，2 小时后自动废。而 refresh 只在刷新那一下用、平时躺着，暴露面小，可以**长命**。这样兼顾了「安全」和「不用每 2 小时重新登录」。

### 3.2 `jti` 是什么？（本项目撤销机制的钥匙）

`jti` = JWT ID，每张令牌一个**唯一编号**（`newJti()` 用 `UUID` 生成）。它同时是：
1. 写进 JWT 里的一个字段；
2. **Redis 里那条会话的 key**（`auth:access:<jti>`）。

于是「令牌」和「Redis 会话」通过 `jti` 一一绑定。**记住这个绑定关系**，第五节撤销全靠它。

### 3.3 JWT 长什么样（JwtTokenProvider.createToken）

```java
return Jwts.builder()
        .id(jti)                              // jti：唯一编号
        .subject(String.valueOf(userId))      // sub：这令牌属于哪个用户
        .claim("username", username)
        .claim("typ", type)                   // typ：access 还是 refresh
        .issuedAt(now)                        // 签发时间
        .expiration(exp)                      // 过期时间
        .signWith(key)                        // ★ 用密钥签名（防伪章）
        .compact();
```

生成出来是形如 `xxxxx.yyyyy.zzzzz` 的三段字符串（Header.Payload.Signature）。**前两段只是 Base64 编码、能被任何人解开看内容——所以 JWT 里绝不放密码等敏感信息**。第三段 `Signature` 是用服务器密钥 `rbac.jwt.secret`（在 `application.yml`）算出来的签名：改动前两段任何一个字符，签名就对不上，`parse` 时当场识破。

> ⚠️ **安全红线**：`rbac.jwt.secret` 一旦泄露，别人就能伪造任意用户的令牌。所以它只能放在服务器配置里，`application.yml` 里那个是本地开发用的，**生产环境必须换成强随机密钥**。

### 3.4 Redis 会话里存了什么（TokenSessionService）

```java
private static final String ACCESS_KEY  = "auth:access:";
private static final String REFRESH_KEY = "auth:refresh:";

public void saveAccessSession(String jti, LoginUser loginUser, long ttlSeconds) {
    redisTemplate.opsForValue().set(ACCESS_KEY + jti, loginUser, ttlSeconds, TimeUnit.SECONDS);
}
public void saveRefreshSession(String jti, Long userId, long ttlSeconds) {
    redisTemplate.opsForValue().set(REFRESH_KEY + jti, userId, ttlSeconds, TimeUnit.SECONDS);
}
```

- access 会话：key=`auth:access:<jti>`，value=**整个 LoginUser**（角色/权限/数据范围都在里面）。这样每次请求验证时能直接拿到，不用反复查库。
- refresh 会话：key=`auth:refresh:<jti>`，value 只存 `userId`（刷新时再用 id 重新查最新的用户信息）。
- 两者都设了**和令牌一样的过期时间**（TTL），Redis 到点自动清理。

登录到这里就完成了。前端拿到 `LoginVO { accessToken, refreshToken, expiresIn }`，把 access 存起来，以后每个请求都带上它。

## 四、每次请求如何被认成"已登录"（JwtAuthenticationFilter）

登录之后，前端每个请求头都带 `Authorization: Bearer <accessToken>`。这些请求进服务器，**第一道关卡**就是这个过滤器（在 Controller 之前执行）：

```java
protected void doFilterInternal(request, response, filterChain) {
    String token = resolveToken(request);   // ① 从 Authorization 头取出 Bearer 后面的令牌
    if (StringUtils.hasText(token) && 当前还没认证) {
        try {
            Claims claims = tokenProvider.parse(token);   // ② 验签+验过期，拿到令牌内容
            if (TYPE_ACCESS.equals(claims.get("typ"))) {   // ③ 必须是 access 类型（refresh 不能当门票用）
                LoginUser loginUser = tokenSessionService.getAccessSession(claims.getId());  // ④ ★用 jti 去 Redis 查会话
                if (loginUser != null) {                    // ⑤ 会话还在 → 认证通过
                    UsernamePasswordAuthenticationToken authentication =
                        new UsernamePasswordAuthenticationToken(loginUser, null, loginUser.getAuthorities());
                    SecurityContextHolder.getContext().setAuthentication(authentication);  // ⑥ ★写进"当前登录上下文"
                }
            }
        } catch (Exception ignored) {
            // 令牌无效/过期：什么都不做，后面由 EntryPoint 返回 401
        }
    }
    filterChain.doFilter(request, response);   // 放行到下一环（无论认没认成，都往下走）
}
```

**逐关拆解（这是本阶段最核心的一段）：**

1. **① 取令牌**：只认 `Authorization: Bearer xxx` 格式，截掉 `Bearer ` 前缀。
2. **② 验令牌**：`parse` 会验签名 + 验是否过期。伪造的、改过的、过期的，这里直接抛异常 → 落到 catch → 不认证。
3. **③ 类型必须是 access**：拿 refresh 令牌来访问普通接口？`typ` 不是 access，拒。防止令牌被乱用。
4. **④ ★关键一步：去 Redis 查会话**。就算令牌本身完好、没过期，只要 `auth:access:<jti>` 这条会话在 Redis 里**不存在了**，`getAccessSession` 返回 null → 不认证。**这就是"可撤销"的实现点**。
5. **⑥ 写入 SecurityContext**：认证通过后，把 `LoginUser` 放进 Spring Security 的「当前请求上下文」。之后 Controller/Service 里任何地方调 `SecurityUtils.getLoginUser()` 拿到的就是这个人。`@PreAuthorize` 判断权限、数据权限取 `dataScope`，都靠它。

> 注意最后一行 `filterChain.doFilter` **无条件放行**到下一环。过滤器本身不负责「拒绝」——它只负责「能认就认」。认没认成的**后果**由后面的规则决定（见第六节 401/403）。

## 五、为什么登出/改密/强踢后，旧令牌立刻失效？（撤销机制）

这是阶段 3 小测必考、也是面试高频题。答案就藏在「第四节第 ④ 步：每次请求都要去 Redis 查会话」。

### 5.1 登出 `AuthService.logout`

```java
public void logout(String accessToken) {
    if (accessToken == null) return;
    try {
        Claims claims = tokenProvider.parse(accessToken);
        sessionService.removeAccessSession(claims.getId());   // ★ 删掉 Redis 里那条会话
    } catch (Exception ignored) { }
}
```

登出做的事只有一件：**根据令牌里的 jti，把 `auth:access:<jti>` 这条 Redis 会话删掉**。

之后会发生什么？那张 access 令牌**本身还没过期、签名也还有效**，但下次它再来请求时，第四节第 ④ 步 `getAccessSession(jti)` 会返回 **null**（会话已删）→ 认证失败 → 401。**令牌当场作废。**

### 5.2 一图看懂

```
登录：         签发令牌(jti=abc)  +  Redis 写入 auth:access:abc = LoginUser
                      │
每次请求：      带令牌(jti=abc) → 过滤器 parse OK → 查 Redis auth:access:abc
                      │                                      │
                  会话在 → 认证通过 ✅            会话被删 → 返回 null → 401 ❌
                      │
登出/改密/强踢：  删除 Redis auth:access:abc  ←── 就是在这里"抽掉"了会话
```

**核心那句话（背下来）**：令牌只是「门票」，Redis 会话才是「今天这张票还认不认」的开关。删了会话 = 撕了这张票，不管票面日期有没有到。

- **登出**：删自己的 access 会话。
- **改密 / 管理员强制下线**：删掉该用户对应的会话（同理），旧令牌全部作废——安全红线「改密后旧 Token 必须失效」就是这么落地的。

> 对比纯 JWT 方案：纯 JWT 没有这个 Redis 环节，令牌签出去就收不回，登出只能靠前端「自己把令牌删了」，但被偷走的那张照样能用到过期。本项目用 Redis 会话补上了这个洞。

## 六、刷新令牌（AuthService.refresh）—— 令牌轮换

access 只有 2 小时，到期后不能让用户重新登录。前端会拿 refresh 去 `/auth/refresh-token` 换新的：

```java
public LoginVO refresh(String refreshToken) {
    Claims claims;
    try {
        claims = tokenProvider.parse(refreshToken);          // ① 验 refresh 令牌
    } catch (Exception e) {
        throw new BusinessException(401, "auth.refreshInvalid");
    }
    if (!TYPE_REFRESH.equals(claims.get("typ"))) {           // ② 必须是 refresh 类型
        throw new BusinessException(401, "auth.refreshTypeError");
    }
    Long userId = sessionService.getRefreshUserId(claims.getId());  // ③ refresh 会话还在吗
    if (userId == null) throw new BusinessException(401, "auth.loginExpired");
    SysUser user = userMapper.selectById(userId);            // ④ 重新查最新用户
    if (user == null || !"ENABLED".equals(user.getStatus()))
        throw new BusinessException(401, "auth.accountUnavailable");

    sessionService.removeRefreshSession(claims.getId());     // ⑤ ★删掉旧 refresh 会话（轮换）
    LoginUser loginUser = loginUserAssembler.assemble(user); // ⑥ 重新装配（拿到最新角色/权限）
    return issueTokens(loginUser);                           // ⑦ 签发全新的 access + refresh
}
```

**要点：**
- **⑤ 令牌轮换（rotation）**：换新令牌时，把旧 refresh 会话删掉，发一张全新的 refresh。这样同一张 refresh 只能用一次，被偷了也难连续利用——安全加固手段。
- **⑥ 重新 `assemble`**：刷新时重新查一遍用户，所以「管理员刚给你加了个角色」在刷新后就生效了。
- **③④ 双重校验**：refresh 会话没了（登出/过期）、或账号被禁用，都刷新失败，逼用户重新登录。

## 七、安全总配置（SecurityConfig）—— 这一切的规则来源

前面所有「过滤器在 Controller 前跑」「白名单放行」「没认证就 401」的规则，都在这一个配置类里定：

```java
@Configuration
@EnableMethodSecurity                       // ★ 开启 @PreAuthorize 方法级鉴权（阶段 4 用）
public class SecurityConfig {

    private static final String[] WHITELIST = {   // 无需登录就能访问的白名单
        "/auth/login", "/auth/refresh-token", "/ping", "/error"
    };

    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) {
        http
            .csrf(disable)                                   // 无状态 API，不需要 CSRF token
            .sessionManagement(STATELESS)                    // ★ 不用传统 Session，纯令牌
            .authorizeHttpRequests(auth -> auth
                .requestMatchers(WHITELIST).permitAll()      // 白名单：放行
                .anyRequest().authenticated())               // 其余：必须已认证
            .exceptionHandling(e -> e
                .authenticationEntryPoint(authenticationEntryPoint)  // 未认证 → 401
                .accessDeniedHandler(accessDeniedHandler))           // 认证了但没权限 → 403
            .addFilterBefore(jwtAuthenticationFilter,        // ★ 把我们的过滤器插到最前面
                             UsernamePasswordAuthenticationFilter.class);
        return http.build();
    }

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();                  // 登录校验密码用的就是它
    }
}
```

**逐条理解：**
- **`STATELESS`**：告诉 Spring Security「别给我建传统 Session」——身份完全靠每个请求自带的令牌，服务器不在内存里记登录态。这正是 JWT 方案的前提。
- **白名单 `permitAll`**：登录、刷新、探活、错误页不需要令牌（不然「登录接口本身」都要求先登录就死循环了）。**其余全部 `authenticated()`**——必须先过第四节那关。
- **`addFilterBefore`**：把 `JwtAuthenticationFilter` 塞在 Spring Security 默认过滤器之前，保证「每个请求先经过我们的 JWT 识别」。
- **`@EnableMethodSecurity`**：打开 `@PreAuthorize` 开关——第二层鉴权（权限码）靠它，**阶段 4 详讲**。

### 401 vs 403（两个必须分清的状态码）

| 状态码 | 含义 | 谁处理 | 什么情况 |
|--------|------|--------|----------|
| **401 Unauthorized** | 没登录 / 令牌无效 | `JwtAuthenticationEntryPoint` | 没带令牌、令牌过期、会话被删（登出后） |
| **403 Forbidden** | 登录了，但没这个权限 | `RestAccessDeniedHandler` | 普通用户去点「删除用户」这种需要 `system:user:delete` 的操作 |

一句话记忆：**401 = 你是谁我不认识（去登录）；403 = 我认识你，但这事不归你管（没权限）。** 前端也据此区别处理：401 去刷新令牌/跳登录页，403 直接提示「无权限」。

## 八、一个登录请求的一生（完整串讲）

```
【登录阶段】
浏览器  POST /api/auth/login {username, password}
   │
AuthController.login ── @Valid 校验非空 ──▶ AuthService.login
   │                                          │
   │   ① selectOne 按用户名查 SysUser
   │   ② passwordEncoder.matches 验 BCrypt 密码
   │   ③ 校验 status=ENABLED
   │   ④ LoginUserAssembler.assemble → 查角色/权限码/部门/dataScope → LoginUser
   │   ⑤ issueTokens：
   │        造 access JWT(jti=A) + refresh JWT(jti=R)
   │        Redis 写 auth:access:A = LoginUser（TTL 2h）
   │        Redis 写 auth:refresh:R = userId（TTL 7d）
   │   ⑥ 更新 last_login_at/ip + 写登录日志
   │
   ◀── 返回 LoginVO { accessToken, refreshToken, expiresIn }
浏览器把 accessToken 存起来

【此后每个请求】
浏览器  GET /api/system/users   Header: Authorization: Bearer <accessToken>
   │
JwtAuthenticationFilter（Controller 之前）
   │   ① 取出 Bearer 令牌
   │   ② parse 验签+验过期
   │   ③ 检查 typ=access
   │   ④ 用 jti 去 Redis 查 auth:access:A
   │        ├─ 会话在  → 认证通过，把 LoginUser 写进 SecurityContext ─▶ 进 Controller
   │        └─ 会话没了/令牌无效 → 不认证 ─▶ 到达 anyRequest().authenticated() 失败 ─▶ 401
   │
【登出 / 改密 / 强踢】
   删除 Redis auth:access:A  ──▶ 上面第 ④ 步查不到会话 ──▶ 旧令牌立刻作废
```

## 九、阶段 3 小测

1. 本项目为什么不用纯 JWT，而要额外配一个 Redis 会话？各自负责什么？
2. access token 和 refresh token 有什么区别？为什么要搞两个、有效期为什么一短一长？
3. `jti` 是什么？它把「令牌」和「Redis 会话」怎么关联起来的？
4. 用户点了「登出」，那张 access 令牌**明明还没过期**，为什么下一个请求就用不了了？（讲清具体机制）
5. `JwtAuthenticationFilter` 里为什么要判断 `typ == access`？拿 refresh 令牌来访问普通接口会怎样？
6. 登录时为什么「用户不存在」和「密码错误」要返回同一个错误信息？
7. `SecurityConfig` 里 `STATELESS` 是什么意思？白名单为什么必须包含 `/auth/login`？
8. 401 和 403 分别代表什么？各举一个本项目里会触发它的场景。
9. `refresh` 方法里第 ⑤ 步「删掉旧 refresh 会话再发新的」这个「令牌轮换」有什么安全意义？
10. （综合）对着第八节的图，用你自己的话把「一个登录请求」+「之后一次带令牌的普通请求」从头到尾讲一遍。

<details>
<summary>👉 点击展开参考答案（先自己想，再对答案）</summary>

**1.** 纯 JWT 的死穴是「签发即不可撤销」——登出/改密/强踢都做不到。本项目让 **JWT 负责证明"你是谁"（验签就知真假，不用查库）**，**Redis 会话负责"你还算不算登录中"（删了就失效）**，两者配合既保留 JWT 无状态验签的好处，又补上了「可撤销」。

**2.** access 每个请求都带、暴露面大，所以**短命**（2h），被偷了也很快废；refresh 只在换令牌时用、平时不动、暴露面小，所以**长命**（7d）。这样既安全又不用频繁重新登录。

**3.** `jti` 是每张令牌的唯一编号（UUID）。它既写进 JWT，又当 Redis 会话的 key（`auth:access:<jti>`）。于是「某张令牌」和「某条会话」一一绑定，撤销时按 jti 删会话即可。

**4.** 因为每次请求在 `JwtAuthenticationFilter` 里，令牌 parse 通过后**还要用 jti 去 Redis 查会话**。登出时 `removeAccessSession` 把 `auth:access:<jti>` 删了，下次 `getAccessSession` 返回 null → 不认证 → 401。令牌票面没过期，但「会话开关」被关了。

**5.** 为了防止令牌被乱用：refresh 是专门用来换令牌的，不该拿它当访问普通接口的门票。`typ != access` 直接不认证，把两种令牌的用途隔离开。

**6.** 防「用户枚举」：若分开报错，攻击者能靠提示判断哪些用户名真实存在。统一成 `auth.badCredentials` 堵住这个信息泄露。

**7.** `STATELESS` = 不创建传统服务器 Session，身份完全靠每个请求自带的令牌，服务器不存登录态。白名单必须含 `/auth/login`，否则「登录接口本身也要求先登录」→ 无法登录的死循环。

**8.** 401=未认证（没登录/令牌无效/会话被删，如登出后再请求）；403=已认证但无权限（如普通用户去调需要 `system:user:delete` 的删除接口）。

**9.** 令牌轮换让同一张 refresh 只能用一次，用完即弃换新的。即使 refresh 被偷，攻击者也难以长期反复利用；也便于检测异常（旧 refresh 复用可发现被盗）。
