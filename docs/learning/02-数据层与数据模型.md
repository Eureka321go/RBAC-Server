## 一、先鸟瞰：14 张表分 4 组

别被"14 张表"吓到，它们按用途分 4 组，其实很有条理：

| 组 | 表 | 作用 |
|----|-----|------|
| **① RBAC 主体表**（5 张） | `sys_user`、`sys_role`、`sys_menu`、`sys_dept`、`sys_post` | 用户、角色、菜单/权限、部门、岗位——五个核心概念各一张 |
| **② 关联表**（4 张） | `sys_user_role`、`sys_role_menu`、`sys_role_dept`、`sys_user_post` | 把主体表"多对多"地连起来（RBAC 的关节） |
| **③ 配置/字典表**（3 张） | `sys_config`、`sys_dict_type`、`sys_dict_data` | 系统参数、数据字典（下拉选项来源） |
| **④ 日志表**（2 张） | `sys_login_log`、`sys_operation_log` | 登录日志、操作日志 |

> 前两组（9 张）是 RBAC 核心，务必吃透；后两组（5 张）是配套功能，脸熟即可，阶段 6 再细看。

## 二、① RBAC 主体表逐张看（记"每张表管什么"，不用背字段）

**`sys_user` 用户表** —— 一个登录账号一行
关键字段：`username`（登录名）、`password`（BCrypt 加密后的密码）、`dept_id`（属于哪个部门）、`status`（ENABLED/DISABLED）、`last_login_at/ip`（最后登录信息）。

**`sys_role` 角色表** —— 一个角色一行
关键字段：`role_code`（角色编码，如 `super_admin`，**代码里靠它判断身份**）、`role_name`（显示名）、`data_scope`（⭐数据范围，`ALL/CUSTOM_DEPT/OWN_DEPT/OWN_DEPT_CHILD/SELF`，阶段 4 主角）、`builtin`（是否内置，内置角色不许删）。

**`sys_menu` 菜单表** —— **一行既可能是菜单，也可能是一个"权限点"**
关键字段：
- `menu_type`：`DIR`(目录) / `MENU`(菜单页) / `BUTTON`(按钮)——**同一张表用类型区分三种东西**。
- `parent_id`：指向父菜单，**0 表示顶级**（所以菜单是一棵树）。
- `permission_code`：⭐**权限码**，如 `system:user:add`。这就是阶段 0/1 见过的 `@PreAuthorize("hasAuthority('system:user:add')")` 里那个字符串的**源头**。
- `path`/`component`：前端路由和组件路径（前端动态菜单用）。

> 💡 **关键领悟**：本项目"权限"没有单独的表，而是**塞在菜单表里**——一个 `BUTTON` 类型的菜单行，它的 `permission_code` 就是一个权限点。"给角色分配权限" = 在 `sys_role_menu` 里连一条"角色↔菜单"记录。

**`sys_dept` 部门表** —— 一个部门一行，`parent_id` 指向上级部门（**又一棵树**：总部→研发部→…）。字段 `leader_user_id`（负责人）。

**`sys_post` 岗位表** —— 一个岗位一行，`post_code`/`post_name`。偏 HR 标签，和权限解耦。

## 三、② 关联表——RBAC 的"关节"（最能体现设计思想）

关联表都很"瘦"，通常就 3 列：`id` + 两个外键。它们表达**"多对多"**关系。

```
sys_user_role   (user_id, role_id)   一个用户可有多个角色，一个角色可给多个用户 → 用户 ⇄ 角色
sys_role_menu   (role_id, menu_id)   一个角色可有多个权限，一个权限可给多个角色 → 角色 ⇄ 权限/菜单
sys_user_post   (user_id, post_id)   用户 ⇄ 岗位
sys_role_dept   (role_id, dept_id, include_children)   角色 ⇄ 授权部门（数据权限用，多一列"是否含子部门"）
```

**为什么要单独的关联表？** 因为一个用户可能同时是"财务"和"审计"两个角色（多对多），没法在 `sys_user` 里用一个字段表示。所以用一张中间表，一行代表一条"连接"：

```
sys_user_role 表实际数据（来自 data.sql）：
  user_id=1 (admin) → role_id=1 (super_admin)
  user_id=2 (test)  → role_id=2 (system_admin)
```

**串起来看一条完整的权限链**（RBAC 的精髓，务必理解）：

```
admin(sys_user)
  └─ sys_user_role ─→ super_admin(sys_role)
                        └─ sys_role_menu ─→ system:user:add 等一堆权限(sys_menu)
```

> 于是"admin 能不能新增用户？"这个问题，就变成"顺着这条链能不能走到 `system:user:add` 这个权限码"。整个授权系统就是在做这种"顺着关联表查"的事。

## 四、公共字段：`BaseEntity`（每张主体表都有的那一截）

回看 schema，你会发现主体表结尾几乎都长一样：

```sql
`created_by` BIGINT   NULL COMMENT '创建人',
`created_at` DATETIME NULL COMMENT '创建时间',
`updated_by` BIGINT   NULL COMMENT '更新人',
`updated_at` DATETIME NULL COMMENT '更新时间',
`deleted`    TINYINT  NOT NULL DEFAULT 0 COMMENT '逻辑删除 0/1',
```

这些"谁建的、啥时候建的、删没删"的字段**每张表都要**，所以抽出来放进 `BaseEntity`，14 个实体 `extends` 它就自动都有（回顾阶段 1 的继承）。看 `BaseEntity.java`：

```java
@Data
public class BaseEntity implements Serializable {

    @TableId(type = IdType.AUTO)                                    // 主键，数据库自增
    private Long id;

    @TableField(value = "created_by", fill = FieldFill.INSERT)      // 只在"插入"时自动填
    private Long createdBy;

    @TableField(value = "created_at", fill = FieldFill.INSERT)
    private LocalDateTime createdAt;

    @TableField(value = "updated_by", fill = FieldFill.INSERT_UPDATE) // 插入和更新时都填
    private Long updatedBy;

    @TableField(value = "updated_at", fill = FieldFill.INSERT_UPDATE)
    private LocalDateTime updatedAt;

    @TableLogic                                                     // ⭐逻辑删除标记
    @TableField("deleted")
    private Integer deleted;
}
```

三个 MyBatis-Plus 注解，逐个理解：

- **`@TableId(type = IdType.AUTO)`**：标记 `id` 是主键，`AUTO` = 用数据库自增（插入时不用你给 id，库自动分配）。
- **`@TableField(value="created_at", fill=FieldFill.INSERT)`**：告诉框架"这个字段对应库里 `created_at` 列，并且**在插入时自动填值**"。`INSERT` = 只插入时填；`INSERT_UPDATE` = 插入和更新时都填。**谁来填？** 看第五节。
- **`@TableLogic`**：标记 `deleted` 是"逻辑删除"字段。看第六节。

## 五、审计字段"自动填充"：`AuditMetaObjectHandler`

上一节说 `created_at` 等字段"自动填"，**填的动作发生在这里**。看 `AuditMetaObjectHandler.java`：

```java
@Component                                          // 登记成 Bean，交给 Spring 管理
public class AuditMetaObjectHandler implements MetaObjectHandler {

    @Override
    public void insertFill(MetaObject metaObject) {  // 每次 insert 时，框架自动回调这里
        LocalDateTime now = LocalDateTime.now();
        Long userId = SecurityUtils.getUserIdOrNull(); // 取"当前登录人是谁"
        strictInsertFill(metaObject, "createdAt", LocalDateTime.class, now);   // 填创建时间=现在
        strictInsertFill(metaObject, "updatedAt", LocalDateTime.class, now);
        strictInsertFill(metaObject, "createdBy", Long.class, userId);         // 填创建人=当前用户
        strictInsertFill(metaObject, "updatedBy", Long.class, userId);
    }

    @Override
    public void updateFill(MetaObject metaObject) {  // 每次 update 时自动回调
        strictUpdateFill(metaObject, "updatedAt", LocalDateTime.class, LocalDateTime.now());
        strictUpdateFill(metaObject, "updatedBy", Long.class, SecurityUtils.getUserIdOrNull());
    }
}
```

**效果**：`UserService.create()` 里只写了塞业务字段，**从没设置 `createdAt`/`createdBy`**，但存进库后这些字段自动有值了——因为插入时框架自动回调 `insertFill` 帮你填。

> 这是又一个"框架帮你干活"的例子，和 Lombok 异曲同工：把"每次都要做的重复事"（记录谁、何时操作）自动化，业务代码就干净了。`SecurityUtils.getUserIdOrNull()`（取当前登录人）阶段 3/4 会讲。

## 六、逻辑删除：数据"假装删了"，其实还在

**物理删除** = 真的 `DELETE FROM` 把行删掉，数据没了。
**逻辑删除** = 只把 `deleted` 从 `0` 改成 `1`，数据还在表里，只是"当作已删除"。本项目**用的是逻辑删除**（数据可追溯、可恢复，更安全）。

三处配合，缺一不可：

1. **实体**：`BaseEntity` 里 `deleted` 字段贴了 `@TableLogic`。
2. **全局配置**：`application.yml` 里（回顾阶段 0）：
   ```yaml
   logic-delete-field: deleted
   logic-delete-value: 1        # 1 = 已删
   logic-not-delete-value: 0    # 0 = 未删
   ```
3. **效果（框架自动做的魔法）**：
   - 你调 `userMapper.deleteById(5)` → 框架实际执行的是 `UPDATE sys_user SET deleted=1 WHERE id=5`，**不是真删**。
   - 你调任何查询（`selectById`、`selectList`…）→ 框架**自动在 SQL 后面加 `AND deleted=0`**，被逻辑删除的行永远查不出来。

> 🔎 现在能解释 schema 里一个"奇怪"设计了：`UNIQUE KEY uk_user_username (username, deleted)`——唯一约束带上了 `deleted`。为什么？因为逻辑删除后行还在，如果只对 `username` 唯一，你就没法再创建同名用户（老的"已删"行还占着名字）。把 `deleted` 加进唯一键，"已删的 zhangsan(deleted=1)"和"新建的 zhangsan(deleted=0)"就不冲突了。**这是逻辑删除的经典配套技巧。**

## 七、MyBatis-Plus 怎么用（看懂项目里的数据库操作）

### 7.1 实体 ↔ 表：`@TableName`

```java
@TableName("sys_user")                 // 声明：这个类对应库里的 sys_user 表
public class SysUser extends BaseEntity { ... }
```

**字段名怎么对上列名？** 靠 `application.yml` 里 `map-underscore-to-camel-case: true`：Java 的 `deptId`（驼峰）自动对应库里的 `dept_id`（下划线）。这就是项目约定"**库用 snake_case、代码用 camelCase**"能自动衔接的原因，绝大多数字段不用手写映射。

### 7.2 空接口白拿一堆现成方法：`BaseMapper`

回顾阶段 0/1：`SysUserMapper extends BaseMapper<SysUser>` 是个空接口，却能用一堆方法——因为 `BaseMapper<SysUser>` 里预置了常用增删改查：

| 方法 | 作用 |
|------|------|
| `insert(user)` | 插入一行 |
| `selectById(id)` | 按主键查一行 |
| `selectList(wrapper)` | 按条件查多行 |
| `selectPage(page, wrapper)` | 分页查 |
| `selectCount(wrapper)` | 统计条数 |
| `updateById(user)` | 按主键更新 |
| `deleteById(id)` | 按主键删（本项目=逻辑删除） |

**你一行实现都没写，这些方法就都能用。** 这是 MyBatis-Plus 最大的省事之处。

### 7.3 拼查询条件：`LambdaQueryWrapper`

不想手写 SQL 的 `WHERE`，用 `Wrappers.lambdaQuery()` 链式拼条件。看 `UserService.page` 真实片段：

```java
var wrapper = Wrappers.<SysUser>lambdaQuery()
    .like(StringUtils.hasText(query.getUsername()), SysUser::getUsername, query.getUsername())
    .eq(query.getDeptId() != null, SysUser::getDeptId, query.getDeptId())
    .eq(StringUtils.hasText(query.getStatus()), SysUser::getStatus, query.getStatus());
```

翻译成 SQL 大致是：`WHERE username LIKE '%xx%' AND dept_id = ? AND status = ?`

三个要点：
- `.like(...)` / `.eq(...)` = SQL 的 `LIKE` / `=`。
- `SysUser::getUsername` = "用哪个字段"（框架据此翻译成列名 `username`）。
- **每个条件的第一个参数是"要不要加这个条件"的开关**：`StringUtils.hasText(query.getUsername())` 为 true（用户传了用户名）才拼 `username` 这一段，没传就跳过。**这就是"动态查询"**——前端传了哪些筛选项，SQL 就只带哪些条件，不用写一堆 `if`。

### 7.4 分页：`Page` + 分页插件

```java
IPage<SysUser> page = userMapper.selectPage(Page.of(query.current(), query.size()), wrapper);
```

`Page.of(第几页, 每页几条)` 造一个分页请求，`selectPage` 就自动帮你在 SQL 里加 `LIMIT`，还顺带查出总条数。

**这个分页魔法能生效，靠 `MybatisPlusConfig` 注册的分页插件**：

```java
@Configuration
public class MybatisPlusConfig {
    @Bean
    public MybatisPlusInterceptor mybatisPlusInterceptor() {
        MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
        interceptor.addInnerInterceptor(new PaginationInnerInterceptor(DbType.MYSQL)); // ← 分页拦截器
        return interceptor;
    }
}
```

> 没注册这个插件，`selectPage` 只会返回全部数据、不分页。所以它是分页能工作的前提。

### 7.5 复杂查询就手写 SQL：`@Select`

`BaseMapper` 的通用方法应付不了的（比如跨表、只取某一列），就在 Mapper 接口上手写。看 `SysUserPostMapper`（你之前打开过）：

```java
public interface SysUserPostMapper extends BaseMapper<SysUserPost> {

    @Select("SELECT post_id FROM sys_user_post WHERE user_id = #{userId}")   // 手写 SQL
    List<Long> selectPostIdsByUserId(Long userId);
}
```

`#{userId}` 是占位符，方法参数 `userId` 会安全地填进去（防 SQL 注入）。**所以项目里数据层有两种写法**：简单的用 `BaseMapper` 现成方法，复杂的用 `@Select`/XML 手写。

## 八、统一分页封装：`PageRequest` / `PageResult`

为了让"所有列表接口的分页参数和返回结构都一致"，项目封了两个类：

**`PageRequest`（入参基类）**：前端传 `page`（第几页，从 1 开始）、`pageSize`（每页几条）。注意它做了**防护**：

```java
public long size() {
    if (pageSize == null || pageSize < 1) return 20;   // 没传或非法 → 默认 20
    return Math.min(pageSize, 200);                     // 最多一次 200 条，防止一次拉爆
}
```

> `UserQuery` 就 `extends PageRequest`，所以自动带了分页能力。

**`PageResult<T>`（出参）**：统一返回 `records`(数据列表) + `total`(总条数) + `page` + `pageSize`。前端拿到的分页结构永远一样，好写通用表格组件。它还有个便利方法 `from(page, mapper)` 一步把"分页实体"转成"分页 VO"。

## 九、初始数据从哪来：`data.sql`

程序启动时会自动执行 `db/schema.sql`（建表）和 `db/data.sql`（塞种子数据），配置见 `application.yml` 的 `spring.sql.init`。种子数据里最重要的是**内置超管账号**：

```sql
-- 用户
INSERT IGNORE INTO sys_user (id, username, nickname, password, ...) VALUES
  (1, 'admin', '超级管理员', '$2a$10$7JB720yubVSZ...', ...);   -- 密码是 BCrypt 哈希，明文见 data.sql 注释
-- 用户角色：把 admin(id=1) 和 super_admin 角色(id=1) 连起来
INSERT IGNORE INTO sys_user_role (id, user_id, role_id) VALUES (1, 1, 1);
```

- `INSERT IGNORE` = 幂等：如果这行已存在（主键冲突）就跳过，**重启不会重复插入/报错**。
- 密码存的是 **BCrypt 哈希**（`$2a$10$...`），不是明文——数据库泄露也拿不到原始密码。阶段 3 讲登录时会看它怎么被校验。
- `admin` 通过 `sys_user_role` 连到 `super_admin` 角色（`data_scope=ALL`），所以它拥有全部权限和全部数据——这就是第三节那条"权限链"的活实例。

**1. 14 张表分哪 4 组？哪 9 张是 RBAC 核心？**
- 四组：① **RBAC 主体表**（`sys_user`/`sys_role`/`sys_menu`/`sys_dept`/`sys_post`，5 张）② **关联表**（`sys_user_role`/`sys_role_menu`/`sys_role_dept`/`sys_user_post`，4 张）③ **配置字典**（`sys_config`/`sys_dict_type`/`sys_dict_data`，3 张）④ **日志**（`sys_login_log`/`sys_oper_log`，2 张）。
- **RBAC 核心 9 张 = 5 张主体表 + 4 张关联表**。

**2. "权限"存在哪张表？`system:user:add` 是什么类型的一行？**
- 存在 **`sys_menu`（菜单表）**——本项目没有单独的"权限表"，权限点就是菜单表里的一行。
- 它是 **`menu_type = 'BUTTON'`** 类型的一行，该行的 `permission_code` 字段值就是 `system:user:add`。这个字符串正是 `@PreAuthorize("hasAuthority('system:user:add')")` 里用的那个。

**3. 为什么要 `sys_user_role` 关联表？不能在 `sys_user` 加个 `role_id` 吗？**
- 因为用户和角色是**多对多**：一个用户可以有多个角色，一个角色也被多个用户拥有。
- 在 `sys_user` 里加**一个** `role_id` 只能表达"一个用户一个角色"，装不下"一个用户多个角色"。关联表用「一行 = 一个 user_id + 一个 role_id」的方式，多对多就能任意组合。（`sys_role_menu`/`sys_user_post` 同理。）

**4. `deleted` 是干嘛的？`deleteById(5)` 实际发生了什么？**
- `deleted` 是**逻辑删除**标记（0=存在，1=已删）。删除不真的把行 delete 掉，只是打个标记，数据可追溯/可恢复。
- 调 `deleteById(5)` 时，因为 `deleted` 贴了 `@TableLogic`，MyBatis-Plus 实际执行的是 **`UPDATE sys_user SET deleted=1 WHERE id=5`**，而**不是** `DELETE`。之后所有查询会自动带上 `AND deleted=0`，这条就查不到了。

**5. 为什么 `uk_user_username` 唯一键要带上 `deleted` 列？**
- 因为删除只是把 `deleted` 改成 1、行还在。如果唯一键只管 `username`，那删掉的 `admin`（仍占着 username='admin' 这行）会**挡住**你再建一个新的 `admin`。
- 把 `deleted` 一起纳入唯一键（`username + deleted`），"已删的 admin(deleted=1)" 和 "新建的 admin(deleted=0)" 就算不同组合，不冲突——**既保证在用的用户名唯一，又允许删除后重名重建**。

**6. `deptId` ↔ `dept_id` 靠什么自动对上？**
- 靠 MyBatis 的**驼峰↔下划线自动映射**：`application.yml` 里配了 `map-underscore-to-camel-case: true`，框架会把库里的 `dept_id` 自动对应到 Java 的 `deptId`（`createdAt`↔`created_at` 同理）。所以字段不用逐个手写映射。

**7. `.eq(query.getDeptId() != null, ...)` 第一个参数起什么作用？**
- 它是**"要不要拼这个条件"的开关**（`condition` 参数，`true`/`false`）。
- `query.getDeptId() != null` → 前端**传了**部门就 `true`，这个 `dept_id = ?` 条件才拼进 SQL；**没传**就 `false`，条件直接跳过。这就是"动态查询"：**有值才拼，没值不拼**，避免把没填的条件也塞进 WHERE 导致查空。

**8. `created_at`/`created_by` 没手动设，为什么有值？谁干的？**
- 是 **`AuditMetaObjectHandler`**（实现了 MyBatis-Plus 的 `MetaObjectHandler`）干的。
- 它在 **insert 时自动填** `createdAt`/`createdBy`（`createdBy` 从 `SecurityUtils` 取当前登录用户 id），**update 时自动填** `updatedAt`/`updatedBy`。配合 `BaseEntity` 上字段的 `@TableField(fill=...)` 标记生效，所以业务代码不用手动 set，这些审计字段也有值。

</details>
