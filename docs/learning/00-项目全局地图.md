## 一、RBAC 到底是个什么东西？（用门禁卡理解）

RBAC = **R**ole **B**ased **A**ccess **C**ontrol，中文叫"基于角色的访问控制"。
一句话：**决定"谁能进哪扇门、能按哪个按钮、能看哪些数据"的系统。**

别背定义，想象一栋公司大楼：

| 现实世界 | 本系统里的概念 | 对应数据库表 |
|----------|----------------|--------------|
| 员工本人 | **用户**（User） | `sys_user` |
| 员工的职务，比如"财务""前台""保安队长" | **角色**（Role） | `sys_role` |
| 一张能力清单，比如"能开财务室的门""能按报销确认钮" | **权限**（Permission） | 藏在 `sys_menu` 里 |
| 大楼里的楼层导航图（你能看到哪些楼层入口） | **菜单**（Menu） | `sys_menu` |
| 员工属于哪个部门（决定他能看哪些人的数据） | **部门**（Dept） | `sys_dept` |

**核心思想**：权限不直接发给"人"，而是发给"角色"，再把角色发给人。

```
        分配角色                 角色拥有
 用户 ───────────► 角色 ───────────► 权限 / 菜单
（张三）         （财务）        （能看报销、能审批）
```

好处：来了 100 个财务，你不用给每个人单独配 50 项权限，只要给他们都挂上"财务"这个角色即可。哪天权限要改，改"财务"角色一处，100 人同时生效。

> 🔑 这就是整个项目的灵魂。后面所有代码，本质都在服务这一句话："**判断当前这个人，有没有资格做当前这件事、看当前这批数据。**"

本项目在标准 RBAC 上还多做了两层，属于"专业级"配置，先混个脸熟：

- **岗位（Post）**：`sys_post`，员工的职位标签（如"项目经理"），偏 HR 属性，和权限解耦。
- **数据权限（Data Scope）**：光有"能看用户列表"的权限还不够，还要控制"能看**哪些**用户"——是全公司、只本部门、还是只自己。这是本项目**最难也最出彩**的部分，留到阶段 4 专门吃透。

## 二、技术栈全景（每个都只记一句话职责）

后端是 Java 项目。你会反复听到这几个名字，先建立"它是干嘛的"的直觉即可：

| 名字 | 一句话职责 | 生活类比 |
|------|-----------|----------|

| **Spring Security** | 安全框架，负责"登录了没""有没有权限" | 大楼的"门禁 + 保安系统" |
| **MyBatis-Plus** | 数据库操作框架，帮你把 Java 对象和数据库表来回搬 | "仓库管理员"，帮你存取货 |
| **MySQL 8** | 关系型数据库，数据最终存这里 | 真正的"仓库" |

## 三、目录结构导览（东西放在哪）

后端代码都在 `backend/src/main/java/com/rbac/` 下。顶层分成 4 大块：

```
com.rbac
├── auth        →【认证】登录、登出、刷新令牌、"我是谁"。用户进门第一站。
├── security    →【安全】JWT 令牌、过滤器、Spring Security 配置。门禁系统本体。
├── common      →【公共地基】所有模块共用的东西：
│   ├── Result           统一返回格式 {code, message, data}
│   ├── domain           BaseEntity（每张表都有的公共字段）、分页
│   ├── exception        业务异常 + 全局异常处理
│   ├── datascope        数据权限计算（最难点）
│   ├── config           各种配置（Redis、MyBatis、国际化、审计）
│   └── util             工具类（取当前登录用户、取国际化文案）
└── system      →【业务模块】8 个高度对称的模块，本项目主体：
    ├── user     用户管理
    ├── role     角色管理
    ├── menu     菜单/权限管理
    ├── dept     部门管理
    ├── post     岗位管理
    ├── config   系统参数管理
    ├── dict     数据字典管理
    ├── log      日志（登录日志 + 操作日志）
    └── dashboard 首页统计
```

**最重要的规律（记住它，后面省一半力气）**：
`system` 下的 8 个业务模块，内部结构**几乎一模一样**，每个都是这 6 层"七件套"：

```
user/
├── controller/  接口层：接收 HTTP 请求，定义 URL（如 /system/users）
├── service/     业务层：真正干活、写业务规则的地方
├── mapper/      数据层：和数据库表打交道（增删改查）
├── entity/      实体：和数据库表一一对应的 Java 类（如 SysUser ↔ sys_user 表）
├── dto/         入参：前端传进来的数据（如"创建用户请求"）
└── vo/          出参：返回给前端的数据（如"用户展示对象"）
```

> 🎯 这就是为什么我们的策略是"**吃透 user 一个模块 = 掌握 80% 代码套路**"。
> 阶段 5 会把 user 模块从头到尾精读一遍，之后其余 7 个模块你自己对照着看就懂了。

## 四、一个请求的一生（全书最重要的一张图）

假设前端要"查询用户列表"，发了一个 HTTP 请求 `GET /api/system/users`。它在后端经历这样一段旅程：

```
 ┌─────────┐
 │ 浏览器  │  带着门禁卡(JWT Token)，请求 GET /api/system/users
 └────┬────┘
      │ ①
      ▼
 ┌──────────────────────────┐
 │ JwtAuthenticationFilter  │  门禁检查：从请求头取出 Token
 │ （安全过滤器，第一道关）  │  → 去 Redis 查"这张卡还有效吗"
 └────┬─────────────────────┘  → 有效则记下"当前登录人是谁"
      │ ②
      ▼
 ┌──────────────────────────┐
 │ @PreAuthorize 权限校验    │  第二道关：这个人有 'system:user:list' 权限吗？
 │ （方法级鉴权）            │  没有 → 直接 403 拒绝
 └────┬─────────────────────┘
      │ ③
      ▼
 ┌──────────────────────────┐
 │ UserController.page()    │  接口层：接住请求，转交给 Service
 └────┬─────────────────────┘
      │ ④
      ▼
 ┌──────────────────────────┐
 │ UserService.page()       │  业务层：核心逻辑
 │  · 算"这个人能看哪些数据" │  ← 第三道关：数据权限（阶段4）
 │  · 拼查询条件            │
 └────┬─────────────────────┘
      │ ⑤
      ▼
 ┌──────────────────────────┐
 │ SysUserMapper            │  数据层：翻译成 SQL
 └────┬─────────────────────┘
      │ ⑥
      ▼
 ┌──────────────────────────┐
 │ MySQL 数据库             │  真正查数据，返回结果
 └────┬─────────────────────┘
      │  原路返回，Service 把 entity 转成 VO，
      │  Controller 包成统一的 Result{code,message,data}
      ▼
 ┌─────────┐
 │ 浏览器  │  收到 JSON：{ "code":200, "message":"...", "data":{...} }
 └─────────┘
```

**看这张图你要读出 3 件事**：

1. **三道安全关卡**（本项目的安全主线，`CLAUDE.md` 里叫"鉴权三层"）：
   - ① 你登录了吗？（`JwtAuthenticationFilter`）
   - ② 你有这个操作的权限码吗？（`@PreAuthorize`）
   - ③ 你能看这批具体数据吗？（`DataScopeService` 数据权限）
2. **分层很清晰**：Controller 只接活、Service 干活、Mapper 碰数据库，各司其职。
3. **进出都统一**：所有返回都包成 `Result`，所以前端拿到的 JSON 格式永远一致。

> 这张图我们后面每个核心阶段都会回来看一次，每次给它填更多细节。现在能大致复述这条链路，阶段 0 就成功了。

## 五、14 张表的关系总图（先脸熟，细节留阶段 2）

```
                    ┌──────────┐
                    │ sys_dept │ 部门（树形，parent_id 指向上级部门）
                    └────┬─────┘
                         │ 用户属于一个部门 (dept_id)
                         ▼
   ┌──────────┐   sys_user_role   ┌──────────┐
   │ sys_user │◄─────(多对多)────►│ sys_role │ 角色（带 data_scope 数据范围）
   └────┬─────┘                   └────┬─────┘
        │                              │
        │ sys_user_post                │ sys_role_menu (多对多)
        │  (多对多)                    ▼
        ▼                         ┌──────────┐
   ┌──────────┐                   │ sys_menu │ 菜单/权限（树形，含权限码）
   │ sys_post │ 岗位              └──────────┘
   └──────────┘                        ▲
                                       │ sys_role_dept (角色↔授权部门)
   ┌──────────┐                   ┌────┴─────┐
   │ sys_dict │ 字典类型+字典数据  │ 数据权限授权用 │
   │ sys_config│ 系统参数          └──────────┘
   │ sys_login_log / sys_operation_log  两类日志
```

**核心记忆点**——三张"关联表"是 RBAC 的关节：

| 关联表 | 连接谁和谁 | 含义 |
|--------|-----------|------|
| `sys_user_role` | 用户 ↔ 角色 | 张三是"财务" |
| `sys_role_menu` | 角色 ↔ 菜单/权限 | "财务"能看报销菜单、能按审批钮 |
| `sys_role_dept` | 角色 ↔ 部门 | "财务"的数据范围是自定义的这几个部门 |

再加两条"树形自关联"（同一张表里用 `parent_id` 指向自己）：
- `sys_dept.parent_id` → 部门是一棵树（总公司 → 分公司 → 科室）
- `sys_menu.parent_id` → 菜单是一棵树（目录 → 菜单 → 按钮）

> 现在不用记字段，只要能指着图说出"用户通过 user_role 连到角色，角色通过 role_menu 连到权限"就够了。

## 六、程序从哪启动？关键入口文件

| 文件 | 作用 | 你现在要知道的 |
|------|------|---------------|
| `com/rbac/RbacServerApplication.java` | **启动类**，程序的 `main` 入口 | 就 19 行，`@SpringBootApplication` 一行注解就把整个框架点着了；`@MapperScan` 告诉框架"数据层类在哪" |
| `src/main/resources/application.yml` | **配置文件** | 端口 `8080`、访问前缀 `/api`、连哪个 MySQL/Redis、JWT 密钥和有效期都在这。注意第 4 行 `context-path: /api`——所以真实地址是 `http://localhost:8080/api/...` |
| `security/config/SecurityConfig.java` | **安全总开关** | 定义了哪些接口免登录（登录/刷新/探活/错误页），其余全部要登录 |
| `controller/PingController.java` | **探活接口** `/api/ping` | 检查程序、数据库、Redis 通不通。你本地启动后第一个该访问的地址 |

**配置文件里现在能读懂的几行**（`application.yml`）：
- `server.port: 8080` + `context-path: /api` → 后端地址前缀 `http://localhost:8080/api`
- `spring.datasource` → 连本地 MySQL 的 `rbac` 库
- `spring.data.redis` → 连本地 Redis
- `rbac.jwt.access-ttl: 7200` → 门禁卡（access token）有效期 2 小时；`refresh-ttl: 604800` → 续期卡 7 天

### 💡 小知识：启动类的三个注解 & 包路径通配符

`RbacServerApplication.java` 全文才 19 行，靠三个注解就把框架点着了：

| 注解 | 作用 |
|------|------|
| `@SpringBootApplication` | 点火，启动整个 Spring Boot（自动配置 + 扫描组件） |
| `@EnableAsync` | 允许方法"异步执行"（如写操作日志时不阻塞主流程） |
| `@MapperScan("com.rbac.**.mapper")` | 登记"数据层接口在哪"，让框架自动为它们生成数据库操作实现 |

**为什么需要 `@MapperScan`？** 项目里的数据层接口都是"空接口"，一行实现都没写：

```java
// com/rbac/system/user/mapper/SysUserMapper.java
public interface SysUserMapper extends BaseMapper<SysUser> {
    // 空的！却能 userMapper.selectById(1) 查数据
}
```

空接口凭什么能查库？就靠 `@MapperScan` 扫到它 → MyBatis-Plus 在运行时**自动帮它生成实现**。没有这句，程序一启动就报"找不到 Mapper"。

**包路径通配符**（写在字符串里的 `*` / `**`）：

| 写法 | 含义 | 例子 |
|------|------|------|
| `*` | 匹配**一层**子包 | `com.rbac.*` 只匹配 `com.rbac.auth`，不匹配 `com.rbac.system.user` |
| `**` | 匹配**任意多层**子包 | `com.rbac.**.mapper` 能匹配 `com.rbac.system.user.mapper`、`com.rbac.system.role.mapper`… |

所以 `com.rbac.**.mapper` = "`com.rbac` 开头、`mapper` 结尾、中间隔几层都行"的所有包——正好把散落在各业务模块里、深度不一的 `mapper` 包一网打尽。

> 记忆点：看到框架配置里出现 `**`，就是"我不在乎中间有几层子包，只要头尾对得上就都算"。

## 八、可选动手（想亲眼看看就做，不做也不影响学习）

如果你想让项目在本地跑起来（需要装了 Docker）：

```bash
# 1. 启动 MySQL + Redis 中间件
cd deploy && docker compose up -d

# 2. 启动后端（在项目根目录执行）
mvn -f backend/pom.xml spring-boot:run

# 3. 探活：看到 UP 就说明全通了
curl -s http://localhost:8080/api/ping
```

跑不起来很正常（环境问题多），**这一步失败完全不影响后面看代码学习**。我们主要靠"读代码 + 文档"来掌握，动手是加分项。
