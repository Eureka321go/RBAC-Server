# 阶段 6 — 其余模块类推 + 收尾 + 毕业实践

> 有了阶段 5 的 User 模板，这一份用「**对照法**」快速扫过其余模块——**只讲各自的「特色 10%」**，结构相同的 90% 不再重复。最后做全局收尾 + 一道毕业作业。

---

## 一、对照法：每个模块只问 3 个问题

读任何一个模块，套这三问即可：
1. **七件套齐不齐？** —— 一定是 `controller/service/mapper/entity/dto/vo`，字段换一批。
2. **权限码是哪一套？** —— 命名恒为 `system:模块:操作`（见下表）。
3. **特色点是什么？** —— 只有这一项需要单独记。

### 全项目权限码总表（共 8 套，一眼看出对称性）

| 模块 | 权限码 | 特色操作 |
|------|--------|---------|
| user | `system:user:list/add/edit/delete` + `reset-password`、`assign-role` | 重置密码、分配角色 |
| role | `system:role:list/add/edit/delete` + `grant-menu`、`grant-data` | **授功能权限、授数据范围** |
| menu | `system:menu:list/add/edit/delete` | 树 + 三类型 |
| dept | `system:dept:list/add/edit/delete` | 树 |
| post | `system:post:list/add/edit/delete` | 最简 CRUD |
| config | `system:config:list/add/edit/delete` | 参数键值 |
| dict | `system:dict:list/add/edit/delete` | 类型-数据两级 |
| log | `system:login-log:list`、`system:operation-log:list` | 只读（查/删/导出） |

> 注意规律：**增删改查四件套是骨架**，个别模块多几个「特色动词」（reset-password / grant-menu…），对应就多一个权限码 + 一个 Controller 方法 + 一个 Service 方法。**一处加，处处对称加。**

## 二、逐模块「特色点」速览

### 2.1 `menu` 菜单模块 —— 树 + 三类型

- **返回的是树不是列表**：`MenuService.tree()` 把扁平的 `sys_menu` 记录按 `parentId` 组装成父子嵌套结构（前端渲染多级菜单/权限树用）。
- **三种 `menuType`**（阶段 0 见过）：
  - `DIR` 目录（可展开的父节点，如「系统管理」）
  - `MENU` 菜单（能点开的页面，对应一个前端路由）
  - `BUTTON` 按钮（**不显示为菜单**，只承载 `permission_code`——阶段 4 的权限码就存在这类行里）
- 记忆点：**menu 表一表两用**——既是「左侧导航菜单」，又是「权限码字典」。BUTTON 类型的行就是权限的定义处。

### 2.2 `role` 角色模块 —— 全项目「授权中枢」（最重要的特色模块）

角色比别的模块多了**两套授权关联**，正好把前面所有知识串起来：

| 方法 | 关联表 | 作用 | 权限码 |
|------|--------|------|--------|
| `grantMenus(roleId, menuIds)` | `sys_role_menu` | 给角色**授功能权限**（勾哪些菜单/按钮） | `system:role:grant-menu` |
| `grantDepts(roleId, deptIds)` | `sys_role_dept` | 给角色**授数据范围**（能看哪些部门的数据） | `system:role:grant-data` |

```java
// 授功能权限：先删角色所有旧的菜单关系，再按新 menuIds 逐条插入（还是"先删后插"套路！）
@Transactional
public void grantMenus(Long roleId, List<Long> menuIds) {
    roleMenuMapper.delete(...eq(roleId));
    for (Long menuId : menuIds) roleMenuMapper.insert(new SysRoleMenu(roleId, menuId));
}

// 授数据范围：替换角色的自定义部门，并把角色 dataScope 置为 CUSTOM_DEPT
@Transactional
public void grantDepts(Long roleId, List<Long> deptIds) { ... 置 CUSTOM_DEPT ... }
```

**这里闭合了整个 RBAC 的两条主线：**
- `grantMenus` → 决定用户登录时 `LoginUserAssembler` 能查出哪些**权限码**（→ 阶段 4 的 `@PreAuthorize`）。
- `grantDepts` → 决定 `DataScopeService.calculate()` 里 `CUSTOM_DEPT` 范围能算出哪些**部门 id**（→ 阶段 4 的数据权限 SQL）。

> 🔑 一句话：**role 是"把权限装进用户"的地方**。你在阶段 3/4 看到的 `permissions` 和 `dataScope`，源头都在这两个 grant 方法。

### 2.3 `dept` 部门模块 —— 树 + 删除保护

- `DeptService.tree()`：和 menu 一样按 `parentId` 组装部门树（阶段 4 数据权限的部门层级就靠它）。
- **特色红线**：删部门前要检查「该部门下**还有没有用户**」——有用户不让删（`DeptService` 注入了 `userMapper` 就是为这个校验），避免用户变「孤儿」。

### 2.4 `dict` 字典模块 —— 类型-数据两级

- **两张表、两级结构**：`sys_dict_type`（字典类型，如「用户性别」）→ `sys_dict_data`（该类型下的具体项，如 男/女/未知）。所以 `DictService` 里方法成对出现：`createType/createData`、`listData(typeId)`……
- 用途：把「性别、状态、是否」这类**下拉选项**集中配置，不写死在代码里。
- `listDataByCode(dictCode)`：前端按字典编码拉取一组选项渲染下拉框。

### 2.5 `config` 参数模块 —— 键值对

系统参数（`configKey → configValue`）的增删改查，最朴素的 CRUD，无树无关联。读它等于复习 User 的简化版。

### 2.6 `post` 岗位模块 —— 最简模板

标准七件套 CRUD，无任何特色。**如果想验证自己会读模块，从 post 开始最轻松。**

### 2.7 `log` 日志模块 —— 只读 + 两类日志

- **登录日志** `sys_login_log`：阶段 3 登录成功/失败时写入。
- **操作日志** `sys_operation_log`：阶段 5 的 `@Log` + `OperationLogAspect` 写入。
- 特色：**只有查询/删除/导出，没有新增/编辑**——日志是系统自动产生的，不该手工造。所以权限码只有 `list`。

## 三、全局配置类回顾（3 个 @Configuration）

这些是「整个应用启动时装好、之后默默生效」的地基：

| 配置类 | 装了什么 | 对应你学过的 |
|--------|---------|-------------|
| `MybatisPlusConfig` | 注册 `PaginationInnerInterceptor` 分页拦截器 | 阶段 2/5 的 `selectPage` 能自动分页，就靠它 |
| `RedisConfig` | 配置 RedisTemplate 序列化方式 | 阶段 3 的 `TokenSessionService` 存 LoginUser 会话 |
| `LocaleConfig` | `AcceptHeaderLocaleResolver`，默认中文、支持中/英 | 阶段 5 的 `MessageUtils` 按请求语言翻译，语言来源就是它 |
| `SecurityConfig` | 过滤器链、白名单、`@EnableMethodSecurity` | 阶段 3/4 的认证与鉴权总规则 |

> `LocaleConfig` 用的是 `AcceptHeaderLocaleResolver`——**语言取自 HTTP 请求头 `Accept-Language`**，前端切语言时带上这个头，后端就返对应语言的文案。

## 四、安全红线清单复盘（对照 `CLAUDE.md`，逐条找到代码落点）

把项目要求的安全红线，和你已学过的代码一一对上——这是「真懂」的终检：

| 安全红线 | 代码落点（你学过的） |
|---------|---------------------|
| 前端隐藏只是体验，敏感操作后端必须再鉴权 | `@PreAuthorize`（阶段4）+ Service 业务红线（阶段5） |
| 数据权限不可绕过、不可漏接列表接口 | `DataScopeService.calculate` + `UserService.page` 的 `1=0` 兜底（阶段4） |
| 登出/改密/强退后旧 Token 必须失效 | 删 Redis 会话 → `JwtAuthenticationFilter` 查不到（阶段3「三步闭环」） |
| 日志/参数返回禁止出现密码、Token、完整身份证 | `UserVO` 不含 password；`OperationLogAspect.safeParams` 容错限长（阶段5） |
| 密码永不明文落库 | `passwordEncoder.encode()`（阶段3/5） |
| 逻辑删除，数据不真删 | `BaseEntity` 的 `@TableLogic`（阶段2/5） |

## 五、毕业作业：新增一个「公告 notice」模块，你要动哪些？

**（只需说清思路 / 看代码回答，不强制写代码）** 这是检验你真正出师的题目：

假设要加一个「系统公告」功能（管理员发公告、列表查看、增删改）。照 User 模板，你需要——

1. **建七件套**（`system/notice/` 下）：
   - `entity/SysNotice`（继承 `BaseEntity`，字段如 title/content/type/status）
   - `mapper/SysNoticeMapper`（`extends BaseMapper<SysNotice>`）
   - `dto/{NoticeQuery, NoticeSaveRequest}`（`@NotBlank` 校验标题）
   - `vo/NoticeVO`（+ `from()` 转换）
   - `service/NoticeService`（CRUD，`page` 里视需要接数据权限）
   - `controller/NoticeController`（`@RequestMapping("/system/notices")` + 各 `@PreAuthorize`）
2. **加权限码**（往 `sys_menu` 插 BUTTON 行）：`system:notice:list/add/edit/delete`，挂到相应角色（`sys_role_menu`）。
3. **要不要接数据权限？** —— 看业务：若「公告全员可见」则不接，`page` 不加 dept 过滤；若「各部门发各自的公告、只看本部门的」则接，仿 `UserService.page` 用 `DataScopeQuery` 收敛。
4. **要不要记操作日志？** —— 发布/删除公告是重要操作，给 Controller 方法加 `@Log(title="公告管理", businessType="...")`。
5. **前端**：菜单表加一条 MENU 行（配前端路由）、按钮权限码用于 `v-permission` 控制增删改按钮显隐。

> ✅ **能把上面 5 步说顺，你就真正掌握了这套 RBAC 后端的「设计范式」**——不是记住了某段代码，而是理解了「一个功能如何在分层架构里落地、如何接入鉴权与数据权限」。

## 六、结业总结：七个阶段串成一张图

```
阶段0 全局地图 ──▶ 阶段1 Java/Spring地基 ──▶ 阶段2 数据层/MyBatis-Plus
                                                      │
        ┌─────────────────────────────────────────────┘
        ▼
阶段3 认证【核心1】──▶ 阶段4 授权+数据权限【核心2】──▶ 阶段5 User模块【万能模板】
   (你是谁)              (你能干啥/看哪些数据)            (一个功能怎么落地)
        │                                                    │
        └──────────────────▶ 阶段6 类推+收尾+毕业 ◀───────────┘
                          (其余模块 & 安全红线复盘)
```

**三条主线，记住就出师：**
1. **认证线**：登录签发 → Redis 会话 → 每次请求过滤器认成已登录 → 登出删会话即失效。（jti 是钥匙，会话是锁芯）
2. **鉴权线**：`sys_menu` 定义权限码 → role 授权装进用户 → `@PreAuthorize` 功能拦截 → Service 业务红线。
3. **数据权限线**：role 授数据范围 → `DataScopeService` 算可见部门 → `page` 里翻译成 SQL 的 `WHERE`。

**分层范式**：Controller 收/包、Service 管业务、Mapper 管表、DTO 防脏、VO 防泄密、横切三件套（Result/异常/分页）+ AOP 日志 + i18n 统一支撑。

> 🎓 恭喜结业。往后再看任何一个新模块或新接口，你都能沿着这三条线 + 分层范式，自己读懂、并判断它有没有踩安全红线。
