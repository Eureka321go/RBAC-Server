# 阶段 0 · 全局架构与实验环境（先把地图摆对）

> 目标：这一章不急着研究 `Envelope`、ACK 或消息定序。先把一套真的能运行的 IM 后端摆在桌面上：
> 两个 Java 进程、三个端口、两个 Kafka topic，以及 MySQL、Redis、Kafka、MongoDB、MinIO 五类基础设施。
>
> 读完后，你应该能看着一条 `SEND` 路径指出“这一步在哪个进程”“依赖哪种基础设施”“故障时先查哪里”，
> 并能独立搭起后续章节需要的本地实验环境。

## 一、先看一条消息经过了哪些边界

先不要打开任何 Java 类。假设用户 A 已经登录，并通过 WebSocket 发送一条文本消息：

```text
客户端 A
  │ WebSocket SEND
  ▼
im-gateway :9001/im
  │ 写入 Kafka：im-inbound
  ▼
backend / com.rbac.im
  │ 校验成员和内容
  │ Redis 生成会话 seq
  │ MongoDB 保存消息正文
  │ MySQL 更新会话摘要/成员位点
  │ 写入 Kafka：im-outbound
  ▼
im-gateway
  │ 找到本机 Channel
  ▼
客户端 A / 其他在线成员
```

这张图至少跨过三类边界：

1. **网络连接边界**：客户端的 WebSocket 连接只终止在 `im-gateway`；
2. **进程边界**：网关和 backend 不是同一个 JVM，不能互相调用内存里的对象；
3. **存储与传输边界**：Kafka 负责搬运，Redis/MySQL/MongoDB 分别保存不同性质的数据。

现在先记住一句话：

> `im-gateway` 管“连接在哪里”，backend 管“这条消息该不该接受、怎样成为系统事实”。

后面的章节会拆开每一个箭头。本章只负责让你不会把箭头画错。

## 二、为什么确定是两个应用进程

### 2.1 第一份证据：根 POM

根目录 [`../../pom.xml`](../../pom.xml) 是一个聚合 POM：

```xml
<packaging>pom</packaging>

<modules>
    <module>backend</module>
    <module>im-gateway</module>
</modules>
```

`module` 表示它们可以由父工程统一构建，但不表示它们会被打进同一个进程。继续找启动类，可以看到两个独立的 `main()`：

| 模块 | 启动类 | 进程职责 |
|---|---|---|
| `backend` | `com.rbac.RbacServerApplication` | REST、权限和 IM 业务逻辑 |
| `im-gateway` | `com.rbac.im.gateway.ImGatewayApplication` | WebSocket 长连接与 Kafka 转发 |

因此本地启动时也要开两个终端：一个进程退出，不会自动带着另一个退出。

### 2.2 第二份证据：依赖完全不同

打开 [`../../backend/pom.xml`](../../backend/pom.xml)，能看到：

- `spring-boot-starter-web`：提供 REST/MVC；
- MyBatis-Plus 与 MySQL 驱动：访问关系数据；
- Spring Data MongoDB：访问消息正文；
- Spring Kafka：消费上行、生产下行；
- AWS S3 SDK：访问兼容 S3 的 MinIO。

再打开 [`../../im-gateway/pom.xml`](../../im-gateway/pom.xml)：

- `netty-all`：真正持有 WebSocket 连接；
- Spring Data Redis：登记跨网关路由；
- Spring Kafka：发送上行、接收下行；
- JWT：握手阶段验证身份；
- **没有** MySQL 驱动、MongoDB、MyBatis-Plus，也没有业务 Controller。

这不是“为了好看而拆目录”。依赖边界已经表明：网关不应该查群成员表，也不应该决定撤回是否超时；backend 不应该保存 Netty `Channel`。

### 2.3 如果硬塞进一个进程会怎样

小项目当然可以把 REST 和 WebSocket 写在一起，但连接层和业务层的扩容依据不同：

| 层 | 主要压力 | 常见扩容依据 |
|---|---|---|
| 网关 | 长连接数、网络 I/O、心跳 | 在线连接数、事件循环负载 |
| backend | 校验、数据库读写、业务计算 | Kafka 积压、请求量、数据库延迟 |

拆开后，可以增加网关实例承接更多连接，而不必复制一套无用的业务处理能力；也可以增加 backend 消费能力，而不迁移已有 WebSocket 连接。

但拆分也有代价：两个进程之间不能直接调用方法，于是必须引入 Kafka；backend 不持有 Channel，于是必须用 Redis 记录“用户在哪台网关”。这两笔账会在第 04 章正式计算。

## 三、三个端口不要混在一起

本项目的配置里能看到三个与应用有关的端口：

| 端口 | 配置来源 | 预期用途 | 当前运行事实 |
|---:|---|---|---|
| `8080` | backend `server.port` | REST 与 backend Actuator，统一带 `/api` context-path | backend 启动后实际监听 |
| `9001` | `im.gateway.ws-port` | Netty WebSocket，路径 `/im` | 网关启动后实际监听 |
| `8090` | 网关 `server.port` | 预期作为 Spring Boot/Actuator 管理端口 | **当前没有 HTTP Web Server 依赖，不会仅因这项配置自动监听** |

### 3.1 `8080/api`：短请求入口

backend 的 [`application.yml`](../../backend/src/main/resources/application.yml) 写着：

```yaml
server:
  port: 8080
  servlet:
    context-path: /api
```

所以会话列表、历史消息、群管理和上传预签名都走 `/api/im/**`。例如：

```text
GET http://localhost:8080/api/im/conversations
```

这里的 `/api` 是 Servlet context-path，不是每个 Controller 重复写出来的路径。

### 3.2 `9001/im`：长连接入口

网关的 [`application.yml`](../../im-gateway/src/main/resources/application.yml) 写着：

```yaml
im:
  gateway:
    ws-port: 9001
```

`NettyWebSocketServer` 在应用就绪后执行 `bind(9001)`，`WebSocketChannelInitializer` 又把协议路径固定为 `/im`。因此 WebSocket 地址是：

```text
ws://localhost:9001/im?token=<JWT>&deviceId=<设备标识>
```

它不经过 backend，也不带 `/api`。

### 3.3 `8090`：配置存在，不等于端口存在

网关配置还有：

```yaml
server:
  port: 8090
```

接口文档把它描述为 Actuator 端口，但当前 `im-gateway/pom.xml` 只有 `spring-boot-starter` 和 `spring-boot-starter-actuator`，没有 `spring-boot-starter-web`、WebFlux 或其他可启动 HTTP Server 的依赖。

你可以用依赖树验证：

```bash
mvn -pl im-gateway dependency:tree \
  -Dincludes=org.springframework.boot:spring-boot-starter-web,\
org.springframework.boot:spring-boot-starter-webflux,\
org.springframework.boot:spring-boot-starter-tomcat
```

当前输出不会列出这些依赖。因此：

- `9001` 是 Netty 代码显式绑定的真实端口；
- `8090` 目前只是一个没有完成运行时闭环的配置目标；
- 本章不能拿 `curl localhost:8090/actuator/health` 当作网关启动成功的证据。

这是本套学习路线的第一个“文档与真实入口交叉验证”案例：**配置文件表达意图，依赖和运行行为才是最终事实。**

## 四、两个 Kafka topic 怎样把进程接起来

两个 Java 进程没有互相发 HTTP 请求，而是通过 Kafka 的两个 topic 交接消息：

```text
                 im-inbound
im-gateway  ─────────────────► backend

                 im-outbound
backend     ─────────────────► im-gateway
```

| topic | 生产者 | 消费者 | 搬运内容 |
|---|---|---|---|
| `im-inbound` | `InboundProducer`（网关） | `InboundMessageConsumer`（backend） | 客户端上行的 SEND、READ、RECALL 等 Envelope |
| `im-outbound` | `OutboundDispatcher`（backend） | `OutboundConsumer`（网关） | 包含目标网关、用户、设备和 Envelope 的下行包 |

源码里可以找到同样的字符串：

```java
public static final String IN = "im-inbound";
public static final String OUT = "im-outbound";
```

Kafka 在这里解决的是**跨进程传输与解耦**。它不替 backend 做下面这些事：

- 不判断发送者是不是群成员；
- 不生成最终 `msgId` 或 `seq`；
- 不负责长期保存可供客户端查询的聊天记录；
- 不知道某个用户的 Channel 在哪台网关。

现在只需认清上下行方向。为什么上行 key 使用 `cid`、消费组怎样影响顺序、ACK 到底确认到哪一层，都留到第 04 章。

## 五、五类基础设施，各自只做一类关键工作

### 5.1 总表：负责什么，也要知道不负责什么

| 组件 | 本项目中的核心职责 | 典型数据 | 明确不负责 |
|---|---|---|---|
| MySQL | 保存关系明确、需要约束和更新的业务事实 | 会话、成员、群、角色、已读/提及位点、摘要 | 不保存每条消息的大正文 |
| Redis | 保存高频、临时或需要原子操作的状态 | 会话 seq、用户到网关/设备的在线路由、链接卡片缓存 | 不是聊天记录的最终真相 |
| Kafka | 在网关与 backend 之间异步搬运消息 | `im-inbound`、`im-outbound` | 不代替业务数据库和权限判断 |
| MongoDB | 保存按会话和 seq 查询的消息文档 | `im_message` | 不保存在线 Channel，也不维护群成员关系 |
| MinIO | 保存图片、音频、文件二进制对象 | `im-media` 私有 bucket 中的 object | 不让大文件正文穿过 backend 和 Kafka |

### 5.2 MySQL：关系与位点是事实数据

[`V3__im_schema.sql`](../../backend/src/main/resources/db/migration/V3__im_schema.sql) 创建了四张核心 IM 表：

```text
im_conversation
im_conversation_member
im_group
im_group_member
```

“某用户是不是群成员”“某成员读到哪个 seq”都适合放 MySQL：它们是需要唯一约束、关系查询和一致更新的业务事实。

消息正文没有一起放进去，不代表 MySQL 不能存 JSON，而是本项目选择把高增长、按会话流式读取的消息文档交给 MongoDB，让关系元数据和消息正文按访问模式分开。

### 5.3 Redis：两种短而热的数据

第一种是会话 seq。`SeqService` 对下面这种 key 执行原子 `INCR`：

```text
im:seq:<cid>
```

第二种是在线路由。网关登记“用户的某个设备位于哪台网关”，backend 扇出时查询：

```text
route:user:<uid>
  deviceId -> gatewayId
```

这两类数据都读写频繁，且路由会随连接断开而消失。Redis 很合适，但不能由此得出“Redis 是聊天数据库”的结论。

### 5.4 MongoDB：消息正文只存一份

`ImMessage` 使用：

```java
@Document("im_message")
```

消息文档携带 `cid`、`seq`、发送者、类型、正文和状态。客户端离线后重新上线，不需要从 Kafka 找旧消息，而是通过 backend 的 REST 接口按 `sinceSeq` 查询 MongoDB。

所以“在线实时推送”和“离线可靠补齐”是两条路径：

```text
在线：Kafka 下行 → 网关 → WebSocket
离线：客户端重连 → REST sinceSeq → MongoDB
```

### 5.5 MinIO：二进制不穿过业务进程

图片或 100 MB 文件如果先上传到 backend，再塞进 Kafka，不但浪费内存和网络，还会放大消息系统的负担。本项目采用 S3 兼容接口：

```text
客户端向 backend 申请预签名 URL
  → 客户端直接 PUT 到 MinIO
  → SEND 只携带 objectKey、size、mime 等元数据
```

因此 MinIO 保存的是对象，MongoDB 消息保存的是对象引用。预签名安全、归属校验和大小/MIME 复核留到第 08 章。

### 5.6 Kafka：是传送带，不是仓库货架

Kafka 确实会按保留策略保存日志，但在本项目的业务语义中，客户端不会调用 Kafka 拉历史消息；客户端可见的最终消息事实来自 MongoDB。

一个简单判断法：

- “这条数据以后要被业务查询和修改吗？”——看 MySQL/MongoDB；
- “这是在线位置或原子计数吗？”——看 Redis；
- “这是两个进程之间正在传递的事件吗？”——看 Kafka；
- “这是大块二进制吗？”——看 MinIO。

## 六、先做静态预演：不启动也能验证一半地图

下面命令都在仓库根目录执行。

### 6.1 看 Compose 有哪些 profile

```bash
docker compose -f deploy/docker-compose.yml config --profiles
```

当前配置应列出：

```text
extra
full
im
```

- `full` 打开 Kafka；
- `im` 打开 MongoDB 与 MinIO；
- `extra` 是本章不需要的 nginx/RabbitMQ。

MySQL、Redis、backend、frontend、caddy 没有 profile，属于 Compose 默认服务。正因为如此，下面这条命令只是**查看解析结果**，不要把它误读成“本章应该把列出的服务全部启动”：

```bash
docker compose -f deploy/docker-compose.yml \
  --profile full --profile im config --services
```

### 6.2 为什么启动时必须写显式服务名

直接执行：

```bash
docker compose -f deploy/docker-compose.yml \
  --profile full --profile im up -d
```

会把所有无 profile 的服务也带起来，包括 Compose 自己构建的 backend、frontend、caddy。这与我们准备在宿主机用 Maven 启动 backend 的实验方式冲突，还可能占用 80/443 等端口。

本章使用显式服务列表，只启动基础设施：

```bash
docker compose -f deploy/docker-compose.yml \
  --profile full --profile im \
  up -d mysql redis kafka mongodb minio
```

这条命令背后的原则比命令本身更重要：**先让 Compose 展开配置，再明确选择本次实验需要的服务。**

### 6.3 确认两个模块能独立构建

先看 Maven 是否能识别模块：

```bash
mvn -q help:evaluate -Dexpression=project.modules -DforceStdout
```

再分别运行与本章最接近的测试：

```bash
mvn -pl im-gateway \
  -Dtest=ChannelRegistryTest,ImFrameHandlerTest test
```

backend 的 IM 测试较多，可以先运行轻量的配置与仓储测试，或按路线总览给出的过滤方式运行：

```bash
mvn -pl backend -Dtest='com.rbac.im.**' test
```

如果 Surefire 版本不接受包通配符，就指定具体测试类，不要为了学习环境修改构建配置。

> 当前 Homebrew JDK 21 环境可能出现 Mockito inline / Byte Buddy 无法自附加：
> `Could not initialize inline Byte Buddy mock maker`。这表示测试运行基础设施没有成功初始化，不能直接归类为 IM 业务断言失败。

## 七、完整启动实操：基础设施 + 两个 Java 进程

### 7.1 启动前检查

确认工具存在：

```bash
java -version
mvn -version
docker --version
docker compose version
```

再检查常用端口是否已经被占用。macOS/Linux 可以执行：

```bash
lsof -nP -iTCP:3306 -iTCP:6379 -iTCP:9092 \
  -iTCP:27017 -iTCP:9000 -iTCP:8080 -iTCP:9001
```

有输出不一定是错误：可能正是你上次启动的容器。先用 `docker compose ps` 判断归属，不要看到端口占用就随手杀进程。

### 7.2 启动五个基础设施服务

```bash
docker compose -f deploy/docker-compose.yml \
  --profile full --profile im \
  up -d mysql redis kafka mongodb minio
```

观察状态：

```bash
docker compose -f deploy/docker-compose.yml ps \
  mysql redis kafka mongodb minio
```

这里要区分两种状态：

- MySQL、Redis 配了 healthcheck，最终应出现 `healthy`；
- Kafka、MongoDB、MinIO 当前 Compose 没有 healthcheck，`Up` 只能证明容器主进程仍在运行。

某个容器没有起来时，先看对应日志，不要把五份日志混在一起：

```bash
docker compose -f deploy/docker-compose.yml logs --tail=100 kafka
docker compose -f deploy/docker-compose.yml logs --tail=100 mongodb
```

### 7.3 终端 A：启动 backend

在仓库根目录执行：

```bash
mvn -pl backend spring-boot:run
```

默认 `dev` 配置会连接宿主机端口：

| 依赖 | 默认地址 |
|---|---|
| MySQL | `localhost:3306/rbac` |
| Redis | `localhost:6379` |
| Kafka | `localhost:9092` |
| MongoDB | `localhost:27017/rbac_im` |
| MinIO | `http://localhost:9000` |

看到应用启动完成后，在另一个终端验证 backend：

```bash
curl -s http://localhost:8080/api/actuator/health
```

匿名请求通常只看到总状态，例如：

```json
{"status":"UP"}
```

注意两个边界：

1. 顶层 health 会聚合 Spring 已注册的健康指标，但不等于完整 SEND 已跑通；
2. Kafka 和 MinIO 不一定因为这个响应是 `UP` 就已完成端到端验证。

所以 health 是“应用与部分依赖可用”的证据，不是“聊天系统所有功能正确”的证据。

### 7.4 终端 B：启动 im-gateway

保持 backend 运行，再打开一个终端：

```bash
mvn -pl im-gateway spring-boot:run
```

网关启动日志应包含类似：

```text
IM Netty WebSocket 网关已监听端口 9001
```

再检查真实监听：

```bash
lsof -nP -iTCP:9001 -sTCP:LISTEN
lsof -nP -iTCP:8090 -sTCP:LISTEN
```

按当前依赖结构，`9001` 应有监听者，`8090` 不应仅凭配置出现监听者。这不是“Actuator 挂了”，而是网关没有 HTTP Web Server 运行时。

不要用普通 HTTP `curl` 请求 `/im` 判断 WebSocket 是否可用。WebSocket 需要 Upgrade 握手，而且本项目握手还要求合法 JWT 与 `deviceId`。真正的握手和鉴权实验放到第 03 章。

### 7.5 你现在实际验证到了哪一层

完成上面步骤，只能下这些结论：

```text
容器状态/日志
  → 五类基础设施进程已启动（健康程度因服务而异）

backend health
  → backend HTTP 入口和已纳入 health 的依赖可响应

网关启动日志 + 9001 LISTEN
  → Netty 已绑定 WebSocket 监听端口
```

还不能下这些结论：

- JWT 握手一定成功；
- `SEND` 一定进入 Kafka；
- backend 一定能完成校验和落库；
- 下行一定找到正确设备；
- 离线补拉一定完整。

这些结论必须在后续章节通过更靠近真实入口的实验逐步获得。

### 7.6 安全收尾

先在两个 Maven 终端按 `Ctrl+C` 停止 Java 进程。

如果后面还要继续学习，可以保留基础设施。只想暂停容器时执行：

```bash
docker compose -f deploy/docker-compose.yml stop \
  mysql redis kafka mongodb minio
```

想移除这五个基础设施容器、但保留数据卷：

```bash
docker compose -f deploy/docker-compose.yml rm -f \
  mysql redis kafka mongodb minio
```

普通 `docker compose down` 会停止并移除同一个 Compose 项目下的其他容器；如果 frontend、caddy 等服务也在运行，它们同样会受影响。因此本章收尾优先使用带显式服务名的 `stop`/`rm`。

不要把下面命令当作日常收尾：

```bash
docker compose -f deploy/docker-compose.yml down -v
```

`-v` 会删除 MySQL、Redis、MongoDB、MinIO 的命名卷，数据难以恢复。只有明确要重置全部本地数据时才考虑它。

## 八、启动失败时，先按边界缩小范围

| 现象 | 先查什么 | 为什么 |
|---|---|---|
| Docker 命令提示无法连接 daemon/socket | Docker Desktop 是否运行、当前用户是否有 socket 权限 | Compose 还没机会读取服务状态 |
| MySQL/Redis 一直 `unhealthy` | `docker compose logs <service>`，再手动执行 healthcheck | 容器活着，但探针连续失败 |
| backend 启动时报数据库连接失败 | `3306`、账号密码、MySQL health、`application-dev.yml` | backend 启动要执行 Flyway 并建立数据源 |
| backend 启动时报 MongoDB/Kafka 连接异常 | `27017`/`9092` 是否监听，对应容器日志 | 它们属于 backend 的 IM 依赖 |
| 网关启动时报 `Address already in use` | `lsof ...:9001` | Netty 无法绑定已占用端口 |
| 网关已打印 Spring 启动日志，但没有 9001 | 查找 `NettyWebSocketServer` 的绑定异常 | Spring 容器启动和 Netty bind 是两件事 |
| `curl localhost:8090/actuator/health` 连接失败 | 先看网关 POM 是否有 Web Server 依赖 | 当前 `8090` 并没有完整运行时支撑 |
| 测试在断言前报 Byte Buddy/Mockito 初始化失败 | JDK 与 Mockito agent/self-attach 环境 | 属于测试运行器问题，不是业务断言结论 |

排错时按下面顺序，比“把所有服务重启一遍”更容易得到证据：

```text
端口是否存在
  → 对应进程/容器是否运行
  → 该进程日志是否报依赖错误
  → 配置指向哪里
  → 真正入口能否完成一次请求/握手
```

## 九、动手练习

### 练习 1：给组件划责任边界

不看上文，给下面七个组件各写一句“负责什么”和“不负责什么”：

```text
im-gateway / backend / MySQL / Redis / Kafka / MongoDB / MinIO
```

<details>
<summary><b>参考答案</b></summary>

- `im-gateway`：负责握手、连接、心跳和帧转发；不决定成员权限和消息存储。
- backend：负责权限、校验、定序、落库和扇出决策；不持有 Netty Channel。
- MySQL：负责会话、成员、群和位点等关系事实；不保存大规模消息正文。
- Redis：负责会话原子 seq、在线路由和短期缓存；不是聊天记录最终来源。
- Kafka：负责两个进程之间的异步上下行；不完成业务校验和历史查询。
- MongoDB：负责消息文档与按会话增量查询；不保存连接状态。
- MinIO：负责媒体二进制对象；不负责消息协议和成员权限。

</details>

### 练习 2：判断该找哪个入口

分别回答：

1. 拉历史消息应连接哪个端口？
2. 发送实时帧应连接哪个端口和路径？
3. backend 的健康检查 URL 是什么？
4. 为什么当前不能把网关 `8090` health 当作验收项？

2. WebSocket 走 `9001/im`。

### 练习 3：解释为什么要显式列服务

下面两条命令有什么实质差别？本章为什么选择第二条？

```bash
docker compose -f deploy/docker-compose.yml \
  --profile full --profile im up -d

docker compose -f deploy/docker-compose.yml \
  --profile full --profile im \
  up -d mysql redis kafka mongodb minio
```

<details>
<summary><b>参考答案</b></summary>

第一条会启动选中 profile 的服务和所有无 profile 的默认服务，所以 backend、frontend、caddy 也会被拉起。第二条把目标限制为五个基础设施，允许我们在宿主机分别用 Maven 启动两个 Java 模块，也避免不必要的镜像构建和端口占用。

</details>

### 练习 4：判断证据能证明什么

下面三条观察分别能证明什么，又不能证明什么？

1. `docker compose ps` 显示 Kafka 为 `Up`；
2. backend health 返回 `{"status":"UP"}`；
3. `lsof` 显示 Java 正在监听 `9001`。

<details>
<summary><b>参考答案</b></summary>

1. 只能证明 Kafka 容器主进程仍运行；当前没有 Compose healthcheck，不能仅凭 `Up` 证明 broker 对所有客户端可用。
2. 能证明 backend HTTP health 可响应，且聚合进来的指标整体为 UP；不能证明完整 SEND/PUSH 链路通过。
3. 能证明某个 Java 进程绑定了 9001；结合网关日志可以确认 Netty 已监听，但不能证明 JWT 握手或消息收发成功。

</details>

## 十、自检与通过标准

不看文档，尝试回答：

1. 为什么本项目需要两个 JVM，而不是两个包？
2. `8080`、`9001`、`8090` 各自表达什么？哪一个目前只是未闭环配置？
3. `im-inbound` 和 `im-outbound` 的方向分别是什么？
4. 为什么在线推送依赖 Kafka，离线补拉却依赖 MongoDB？
5. 为什么 backend 不能直接从内存中找到用户的 Channel？
6. MySQL、Redis、MongoDB 都能存数据，为什么不能因此随便选一个？
7. 为什么容器 `Up`、Actuator `UP` 和完整消息链路成功是三个不同结论？
8. 怎样只启动本章需要的五个基础设施，而不拉起 frontend/caddy？

<details>
<summary><b>自检参考答案</b></summary>

1. `backend` 和 `im-gateway` 各有独立启动类，会运行在两个 JVM 中。网关长期持有 WebSocket `Channel`，按连接数和网络 I/O 扩容；backend 执行权限校验、定序和存储，按业务量与 Kafka 积压扩容。如果它们只是同一 JVM 里的两个包，就无法独立部署、故障隔离和扩容，也不会真正形成当前的 Kafka 进程边界。
2. `8080` 是 backend 的 HTTP 端口，REST 和 Actuator 都带 `/api` context-path；`9001` 是 im-gateway 中 Netty 实际监听的 WebSocket 端口，协议路径是 `/im`；`8090` 是网关配置中预留的 Spring Boot/Actuator 端口。当前 im-gateway 没有 HTTP Web Server starter，因此 `8090` 只是未闭环配置，不会自动产生监听端口。
3. `im-inbound` 的方向是 **im-gateway → backend**，承载客户端上行的 `SEND`、`READ`、`RECALL` 等 Envelope；`im-outbound` 的方向是 **backend → im-gateway**，承载 backend 完成业务处理后要推给目标网关、用户和设备的下行包。
4. 在线推送是“现在把事件送到持有连接的网关”，需要 Kafka 跨进程搬运和解耦；离线补拉是“按 `cid + seq` 查询已经成为业务事实的历史消息”，需要 MongoDB 的持久化文档。Kafka 虽然有保留日志，但在本项目中不是客户端历史消息查询接口，也不是消息的最终业务真相。
5. Netty `Channel` 是 im-gateway JVM 里的内存对象，backend 运行在另一个 JVM，不能直接读取该对象。而且多网关部署时，backend 还需要先通过 Redis 路由知道用户在哪台网关，再经 `im-outbound` 把消息送到那台网关，由网关查找本机 Channel。
6. 选存储不只看“能不能存”，还要看数据语义和访问模式。MySQL 适合需要关系、约束和一致更新的会话/成员/已读位点；Redis 适合高频、临时和需要原子操作的 seq 与在线路由；MongoDB 适合按会话连续写入、按 seq 增量读取的消息文档。随意替换会丢掉所需的约束、原子性、查询效率或数据持久性。
7. 它们分别是三层证据：容器 `Up` 只说明容器主进程没退出；Actuator `UP` 说明应用 health 端点可响应，以及已纳入聚合的 indicator 正常；完整链路成功还要求 WebSocket 握手、身份校验、两个 topic、定序落库、路由和下行推送全部通过。前两者都不能单独证明第三者。
8. 显式写出五个服务名：

   ```bash
   docker compose -f deploy/docker-compose.yml \
     --profile full --profile im \
     up -d mysql redis kafka mongodb minio
   ```

   `--profile full --profile im` 让 Kafka、MongoDB 和 MinIO 进入可选服务集，末尾的显式服务名又把实际启动目标限定在 MySQL、Redis、Kafka、MongoDB 和 MinIO，因此不会顺带启动 frontend/caddy。

</details>
