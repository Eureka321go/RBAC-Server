# IM 后端学习路线：从一条消息到完整分布式链路

> 这不是一份“按文件夹看代码”的目录，而是一条可以实际走完的路线。
>
> 你会从一条 `SEND` 文本消息出发，依次拆开 WebSocket 网关、Kafka、消息定序、MongoDB、MySQL、Redis 路由、离线同步和群聊，最后能独立画出完整时序图、定位链路故障，并判断当前实现与设计文档是否一致。

---

## 一、学完之后，你应该能做到什么

完成这套路线后，你应当能不看文档回答下面这些问题：

1. 为什么 IM 要把 `im-gateway` 和 `backend` 拆成两个进程？
2. 客户端发送一条消息后，为什么先收到 `ACK`，稍后才收到带 `seq` 的 `PUSH`？
3. Kafka 的 key 为什么用 `cid`？它保证了什么，又没有保证什么？
4. `clientMsgId`、`msgId`、`seq` 分别是谁生成的，解决什么问题？
5. 为什么消息正文放 MongoDB，而会话成员和已读位点放 MySQL？
6. 用户离线时为什么不需要单独维护一张“离线消息表”？
7. backend 如何知道用户连接在哪台网关、哪个设备上？
8. 未读数、已读回执、`@我` 提醒为什么都可以建立在 `seq` 上？
9. 群聊为什么采用“消息只存一份、在线按成员扇出”的读扩散模型？
10. 富媒体为什么走 MinIO 预签名直传，而不是先上传到 backend？
11. 如何从 WebSocket、Kafka、Redis、MongoDB、MySQL 五个位置定位“消息没有到达”？
12. 如何验证设计文档描述的功能在真实入口上确实可以跑通？

最终验收不是“把所有类看过一遍”，而是完成一次完整的链路复述：

```text
握手鉴权
  → SEND
  → ACK
  → im-inbound
  → 权限与内容校验
  → Redis 定序
  → MongoDB 落消息
  → MySQL 更新摘要
  → im-outbound
  → 在线 PUSH
  → 离线 sinceSeq 补拉
  → READ 推进已读位点
```

## 二、学习范围与约定

### 2.1 覆盖范围

本路线聚焦 IM 后端完整链路：

| 组件 | 本项目位置 | 学习重点 |
|---|---|---|
| WebSocket 网关 | `im-gateway/` | Netty、握手鉴权、连接表、心跳、Kafka 收发 |
| IM 逻辑层 | `backend/src/main/java/com/rbac/im/` | 校验、定序、落库、扇出、群聊及高级消息能力 |
| Kafka | `im-inbound` / `im-outbound` | 解耦、分区顺序、消费组、失败边界 |
| Redis | 会话 seq、在线路由 | 原子计数、跨网关路由、TTL |
| MySQL | 会话、成员、群、位点 | 关系数据、权限、未读与 @提醒 |
| MongoDB | `im_message` | 消息正文、按会话增量查询、撤回状态 |
| MinIO | `im-media` | 私有对象、预签名 PUT/GET、富媒体校验 |

不展开 React Native 页面和客户端 UI。客户端只作为协议参与者，用来理解它应该发送什么、收到什么，以及如何保存同步位点。

### 2.2 需要的前置知识

默认你已经能读懂：

- Java 类、接口、集合和异常；
- Spring Boot 的依赖注入、`Controller`、`Service`；
- 基础 HTTP、JSON 和 SQL；
- Maven 测试命令。

不要求提前掌握 Netty、Kafka、MongoDB 或分布式系统。遇到这些概念时，从本项目的真实代码切入。

### 2.3 学习节奏

采用里程碑制，不绑定日期。每个单元建议投入 **2～4 小时**：

```text
先看问题和时序图（15～30 分钟）
  → 按入口顺序读代码（60～90 分钟）
  → 跑测试或实验（30～60 分钟）
```

只有在能完成本单元“通过标准”后，才进入下一单元。看懂不等于掌握，能预测输入输出、解释失败边界才算过关。

## 三、先看全局：这套 IM 是怎样拆开的

```text
                         REST :8080/api/im
                  ┌─────────────────────────┐
                  │ 会话列表、历史拉取、群管理 │
                  │      上传预签名          │
                  ▼                         │
客户端 ── WebSocket ──► im-gateway          │
          :9001/im       │                  │
                         │ im-inbound        │
                         ▼                  │
                       Kafka                │
                         │                  │
                         ▼                  │
                  backend / com.rbac.im ◄───┘
                    │      │       │
          Redis ◄───┤      │       ├───► MySQL
          路由/seq   │      │       │    会话/成员/位点
                    │      ▼       │
                    │   MongoDB    │
                    │   消息正文    │
                    │              │
                    └──► Kafka ── im-outbound ──► im-gateway ──► 客户端
                         │
                         └── MinIO：富媒体对象不经过业务进程
```

这个拆分首先解决的是职责问题：

- `im-gateway` 管连接，不决定群权限、撤回窗口或消息怎么存；
- backend 管业务，不持有 Netty `Channel`；
- Redis 保存跨进程都能查询的在线路由；
- Kafka 让网关和逻辑层不需要直接调用彼此；
- 在线用户实时推送，离线用户以后按 `seq` 增量补齐。

学习时始终追问两个问题：**现在这段代码属于连接层还是业务层？这里保存的是事实数据还是临时状态？**

## M1 · 协议、ID 与会话模型

### 本单元要解决的问题

- 为什么所有操作都放进统一的 `Envelope`？
- `cid`、`clientMsgId`、`msgId`、`seq` 分别解决什么问题？
- 单聊和群聊怎样使用同一条消息链路？

### 源码入口

- `backend/.../im/protocol/Envelope.java`
- `im-gateway/.../protocol/Envelope.java`
- `backend/.../im/protocol/OutboundPacket.java`
- `ConversationService.singleCid()` 与 `groupIdFromCid()`
- `ImMessage.java`

### 必须形成的概念表

| 字段 | 生成方 | 作用 | 是否会话内有序 |
|---|---|---|---|
| `cid` | 服务端会话模型 | 标识单聊或群聊 | 不适用 |
| `clientMsgId` | 客户端 | 重试关联、幂等检查、ACK/PUSH 对账 | 否 |
| `msgId` | backend | 服务端全局消息标识 | 否 |
| `seq` | backend / Redis | 会话内排序、同步和位点计算 | 是 |

### 动手实验

手写三组合法 Envelope：TEXT SEND、READ、RECALL。然后逐字段标注：哪些值客户端可信，哪些值必须由服务端覆盖或产生。

### 通过标准

别人给你一个 `PUSH` JSON，你能指出它对应哪个会话、哪条客户端消息、服务端最终编号是什么，以及它是否可以用于跨会话排序。

## M2 · WebSocket 握手与连接生命周期

### 本单元要解决的问题

- HTTP 请求怎样升级为 WebSocket？
- JWT 身份怎样挂到 Netty `Channel` 上？
- 为什么 `Channel` 只能保存在网关本机内存？
- 心跳超时和连接断开时必须清理什么？

### 源码阅读顺序

1. `NettyWebSocketServer`：端口启动；
2. `WebSocketChannelInitializer`：pipeline 的工位顺序；
3. `HandshakeAuthHandler`：读取 token/deviceId、校验、写 Channel 属性；
4. `ChannelRegistry`：本机 userId/deviceId → Channel；
5. `ImFrameHandler`：PING/PONG、消息帧、空闲关闭和断连清理；
6. `GatewayJwtVerifier`：JWT 与 Redis 登录会话校验。

### 动手实验

运行网关测试：

```bash
mvn -pl im-gateway \
  -Dtest=GatewayJwtVerifierTest,ChannelRegistryTest,ImFrameHandlerTest test
```

当前环境实测 `ChannelRegistryTest`、`ImFrameHandlerTest` 通过；`GatewayJwtVerifierTest` 可能触发 M0 记录的 Mockito/Byte Buddy 自附加问题。遇到时应区分“测试运行器没有启动成功”和“业务断言失败”。

在纸上画出 `HttpRequest` 进入 pipeline 后，`HandshakeAuthHandler` 为什么要：

1. 剥掉 URI query；
2. `retain(req)` 后转交下一处理器；
3. 从 pipeline 移除自己。

### 通过标准

能解释“认证成功”与“WebSocket 升级成功”不是同一件事，并能完整描述连接注册、心跳续命、超时关闭和路由清理。

## M3 · Redis 路由与多端连接

### 本单元要解决的问题

- backend 不持有 Channel，怎样把消息送到正确网关？
- 同一个用户同时登录手机和网页时，路由怎样表示？
- TTL 解决了什么故障，又可能留下什么短暂不一致？

### 源码入口

- `RouteService`
- `ChannelRegistry`
- `OutboundDispatcher`
- `OutboundConsumer`

Redis 路由形态：

```text
route:user:<userId>  (Hash)
  field = deviceId
  value = gatewayId
```

例如：

```text
route:user:42
  iphone-15 → gw1
  chrome-mac → gw3
```

### 动手实验

画出“用户 42 有两个设备，分别连接 gw1 和 gw3”时，一条消息会生成几个 `OutboundPacket`。逐个写出 `gatewayId`、`targetUserId`、`deviceId`。

进阶考古：检查 TTL 是加在整个用户 Hash 上，还是单个设备路由上；分析某一设备续期对同用户其他设备路由的影响。

### 通过标准

能解释本机连接表和 Redis 全局路由为什么缺一不可，以及网关异常退出后 stale route 最迟怎样消失。

## M4 · Kafka 上下行与 ACK 语义

### 本单元要解决的问题

- 为什么网关不直接调用 backend？
- `im-inbound` 和 `im-outbound` 分别承载什么？
- 用 `cid` 作为 Kafka key 能提供怎样的顺序？
- ACK 到底确认到了哪一层？

### 源码阅读顺序

1. `InboundProducer.send()`；
2. `InboundMessageConsumer.onMessage()`；
3. `OutboundDispatcher.send()`；
4. `OutboundConsumer.onOutbound()`；
5. `ImKafkaTopics` 与两个模块的 Kafka 配置。

### 必须分清的确认语义

```text
ACK   = 网关已接收 SEND，并调用 Kafka producer
PUSH  = backend 已完成定序、落库和扇出构造
ERROR = backend 业务校验拒绝了消息
```

当前 ACK 不是数据库提交证明。学习时要继续追踪 `kafka.send()` 的异步结果有没有被等待或处理，不能仅凭方法名推断交付保证。

### 动手实验

为以下三个故障分别写出客户端可能看到什么：

1. 网关解析 JSON 失败；
2. ACK 已发出，但 backend 的成员校验失败；
3. backend 已落 MongoDB，但下行网关没有活跃 Channel。

### 通过标准

能画出上下行 topic、producer、consumer、Kafka key 和消费组，并明确区分“收到”“持久化”“推送到设备”。

## M5 · 单聊消息闭环：整套系统的主干

### 本单元要解决的问题

- 一条 TEXT 消息在 backend 内部按什么顺序处理？
- 为什么校验必须发生在定序和落库之前？
- 为什么一次写入同时涉及 Redis、MongoDB、MySQL 和 Kafka？
- 这些操作之间有没有数据库事务？失败时会出现什么中间状态？

### 核心源码阅读顺序

1. `InboundMessageConsumer.onMessage()`：总编排入口；
2. `ConversationService.isMember()` / `isGroupMuted()`：发送权限；
3. `MessageAppender.append()`：统一写入主干；
4. `SeqService.nextSeq()`：Redis `INCR`；
5. `ImMessageRepository`：MongoDB 消息存储；
6. `MessageAppender.updateSummary()`：MySQL 会话摘要；
7. `OutboundDispatcher.dispatch()`：在线成员扇出。

### 主干时序

```text
反序列化 Envelope
  → clientMsgId 幂等检查
  → 会话成员检查
  → 群禁言检查
  → 富媒体/@提及检查
  → Redis INCR 取得 seq
  → MongoDB save
  → MySQL 更新 last_msg_seq / preview
  → 构造 PUSH
  → 查询成员与在线路由
  → Kafka im-outbound
```

### 动手实验

```bash
mvn -pl backend \
  -Dtest=InboundMessageConsumerTest,InboundSendCheckTest,MessageAppenderTest test
```

然后挑一条 TEXT 消息，给每个步骤记录：输入、输出、读写的存储、可能抛出的异常。

进阶考古：Redis 已产生 seq 后，如果 MongoDB 保存失败，这个 seq 是否会被回收？这种“空洞”是否影响排序和增量同步？

### 通过标准

关闭代码，仅凭记忆把主干时序画出来；重新打开代码核对时，步骤顺序和每种存储职责都正确。

## M6 · 离线、多端同步与已读

### 本单元要解决的问题

- 用户离线时消息保存在哪里？

### 源码阅读顺序

1. `ImMessageController.messages()`；
2. `MessageQueryService.pull()`；

4. `ConversationService.listMyConversations()`；

### 动手实验

假设会话最新 `lastMsgSeq=125`：

- 手机本地同步到 120；
- 网页本地同步到 118；

分别计算两端应该用什么 `sinceSeq` 补拉、当前未读数是多少。再分析客户端错误上报 `readSeq=999` 时，服务端为什么要钳制到 `lastMsgSeq`。

运行相关测试：

```bash

  -Dtest=MessageQueryServiceTest,ConversationServiceListTest,ReadServiceTest,ReadReceiptE2ETest test
```

### 通过标准

能解释“在线 PUSH 只是低延迟通道，REST 增量拉取才是状态恢复通道”，并能用 seq 位点推导离线、多端、未读和已读。

## M8 · 富媒体与链接卡片安全

### 本单元要解决的问题

- 图片为什么不经过 backend 字节流？
- 预签名 PUT 与预签名 GET 分别在什么时候产生？

- 服务端抓取网页链接时为什么会产生 SSRF 风险？

### 富媒体阅读顺序

## M10 · 测试、排错与架构复盘

### 本单元要解决的问题

- 怎样证明一项 IM 能力不仅 Service 有实现，而且客户端入口确实可达？
- 消息没有到达时应该按什么顺序排查？
- 当前实现在哪些地方只是 MVP，而不是生产级交付保证？

### 第一部分：按链路排错

遇到“发送方点了发送，接收方没有收到”，按顺序查：

```text
1. WebSocket 是否握手成功、Channel 是否活跃
2. 网关是否解析帧并发出 ACK
3. im-inbound 是否收到消息、key 是否为正确 cid
4. backend 是否因成员/禁言/媒体/@校验返回 ERROR
5. Redis seq 是否推进、MongoDB 是否存在消息
6. MySQL last_msg_seq 是否更新
7. 接收者 route:user:<uid> 是否有在线路由
8. im-outbound 是否产生目标 packet
9. 目标 gateway 的 ChannelRegistry 是否找到设备
10. 若用户离线，sinceSeq 补拉是否能恢复消息
```

### 第二部分：代码考古任务

设计文档是线索，不是运行事实。至少完成以下核对：

1. **READ/RECALL 的真实入口**：接口文档把它们列为 WebSocket 上行 op；检查 `ImFrameHandler` 是否真的把它们投递到 `im-inbound`，再用测试证明结论。
2. **ACK 语义**：检查 Kafka `send()` 的异步结果是否被等待；判断 ACK 能否代表 Kafka broker 接收或 MongoDB 落库。
3. **幂等约束**：比较代码中的“senderId + clientMsgId”查询与 MongoDB 实际索引，判断并发重试时依赖的是应用检查还是数据库唯一约束。
4. **跨存储一致性**：枚举 Redis 定序、MongoDB 保存、MySQL 摘要、Kafka 下行之间任一步失败时的可见状态。
5. **路由 TTL**：分析用户级 Hash TTL 对多设备上下线的影响。

这里只要求用源码和测试得出结论，不在学习文档阶段直接修改实现。发现问题后单独形成修复任务。

### 第三部分：完整环境联调

启动基础设施：

```bash
cd deploy
docker compose --profile full --profile im up -d
docker compose ps
```

分别启动业务与网关：

```bash
mvn -f backend/pom.xml spring-boot:run
mvn -f im-gateway/pom.xml spring-boot:run
```

联调验收场景：

1. 两个用户登录并完成 WebSocket 握手；
2. A 发 TEXT，收到 ACK，A/B 都收到最终 PUSH；
3. B 离线，A 再发一条，B 重连后用 `sinceSeq` 补齐；
4. B 上报 READ，A 收到单聊已读回执；
5. 创建群聊并验证权限、禁言和 SYSTEM 消息；
6. 预签名上传一个小文件并完成发送、拉取；
7. 撤回消息，确认在线与补拉结果一致。

### 通过标准

你能在没有老师给出文件名的情况下，从“消息未到达”的现象逐层缩小范围；能区分设计目标、当前实现和生产级改进项。
