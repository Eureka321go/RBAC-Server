# 阶段 1 · 协议、会话与消息标识（先分清每个编号在回答什么）

> 目标：拿起一份真实 `Envelope`，分清 `cid`、`clientMsgId`、`msgId` 和 `seq`。
>
> 读完后，你应该能从客户端的一条 `SEND` 开始，写出网关即时返回的 `ACK` 和 backend 最终生成的 `PUSH`；
> 还能解释单聊、群聊为什么可以共用一条处理链路，以及哪些字段绝不能相信客户端自报。

---

## 一、先看同一条消息的三份 JSON

用户 7 给用户 19 发送“你好”。客户端首先产生的是一份还没有服务端编号的意图：

```json
{
  "op": "SEND",
  "cid": "c_7_19",
  "clientMsgId": "01JHZX8D6M7H4V6W8Q2A9K3N5P",
  "type": "TEXT",
  "body": {
    "text": "你好"
  }
}
```

网关收到帧后，立即沿原 WebSocket 连接返回：

```json
{
  "op": "ACK",
  "clientMsgId": "01JHZX8D6M7H4V6W8Q2A9K3N5P"
}
```

backend 完成成员校验、定序和落库后，再向会话成员推送最终消息：

```json
{
  "op": "PUSH",
  "cid": "c_7_19",
  "senderId": 7,
  "clientMsgId": "01JHZX8D6M7H4V6W8Q2A9K3N5P",
  "type": "TEXT",
  "body": {
    "text": "你好"
  },
  "seq": 42,
  "msgId": "0d2a430ac54749908e165a78e75089fd",
  "ts": 1785200000000
}
```

这三份 JSON 不是三条业务消息，而是同一发送意图在三个阶段的形态：

```text
客户端意图 SEND
  │ clientMsgId：我本地正在发送哪一条？
  ▼
网关接收 ACK
  │ 只证明网关已经接住并准备送往 Kafka
  ▼
backend 最终 PUSH
    msgId：服务端最终认定是哪一条消息？
    seq：它在这个会话里排第几？
```

后续所有离线同步、未读数、已读回执和撤回都建立在这组区别上。

> 上面的 JSON 为了突出有效字段省略了 `null`。当前两个模块都直接使用默认 Jackson `ObjectMapper`，实际序列化时可能保留其他值为 `null` 的 Envelope 字段。判断协议时看字段语义，不要把“是否省略 null”误当成业务差异。

## 二、为什么使用统一的 Envelope

### 2.1 两个模块各有一份同构类

先对照这两个文件：

- [`../../backend/src/main/java/com/rbac/im/protocol/Envelope.java`](../../backend/src/main/java/com/rbac/im/protocol/Envelope.java)
- [`../../im-gateway/src/main/java/com/rbac/im/gateway/protocol/Envelope.java`](../../im-gateway/src/main/java/com/rbac/im/gateway/protocol/Envelope.java)

它们不在同一个 Maven 模块，Java 类型也不是同一个类，但字段必须保持一致：

```java
private String op;
private String cid;
private Long senderId;
private String deviceId;
private String clientMsgId;
private String type;
private Map<String, Object> body;
private Long seq;
private String msgId;
private Long ts;
```

跨 JVM 传递的不是 Java 对象引用，而是 JSON。只要两端字段名和数据形态一致，网关的 `Envelope` 序列化后就能被 backend 的 `Envelope` 反序列化。

这也意味着协议兼容性由开发者负责。若只在一侧把 `seq` 改名为 `messageSeq`，编译器不会跨模块提醒另一侧，运行时却可能静默得到 `null`。

### 2.2 `op` 决定做什么，`type` 决定承载什么

这两个字段最容易混淆：

| 字段 | 回答的问题 | 例子 |
|---|---|---|
| `op` | 现在要执行什么协议动作？ | `SEND`、`ACK`、`PUSH`、`READ`、`RECALL`、`PING` |
| `type` | 这条可持久化消息是什么内容？ | `TEXT`、`IMAGE`、`FILE`、`SYSTEM`、`RECALL` |

例如，用户请求撤回时发送的是：

```json
{
  "op": "RECALL",
  "cid": "c_7_19",
  "body": {
    "targetSeq": 41
  }
}
```

backend 校验成功后追加一条可持久化的撤回控制消息，向成员发出的形态则是：

```json
{
  "op": "PUSH",
  "cid": "c_7_19",
  "senderId": 7,
  "type": "RECALL",
  "body": {
    "targetSeq": 41
  },
  "seq": 43,
  "msgId": "e4752842d73a461c8aa63930324047bf",
  "ts": 1785200010000
}
```

所以 `op=RECALL` 是一个请求动作，`op=PUSH + type=RECALL` 是一条已经成为会话事实的控制消息。两者不能互换。

已读又不同：`op=READ` 只推进成员位点，不写入 `im_message`，也不占用新的消息 `seq`。

### 2.3 `body` 为什么是 `Map<String, Object>`

不同消息类型需要不同正文：

```json
{ "text": "hello" }
```

```json
{
  "objectKey": "im/c_7_19/7/abc.png",
  "mime": "image/png",
  "size": 12345,
  "filename": "abc.png"
}
```

```json
{ "targetSeq": 41 }
```

统一 Envelope 固定了外层路由信息，`body` 则给不同类型保留扩展空间。代价是编译期类型约束较弱：`targetSeq` 到底是不是数字，要由 `RecallService` 在业务边界检查；不能因为 JSON 能反序列化，就认为业务输入合法。

## 三、字段不是“客户端填”或“服务端填”这么简单

### 3.1 按消息阶段划分责任

| 字段 | 客户端 SEND | 网关处理 | backend 最终 PUSH | 主要作用 |
|---|---:|---|---:|---|
| `op` | 填 `SEND` | 判断分支 | 改为 `PUSH` | 协议动作 |
| `cid` | 填已有会话 | 原样转发 | 原样携带 | 会话路由与数据隔离 |
| `senderId` | 即使填了也不可信 | 用握手身份覆盖 | 携带可信发送者 | 身份 |
| `deviceId` | 即使填了也不可信 | 用当前连接设备覆盖 | 普通 PUSH 不设置 | 上行设备上下文 |
| `clientMsgId` | 生成并填写 | ACK 原样带回 | 幂等查询并在 PUSH 带回 | 本地发送关联 |
| `type` | 填消息类型 | 原样转发 | 校验后带回 | 正文类型 |
| `body` | 填业务内容 | 原样转发 | 校验/补充后带回 | 消息正文 |
| `seq` | 不应填写 | 不产生 | Redis 定序后填写 | 会话内位置 |
| `msgId` | 不应填写 | 不产生 | backend 生成 | 服务端消息标识 |
| `ts` | 不应作为最终时间 | 不产生 ACK 时间 | backend 生成 | 服务端落消息时间 |

### 3.2 身份必须来自连接，而不是 JSON

`ImFrameHandler` 先从已鉴权 Channel 读取身份：

```java
Long userId = ctx.channel().attr(HandshakeAuthHandler.USER_ID).get();
String deviceId = ctx.channel().attr(HandshakeAuthHandler.DEVICE_ID).get();
```

进入 `SEND` 分支后，它覆盖客户端自报字段：

```java
env.setSenderId(userId);
env.setDeviceId(deviceId);
```

假设用户 7 发送下面这份伪造 JSON：

```json
{
  "op": "SEND",
  "cid": "c_7_19",
  "senderId": 19,
  "deviceId": "victim-phone",
  "clientMsgId": "local-8",
  "type": "TEXT",
  "body": { "text": "伪造内容" },
  "seq": 999999,
  "msgId": "fake"
}
```

当前网关会把 `senderId` 和 `deviceId` 改回连接的真实身份。backend 的 `MessageAppender` 也不会沿用上行的 `seq`、`msgId` 和 `ts`，而是重新产生这三个最终字段。

这条边界可以概括为：

```text
握手身份                  客户端消息内容
  │可信                       │待校验
  ├──覆盖 senderId/deviceId───┤
  │                           ▼
  └────────────────────── backend
                              │
                              └──生成 seq/msgId/ts
```

但是 `cid`、`type` 和 `body` 仍来自客户端。backend 必须继续验证发送者是否属于该 `cid`、消息类型是否支持、正文是否合规。网关覆盖身份不是全部授权检查。

## 四、`cid`：回答“这件事属于哪个会话”

### 4.1 单聊 cid 为什么要排序

[`ConversationService.singleCid()`](../../backend/src/main/java/com/rbac/im/service/ConversationService.java) 的规则很短：

```java
public String singleCid(long a, long b) {
    long min = Math.min(a, b);
    long max = Math.max(a, b);
    return "c_" + min + "_" + max;
}
```

于是：

```text
singleCid(7, 19)  = c_7_19
singleCid(19, 7)  = c_7_19
```

若不排序，A 找 B 可能得到 `c_7_19`，B 找 A 却得到 `c_19_7`，同一对用户会出现两个单聊会话。升序拼接让“这一对用户”天然映射到同一个候选 cid。

数据库还在 `im_conversation.cid` 上设置了 `uk_cid` 唯一键。字符串规则负责得到同一个候选值，唯一约束负责阻止数据库出现两个同名会话；它们解决的不是同一层问题。

### 4.2 群聊 cid 为什么不能拼成员

群聊采用：

```text
g_<groupId>
```

例如群 203 的会话是 `g_203`。群成员会不断加入和退出，如果把成员列表编码进 cid，成员变化就会导致会话身份变化。用稳定 `groupId` 关联群，使消息历史不随成员变化而改名。

`groupIdFromCid()` 负责识别群会话：

```java
public static Long groupIdFromCid(String cid) {
    return cid != null && cid.startsWith("g_")
            ? Long.valueOf(cid.substring(2))
            : null;
}
```

它表达的是当前项目约定：`g_` 开头表示群聊，其他 cid 在这个方法中返回 `null`。

注意它不是完整的输入校验器。`g_abc` 会在 `Long.valueOf()` 处抛出异常，`c_7_19` 是否真的存在也不能靠字符串格式判断。真实权限仍要查询会话成员数据。

### 4.3 `cid` 怎样统一后续链路

不论单聊还是群聊，得到 cid 后都可以复用同一组操作：

```text
Kafka key = cid
Redis seq key = im:conv:<cid>:seq
Mongo 查询/唯一索引 = cid + seq
MySQL 会话成员查询 = cid + userId
历史补拉参数 = cid + sinceSeq
```

差异被压缩在“会话怎样创建、成员是谁、权限怎样判断”上；一旦进入消息主链路，定序、落库和增量拉取不需要为单聊、群聊各写一套。

### 4.4 `cid` 不是秘密，也不是授权凭证

`c_7_19` 和 `g_203` 都很容易猜。安全性不能建立在“别人不知道 cid”上。

客户端可以提交 cid，但 backend 在发送和拉取前仍要执行：

```java
conversationService.isMember(cid, userId)
```

因此 cid 的职责是标识与路由，不是证明“我有权访问这个会话”。

## 五、三个消息标识分别解决什么问题

### 5.1 先建立不能混用的总表

| 标识 | 当前生成方 | 当前形态/作用域 | 回答的问题 | 是否用于排序 |
|---|---|---|---|---:|
| `clientMsgId` | 客户端 | 字符串；幂等查询实际按发送者 + clientMsgId | 这是我本地哪次发送？ | 否 |
| `msgId` | backend | 去横线 UUID，32 位十六进制字符串 | 服务端最终是哪条消息？ | 否 |
| `seq` | backend 调用 Redis | Long；每个 cid 独立递增 | 它在当前会话排第几？ | 是，仅会话内 |

MongoDB 自己的 `_id` 也存在，但它是持久化文档主键，不在当前实时 PUSH 或历史 `ImMessageVO` 中暴露给客户端。不要把 `_id` 和协议 `msgId` 混为一谈。

### 5.2 `clientMsgId`：先于网络存在的本地关联号

客户端按下发送时，还没有 `msgId` 和 `seq`，但 UI 已经需要创建一条“发送中”记录。因此客户端先产生 `clientMsgId`：

```text
local-123 / UUID / ULID
```

当前服务端没有强制格式，只要能作为稳定字符串即可。客户端重试同一次发送时必须复用原值；一条全新的消息必须换新值。

它承担两项直接职责。

第一，关联状态：

```text
本地消息(clientMsgId=local-123, status=sending)
  → ACK(clientMsgId=local-123): status=accepted
  → PUSH(clientMsgId=local-123, seq=42): status=sent，补齐最终编号
```

第二，降低重复处理：`InboundMessageConsumer` 查询：

```java
repo.existsBySenderIdAndClientMsgId(senderId, clientMsgId)
```

若同一发送者的该 `clientMsgId` 已存在，就跳过再次追加。

这里要准确理解当前边界：

- 查询作用域是“发送者 + clientMsgId”，没有包含 cid；
- `clientMsgId` 字段只有普通索引，不是唯一索引；
- 逻辑是“先查再写”，并发请求仍可能同时查到不存在；
- 因此它提供应用层幂等检查，但不是数据库唯一约束意义上的严格并发幂等。

现阶段的客户端应当让 `clientMsgId` 至少在同一用户范围内长期不重复，而不是只在某个会话内从 1 重新计数。严格幂等约束会在 M10 架构复盘中继续检查。

### 5.3 `msgId`：服务端生成的消息身份

`MessageAppender` 使用：

```java
String msgId = UUID.randomUUID().toString().replace("-", "");
```

它与具体会话位置无关。消息即使在不同 cid 中，也应拥有不同的服务端身份。当前实现把它持久化到 `ImMessage.msgId`，并在 PUSH 与历史查询中返回。

但 `msgId` 不能用来排序。随机 UUID 的字典顺序既不代表发送顺序，也不代表落库时间。想知道同一会话的先后必须看 `seq`。

还要区分“生成策略上期望全局唯一”和“数据库强制唯一”。当前 MongoDB 模型没有给 `msgId` 声明唯一索引；真正存在的唯一复合索引是 `cid + seq`。因此文档说“服务端全局消息标识”是在描述协议职责，不是在声称数据库已经建立 `msgId` 唯一约束。

### 5.4 `seq`：会话内位置，而不是全站时间线

`SeqService` 对每个会话自己的 Redis key 执行原子递增：

```text
im:conv:c_7_19:seq
im:conv:g_203:seq
```

如果两个 key 当前值分别为 41 和 900，下一条消息会得到：

```text
c_7_19 → seq 42
g_203  → seq 901
```

`42 < 901` 不表示单聊消息更早。两个 seq 只在各自 cid 内有意义。

seq 的用途非常集中：

```text
会话内排序：ORDER BY seq ASC
离线补拉：seq > sinceSeq
未读计算：lastMsgSeq - lastReadSeq
已读推进：lastReadSeq 向前移动
撤回定位：cid + targetSeq
@我提醒：mentionSeq > lastReadSeq
```

MongoDB 的 `@CompoundIndex(name = "cid_seq", ..., unique = true)` 进一步保证同一个 cid 不能保存两条相同 seq 的文档。

Redis `INCR` 发生在 MongoDB 保存之前，所以故障可能消耗一个 seq 却没有形成消息。例如拿到 42 后落库失败，下一次可能直接得到 43。当前协议需要的是单调、唯一、可比较，不承诺绝对连续；客户端不能因为缺少 42 就擅自构造一条消息。

## 六、从 SEND 到 PUSH：四个标识怎样落到真实代码

### 6.1 客户端提交意图

一份最小 TEXT SEND 是：

```json
{
  "op": "SEND",
  "cid": "c_7_19",
  "clientMsgId": "local-123",
  "type": "TEXT",
  "body": {
    "text": "你好"
  }
}
```

此时客户端可以知道目标会话和本地发送号，但不能知道最终 seq。

### 6.2 网关覆盖身份并即时 ACK

网关做的关键动作是：

```text
解析 Envelope
  → 从 Channel 取 userId/deviceId
  → 覆盖 senderId/deviceId
  → 发送到 im-inbound，Kafka key=cid
  → 原连接返回 ACK(clientMsgId)
```

ACK 中没有 seq，因为 backend 尚未处理；也没有 msgId，因为网关不负责生成最终消息身份。

更精确地说，当前代码在调用 `kafka.send(...)` 后立即构造 ACK，没有等待 Kafka future 确认 broker 已成功持久化，也没有等待 backend。于是 ACK 表达“网关已接收并发起上行发送”，不是“消息已经落入 MongoDB”。

### 6.3 backend 完成业务处理

`InboundMessageConsumer` 收到 JSON 后：

```text
clientMsgId 幂等检查
  → cid 成员校验
  → 群禁言/媒体/@提及等校验
  → MessageAppender.append(...)
```

`MessageAppender` 再执行：

```text
Redis INCR 生成 seq
  → UUID 生成 msgId
  → 系统时间生成 ts
  → MongoDB 保存 ImMessage
  → MySQL 更新 lastMsgSeq / 摘要
  → 构造 PUSH
  → 按 cid 扇出
```

最终 PUSH 同时保留 `clientMsgId`、`msgId` 和 `seq`，因为发送方需要把本地临时记录升级为服务端最终记录，其他接收方则主要依赖 `msgId` 与 `seq`。

### 6.4 ERROR 与 ACK 并不矛盾

如果用户不是会话成员，时间线可能是：

```text
客户端 SEND
  ← 网关 ACK(clientMsgId)
  → backend 校验发现 NOT_MEMBER
  ← ERROR(clientMsgId, reason=NOT_MEMBER)
```

先 ACK 后 ERROR 是两层确认的自然结果：网关确实接住了帧，但业务层最终拒绝。客户端不能在收到 ACK 时就把消息标记为最终发送成功；应等待匹配的 PUSH，或把 ERROR 映射为失败。

## 七、Envelope 与 OutboundPacket 不要混在一起

backend 向 Kafka `im-outbound` 写出的不是裸 Envelope，而是 `OutboundPacket`：

```json
{
  "gatewayId": "gateway-a",
  "targetUserId": 19,
  "deviceId": "phone-1",
  "envelope": {
    "op": "PUSH",
    "cid": "c_7_19",
    "senderId": 7,
    "clientMsgId": "local-123",
    "type": "TEXT",
    "body": { "text": "你好" },
    "seq": 42,
    "msgId": "0d2a430ac54749908e165a78e75089fd",
    "ts": 1785200000000
  }
}
```

两层结构回答不同问题：

| 层 | 消费者 | 回答的问题 |
|---|---|---|
| `OutboundPacket` | 网关内部的 Kafka 消费者 | 应送到哪台网关、哪个用户、哪个设备？ |
| `Envelope` | 客户端协议处理层 | 用户最终收到什么业务消息？ |

`gatewayId` 和 `targetUserId` 是投递元数据，不应该混入客户端消息正文。网关消费 `OutboundPacket`、确认目标是本实例后，只把里面的 Envelope 序列化为 WebSocket 帧。

和 Envelope 一样，backend 与 gateway 也各有一份同构 `OutboundPacket` 类。修改一侧字段时必须同步另一侧。

## 八、三种上行 Envelope 手写实验

本节先练协议形态，不要求启动基础设施。

### 8.1 TEXT SEND

```json
{
  "op": "SEND",
  "cid": "c_7_19",
  "clientMsgId": "local-124",
  "type": "TEXT",
  "body": {
    "text": "今晚 8 点开会"
  }
}
```

逐字段标注：

| 字段 | 信任结论 |
|---|---|
| `cid` | 客户端选择，但 backend 必须验证成员身份 |
| `clientMsgId` | 客户端负责稳定生成，backend 用于幂等检查 |
| `type/body` | 客户端输入，必须做类型与内容校验 |
| `senderId/deviceId` | 不应依赖客户端填写，网关从连接身份覆盖 |
| `seq/msgId/ts` | 不应依赖客户端填写，backend 重新生成 |

### 8.2 READ

```json
{
  "op": "READ",
  "cid": "c_7_19",
  "body": {
    "readSeq": 42
  }
}
```

它表达“我已经读到当前会话的 42”。`readSeq` 必须和 cid 一起解释；单独一个 42 没有全局意义。backend 还会把超出会话 `lastMsgSeq` 的值钳制回来，并只允许位点向前推进。

READ 不需要 `type`、`clientMsgId` 或新 seq，因为它不是新增消息。单聊成功推进后，对端收到的也是 `op=READ` 回执，而不是 `op=PUSH + type=READ`。

### 8.3 RECALL

```json
{
  "op": "RECALL",
  "cid": "c_7_19",
  "clientMsgId": "recall-local-1",
  "body": {
    "targetSeq": 41
  }
}
```

`targetSeq=41` 定位的是 `c_7_19` 内第 41 条消息。backend 不能只按 targetSeq 查询，否则另一个会话的 41 也可能被命中。

当前 `RecallService` 的错误响应没有复制源 `clientMsgId`，而 `InboundMessageConsumer` 的普通发送错误会复制。接口文档把 ERROR 描述为可用 `clientMsgId` 关联，但撤回错误的当前实现与普通发送并不完全一致；客户端不能假设所有 ERROR 都一定有该字段。

## 九、设计协议与当前真实入口的差异

这是本章必须完成的一次实现核对。

接口文档把下面四种操作列为客户端上行：

```text
SEND / RECALL / READ / PING
```

backend 的 `InboundMessageConsumer` 确实有 `RECALL` 与 `READ` 分支，相关服务和测试也存在。但是当前网关 [`ImFrameHandler`](../../im-gateway/src/main/java/com/rbac/im/gateway/netty/ImFrameHandler.java) 只处理：

```java
if ("PING".equals(env.getOp())) {
    // 回 PONG
    return;
}
if ("SEND".equals(env.getOp())) {
    // 覆盖身份、发 Kafka、回 ACK
}
```

因此当前真实 WebSocket 入口的结果是：

| 客户端 op | 网关当前行为 | 能否到 backend |
|---|---|---:|
| `PING` | 本地回 `PONG` | 否，也不需要 |
| `SEND` | 覆盖身份、发 `im-inbound`、回 ACK | 是 |
| `READ` | 没有命中分支，无响应 | 否 |
| `RECALL` | 没有命中分支，无响应 | 否 |
| 未知 op | 没有命中分支，无 ERROR | 否 |

这不是说 backend 的 READ/RECALL 逻辑不存在，而是它们目前只能在直接调用 consumer/service 的测试路径中到达，尚未从真实网关入口闭环。

还有一个身份边界问题：现在只有 `SEND` 分支会覆盖 `senderId/deviceId`。未来给网关接通 `READ` 与 `RECALL` 时，也必须在转发前从 Channel 写入可信 `senderId`，不能原样相信帧里的操作者身份。

本阶段只记录差异，不修改实现。后续学习和验收要始终分开三个结论：

```text
协议文档声明了什么
  ≠ backend 某个 service 能做什么
  ≠ 客户端通过真实入口现在能做什么
```

## 十一、常见误判

### 误判 1：收到 ACK 就表示消息发送成功

不对。ACK 由网关即时返回，早于 backend 校验和落库。最终成功要看匹配 `clientMsgId` 的 PUSH；业务拒绝则看 ERROR。

### 误判 2：`msgId` 可以代替 `seq` 排序

不对。当前 msgId 是随机 UUID 字符串。会话内排序、补拉和位点都使用 seq。

### 误判 3：seq 越大全站越新

不对。每个 cid 使用独立 Redis key。跨会话 seq 不可比较。

### 误判 4：cid 能被猜到，所以它不安全

cid 可猜本身不是漏洞。若后端只凭 cid 放行才是漏洞。当前成员检查必须始终保留。

### 误判 5：`clientMsgId` 重试时应该重新生成

不对。同一次发送重试必须复用，才能关联 ACK/PUSH 并触发幂等检查。新业务消息才生成新值。

### 误判 6：MongoDB `_id` 就是 msgId

不对。`ImMessage` 同时有 `@Id String id` 和协议字段 `String msgId`。当前 API 返回 msgId，不返回 Mongo `_id`。

### 误判 7：backend 有 READ 测试，客户端 READ 就一定可用

不对。测试可以直接调用 backend consumer；真实 WebSocket 帧还要经过网关，而当前网关没有转发 READ/RECALL。

## 十二、动手练习

### 练习 1：补齐三阶段消息

给定客户端 SEND：

```json
{
  "op": "SEND",
  "cid": "g_203",
  "clientMsgId": "m-900",
  "type": "TEXT",
  "body": { "text": "收到" }
}
```

假设握手用户为 7、backend 生成 `seq=88`、`msgId=srv-abc`、`ts=1000`，写出 ACK 和最终 PUSH。

<details>
<summary><b>参考答案</b></summary>

ACK：

```json
{
  "op": "ACK",
  "clientMsgId": "m-900"
}
```

PUSH：

```json
{
  "op": "PUSH",
  "cid": "g_203",
  "senderId": 7,
  "clientMsgId": "m-900",
  "type": "TEXT",
  "body": { "text": "收到" },
  "seq": 88,
  "msgId": "srv-abc",
  "ts": 1000
}
```

ACK 没有最终 seq/msgId/ts；PUSH 的 senderId 来自握手身份，而不是客户端自报。

</details>

### 练习 2：判断四个编号能否比较

已知：

```text
A = (cid=c_7_19, clientMsgId=x1, msgId=m1, seq=42)
B = (cid=c_7_19, clientMsgId=x2, msgId=m9, seq=43)
C = (cid=g_203,  clientMsgId=x3, msgId=m2, seq=901)
```

回答：

1. A 与 B 谁在当前会话中更晚？
2. B 与 C 谁在全站更晚？
3. 哪个字段可用于把发送方本地记录与 PUSH 对上？
4. 哪个字段表示服务端最终消息身份，但不能排序？

<details>
<summary><b>参考答案</b></summary>

1. B，因为两者 cid 相同且 `43 > 42`。
2. 无法从 seq 判断，因为 cid 不同；msgId 和 clientMsgId 也不表达时间顺序。
3. `clientMsgId`。
4. `msgId`。

</details>

### 练习 3：识别不可信字段

用户 7 的已鉴权连接发来：

```json
{
  "op": "SEND",
  "cid": "g_203",
  "senderId": 99,
  "deviceId": "admin-phone",
  "clientMsgId": "m-901",
  "type": "TEXT",
  "body": { "text": "hello" },
  "seq": 999,
  "msgId": "chosen-by-client",
  "ts": 1
}
```

说出每个字段的处理结论。

<details>
<summary><b>参考答案</b></summary>

- `senderId`、`deviceId`：网关用用户 7 当前 Channel 上的身份覆盖。
- `seq`、`msgId`、`ts`：不能作为最终值，backend 的 appender 重新生成。
- `cid`：可以作为目标提交，但 backend 必须检查用户 7 是不是 `g_203` 成员。
- `clientMsgId`：由客户端提供，用于本地关联和应用层幂等检查。
- `type/body`：来自客户端，必须经过业务校验，不能只因 JSON 合法就接受。
- `op`：网关只允许进入已实现的协议分支；当前 SEND 会转发。

</details>

### 练习 4：解释单聊和群聊如何共用主链路

为什么 `c_7_19` 和 `g_203` 能共用 `MessageAppender`、MongoDB 查询和离线补拉？哪些逻辑仍然不同？

<details>
<summary><b>参考答案</b></summary>

两类会话都被归一为 cid。定序使用 `im:conv:<cid>:seq`，消息保存与查询使用 `cid + seq`，扇出先按 cid 查成员，客户端也用 `cid + sinceSeq` 补拉，所以主链路可以复用。

不同点仍在会话与权限层：单聊 cid 由两个用户 id 排序生成，成员固定为双方；群聊 cid 关联 groupId，成员可变，还有 OWNER/ADMIN/MEMBER、禁言、@全体等群权限。

</details>

### 练习 5：判断当前真实入口

下面哪些帧在当前 `ImFrameHandler` 中会进入 `im-inbound`？

```text
PING / SEND / READ / RECALL / UNKNOWN
```

<details>
<summary><b>参考答案</b></summary>

只有 SEND。PING 由网关本地回复 PONG；READ、RECALL 和未知 op 当前都不命中转发分支。backend 虽然实现了 READ/RECALL 的消费逻辑，但真实网关入口尚未接通。

</details>

## 十三、自检与通过标准

不看文档，尝试回答：

1. 为什么 backend 和 gateway 各有一份 Envelope，它们怎样互通？
2. `op=RECALL` 与 `op=PUSH,type=RECALL` 有什么区别？
3. 为什么 `senderId` 必须来自 Channel，而不能相信 JSON？
4. `c_19_7` 为什么不应该和 `c_7_19` 同时存在？
5. 群成员变化时，为什么 `g_203` 不需要变化？
6. `clientMsgId`、`msgId`、`seq` 分别由谁生成、解决什么问题？
7. 为什么 `seq=901` 不一定比 `seq=42` 更新？
8. ACK、PUSH、ERROR 各自怎样驱动客户端发送状态？
9. `OutboundPacket` 为什么还要在 Envelope 外面包一层？
10. 为什么接口文档中的 READ/RECALL 目前不能直接证明真实 WebSocket 可用？

<details>
<summary><b>自检参考答案</b></summary>

1. 两个模块不能共享运行时 Java 对象，因此各自定义同构类，通过 JSON 字段互操作。两侧十个字段的名称与类型必须同步，否则编译器不会自动保证跨模块协议兼容。
2. `op=RECALL` 是客户端请求撤回某个 `cid + targetSeq`；校验成功后，backend 追加一条 `type=RECALL` 的持久化控制消息，并以 `op=PUSH` 扇出。前者是动作，后者是会话中已经发生的事实。
3. JSON 可被客户端任意修改。Channel 身份来自 WebSocket 握手鉴权；网关必须用该身份覆盖 senderId/deviceId，backend 再基于真实 senderId 检查会话成员和权限。
4. 单聊双方无方向性。`singleCid()` 对用户 id 排序，使 19 找 7 和 7 找 19 都得到 `c_7_19`；MySQL 的 `uk_cid` 再阻止同名会话重复落库。
5. 群聊身份来自稳定 groupId，不来自成员集合。成员加入和退出只改变关系表，不改变群会话历史所属的 cid。
6. clientMsgId 由客户端在发送前产生，用于本地记录、ACK/PUSH 对账和应用层幂等；msgId 由 backend 生成，用作服务端最终消息身份；seq 由 backend 调用 Redis 按 cid 递增生成，用于会话内排序、补拉和位点。
7. seq 的作用域是单个 cid。`g_203:901` 与 `c_7_19:42` 来自两个 Redis key，无法比较全局先后。
8. ACK 表示网关接住并发起上行，客户端可从 sending 进入 accepted；匹配 clientMsgId 的 PUSH 带回最终 seq/msgId，才进入 sent；ERROR 表示业务拒绝，应进入 failed。ACK 和后续 ERROR 可以先后出现而不矛盾。
9. Envelope 是客户端能理解的业务协议；OutboundPacket 额外携带 gatewayId、targetUserId 和 deviceId，供下行基础设施把 Envelope 路由到具体网关与设备。这些投递元数据不应暴露为消息正文。
10. 当前 gateway 只把 SEND 转发到 Kafka，PING 本地处理，READ/RECALL 不命中任何分支。backend service 和直接 consumer 测试通过，只能证明逻辑层能力，不能证明真实入口闭环。

</details>

本章通过标准是：

- 能不看文档写出 TEXT SEND、ACK、最终 PUSH 三份 Envelope；
- 能给 `cid`、`clientMsgId`、`msgId`、`seq` 各写一句唯一且不重叠的职责；
- 能解释单聊排序 cid、群聊稳定 cid 和成员校验三者的关系；
- 能指出客户端可填字段、网关覆盖字段和 backend 生成字段；
- 能说明 ACK 为什么早于最终成功，以及 ERROR 为什么可能出现在 ACK 之后；
- 能从源码指出 READ/RECALL 的 backend 能力与当前网关入口差异。

<details>
<summary><b>通过标准参考产物</b></summary>

**1. 一张字段责任表：**

| 字段 | 一句话职责 |
|---|---|
| `cid` | 标识并路由一个单聊或群聊会话，不充当授权凭证 |
| `clientMsgId` | 关联客户端发送尝试、ACK 与最终 PUSH，并参与应用层幂等 |
| `msgId` | 标识 backend 最终产生的服务端消息，不用于排序 |
| `seq` | 表示消息在当前 cid 内的位置，用于排序和同步位点 |

**2. 一条完整状态转换：**

```text
local sending(clientMsgId)
  → ACK(clientMsgId)
  → accepted
  → PUSH(clientMsgId, msgId, seq)
  → sent
```

或业务拒绝分支：

```text
accepted
  → ERROR(clientMsgId?, reason)
  → failed
```

问号表示当前并非所有错误分支都复制 clientMsgId，撤回错误就是已发现的差异。

**3. 一条会话统一链路：**

```text
c_7_19 / g_203
  → 统一 cid
  → Kafka key
  → Redis 每会话 seq
  → Mongo cid+seq
  → MySQL cid+userId
  → REST cid+sinceSeq
```

**4. 一个当前实现结论：**

```text
真实 WebSocket：SEND 可上行，PING 本地闭环；READ/RECALL 尚未转发。
backend 逻辑：SEND、READ、RECALL 均已有消费分支。
```

能同时说清这两句，才算真正区分了协议设计、逻辑实现和端到端能力。

</details>
