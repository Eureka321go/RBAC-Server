# 练习册 01 · 核心链路手工查询（不许用 JOIN）

> 目标：用最笨的办法——**三条独立的 SELECT，手工接力**——把 RBAC 的核心链路
> `用户 → 角色 → 菜单` 走一遍，亲手数出 admin 有多少个菜单。
> 读完你能：说清两座"桥表"各自拦住了什么，并且**提前看见 `04` 用 JOIN 合并这三步时会踩的坑**。
>
> 这份是练习册，不是新章节。它夹在 `00`（认识了 20 张表和两座桥）和 `02`（索引原理）之间，
> 用途是：在你还没有任何索引/执行计划知识的时候，先**把数据摸熟**。
> 后面 `02`/`03` 跑 EXPLAIN 时，你对这些表里到底有什么已经有肌肉记忆了。

## 一、为什么要先手工走一遍

`00` 里给过这张链路图：

```
sys_user ──[sys_user_role]── sys_role ──[sys_role_menu]── sys_menu
   谁            桥 1            什么角色       桥 2          能看什么
```

`backend/src/main/java/com/rbac/system/menu/mapper/SysMenuMapper.java` 里，这条链路是**一条四表 JOIN** 干完的。那条 SQL 是 `04` 的主教材，现在别看。

先用三条 SELECT 手工走，有两个理由，第二个比第一个重要得多：

1. **你会记住每张表里到底有什么。** JOIN 写出来是一行结果，中间发生了什么被优化器藏起来了。手工走，每一步的中间结果都摊在你面前。
2. **手工走看不见的坑，一合并成 JOIN 就会暴露。** 这才是重点——本练习册最后会让你亲眼看见其中一个。

> 🔑 手工三步和一条 JOIN，**结果相同不代表等价**。差别不在性能，在于 JOIN 强迫你回答一些手工三步可以蒙混过关的问题（比如"关联表里的行，要不要跟着主表的逻辑删除一起失效"）。

## 三、示范：admin 的菜单有多少个

### 第一步 · 从用户名拿 id

```sql
SELECT id, username, status FROM sys_user WHERE username = 'admin';
```

```
+----+----------+---------+
| id | username | status  |
+----+----------+---------+
|  1 | admin    | ENABLED |
+----+----------+---------+
```

拿到 `id = 1`。

### 第二步 · 过桥 1，拿 role_id

```sql
SELECT user_id, role_id FROM sys_user_role WHERE user_id = 1;
```

```
+---------+---------+
| user_id | role_id |
+---------+---------+
|       1 |       1 |
+---------+---------+
```

一条，`role_id = 1`。**注意这里是"碰巧一条"**：`sys_user_role` 是多对多，一个用户挂三个角色是完全合法的，那样第三步就得拿三个 role_id 去查、再对结果去重。`SysMenuMapper` 那条 JOIN 里的 `DISTINCT` 就是为这个准备的。

### 第三步 · 过桥 2，拿 menu_id

```sql
SELECT COUNT(*) AS menu_count FROM sys_role_menu WHERE role_id = 1;
```

```
+------------+
| menu_count |
+------------+
|         48 |
+------------+
```

**答案：admin 有 48 个 menu_id。**

### 这个 48 是什么

```sql
SELECT COUNT(*) AS 菜单总数 FROM sys_menu WHERE deleted = 0;
SELECT menu_type, COUNT(*) AS cnt FROM sys_menu WHERE deleted = 0 GROUP BY menu_type;
```

```
+--------------+
| 菜单总数     |
+--------------+
|           48 |
+--------------+
+-----------+-----+
| menu_type | cnt |
+-----------+-----+
| DIR       |   4 |
| MENU      |  14 |
| BUTTON    |  30 |
+-----------+-----+
```

48 = 4 个目录 + 14 个菜单 + 30 个按钮，**正好是全表**。admin 挂的 `super_admin` 拿到了系统里每一个菜单，符合预期。

| 概念 | 本项目 | 实际作用 |
|------|--------|---------|
| 谁 | `sys_user.id = 1` | 登录主体 |
| 桥 1 | `sys_user_role (user_id, role_id)` | 用户↔角色多对多，一行 = 一次授权 |
| 什么角色 | `sys_role.id = 1`，`role_code = super_admin` | 权限的载体，`data_scope = ALL` |
| 桥 2 | `sys_role_menu (role_id, menu_id)` | 角色↔菜单多对多 |
| 能看什么 | `sys_menu` 的 48 行 | 前端动态路由 + 按钮权限码的来源 |

### ⚠️ 但真实的应用**不是这么算 admin 的菜单的**

这点必须现在说清楚，否则你会建立一个错误的心智模型。

打开 `backend/src/main/java/com/rbac/system/menu/mapper/SysMenuMapper.java`，你会发现它有**两套**方法：

| 谁登录 | 查权限码 | 查菜单树 | 走 JOIN 吗 |
|--------|---------|---------|-----------|
| 普通用户 | `selectPermissionCodesByUserId` | `selectVisibleMenusByUserId` | ✅ 四表 JOIN |
| **超管** | `selectAllPermissionCodes` | `selectAllVisibleMenus` | ❌ **单表，直接全捞** |

分叉发生在 `LoginUserAssembler.java:59-61`：

```java
boolean isSuper = roleCodes.contains(SUPER_ADMIN);
List<String> codes = isSuper
        ? menuMapper.selectAllPermissionCodes()      // 超管：SELECT ... FROM sys_menu，没有 JOIN
        : menuMapper.selectPermissionCodesByUserId(userId);   // 普通用户：四表 JOIN
```

所以你刚才手工走的三步，**admin 在真实登录流程里一步都没走**。系统认出他是超管，直接 `SELECT * FROM sys_menu WHERE deleted = 0 AND status = 'ENABLED'` 全捞。

结果一样（都是 48），**路径完全不同**。

为什么要短路？因为超管的 JOIN 结果**恒等于全表**——既然结论已知，何必付出三次 JOIN 加一次 `DISTINCT` 去重的代价。这是"用业务知识优化查询"的典型：一个布尔判断换掉一条四表 JOIN。

> 🔑 于是你手工数出的 48 有了双重含义：它既是"admin 通过两座桥能拿到的菜单数"，也是"`sys_menu` 的全表行数"。**这两个数字相等，正是超管短路成立的前提。** 哪天有人手滑删了 `sys_role_menu` 里 role 1 的几行，这两个数就不相等了——而超管**照样看得见全部菜单**，因为他根本不查那张表。

用 `test`（普通用户，走 JOIN）做同样的练习，才是在模拟真实链路。这就是下面 B 组第 8 题的意义。

## 四、手工三步藏起来的坑

跑完上面三步，你很容易得出"admin 有全部 48 个菜单"就收工。但这里有一个**手工走绝对看不见**的东西：

```sql
SHOW COLUMNS FROM sys_role_menu;
```

```
+---------+--------+------+-----+---------+----------------+
| Field   | Type   | Null | Key | Default | Extra          |
+---------+--------+------+-----+---------+----------------+
| id      | bigint | NO   | PRI | NULL    | auto_increment |
| role_id | bigint | NO   | MUL | NULL    |                |
| menu_id | bigint | NO   |     | NULL    |                |
+---------+--------+------+-----+---------+----------------+
```

**`sys_role_menu` 没有 `deleted` 列。** 两座桥表都没有——它们不参与逻辑删除。

于是：假设运维把 `sys_menu` 里某个菜单逻辑删除了（`deleted = 1`），`sys_role_menu` 里指向它的那一行**纹丝不动**。你手工走第三步 `SELECT ... FROM sys_role_menu WHERE role_id = 1` 照样数出 48，因为你**压根没查 `sys_menu`**。

但 `04` 把三步合成一条 JOIN 之后，`sys_menu` 就进到查询里了。这时候如果 JOIN 条件里漏写 `sys_menu.deleted = 0`，那个已删除的菜单会被**捞回结果集**，前端菜单树上就会冒出一个幽灵条目。

> 🔑 逻辑删除是**应用层的约定**，不是数据库的机制。`@TableLogic` 只在 MyBatis-Plus 生成的 SQL 里自动加 `deleted = 0`，它管不到手写 SQL，更管不到关联表。**桥表不带 `deleted`，就意味着每一条碰它的 JOIN 都必须自己记得过滤主表。**

这条线 `07`（逻辑删除的取舍）会算总账，`04` 会先让你看见它怎么炸。

## 七、面试怎么问

**Q1：用户-角色-菜单这种 RBAC 模型，表怎么设计？**

标准答法是五张表：`user` / `role` / `menu`(或 `permission`) + 两张关联表 `user_role` / `role_menu`。要点是**两处多对多必须各用一张中间表**，不能在用户表塞 `role_ids` 字段（理由见 `00` 自检 2：违反第一范式、没法建索引、没法保证引用完整性、并发下读-改-写互相覆盖）。

用项目举例：本项目正是这五张表，`sys_user_role` 的 `uk_user_role (user_id, role_id)` 唯一键顺手保证了同一用户不会重复挂同一角色。

**Q2：查一个用户的所有菜单，你会怎么写 SQL？**

先说思路是"两次穿桥"，再说实现选择：

- 一条四表 JOIN（本项目的做法），一次往返；因为一个用户可能有多个角色、多个角色可能配置了同一个菜单，**必须 `DISTINCT` 去重**。
- 也可以拆成两步：先查 role_id 集合，再 `WHERE role_id IN (...)`。SQL 更简单，但两次数据库往返。

加分项：主动提"要注意 `sys_menu` 的逻辑删除和 `status`、以及 `sys_role.status` 禁用的角色要排除"——这正是本项目 JOIN 里连 `sys_role` 的唯一理由。

**Q3：菜单权限和数据权限是一回事吗？**

不是，**两条独立的轴**，这是高频混淆点。

- 菜单权限（`role_menu`）决定**能不能看见这个功能入口**。
- 数据权限（`sys_role.data_scope`）决定**同一个功能里能看见哪些行**（全部 / 本部门 / 本部门及下级 / 仅本人）。

用项目举例：`audit_admin` 的 `data_scope = ALL`（数据上能看全部），但 `sys_role_menu` 里**一条菜单都没配**——登录进去菜单树是空的。权限全开、界面全无，两条轴互不干涉，这个反例最能说明问题。

**Q4：为什么关联表不加逻辑删除？**

因为关联表的行**本身没有业务生命周期**——取消授权就是取消了，没有"被软删的授权"这种状态需要保留。加了 `deleted` 反而制造麻烦：唯一键得跟着变成 `(user_id, role_id, deleted)`，而 `deleted` 只有 0/1，导致"同一个授权只能被软删一次"（和 `00` 自检 4 里 `uk_user_username` 一模一样的洞）。

代价是：桥表不带 `deleted`，所以**每一条碰它的 JOIN 都必须自己记得过滤主表的 `deleted = 0`**，漏一个就是幽灵数据。这是个有意识的取舍，`07` 会展开。

<details>
<summary>A 组 3-7：单表计数</summary>

```sql
SELECT COUNT(*) FROM sys_menu WHERE deleted = 0 AND menu_type = 'BUTTON';   -- 30
SELECT COUNT(*) FROM sys_menu WHERE deleted = 0 AND parent_id = 0;          -- 3
SELECT COUNT(*) FROM sys_menu WHERE deleted = 0 AND permission_code IS NOT NULL;  -- 41
SELECT COUNT(*) FROM sys_menu WHERE deleted = 0 AND keep_alive = 1;         -- 14
SELECT COUNT(*) FROM sys_dept WHERE deleted = 0 AND parent_id = 1;          -- 2
```

三个值得琢磨的地方：

**第 5 题的 41 而不是 48**：7 个菜单没有权限码。`DIR` 是纯容器（点开只展开子项，不发请求），部分 `MENU` 也不单独配权限码——它们的可见性由子按钮决定。这也解释了为什么 `permission_code` 列是 `NULL` 允许的。

**判空必须用 `IS NOT NULL`**：`permission_code != NULL` 恒为 `NULL`（不是 `TRUE` 也不是 `FALSE`），`WHERE` 只放行 `TRUE`，所以那样写**永远返回 0 行**。SQL 的三值逻辑，面试爱问。

**第 4 题的 3 个根节点 vs 第 A 组的 4 个 DIR**：说明有一个 `DIR` 不是根节点。查出来是谁：

```sql
SELECT id, menu_type, menu_name_zh, parent_id FROM sys_menu WHERE deleted = 0 AND menu_type = 'DIR';
```

```
+-----+-----------+--------------+-----------+
| id  | menu_type | menu_name_zh | parent_id |
+-----+-----------+--------------+-----------+
|   1 | DIR       | 系统管理     |         0 |   ← 根
|  80 | DIR       | 日志管理     |         1 |   ← 挂在「系统管理」下面的二级目录
|  90 | DIR       | 工作流       |         0 |   ← 根
| 100 | DIR       | 我的审批     |         0 |   ← 根
+-----+-----------+--------------+-----------+
```

「日志管理」是二级目录。**目录可以嵌套**——这正是 `00` 讲的邻接表存树：`parent_id` 指向父节点，深度不受限制，代价是查子孙要递归（本项目在 Java 内存里递归，没用 `WITH RECURSIVE`，`07` 会讲）。

**第 6 题的 14 正好等于 `MENU` 的数量**：不是巧合。验证一下 `keep_alive = 1` 的到底是哪些类型：

```sql
SELECT menu_type, COUNT(*) FROM sys_menu WHERE deleted = 0 AND keep_alive = 1 GROUP BY menu_type;
```

```
+-----------+----------+
| menu_type | COUNT(*) |
+-----------+----------+
| MENU      |       14 |
+-----------+----------+
```

**14 个 `MENU` 全部开了 `keep_alive`，且只有 `MENU` 开。** `keep_alive` 是给前端 `<keep-alive>` 组件做页面缓存用的，只有真正对应一个页面组件的 `MENU` 才有意义——`DIR` 只是容器，`BUTTON` 根本不渲染页面。所以这是设计，不是碰巧。

</details>


**第 10 题的意外**：`wangqiang` 也挂着 `super_admin`。**admin 不是唯一的超管**，`id = 1` 只是"第一个"超管，不是"那个"超管。

这个事实值得警觉，因为它是一类经典 bug 的温床：CLAUDE.md 的安全红线写着"禁止删除超管"，如果这条校验是硬编码 `userId != 1` 实现的，那 `wangqiang` 就是个**能被删掉的超管**。

本项目做对了。查 `backend/src/main/java/com/rbac/system/user/service/UserService.java:219-222`：

```java
private boolean isSuperAdmin(Long userId) {
    return roleMapper.selectRolesByUserId(userId).stream()
            .anyMatch(r -> SUPER_ADMIN.equals(r.getRoleCode()));
}
```

判断的是**"这个用户是否持有 `super_admin` 角色"**，不是"这个用户 id 是不是 1"。全仓一致（`SecurityUtils`、`LoginUserAssembler`、`AuthService` 都是比对 `role_code`），没有一处硬编码 id。

> 🔑 记住这个区别：**`id = 1` 是数据的偶然，`role_code = 'super_admin'` 才是业务的必然。** 一切"这个用户是不是特殊角色"的判断，都必须走角色，不能走主键。面试问"你项目里怎么防止超管被删"，答"查该用户是否持有 super_admin 角色，而不是判断 id"，就比"我判断 id != 1"高一档——而且能顺带说出"因为超管可以有多个，我库里就有两个"。

**第 9 题的 0**：`audit_admin` 一个菜单都没配。`sys_role_menu` 全表 96 行，被 role 1 和 role 2 平分（各 48），role 3 一行都没有。lina 登录后菜单树是空的。

<summary>B 组 11-12：zhangwei 的 role_code 与 lina 的 data_scope（本练习册的重点）</summary>

```sql
-- zhangwei: id=3 → role_id=2 → system_admin
SELECT id FROM sys_user WHERE username = 'zhangwei';   -- 3
```

| 维度 | 值 | 含义 |
|------|-----|------|
| 菜单权限 | **0 个** | 界面上什么入口都没有 |
| 数据权限 | **ALL** | 数据上能看全部，不受部门限制 |

**这就是"菜单权限和数据权限是两条独立的轴"的活证据。** 一个审计管理员，数据全开、界面全无——听起来矛盾，其实合理：审计角色的设计意图可能是走专用报表接口或后台任务，不走菜单树。

面试问"菜单权限和数据权限有什么区别"，很多人只会背定义。你能说"我项目里有个 `audit_admin`，`data_scope=ALL` 但 `role_menu` 里零配置"，就是完全不同的层次。

> 🔑 `data_scope` 管**行**（同一个功能里能看见哪些数据），`role_menu` 管**入口**（能不能看见这个功能）。两者互不干涉，任何一条都不能替另一条兜底——所以 `07` 会强调：**前端藏了菜单不代表接口安全，后端必须再鉴权。**

<summary>D 组 17-18：GROUP BY 与它不会告诉你的事</summary>

```sql
SELECT menu_type, COUNT(*) AS cnt FROM sys_menu WHERE deleted = 0 GROUP BY menu_type;
```

```
+-----------+-----+
| menu_type | cnt |
+-----------+-----+
| DIR       |   4 |
| MENU      |  14 |
| BUTTON    |  30 |
+-----------+-----+
```

```sql
SELECT role_id, COUNT(*) AS menu_cnt FROM sys_role_menu GROUP BY role_id;
```

```
+---------+----------+
| role_id | menu_cnt |
+---------+----------+
|       1 |       48 |
|       2 |       48 |
+---------+----------+
```

**只有两行，但 `sys_role` 有三个角色。** `role_id = 3` 从结果里彻底消失了。

原因：`GROUP BY` 只能对**已存在的行**分组。`sys_role_menu` 里压根没有 `role_id = 3` 的行，自然分不出这个组。**`COUNT(*)` 永远不会返回 0**——没有行，就没有组，没有组，就没有那一行输出。

这是聚合查询最经典的陷阱：**你以为在统计"每个角色有多少菜单"，实际在统计"每个有菜单的角色有多少菜单"。** 报表少一行、图表缺一根柱子，十有八九是这个。

想让 role 3 显示成 0，必须以 `sys_role` 为驱动表 `LEFT JOIN` 过来：

```sql
-- 预告 04，现在不用会写
SELECT r.id, COUNT(rm.menu_id) AS menu_cnt
FROM sys_role r
LEFT JOIN sys_role_menu rm ON r.id = rm.role_id
WHERE r.deleted = 0
GROUP BY r.id;
```

```
+----+----------+
| id | menu_cnt |
+----+----------+
|  1 |       48 |
|  2 |       48 |
|  3 |        0 |   ← 回来了
+----+----------+
```

注意是 `COUNT(rm.menu_id)` 而**不是** `COUNT(*)`。`LEFT JOIN` 没匹配上时，右表的列全填 `NULL`，而 `COUNT(列名)` **不数 NULL**，正好得到 0。写成 `COUNT(*)` 会把那行"全是 NULL 的匹配"也数进去，实测：

```sql
SELECT r.id, COUNT(*) AS menu_cnt      -- 错误示范
FROM sys_role r
LEFT JOIN sys_role_menu rm ON r.id = rm.role_id
WHERE r.deleted = 0
GROUP BY r.id;
```

```
+----+----------+
| id | menu_cnt |
+----+----------+
|  1 |       48 |
|  2 |       48 |
|  3 |        1 |   ← 错！audit_admin 明明一个菜单都没有
+----+----------+
```

**一个字符之差，0 变成 1。** `COUNT(*)` 数的是"行数"，`LEFT JOIN` 给 role 3 补的那一行虽然右半边全是 `NULL`，它也是一行。`COUNT(列名)` 数的是"该列非 NULL 的个数"，才是你要的语义。

> 🔑 `COUNT(*)` 和 `COUNT(列)` 在没有 `LEFT JOIN` 时结果通常一样，于是很多人以为它们等价。**一旦碰上 `LEFT JOIN` 或可空列，差别立刻致命**——而且它不报错，只是悄悄给你一个错数字。面试高频题。

> 🔑 **这才是 `04` 讲 JOIN 的第一个真实动机。** "把三步合并成一条"只是省了两次往返，不痛不痒；而"让没有关联数据的主表记录也出现在结果里、并且计数为 0"，是子查询和 `GROUP BY` **做不到**的事。JOIN 不是为了少写几行 SQL，是为了表达"以谁为准"。

<summary>D 组 19-20：差集与前缀匹配</summary>

```sql
SELECT COUNT(*) FROM sys_role_menu
WHERE role_id = 1
  AND menu_id NOT IN (SELECT menu_id FROM sys_role_menu WHERE role_id = 2);
```

结果 **0 条**。`super_admin` 有的菜单，`system_admin` 一个不少——两个角色在菜单维度**完全一致**。

那它们的区别在哪？只在 `data_scope`：

| 角色 | 菜单 | data_scope | 实际差别 |
|------|------|-----------|---------|
| `super_admin` | 48 | `ALL` | 所有功能，所有数据 |
| `system_admin` | 48 | `OWN_DEPT_CHILD` | 所有功能，**只有本部门及下级的数据** |

同样点开"用户管理"，超管看见全部 5 个用户，系统管理员只看见自己部门树里的。**同样的界面，不同的行。** 又一次印证了两条轴的独立性。

⚠️ `NOT IN` + 子查询有个著名的坑：**如果子查询的结果集里含有 `NULL`，`NOT IN` 会返回空集**。因为 `x NOT IN (1, NULL)` 等价于 `x != 1 AND x != NULL`，后半段恒为 `NULL`，整个条件永远不为 `TRUE`。这题安全是因为 `sys_role_menu.menu_id` 是 `NOT NULL`。换成可空的列，必须用 `NOT EXISTS` 或在子查询里加 `WHERE ... IS NOT NULL`。

```sql
SELECT COUNT(*) FROM sys_menu WHERE deleted = 0 AND permission_code LIKE 'system:user:%';
```

结果 **6**：

```
+----+----------------------------+
| id | permission_code            |
+----+----------------------------+
| 10 | system:user:list           |
| 11 | system:user:add            |
| 12 | system:user:edit           |
| 13 | system:user:delete         |
| 14 | system:user:reset-password |
| 15 | system:user:assign-role    |
+----+----------------------------+
```

标准的 `模块:资源:操作` 三段式命名。这 6 个权限码会原样出现在后端的 `@PreAuthorize("hasAuthority('system:user:delete')")` 和前端的 `v-permission` 里——**数据库里的这一行字符串，就是整条鉴权链的源头。**

关于 `LIKE`，埋个扣：`LIKE 'system:user:%'` 是**前缀匹配**，通配符在右边，能用上索引；`LIKE '%:delete'` 通配符在左边，**索引直接失效**，只能全表扫。为什么？`02` 讲 B+ 树和最左前缀时会给你看清楚——索引是按值**排好序**的，前缀确定才能二分定位，前缀不确定就只能挨个翻。

<summary>自检 1：GROUP BY 少一行，怎么补？</summary>

1. **`GROUP BY` 只对已存在的行分组**，`sys_role_menu` 里没有 role 3 的行 → 没有 role 3 的组 → 输出里没有 role 3。`COUNT(*)` 不可能返回 0。

<details>
<summary>自检 2：给 sys_role_menu 加 deleted 列会怎样？</summary>

会**同时**制造两个问题，而收益几乎为零。

**问题一，唯一键被迫扩容且立刻出洞。** 现在 `sys_user_role` 上有 `uk_user_role (user_id, role_id)` 保证不重复授权。加了 `deleted` 后，软删的行还占着位置，唯一键必须扩成 `(user_id, role_id, deleted)`。而 `deleted` 只有 0/1 → **同一个授权只能被软删一次**：给 A 授角色 1、撤销（`deleted=1`）、再授、再撤销 → 第二次撤销要写入一条 `(A, 1, 1)`，撞唯一键报错。

这个洞和 `00` 自检 4 里 `uk_user_username (username, deleted)` 的洞**是同一个洞**——都是拿一个只有两种取值的列去参与唯一键。`07` 会把这条线串起来算总账。

**问题二，每条 SQL 都要多记一个过滤条件**，漏一个就查出已撤销的授权，属于**权限泄露级别**的 bug。

**收益呢？** 授权行没有独立的业务生命周期——"被软删的授权"不是一种需要保留的业务状态。真要审计"谁在什么时候撤销了谁的角色"，那是 `sys_operation_log` 的职责，不该让业务表兼职当日志表。

**顺带一个实证。** 看 `sys_user_role` 的建表语句：

```sql
SHOW CREATE TABLE sys_user_role\G
```

```
CREATE TABLE `sys_user_role` (
  `id` bigint NOT NULL AUTO_INCREMENT COMMENT '主键',
  `user_id` bigint NOT NULL COMMENT '用户 ID',
  `role_id` bigint NOT NULL COMMENT '角色 ID',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_user_role` (`user_id`,`role_id`)
) ENGINE=InnoDB AUTO_INCREMENT=12 ...
```

两处信息：

1. **表只有三列**，没有 `deleted`，也没有审计五件套（`created_by/created_at/...`）。桥表不继承 `BaseEntity`，它就是纯粹的关系载体。
2. **`AUTO_INCREMENT=12`，但表里只有 5 行。** 自增计数器只增不减，说明历史上一共插入过 11 行，其中 6 行**被真删了**（`DELETE`，不是 `deleted=1`）。这就是"桥表走硬删"的直接证据——不是我说的，是自增计数器和行数的差值说的。

**那 6 行是怎么没的？** 机制就在 `UserService.java:224-230`：

```java
private void replaceRoles(Long userId, List<Long> roleIds) {
    userRoleMapper.delete(Wrappers.<SysUserRole>lambdaQuery().eq(SysUserRole::getUserId, userId));
    if (roleIds != null) {
        for (Long roleId : roleIds) {
            userRoleMapper.insert(new SysUserRole(userId, roleId));
        }
    }
}
```

改角色的实现是**先把这个用户的所有关联行 `delete` 掉，再逐条 `insert` 回去**。注意这是真 `delete`——`SysUserRole` 不继承 `BaseEntity`，没有 `@TableLogic`，MyBatis-Plus 不会把它翻译成 `UPDATE ... SET deleted=1`。所以每改一次角色，就消耗掉若干自增值，哪怕角色内容没变。

这个"全删再全插"的写法还有两个值得琢磨的点，`05` 和 `06` 会回来：

- **它必须在事务里。** 删完还没插完时崩了，用户就没有任何角色了——权限凭空消失。
- **并发下会丢更新。** 两个管理员同时改同一个用户的角色，后提交的会把先提交的整个覆盖掉（不是合并）。

第 2 点也预告了 `02` 的一个知识点：`AUTO_INCREMENT` 的当前值和实际行数没有任何关系，删了行它不回退。面试问"怎么知道一张表历史上删过数据"，这是个能用的切入角度（虽然不精确——回滚的事务同样会消耗自增值，`05` 讲事务时会明白为什么）。

所以现在这个设计（桥表硬删、不带 `deleted`）是对的。**代价是每条碰桥表的 JOIN 必须自己记得过滤主表的 `deleted = 0`**——把复杂度从"每次写"挪到了"每次读"，是有意识的取舍。

<details>
<summary>自检 4：手工三步和四表 JOIN 什么时候结果不同？</summary>

至少四种情况，前两种是**手工三步会多数**，后两种是**手工三步会漏数或重复**：

**1. 菜单被逻辑删除时**（§四 讲的那个坑）。`sys_menu.deleted = 1` 但 `sys_role_menu` 里的关联行还在。手工第三步只查 `sys_role_menu`，照数不误；JOIN 带上 `sys_menu.deleted = 0` 就会正确排除。**手工多数。**

**2. 菜单或角色被禁用时**（`status = 'DISABLED'`）。同理，`sys_role_menu` 不知道也不关心 `status`。`SysMenuMapper` 那条 JOIN 特意连上 `sys_role` 就是为了过滤禁用角色——这是它连第四张表的唯一理由。**手工多数。**

**3. 用户有多个角色时。** 手工第二步会拿到多个 role_id，第三步得逐个查再**手工去重**（不同角色很可能配了同一个菜单）。忘了去重就重复计数。JOIN 里的 `DISTINCT` 就是干这个的。**手工可能重复。**

**4. 用户没有任何角色时。** 手工第二步返回空，你自然知道是 0。但如果你写成 `WHERE role_id IN ()` 这种空集合，SQL 语法就报错了——得在应用层判空短路。这正是 `SysMenuMapper` 用 JOIN 而不用两步 `IN` 查询的一个隐性好处。

> 🔑 归纳：**手工三步的每一步都只看一张表，所以它对"其他表的状态"一无所知。** JOIN 的价值不是把三条 SQL 压成一条，而是**强迫你在一个语句里同时面对所有表的约束**——逻辑删除、状态、去重。这些约束在手工模式下不是消失了，是被你忽略了。
