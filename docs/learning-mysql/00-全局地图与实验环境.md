## 一、这套文档和你读过的两套不一样

你已经读完了 `docs/learning-spring-boot/`（8 篇）和 `docs/learning-docker/`（9 篇）。Docker 那套的打法是**纯精读 `deploy/` 目录**——因为 `deploy/` 是自包含的：Compose 的每个字段都在那儿摆着，读完就是全部。

**MySQL 这套不能这么打。** 原因很直接：把项目里的 MySQL 素材盘一遍，你会发现它只覆盖了面试考点的一半。

| 项目里**有**真素材的 | 项目里**完全没有**的 |
|---------------------|---------------------|
| 20 张表的 DDL（InnoDB、utf8mb4、索引、唯一键） | EXPLAIN / 执行计划 / 索引原理 |
| 四表 JOIN（`SysMenuMapper`） | 事务隔离级别、MVCC、锁（只有一处乐观锁） |
| 逻辑删除、乐观锁 `@Version` | 子查询、EXISTS、GROUP BY、窗口函数 |
| 14 处 `@Transactional` | 慢查询日志、`my.cnf`、备份恢复 |
| 数据权限过滤 SQL | 分库分表、主从复制 |

右边那一列，恰恰是面试问得最狠的地方。

所以这套文档的打法是 **「考点为主线，项目真表当实验台」**：

1. **先讲原理**（B+ 树到底长什么样、MVCC 怎么实现的），不含糊；
2. **再用项目的真实表证明**——你不是在看教科书的 `student` 表，你看的是自己跑着的 `sys_user`；
3. **项目里没有的**，不回避、不空讲，用 `rbac_lab` 实验库灌 100 万行数据，**亲手验给你看**。

> 🔑 这么做的收益：面试时你不是背"索引用 B+ 树因为树矮"，而是能说"我在自己项目的 `sys_user` 上灌了 100 万行，加索引前 `type=ALL` 扫 99 万行，加完 `type=ref` 扫 1 行，`Extra` 还出现了 `Using index`——因为那个查询被覆盖索引兜住了"。**后者是能讲出证据的答案。**

## 二、先看森林：20 张表分五组

打开 `backend/src/main/resources/db/schema.sql`（332 行），20 个 `CREATE TABLE`。别被数量吓到，它们分五组，**只有第一、二组需要你现在就理解**：

| 组 | 表 | 数量 | 干什么 |
|----|-----|------|--------|
| **① 主体表** | `sys_dept` `sys_user` `sys_role` `sys_menu` `sys_post` | 5 | RBAC 的五个主角：部门、用户、角色、菜单、岗位 |
| **② 关联表** | `sys_user_role` `sys_role_menu` `sys_role_dept` `sys_user_post` | 4 | 主角之间的**多对多**桥梁 |
| **③ 配置字典** | `sys_config` `sys_dict_type` `sys_dict_data` | 3 | 系统参数、下拉框选项 |
| **④ 日志表** | `sys_login_log` `sys_operation_log` | 2 | 登录日志、操作日志 |
| **⑤ 工作流表** | `wf_process_definition` `wf_process_node` `wf_process_instance` `wf_process_task` `wf_process_record` `wf_process_cc` | 6 | 审批流（后加的，本套只在讲乐观锁时用到 `wf_process_instance`） |

### RBAC 的核心链路：从"人"到"能点哪个按钮"

这是整个系统最重要的一条链，也是 `04` 那节要精读的四表 JOIN 的由来：

```
 sys_user          sys_user_role         sys_role         sys_role_menu        sys_menu
 (谁)      ──►     (人↔角色的桥)  ──►   (什么角色) ──►   (角色↔菜单的桥) ──►  (能点什么)
   id       ◄──      user_id              id        ◄──     role_id              id
                     role_id                                 menu_id         permission_code
```

一句话：**用户不直接拥有权限，用户拥有角色，角色拥有菜单/按钮。** 中间隔着两座桥（`sys_user_role`、`sys_role_menu`），这就是 RBAC（Role-Based Access Control，基于角色的访问控制）里那个 R 的含义。

> 🔑 为什么要中间表？为什么不在 `sys_user` 加一列 `role_ids` 存 `"1,2,3"`？——这是面试送分题，答案见本节末尾的自检题 2。

### 两棵树：自引用表

`sys_dept` 和 `sys_menu` 都有 `parent_id` 列，指向**同一张表自己的 id**：

```sql
-- schema.sql:6
`parent_id` BIGINT NOT NULL DEFAULT 0 COMMENT '父部门 ID，0 为顶级',
```

这叫**邻接表（Adjacency List）**存树：每行只记自己的爹是谁，`0` 表示"我是根"。部门树、菜单树都这么存。

这个设计在 `07` 会翻旧账——因为**查"某部门及其所有子孙部门"时，邻接表需要递归**，而本项目选择了在 Java 内存里递归展开，而不是用 MySQL 的 `WITH RECURSIVE`。那是个值得在面试里讲的取舍。

### 五张关联表？不，是四张

顺带纠正一个容易数错的地方：关联表（junction table，也叫中间表/桥表）**只有 4 张**。判断标准很简单——看它的唯一键是不是"两个外键 ID 的组合"：

```sql
-- 实测 grep 结果，四张关联表的唯一键：
UNIQUE KEY `uk_user_role` (`user_id`, `role_id`)     -- 用户 ↔ 角色
UNIQUE KEY `uk_role_menu` (`role_id`, `menu_id`)     -- 角色 ↔ 菜单
UNIQUE KEY `uk_role_dept` (`role_id`, `dept_id`)     -- 角色 ↔ 部门（自定义数据范围用）
UNIQUE KEY `uk_user_post` (`user_id`, `post_id`)     -- 用户 ↔ 岗位
```

`sys_dict_data` 虽然有 `dict_type_id` 指向 `sys_dict_type`，但那是**一对多的子表**，不是桥。

## 三、贯穿全库的三个统一约定

这三条在 20 张表里到处出现，先认脸，后面每节都会再遇到。

### 1. 审计五件套

几乎每张主体表的尾巴都长一样：

```sql
-- schema.sql:13-17（sys_dept 的尾巴，其它表几乎复制粘贴）
`created_by` BIGINT  NULL COMMENT '创建人',
`created_at` DATETIME NULL COMMENT '创建时间',
`updated_by` BIGINT  NULL COMMENT '更新人',
`updated_at` DATETIME NULL COMMENT '更新时间',
`deleted`    TINYINT NOT NULL DEFAULT 0 COMMENT '逻辑删除 0/1',
```

注意 `created_at` / `updated_at` **没有** `DEFAULT CURRENT_TIMESTAMP`，也**没有** `ON UPDATE CURRENT_TIMESTAMP`——也就是说，**MySQL 不管填时间这件事，是 Java 侧填的**（`AuditMetaObjectHandler`）。这是个设计选择，`08` 会讨论它的代价。

### 2. 逻辑删除：`deleted` 0/1

`DELETE FROM sys_user WHERE id=5` 这条语句在本项目里**几乎不会执行**。删用户实际上是 `UPDATE sys_user SET deleted=1 WHERE id=5`，数据还躺在表里。

代价马上就来了——看 `sys_user` 的唯一键：

```sql
-- schema.sql:42
UNIQUE KEY `uk_user_username` (`username`, `deleted`),
```

为什么唯一键要带上 `deleted`？因为如果只写 `UNIQUE KEY (username)`，那么删掉的 `zhangsan` 还占着位置，你就**永远不能再建一个叫 `zhangsan` 的用户了**。加上 `deleted` 后，`('zhangsan', 1)` 和 `('zhangsan', 0)` 是两条不同的记录，位置就腾出来了。

> 🔑 但这个方案有个**藏得很深的缺陷**：`deleted` 只有 0/1 两个值，所以你只能软删**一个** `zhangsan`。删第二个的时候，`('zhangsan', 1)` 已经存在 → 撞唯一键报错。`07` 会专门算这笔账。

### 3. 枚举用 VARCHAR 落库

```sql
`status`    VARCHAR(16) NOT NULL DEFAULT 'ENABLED' COMMENT '状态 ENABLED/DISABLED',
`menu_type` VARCHAR(16) NOT NULL COMMENT '类型 DIR/MENU/BUTTON',
```

没用 MySQL 的 `ENUM` 类型，也没用 `TINYINT` 存 0/1/2，而是**直接存字符串**。`01` 会算这笔账（存储空间 vs 可读性 vs 改起来疼不疼）。

> 📎 **和已有文档的边界**：上面这三条，`docs/learning-spring-boot/02-数据层与数据模型.md` 已经从 **Java 侧**讲过（`BaseEntity`、`@TableLogic`、自动填充是怎么配的）。本套一律从**数据库侧**讲——同一件事，那边讲"MyBatis-Plus 怎么帮你写 SQL"，这边讲"这条 SQL 到了 MySQL 会发生什么"。需要时我会回指。
>
> ⚠️ 另外那份文档写的是"14 张表"，是工作流表加进来之前写的，**现在实际是 20 张**。以 `schema.sql` 为准。

### 2. 连进去（注意那个不能省的参数）

```bash
docker exec -it rbac-mysql mysql -uroot -prbac_root_123 --default-character-set=utf8mb4
```

密码 `rbac_root_123` 来自 `deploy/.env`（本地开发用；`docs/learning-docker/07` 讲过线上那台还是默认密码这件事）。

**`--default-character-set=utf8mb4` 千万别省。** 不加会怎样？实测给你看：

```
-- 不加参数：
`id` bigint NOT NULL AUTO_INCREMENT COMMENT '??',
`username` varchar(64) NOT NULL COMMENT '????',

-- 加了参数：
`id` bigint NOT NULL AUTO_INCREMENT COMMENT '主键',
`username` varchar(64) NOT NULL COMMENT '登录账号',
```

中文全变问号。原因是**客户端字符集**和服务端对不上——注意这跟"表里的数据坏了"完全是两回事，数据好好的，只是传输过程中被按错误的字符集解码了。`01` 会把这条链讲透。

### 3. 看一眼真实规模（顺便理解为什么需要实验库）

```sql
SELECT table_name, table_rows, engine FROM information_schema.tables
WHERE table_schema='rbac' ORDER BY table_rows DESC LIMIT 6;
```

实测输出：

```
TABLE_NAME	TABLE_ROWS	ENGINE
sys_role_menu	96	InnoDB
sys_menu	48	InnoDB
sys_login_log	33	InnoDB
sys_user	5	InnoDB
sys_user_role	5	InnoDB
sys_user_post	5	InnoDB
```

**最大的表 96 行，`sys_user` 只有 5 行。**

这就是问题所在：MySQL 的优化器不傻，**表只有 5 行时它根本不屑于走索引**——直接全表扫描反而更快（读一个数据页就完事了，走索引还得回表）。所以你在这个库上跑 `EXPLAIN`，看到的永远是 `type=ALL`，**索引的效果一点都体现不出来**。

> 🔑 所以我们的实验环境是**两套并行**：
> - **`rbac` 库 = 只读观察区**。看真实 schema、看真实业务 SQL 长什么样。**全程只 SELECT / EXPLAIN / SHOW，绝不写。**
> - **`rbac_lab` 库 = 实验区**。灌 100 万行进去，随便造、随便建索引、随便删。搞坏了 `DROP DATABASE` 重来，不心疼。

### 4. 建实验库

```sql
CREATE DATABASE IF NOT EXISTS rbac_lab
  DEFAULT CHARACTER SET utf8mb4
  DEFAULT COLLATE utf8mb4_unicode_ci;
```

（灌数据的脚本放在 `02`，那时候才用得上。这里先把库建好。）

它和 `rbac` 在**同一个容器、同一个数据卷**（`mysql-data`）里，所以：
- 它会跟着 `docker compose down -v` 一起没——这正是我们想要的，实验产物不该长期占地方；
- 它**不影响** `rbac` 库，后端应用连的是 `rbac`，压根看不见 `rbac_lab`。

> 📎 `mysql-data` 这个命名卷、以及 `initdb.d` 为什么只在空卷时跑，`docs/learning-docker/05-数据持久化-卷与配置挂载.md` 已经讲透，这里不重复。

## 面试怎么问

这一节是地图，对应的面试题都是**数据模型设计题**——通常出现在"讲讲你做过的项目"之后的追问里。

**Q1：讲讲 RBAC 权限模型，表怎么设计？**

要点：五个主体（用户/角色/菜单/部门/岗位）+ 关联表。核心链路是 `用户 →(sys_user_role)→ 角色 →(sys_role_menu)→ 菜单/按钮`。**关键是说清"用户不直接持有权限"**——权限挂在角色上，用户通过角色间接获得。这样加人只需挂角色，调权限只需改角色，不用逐个用户改。

**Q2：为什么要中间表？在用户表加一列 `role_ids` 存 `"1,2,3"` 不行吗？**

高频送分题，要能一口气说出至少三个理由：① 违反第一范式，字段不可再分；② **没法建索引**，查"哪些用户有角色 2"只能 `LIKE '%2%'` 全表扫，而且会误匹配到 `12`、`20`；③ 没法保证引用完整性，角色删了字符串里还留着脏 ID；④ 增删单个角色要读出来、字符串拼接、再写回去，并发下会互相覆盖。

**Q3：部门树怎么存？除了 `parent_id` 还有别的方案吗？**

要点：本项目用**邻接表**（`parent_id`），优点是改动简单（挪部门只改一行），缺点是**查子孙要递归**。其它方案：路径枚举（存 `/1/3/7/`，查子孙一个 `LIKE '/1/3/%'` 就够，但改动要批量更新）、嵌套集（查询快、写入贵）、闭包表（空间换时间）。**能说出"本项目选了邻接表，所以数据权限那块要在 Java 里递归展开"就是加分**——这个坑 `07` 细讲。

**Q4：你们表用了外键吗？**

本项目答案是**一个都没有**（实测 `grep -ci "FOREIGN KEY" schema.sql` = 0），关系全靠应用层维护。这个回答本身要能自圆其说——利弊在 `07` 展开，现在先记住这个事实。

## 附：答案与解析

<details>
<summary>练习 4 参考答案（admin 有多少个 menu_id）</summary>

三条 SQL：

```sql
SELECT id FROM rbac.sys_user WHERE username='admin';
SELECT role_id FROM rbac.sys_user_role WHERE user_id=<上一步的 id>;
SELECT COUNT(*) FROM rbac.sys_role_menu WHERE role_id=<上一步的 role_id>;
```

参考：`sys_role_menu` 共 96 行，`sys_role` 只有 3 个角色，其中超管角色通常挂了全部 48 个菜单。你实际跑出来的数字以自己的库为准——**重点不是数字，是体会到"要走两次桥"**。

顺带注意一个细节：这三步里你**没有**写 `AND deleted=0`。真实业务代码里 MyBatis-Plus 会自动帮你加上（`@TableLogic`），所以你在应用里查不到软删的数据，但**在 CLI 里手写 SQL 是不会自动加的**——这是很多人线上排查时"为什么我 SQL 查得到、应用查不到"的原因。

</details>

<details>
<summary>自检 1：为什么不能纯精读项目配置？</summary>

因为 `deploy/` 是自包含的，Compose 的每个字段都在文件里摆着；但 MySQL 的核心知识（索引原理、执行计划、事务隔离级别、锁、MVCC）**项目里根本没有对应的代码或配置**——项目只是"用"了 MySQL，没有"体现"这些机制。

比如项目里连一条 `EXPLAIN` 都没有，连 `my.cnf` 都没有（MySQL 配置全靠 compose 的 `command:` flags）。你把项目所有 SQL 读一百遍，也读不出 B+ 树是什么。

所以本套的方法是"考点为主线，项目真表当实验台"：原理讲透，再用真表证明；项目没有的，用 `rbac_lab` 灌数据亲手验。

</details>

<details>
<summary>自检 2：为什么要中间表，不用 `role_ids="1,2,3"`？（高频送分题）</summary>

至少四个理由，面试时能说出三个就够：

1. **违反第一范式**：字段应当是不可再分的原子值，`"1,2,3"` 是把三个值塞进一个格子。
2. **没法建索引**（最致命）：查"哪些用户有角色 2"，只能 `WHERE role_ids LIKE '%2%'`，**全表扫描**。而且 `LIKE '%2%'` 会误匹配到 `12`、`20`、`21`……你得写成 `FIND_IN_SET(2, role_ids)`，照样用不上索引。
3. **没法保证引用完整性**：角色 2 被删了，所有用户的字符串里还留着 `2`，成了脏数据，得写脚本全表清洗。
4. **并发下会互相覆盖**：给用户加一个角色，要"读出 `"1,2"` → 拼成 `"1,2,3"` → 写回"。两个请求同时做，一个加角色 3、一个加角色 4，后写的会把前一个的结果冲掉（读-改-写竞争）。用中间表就是 `INSERT` 一行，天然没这问题。

反过来，中间表的成本只是"多一张表 + 查询要 JOIN"，而 `uk_user_role (user_id, role_id)` 这个唯一键还顺手保证了"同一个用户不会重复挂同一个角色"。

</details>

<details>
<summary>自检 3：为什么 5 行的表做索引实验没意义？</summary>

因为**优化器会主动放弃索引**。

MySQL 的数据是按**数据页**（默认 16KB）读的。`sys_user` 只有 5 行，全部数据加起来一个数据页就装下了——全表扫描 = 读 1 个页。

而走二级索引呢？先读索引页找到主键值，再拿主键回聚簇索引取整行（**回表**），至少 2 次页读取，还是随机 I/O。**比全表扫描更慢。**

优化器基于代价估算（cost-based），算出来全表扫描更便宜，就直接 `type=ALL` 了。所以你在 5 行的表上加索引、跑 EXPLAIN，会发现索引"没生效"——不是索引坏了，是**优化器嫌它不划算**。

这也是为什么要灌 100 万行到 `rbac_lab`：只有数据量上来，索引的收益才会超过回表的成本，优化器才会用它。`02`、`03` 会把这个临界点实测给你看。

</details>

<details>
<summary>自检 4：唯一键里的 `deleted` 是干什么的？</summary>

**保证软删之后，用户名能被重新使用。**

如果只写 `UNIQUE KEY (username)`：
- 建用户 `zhangsan` → 表里有 `('zhangsan', deleted=0)`
- 软删他 → 变成 `('zhangsan', deleted=1)`，**行还在**
- 再建一个 `zhangsan` → 撞 `UNIQUE KEY (username)` → **报错**。用户名被一个已删除的用户永久占用了。

加上 `deleted` 后，唯一性判断的是 `(username, deleted)` 这个**组合**：`('zhangsan',1)` 和 `('zhangsan',0)` 不冲突，新用户建得出来。

**但这个补丁有洞**：`deleted` 只有 0/1 两个值。删掉第一个 `zhangsan` 后表里是 `('zhangsan',1)`；再建一个 `zhangsan` 再删掉，又要写入 `('zhangsan',1)` → **撞唯一键**。所以这个方案只允许软删**一份**同名记录。

业界常见的修法是把 `deleted` 从 0/1 改成"删除时间戳"或"删除时填自己的 id"，让每次软删产生不同的值。本项目没这么做——`07` 会算这笔账。

</details>

<details>
<summary>自检 5：中文乱码说明数据坏了吗？</summary>

**没有。数据好好的。**

乱码发生在**传输和显示**环节，不是存储环节。这条链上有好几个字符集：

```
表/列的字符集(数据实际怎么存)  →  连接字符集(character_set_client/connection/results)  →  终端显示
```

`--default-character-set=utf8mb4` 设的是**客户端连接**的字符集。不加的话，MySQL 用默认值（可能是 latin1）把 utf8mb4 的中文字节按错误规则解码，就成了 `?`。

证据：同一张表，加参数前显示 `'??'`，加参数后显示 `'主键'`——**表一个字节都没动过**。

真正"数据坏了"是另一回事：写入时字符集就错了，坏字节**存进了磁盘**。那种情况加参数也救不回来。`01` 会讲怎么区分这两种。

</details>

<details>
<summary>自检 6：`rbac_lab` 会影响后端应用吗？`down -v` 之后还在吗？</summary>

**不影响。** 后端 `application.yml` 里 JDBC URL 连的是 `rbac` 库，MySQL 的库之间是隔离的命名空间，应用压根看不见 `rbac_lab`。（前提是你守住"只在 `rbac_lab` 写"这条线——如果你手滑在 `rbac` 库 `DROP TABLE`，那当然会炸。）

**`down -v` 之后就没了。** 因为两个库都在同一个 `mysql-data` 命名卷里，`-v` 会删卷 → 整个 MySQL 数据目录（含 `rbac` 和 `rbac_lab`）一起没。

注意区别：
- `docker compose down`（不带 `-v`）→ 只删容器，卷还在 → 两个库都还在
- `docker compose down -v` → 删卷 → 两个库都没了，下次 `up` 时 `initdb.d` 会重新跑，`rbac` 库会被重建（但 `rbac_lab` 不会，因为 `01-init.sql` 里没有它）

这块机制 `docs/learning-docker/05-数据持久化-卷与配置挂载.md` 讲透了。

</details>
