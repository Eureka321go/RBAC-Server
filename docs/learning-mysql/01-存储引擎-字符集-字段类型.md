# 阶段 1 · 存储引擎、字符集、字段类型（地基三件事）

> 目标：读完这一份，你能回答面试里三道高频送分题——"InnoDB 和 MyISAM 有什么区别"、"utf8 和 utf8mb4 有什么区别"、"字段类型怎么选"。
> 更重要的是：**上一节留的那桩悬案，这一节破**。三处声明排序规则，两处生效，表却是第三个值——你会亲手把元凶挖出来，而且会发现一个意想不到的反转。

## 一、存储引擎：为什么 20 张表都写 `ENGINE = InnoDB`

### 先看事实

`schema.sql` 里 20 个 `CREATE TABLE`，每一个的结尾都是同一句：

```sql
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '用户表';
```

**存储引擎是"表"级别的属性**，不是数据库级别的——这是第一个容易错的点。理论上你可以让同一个库里的 A 表用 InnoDB、B 表用 MyISAM。

### 引擎不止一个

```sql
SHOW ENGINES;
```

实测输出（节选）：

```
Engine      Support   Comment                                                    Transactions  XA    Savepoints
InnoDB      DEFAULT   Supports transactions, row-level locking, and foreign keys  YES          YES   YES
MyISAM      YES       MyISAM storage engine                                       NO           NO    NO
MEMORY      YES       Hash based, stored in memory, useful for temporary tables   NO           NO    NO
ARCHIVE     YES       Archive storage engine                                      NO           NO    NO
BLACKHOLE   YES       /dev/null storage engine (anything you write to it disappears)  NO       NO    NO
CSV         YES       CSV storage engine                                          NO           NO    NO
```

注意 `Support` 那列：**InnoDB 是 `DEFAULT`**（默认引擎），MyISAM 是 `YES`（可用但不默认）。所以在 MySQL 8.4 里，就算你不写 `ENGINE = InnoDB`，建出来的也是 InnoDB。

那 `schema.sql` 为什么还要每张表都写一遍？——**显式优于隐式**。默认值是会变的（MySQL 5.5 之前默认就是 MyISAM），写死了就不用担心换环境后行为不同。这和 `01` 里 `--character-set-server` 那些 flag 是同一个思路。

### InnoDB vs MyISAM：面试要点

`SHOW ENGINES` 的 Comment 列已经把 InnoDB 的三个卖点直接印出来了：**transactions、row-level locking、foreign keys**。

| 维度 | InnoDB | MyISAM |
|------|--------|--------|
| **事务** | 支持（ACID） | **不支持** |
| **锁粒度** | **行锁** | **表锁**（改一行锁全表） |
| **外键** | 支持 | 不支持 |
| **崩溃恢复** | 支持（靠 redo log） | 不支持，容易坏表 |
| **索引结构** | **聚簇索引**（数据和主键索引在一起） | 非聚簇（索引和数据分开存） |
| **`COUNT(*)`** | 要实际扫描 | **存了行数，O(1) 直接返回** |

> 🔑 面试的标准答法：**InnoDB 支持事务和行锁，MyISAM 不支持**——这是最本质的区别，其它都是衍生的。MyISAM 唯一还剩的优势是 `COUNT(*)` 快（因为它维护了行数计数器），但它连事务都没有，这点优势毫无意义。**MySQL 5.5 起默认就是 InnoDB，新项目没有任何理由用 MyISAM。**

**追问陷阱**："MyISAM 的 `COUNT(*)` 为什么快？InnoDB 为什么不能也存个计数器？"——因为 InnoDB 有事务和 MVCC：**不同事务在同一时刻看到的行数是不一样的**（你的事务里插了一行还没提交，别的事务不该看见）。所以根本不存在"一个全局正确的行数"可存。MyISAM 没事务，才有资格存。

这个"不同事务看到的数据不一样"就是 MVCC，是 `05` 的主角。

### 行格式

顺带一个小考点：

```sql
SHOW VARIABLES LIKE 'innodb_default_row_format';
SELECT table_name, row_format FROM information_schema.tables WHERE table_schema='rbac' LIMIT 3;
```

实测：

```
Variable_name              Value
innodb_default_row_format  dynamic

TABLE_NAME    ROW_FORMAT
sys_config    Dynamic
sys_dept      Dynamic
sys_dict_data Dynamic
```

`Dynamic` 是 MySQL 5.7+ 的默认行格式。它和老的 `Compact` 的区别主要在**大字段（TEXT/BLOB/长 VARCHAR）怎么存**：`Dynamic` 会把放不下的大字段整个挪到溢出页，行内只留 20 字节指针；`Compact` 会在行内留 768 字节前缀再溢出。本项目没有 TEXT/BLOB，最长的字段是 `VARCHAR(2000)`，所以这个区别基本碰不到，**知道有这回事即可**。

## 二、字符集：utf8 是个坑

### `utf8` ≠ UTF-8

这是 MySQL 最著名的历史包袱，也是面试必问：

- **`utf8`（即 `utf8mb3`）**：每个字符最多 **3** 字节。**存不了 emoji，存不了部分生僻字。**
- **`utf8mb4`**：每个字符最多 **4** 字节。这才是真正的 UTF-8。

`mb4` = **m**ulti **b**yte **4**。

实测什么叫"存不了"：

```sql
CREATE TABLE mb3 (v VARCHAR(8)) DEFAULT CHARSET=utf8mb3;
INSERT INTO mb3 VALUES ('😀');
```

```
ERROR 1366 (HY000): Incorrect string value: '\xF0\x9F\x98\x80' for column 'v' at row 1
```

`\xF0\x9F\x98\x80` 正是 😀 的 4 个字节。utf8mb3 的格子只有 3 字节宽，塞不进去，**直接报错**（如果 SQL 模式宽松，还会更糟——静默截断成 `???`，数据真的坏在磁盘上）。

> 🔑 面试标准答法：**MySQL 的 `utf8` 是个骗人的别名，它实际是 `utf8mb3`，每字符最多 3 字节，存不了 emoji。真正的 UTF-8 是 `utf8mb4`。** 新项目一律用 `utf8mb4`，没有例外。

### 一个字符到底占几字节

实测：

```sql
SELECT LENGTH('ENABLED') AS 字节数, CHAR_LENGTH('ENABLED') AS 字符数;  -- 7, 7
SELECT LENGTH('中')       AS 字节数, CHAR_LENGTH('中')       AS 字符数;  -- 3, 1
SELECT LENGTH('😀')      AS 字节数, CHAR_LENGTH('😀')      AS 字符数;  -- 4, 1
```

记住两个函数的区别：**`LENGTH` 数字节，`CHAR_LENGTH` 数字符。**

重点：**`VARCHAR(64)` 里的 64 是字符数，不是字节数。** 所以 `sys_user.username VARCHAR(64)` 能存 64 个汉字（占 192 字节），不是 21 个。这也是面试常见的误解点。

### 项目里的字符集是怎么设的

三个地方，逐个看：

**① 服务器级** —— `deploy/docker-compose.yml:33-36`：

```yaml
command: #启动参数
  - --character-set-server=utf8mb4
  - --collation-server=utf8mb4_unicode_ci
  - --default-time-zone=+08:00
```

**② 库级** —— `deploy/config/mysql/init/01-init.sql:4-6`：

```sql
CREATE DATABASE IF NOT EXISTS `rbac`
  DEFAULT CHARACTER SET utf8mb4
  DEFAULT COLLATE utf8mb4_unicode_ci;
```

**③ 表级** —— `schema.sql` 每张表的结尾：

```sql
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '用户表';
```

三处都写了 `utf8mb4`，看起来天衣无缝。**但注意 ③ 只写了 CHARSET，没写 COLLATE。** 记住这个细节，第三节要它命。

### 客户端字符集：`00` 那个乱码的真相

`00` 里让你体验过：不加 `--default-character-set=utf8mb4`，中文 COMMENT 全变 `?`。

原因是字符集**不止表上有**，整条链上都有：

```
  表/列字符集          连接字符集                      终端
  (数据实际怎么存)  →  character_set_client            →  显示
                      character_set_connection
                      character_set_results
```

`--default-character-set=utf8mb4` 一次性设置了后面那三个连接变量。不加的话，客户端可能用 latin1 去解码 utf8mb4 的字节流，中文就成了 `?`。

> 🔑 **关键区分：传输乱码 vs 数据真坏了。**
> - **传输乱码**：磁盘上的字节是好的，只是解码时用错了字符集。**改连接字符集就能救回来**，数据一个字节没动。`00` 那个就是这种。
> - **数据真坏了**：**写入时**字符集就错了，坏字节**已经落盘**。这时候你改多少次连接字符集都没用，因为原始信息已经丢了（比如 emoji 被 utf8mb3 截断成 `?`，那 4 个字节永久变成了 1 个 `?`）。
>
> 判断方法：`SELECT HEX(列名) FROM 表` 看原始字节。如果字节还是完整的 UTF-8 序列（中文是 `E4B8AD` 这种三字节），那是传输问题；如果已经变成 `3F`（问号的 ASCII），那就是真坏了，只能从备份恢复。

## 三、破案：那桩排序规则悬案

### 案情回顾

`00` 结尾留的扣：`docker-compose.yml` 和 `01-init.sql` 都声明了 `utf8mb4_unicode_ci`，但表不是这个值。

先验证前两处确实生效了：

```sql
SHOW VARIABLES LIKE 'collation_server';
SELECT default_character_set_name, default_collation_name
FROM information_schema.schemata WHERE schema_name='rbac';
```

实测：

```
Variable_name     Value
collation_server  utf8mb4_unicode_ci          ← ① 服务器级：生效了 ✅

DEFAULT_CHARACTER_SET_NAME  DEFAULT_COLLATION_NAME
utf8mb4                     utf8mb4_unicode_ci  ← ② 库级：生效了 ✅
```

两处都没问题。现在看表：

```sql
SHOW CREATE TABLE rbac.sys_user\G
```

实测输出的最后一行：

```
) ENGINE=InnoDB AUTO_INCREMENT=6 DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='用户表'
```

**`COLLATE=utf8mb4_0900_ai_ci`。** 不是 `unicode_ci`。

而且不是个别表：

```sql
SELECT DISTINCT table_collation FROM information_schema.tables WHERE table_schema='rbac';
SELECT COUNT(*) FROM information_schema.tables
WHERE table_schema='rbac' AND table_collation='utf8mb4_unicode_ci';
```

实测：

```
TABLE_COLLATION
utf8mb4_0900_ai_ci     ← 只有这一个值

COUNT(*)
0                      ← 用 unicode_ci 的表：一张都没有
```

**20 张表，全军覆没。** 库和服务器都说 `unicode_ci`，20 张表没一张听话。

### 抓凶手：三张对照表

嫌疑人只可能是建表语句本身。做个实验——建一个默认排序规则是 `unicode_ci` 的库，然后用三种写法建表：

```sql
CREATE DATABASE lab_tmp DEFAULT CHARACTER SET utf8mb4 DEFAULT COLLATE utf8mb4_unicode_ci;
USE lab_tmp;

CREATE TABLE t1 (name VARCHAR(32));                                              -- 什么都不写
CREATE TABLE t2 (name VARCHAR(32)) DEFAULT CHARSET = utf8mb4;                    -- 只写 CHARSET ← 项目的写法
CREATE TABLE t3 (name VARCHAR(32)) DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_unicode_ci;  -- 都写

SELECT table_name, table_collation FROM information_schema.tables WHERE table_schema='lab_tmp';
```

实测结果：

```
TABLE_NAME  TABLE_COLLATION
t1          utf8mb4_unicode_ci      ← 什么都不写，乖乖继承了库 ✅
t2          utf8mb4_0900_ai_ci      ← 只写 CHARSET，被覆盖了 ❌  ← 就是它！
t3          utf8mb4_unicode_ci      ← 都写，正确 ✅
```

**凶手抓到了。**

### 机制：为什么"写了反而坏事"

MySQL 决定表的排序规则，规则是这样的：

| 建表语句 | 结果 |
|---------|------|
| 既不写 CHARSET 也不写 COLLATE | **继承库**的字符集和排序规则 |
| **只写 CHARSET，不写 COLLATE** | 用**该字符集的默认排序规则** ← 库的设置被绕过了 |
| 只写 COLLATE，不写 CHARSET | 用该排序规则对应的字符集 |
| 两个都写 | 按写的来（但必须匹配，否则报错） |

关键在第二行：**一旦你显式指定了 CHARSET，MySQL 就认为"这张表的字符集由我说了算"，于是配套的排序规则也用这个字符集的默认值，而不再去问库。**

而 `utf8mb4` 在 MySQL 8.0+ 的**默认排序规则**是 `utf8mb4_0900_ai_ci`（8.0 之前是 `utf8mb4_general_ci`）。所以：

```sql
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '用户表';
   ↑ 写了这个 utf8mb4
   → MySQL：好，字符集你定了，那排序规则我用 utf8mb4 的默认值 utf8mb4_0900_ai_ci
   → 库的 utf8mb4_unicode_ci 被完全忽略
```

> 🔑 **这就是最讽刺的地方：`schema.sql` 那句 `DEFAULT CHARSET = utf8mb4` 什么都不写反而是对的。** 写了它，才把库的排序规则设置给覆盖掉。上面 `t1` 证明了这一点——什么都不写的表，老老实实继承了 `unicode_ci`。
>
> 一个"为了显式、为了保险"而加的声明，恰恰破坏了另一处的显式声明。**这就是配置分散在三个地方的代价。**

### 反转：这个"错误"其实修对了

到这儿你可能觉得该赶紧发个 PR 修掉。**先别急，看两个实验。**

`utf8mb4_unicode_ci` 基于 **UCA 4.0.0**（Unicode 排序算法，2003 年），`utf8mb4_0900_ai_ci` 基于 **UCA 9.0.0**（2016 年）。中间隔了 13 年的 Unicode 演进，最大的差别是——**emoji**。

```sql
SELECT '😀' = '😃' COLLATE utf8mb4_unicode_ci AS unicode_ci结果,
       '😀' = '😃' COLLATE utf8mb4_0900_ai_ci AS ai_0900结果;
```

实测：

```
unicode_ci结果   ai_0900结果
1                0
```

**在 `utf8mb4_unicode_ci` 眼里，😀 和 😃 是同一个字符。**

不是 bug，是 UCA 4.0.0 那会儿 emoji 还没进 Unicode，这些码位**没有分配排序权重**。没权重的字符，比较时一律视为相等。所以在 `unicode_ci` 下，**所有 emoji 彼此全部相等**。

后果有多严重？加个唯一键就知道了：

```sql
CREATE TABLE emoji_uni (v VARCHAR(8), UNIQUE KEY uk(v)) DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
INSERT INTO emoji_uni VALUES ('😀');
INSERT INTO emoji_uni VALUES ('😃');
```

```
ERROR 1062 (23000): Duplicate entry '?' for key 'emoji_uni.uk'
```

**两个不同的 emoji 撞唯一键了。** 换成 `0900_ai_ci` 同样的表：

```sql
CREATE TABLE emoji_0900 (v VARCHAR(8), UNIQUE KEY uk(v)) DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
INSERT INTO emoji_0900 VALUES ('😀');
INSERT INTO emoji_0900 VALUES ('😃');
SELECT COUNT(*) FROM emoji_0900;   -- 2 ✅
```

> 🔑 **所以项目实际生效的 `utf8mb4_0900_ai_ci` 比它想要的 `utf8mb4_unicode_ci` 更正确。** 如果哪天有人在昵称里用 emoji，`unicode_ci` 会闹出"这个昵称已被占用"的灵异事件，而项目因为这个"错误"逃过一劫。
>
> 面试时这是个很好的故事：**不是所有不一致都要立刻改成"声明的那个"，先搞清哪个行为才是你要的。**

### 那到底要不要修

要修的是**不一致本身**，不是把表改成 `unicode_ci`。因为不一致真的会爆雷——

```sql
-- rbac.sys_user 是 0900_ai_ci，lab_tmp.t3 是 unicode_ci
SELECT u.username FROM rbac.sys_user u JOIN lab_tmp.t3 t ON u.username = t.name;
```

实测：

```
ERROR 1267 (HY000): Illegal mix of collations
(utf8mb4_0900_ai_ci,IMPLICIT) and (utf8mb4_unicode_ci,IMPLICIT) for operation '='
```

**两个排序规则不同的 VARCHAR 列没法直接比较。** 目前项目只有一个库、所有表又碰巧统一成了 `0900_ai_ci`，所以没事。但只要哪天：

- 新加的表用了别的写法（比如某人写了 `COLLATE=utf8mb4_unicode_ci`），
- 或者要和另一个库做 JOIN，

就会撞上 `ERROR 1267`。而且这个错**只在跑到那条 SQL 时才炸**，建表时一声不吭。

合理的修法（本节只提结论，不动代码）：**统一到 `utf8mb4_0900_ai_ci`**——把 `docker-compose.yml` 的 `--collation-server` 和 `01-init.sql` 的 `DEFAULT COLLATE` 都改成 `utf8mb4_0900_ai_ci`，让声明追上现实。这样三处一致，且保留了正确的 emoji 行为，**且一张表都不用动**（改表要 `ALTER TABLE ... CONVERT TO`，20 张表全量重建，代价大得多）。

> ⚠️ 注意 `utf8mb4_0900_ai_ci` 是 MySQL 8.0+ 独有的，MariaDB 和 5.7 都没有。如果项目要兼容那些，就只能反过来统一到 `unicode_ci`，然后接受 emoji 的坑。**本项目锁死 `mysql:8.4`，没这个顾虑。**

### 顺带认识排序规则的命名

```sql
SELECT COUNT(*) FROM information_schema.collations WHERE character_set_name='utf8mb4';
-- 89
```

utf8mb4 有 **89** 种排序规则。名字是拼出来的：

| 部分 | 含义 |
|------|------|
| `utf8mb4_` | 字符集 |
| `0900` / `unicode` / `general` | 排序算法（UCA 9.0.0 / UCA 4.0.0 / MySQL 自己的简化算法） |
| `ai` / `as` | **a**ccent **i**nsensitive / **s**ensitive（重音敏感否，`é` = `e`？） |
| `ci` / `cs` / `bin` | **c**ase **i**nsensitive / **s**ensitive / 二进制（大小写敏感否） |

所以 `utf8mb4_0900_ai_ci` = UCA 9.0.0 + 重音不敏感 + 大小写不敏感。

验证一下大小写不敏感：

```sql
SELECT 'a' = 'A' COLLATE utf8mb4_0900_ai_ci;  -- 1
```

> 🔑 **这条对本项目有实际影响**：`sys_user.username` 是 `ci`（大小写不敏感），意味着 **`admin` 和 `ADMIN` 会撞 `uk_user_username` 唯一键**——注册时输 `ADMIN` 会提示"用户名已存在"。这通常正是你想要的（用户名不该区分大小写），但**如果哪天要做区分大小写的字段（比如 Base64 token、密码哈希），就得单独给那列指定 `_bin` 或 `_as_cs`**。
>
> `sys_user.password` 存的是 BCrypt 哈希（区分大小写！），它现在是 `ci`……好在 BCrypt 校验是在 Java 侧做的，MySQL 只负责存取，不做比较，所以没出事。**但如果有人写了 `WHERE password = ?` 去查，就会有安全隐患。**

## 四、字段类型：项目怎么选的

实测项目的类型分布（`grep -oE ... | sort | uniq -c`）：

```
  74 BIGINT
  36 DATETIME
  22 TINYINT
  21 VARCHAR(64)
  18 VARCHAR(16)
  17 VARCHAR(255)
  11 VARCHAR(128)
  11 INT
   6 VARCHAR(32)
   2 VARCHAR(512)
   2 VARCHAR(2000)
   1 JSON
```

逐个说重点。

### 1. 主键为什么是 BIGINT

```sql
`id` BIGINT NOT NULL AUTO_INCREMENT COMMENT '主键',
```

- `INT` 有符号最大 **21 亿**（`2^31-1`）。听着够用，但**日志表**（`sys_operation_log`）是只增不减的，一天 10 万条，58 年爆——听起来远，可 `AUTO_INCREMENT` 是**只增不复用**的，删了数据也不回退。真出事的公司不少。
- `BIGINT` 最大 **922 京**（`2^63-1`），实际上用不完。
- 代价：8 字节 vs 4 字节。**而且这个代价会被放大**——`02` 会讲，InnoDB 的**每个二级索引都会存一份主键值**。所以主键宽 4 字节，`sys_user` 上的 `idx_user_dept` 和 `uk_user_username` 就各自多占 4 字节/行。

> 🔑 面试标准答法：**用 BIGINT 是拿空间换"永不溢出"的确定性**。空间的代价会被二级索引放大（每个二级索引都存主键），但对绝大多数业务，这点空间远比"某天凌晨主键溢出、`INSERT` 全线报错"便宜。

**追问**："为什么不用 UUID 做主键？"——这是 `02` 的经典题。简答：UUID 无序，插入时会在 B+ 树里**随机位置**插，导致页分裂和碎片；而 `AUTO_INCREMENT` 是顺序追加，永远插在最右边。而且 UUID 占 36 字节（字符串形式），二级索引里存 36 字节的主键，膨胀得厉害。

### 2. 布尔值为什么是 TINYINT

```sql
`deleted`     TINYINT NOT NULL DEFAULT 0 COMMENT '逻辑删除 0/1',
`visible`     TINYINT NOT NULL DEFAULT 1 COMMENT '是否显示 0/1',
`builtin`     TINYINT NOT NULL DEFAULT 0 COMMENT '是否内置 0/1',
```

**MySQL 没有真正的 BOOLEAN 类型。** `BOOLEAN` 和 `BOOL` 只是 `TINYINT(1)` 的别名——你写 `BOOLEAN`，MySQL 存的还是 TINYINT。所以项目直接写 `TINYINT`，诚实且无歧义。

顺带澄清一个高频误解：**`TINYINT(1)` 里的 `1` 不是"只能存 1 位"**。它是**显示宽度**，和存储范围毫无关系——`TINYINT(1)` 照样能存 `-128 ~ 127`。这个显示宽度在 MySQL 8.0.17 起已被废弃。项目写的是不带括号的 `TINYINT`，是对的。

### 3. 枚举为什么是 VARCHAR(16) 而不是 ENUM 或 TINYINT

```sql
`status`    VARCHAR(16) NOT NULL DEFAULT 'ENABLED' COMMENT '状态 ENABLED/DISABLED',
`menu_type` VARCHAR(16) NOT NULL COMMENT '类型 DIR/MENU/BUTTON',
```

三个候选方案：

| 方案 | 存储 | 优点 | 缺点 |
|------|------|------|------|
| `TINYINT` 存 0/1/2 | 1 字节 | 最省 | **可读性为零**。`SELECT * FROM sys_menu` 看到 `menu_type=1`，你得去翻代码才知道 1 是啥 |
| `ENUM('DIR','MENU','BUTTON')` | 1-2 字节 | 省，且有约束 | **加一个枚举值要 `ALTER TABLE`**（大表上是重操作）；顺序有坑（`ORDER BY` 按定义顺序而非字母序）；跨 ORM 兼容差 |
| **`VARCHAR(16)` 存字符串** ← 项目选的 | 实际长度+1 字节 | **可读性最好**；加值不用改表结构 | 费空间；**没有数据库层约束**（能写进去任何字符串） |

实测 `'ENABLED'` 是 7 字节 + 1 字节长度前缀 = **8 字节**，比 TINYINT 多 7 字节。`sys_menu` 48 行的话，多占 336 字节——**完全不值得纠结**。

> 🔑 项目的取舍：**用空间换可读性和演进灵活性**。这符合 `CLAUDE.md` 里"枚举固定字符串，API 层必须是 `ENABLED`/`DISABLED`"的约定——**DB 存什么，API 就返什么，中间不用转换表**，少一层认知负担和一处 bug 来源。
>
> 代价是**没有 DB 层约束**：`UPDATE sys_user SET status='ENABLE'`（少个 D）能成功写进去，MySQL 不管。约束只存在于 Java 的枚举里。这是**把校验责任从 DB 移到应用层**的又一例——和"零外键"是同一个哲学，`07` 会把这条线串起来。

**VARCHAR(16) 的 16 够吗？** `'DISABLED'` 8 个字符，`'OWN_DEPT_CHILD'`（`sys_role.data_scope`，那列是 `VARCHAR(32)`）14 个字符。目前够，但**留的余量不大**。`VARCHAR(16)` 和 `VARCHAR(255)` 在 `Dynamic` 行格式下**存储开销几乎一样**（都按实际长度存），所以这里抠字节没什么意义——**除非那列要建索引**，索引长度是按声明的最大长度算的。

### 4. DATETIME 而不是 TIMESTAMP：一个有后果的选择

项目 36 处时间字段，**全是 `DATETIME`**，一个 `TIMESTAMP` 都没有。

两者的核心区别不是范围，是**时区行为**。实测：

```sql
CREATE TABLE tz (dt DATETIME, ts TIMESTAMP);
INSERT INTO tz VALUES ('2026-07-15 12:00:00','2026-07-15 12:00:00');
SELECT @@time_zone;  -- +08:00
SELECT * FROM tz;
```

```
dt                    ts
2026-07-15 12:00:00   2026-07-15 12:00:00     ← 一样
```

现在**只改会话时区**，不动数据：

```sql
SET time_zone='+00:00';
SELECT * FROM tz;
```

```
dt                    ts
2026-07-15 12:00:00   2026-07-15 04:00:00     ← ts 自己变了！
```

**`DATETIME` 纹丝不动，`TIMESTAMP` 自动变成了 04:00。**

机制：
- **`DATETIME` 存的是"墙上时钟"**——就是字面上那串数字，不带时区信息。你存 12:00，谁读都是 12:00。
- **`TIMESTAMP` 存的是 UTC 时间戳**——写入时按当前时区转成 UTC 存，读取时再按当前时区转回来。

| | DATETIME | TIMESTAMP |
|---|---|---|
| 存储 | 8 字节（5.6+ 是 5 字节+小数秒） | **4 字节** |
| 范围 | 1000 ~ 9999 年 | 1970 ~ **2038** 年 ⚠️ |
| 时区 | **无感**，存啥读啥 | **自动转换** |
| `ON UPDATE CURRENT_TIMESTAMP` | 支持（5.6+） | 支持 |

> 🔑 面试标准答法：**`TIMESTAMP` 省一半空间且自动处理时区，但有 2038 年问题（4 字节存 Unix 时间戳，2038-01-19 溢出）；`DATETIME` 范围大、行为直白，但不理时区。**

**本项目为什么全用 DATETIME？** 项目在三个地方把时区钉死成了东八区：

```yaml
# docker-compose.yml
- --default-time-zone=+08:00
TZ: Asia/Shanghai
```
```yaml
# application.yml 的 JDBC URL
serverTimezone=Asia/Shanghai
```

**既然全链路只有一个时区，`TIMESTAMP` 的自动转换就毫无价值，反而是 2038 问题的纯风险。** 用 `DATETIME` 是合理的。

**但代价是**：如果这个系统哪天要做跨时区（比如海外分公司），`DATETIME` 里那堆数字**没有任何时区信息**，你根本不知道 `2026-07-15 12:00:00` 是北京时间还是伦敦时间——只能靠"我们约定了都是东八区"这个口头契约。到那时改造成本极高。**这是个典型的"现在正确、未来可能后悔"的决定**，面试时能说出这层就很到位。

顺带回收 `00` 埋的扣：`created_at` **没有** `DEFAULT CURRENT_TIMESTAMP`，也没有 `ON UPDATE CURRENT_TIMESTAMP`，时间是 Java 侧 `AuditMetaObjectHandler` 填的。**后果是：绕过应用直接写 SQL 的话（比如你在 CLI 里 `INSERT`），`created_at` 会是 `NULL`。** `08` 会展开这笔账。

### 5. 唯一的 JSON 列

```sql
-- schema.sql:270
`form_data`          JSON         NULL COMMENT '表单快照',
```

`wf_process_instance.form_data`（`schema.sql:260` 建表、`:270` 该列），**全库唯一一个 JSON 列**。审批表单的字段是动态的（每个流程定义不一样），塞进 JSON 是合理的——**否则你得为每种表单建一张表**。

但要知道代价：**JSON 列没法直接建普通索引**（要用生成列 + 索引，或 MySQL 8 的多值索引）。

而项目里这列**从来没被当 JSON 查过**——没有任何 `JSON_EXTRACT` 或 `->` 。证据在实体类里：

```java
// WfProcessInstance.java:30
private String formData;     // ← JSON 列映射成了 Java String
```

**一个 JSON 列，映射成 String，整存整取。** 那其实用 `TEXT` 也行，区别只在于 JSON 类型会**校验格式**（写入非法 JSON 会报错）并用二进制格式存储（读取时不用重新解析文本）。所以这里用 JSON 的实际收益就是**那层格式校验**——考虑到项目其它地方都在"把校验责任交给应用层"（枚举没约束、零外键），这一处反倒是全库少见的、让 DB 帮忙把关的地方。

## 面试怎么问

**Q1：InnoDB 和 MyISAM 的区别？**

标准答法：**最本质的是事务和锁粒度——InnoDB 支持事务、行锁、外键、崩溃恢复，MyISAM 都不支持，只有表锁。** 索引结构上 InnoDB 是聚簇索引（数据挂在主键 B+ 树的叶子上），MyISAM 索引和数据分开。MyISAM 唯一优势是 `COUNT(*)` O(1)（存了行数），但没事务这优势毫无意义。**5.5 起默认 InnoDB，新项目没理由用 MyISAM。**

追问"InnoDB 为什么不能也存行数计数器"→ 因为 MVCC，不同事务看到的行数不同，不存在唯一正确的行数。

**Q2：utf8 和 utf8mb4 的区别？**

标准答法：**MySQL 的 `utf8` 是 `utf8mb3` 的别名，每字符最多 3 字节，存不了 emoji 和部分生僻字；`utf8mb4` 才是真正的 UTF-8，最多 4 字节。** 能补一句"存 emoji 会报 `ERROR 1366 Incorrect string value`，宽松模式下更糟——静默截断，数据真坏在磁盘上"就很实在。

**Q3：`utf8mb4_general_ci`、`utf8mb4_unicode_ci`、`utf8mb4_0900_ai_ci` 怎么选？**

- `general_ci`：MySQL 自研的简化算法，快但不准（不完全遵循 Unicode 规范）。
- `unicode_ci`：UCA 4.0.0，准但慢，**且 2003 年的标准——所有 emoji 在它眼里彼此相等**。
- `0900_ai_ci`：UCA 9.0.0，MySQL 8.0 的默认，**又快又准**（8.0 做了大量优化），emoji 也能正确区分。

**MySQL 8 就用 `0900_ai_ci`，别用另外两个。** 拿项目举例：我们项目声明的是 `unicode_ci`，但实际生效的是 `0900_ai_ci`，我做实验发现 `'😀' = '😃'` 在 `unicode_ci` 下返回 1，加了唯一键会撞 `Duplicate entry` ——所以这个"配置事故"反而让我们躲过了坑。

**Q4：`VARCHAR(64)` 的 64 是字节还是字符？**

**字符。** `VARCHAR(64)` 能存 64 个汉字（utf8mb4 下占 192 字节）。用 `LENGTH()` 数字节、`CHAR_LENGTH()` 数字符可以验证。

**Q5：DATETIME 和 TIMESTAMP 怎么选？**

标准答法：**`TIMESTAMP` 4 字节、存 UTC、自动按时区转换，但 2038 年溢出；`DATETIME` 8 字节、存"墙上时钟"、不理时区，范围到 9999 年。**

拿项目举例：我们全用 `DATETIME`，因为 compose 的 `--default-time-zone=+08:00`、容器 `TZ`、JDBC 的 `serverTimezone` 三处都钉死了东八区，全链路单时区，`TIMESTAMP` 的自动转换没价值反而是 2038 风险。**代价是将来要做跨时区就很难改**——`DATETIME` 里的数字不带时区信息。

**Q6（进阶，能主动抛出来是加分项）：讲讲你在项目里发现的一个配置问题？**

就讲这节的排序规则悬案：三处声明、两处生效、20 张表全是第三个值；根因是表级 `DEFAULT CHARSET=utf8mb4` 只写字符集不写排序规则，MySQL 会用该字符集的默认排序规则、绕过库继承——**"什么都不写反而是对的"**；但深入验证后发现实际生效的值行为更正确（emoji），所以正确的修法是让声明追上现实（改 compose 和 init.sql），而不是动 20 张表。

**这个回答同时展示了：会查、懂机制、能权衡、知道 `ALTER TABLE` 的代价。** 比背十条八股有用。

## 附：答案与解析

<details>
<summary>练习 5 参考答案（password 是 ci 为什么没出安全问题）</summary>

**因为 MySQL 从来没有比较过这一列。**

BCrypt 的校验流程是：
1. Java 按 username 查出整行：`SELECT * FROM sys_user WHERE username = ?`
2. 拿到 `password` 列的哈希字符串
3. **在 Java 内存里**用 `BCryptPasswordEncoder.matches(明文, 哈希)` 比对

MySQL 在第 1 步只做了 `username` 的比较（那列是 ci，符合预期——用户名不该区分大小写），`password` 列只是被**读出来**，没参与任何比较。排序规则只影响**比较和排序**，不影响存取。

**什么情况下会出问题？** 如果有人写了这样的 SQL：

```sql
SELECT * FROM sys_user WHERE username = ? AND password = ?   -- 危险！
```

那 `password` 的比较就会走 `ci` 规则——BCrypt 哈希是 Base64 变体，**大小写有意义**，`$2a$10$Abc...` 和 `$2a$10$aBC...` 是不同的哈希，但在 `ci` 下会被判定相等。理论上这扩大了碰撞面。

不过实际上这种写法本身就是错的（BCrypt 每次加盐结果都不同，根本没法直接用 `=` 比对），所以真正的防线是"密码校验必须在应用层做"，而不是靠排序规则。

**如果真要存大小写敏感的字符串**（比如 API token、Base64 值），应该给那列单独指定：

```sql
`token` VARCHAR(64) COLLATE utf8mb4_bin NOT NULL
```

</details>

<details>
<summary>自检 1：InnoDB vs MyISAM 最本质的区别</summary>

**事务和锁粒度。** InnoDB 支持事务（ACID）、行级锁；MyISAM 两个都没有，只有表锁——改一行锁整张表，并发写直接排队。其它差异（外键、崩溃恢复、聚簇索引）都是从这个根本设计衍生的。

**为什么 InnoDB 不能存行数计数器？**

因为 MVCC（多版本并发控制）。InnoDB 里，**不同事务在同一时刻看到的行数是不同的**：

- 事务 A 插了 100 行还没提交 → A 自己看到 `COUNT(*)` = 1100，事务 B 看到的还是 1000
- 事务 C 用可重复读隔离级别开了个快照 → 它看到的是快照那一刻的行数

**根本不存在"一个全局正确的行数"可以存进计数器。** 所以 InnoDB 的 `COUNT(*)` 必须实时扫描，按当前事务的可见性逐行判断。

MyISAM 没有事务，任何时刻所有连接看到的都是同一份数据，"行数"才是个确定的值，才有资格存。

（`05` 讲 MVCC 时会回到这里。）

</details>

<details>
<summary>自检 2：`DEFAULT CHARSET = utf8mb4` 坏在哪？删掉会怎样？</summary>

**坏在它覆盖了库的排序规则继承。**

MySQL 的规则：**只要你在建表时显式写了 CHARSET，MySQL 就认为字符集由建表语句说了算，于是排序规则也跟着用"该字符集的默认值"，不再去继承库。** 而 `utf8mb4` 在 MySQL 8.0+ 的默认排序规则是 `utf8mb4_0900_ai_ci`。

于是 `01-init.sql` 里辛辛苦苦写的 `DEFAULT COLLATE utf8mb4_unicode_ci` 被完全绕过。

**删掉会怎样？** 表会老老实实继承库的 `utf8mb4` + `utf8mb4_unicode_ci`。实验里的 `t1`（什么都不写）就是证明——它拿到了 `utf8mb4_unicode_ci`。

**讽刺点**：这行是为了"显式、保险"才写的，结果恰恰破坏了另一处的显式声明。**配置分散在三个地方，每一处都"为了保险"而重复声明，反而互相打架。**

（但注意：删掉它会让表变成 `unicode_ci`，而那个值的 emoji 行为更差。所以正确的修法不是删这行，见自检 3。）

</details>

<details>
<summary>自检 3：为什么 `0900_ai_ci` 比 `unicode_ci` 更正确？</summary>

**因为 emoji。**

`utf8mb4_unicode_ci` 基于 **UCA 4.0.0**（2003 年的 Unicode 排序算法）。那时候 emoji 还没进 Unicode 标准，所以这些码位**没有分配排序权重**。而没有权重的字符，在比较时**一律视为相等**。

结果就是：在 `utf8mb4_unicode_ci` 下，**所有 emoji 彼此全部相等**。实测：

```sql
SELECT '😀' = '😃' COLLATE utf8mb4_unicode_ci;  -- 1  ← 认为相等！
SELECT '😀' = '😃' COLLATE utf8mb4_0900_ai_ci;  -- 0  ← 正确
```

加上唯一键就是事故：

```
INSERT INTO emoji_uni VALUES ('😀');   -- OK
INSERT INTO emoji_uni VALUES ('😃');   -- ERROR 1062: Duplicate entry '?' for key
```

如果 `sys_user.nickname` 用了 `unicode_ci` 并且有唯一键，那么用户 A 昵称用 😀、用户 B 想用 😃，B 会被告知"昵称已存在"——**一个几乎无法排查的灵异 bug**。

`utf8mb4_0900_ai_ci` 基于 UCA 9.0.0（2016），emoji 都有正确权重，而且 MySQL 8.0 对它做了大量性能优化，**比 `unicode_ci` 又快又准**。

所以项目这个"配置事故"，阴差阳错躲过了一个坑。

</details>

<details>
<summary>自检 4：排序规则不一致什么时候爆雷？为什么建表时不报错？</summary>

**爆雷时机：两个排序规则不同的字符串列做比较时**——JOIN 的 `ON`、`WHERE a.col = b.col`、`UNION`、子查询里的 `IN` 等。

实测：

```sql
SELECT u.username FROM rbac.sys_user u JOIN lab_tmp.t3 t ON u.username = t.name;
```
```
ERROR 1267 (HY000): Illegal mix of collations
(utf8mb4_0900_ai_ci,IMPLICIT) and (utf8mb4_unicode_ci,IMPLICIT) for operation '='
```

**为什么建表时不报错？** 因为建表时这两张表毫无关系——每张表自己的排序规则都是合法的，MySQL 没理由拒绝。**只有当你把两个不同排序规则的列放在一起比较时，MySQL 才发现"我不知道该按谁的规则比"。**

这就是这类问题的阴险之处：**建表时静悄悄，上线跑到那条 SQL 才炸**，而且往往是某个很少走到的分支。

本项目目前安全，纯粹是因为**碰巧 20 张表全被统一成了 `0900_ai_ci`**（因为 `schema.sql` 20 处写法完全一致）。哪天有人加了张表写成 `COLLATE=utf8mb4_unicode_ci`，或者要跨库 JOIN，就会撞上。

应急解法（SQL 里临时指定）：
```sql
... ON u.username = t.name COLLATE utf8mb4_0900_ai_ci
```
但这会让**索引失效**（`02` 会讲为什么——列上加了函数/转换就用不了索引了）。所以是应急，不是长久之计。

</details>

<details>
<summary>自检 5：VARCHAR(16) vs TINYINT 的账</summary>

**多花 7 字节。** `'ENABLED'` 实测 `LENGTH()` = 7 字节，加 1 字节的长度前缀 = 8 字节；`TINYINT` = 1 字节。

**为什么划算？**

1. **可读性**：`SELECT * FROM sys_menu` 直接看到 `menu_type='BUTTON'`，不用翻代码查"1 是什么意思"。排查线上问题时这个价值极大。
2. **演进灵活**：加一个新状态，直接写字符串进去，**不用 `ALTER TABLE`**（如果用 `ENUM` 就得改表结构，大表上是重操作）。
3. **和 API 契约对齐**：`CLAUDE.md` 规定 API 层必须是 `ENABLED`/`DISABLED` 字符串。DB 直接存字符串 → **中间不需要转换表**，少一层认知负担、少一处 bug 来源。
4. **量级**：`sys_menu` 48 行 × 7 字节 = 336 字节。真的不值得纠结。

**代价是什么？**

**丢掉了数据库层的约束。** `UPDATE sys_user SET status='ENABLE'`（少个 D）会成功写进去，MySQL 一声不吭。约束只存在于 Java 的枚举里——**只要有人绕过应用直接写 SQL，脏数据就进来了**。

`ENUM` 类型本来能提供这层约束，但它有自己的坑（改值要 ALTER、`ORDER BY` 按定义顺序而非字母序、跨 ORM 兼容差），项目选择了放弃约束换灵活性。

**这和"零外键"是同一个哲学：把数据完整性的责任从 DB 移到应用层。** 好处是 DB 简单、迁移和分库容易；坏处是 DB 自己不再保证任何东西，**一旦有人绕过应用，什么脏数据都可能进来**。`07` 会把这条线完整串起来。

</details>

<details>
<summary>自检 6：为什么全用 DATETIME？什么时候会后悔？</summary>

**理由：项目全链路只有一个时区，`TIMESTAMP` 的自动转换毫无价值，反而白担 2038 风险。**

时区在三个地方被钉死成东八区：
```yaml
# docker-compose.yml
- --default-time-zone=+08:00
TZ: Asia/Shanghai
```
```
# application.yml 的 JDBC URL
serverTimezone=Asia/Shanghai
```

既然写入和读取永远是同一个时区，`TIMESTAMP` 那套"存 UTC、读时转回来"就是白转一圈，结果和 `DATETIME` 一模一样。而 `TIMESTAMP` 还带着 **2038-01-19 溢出**的定时炸弹（4 字节存 Unix 时间戳）。所以选 `DATETIME` 是对的。

**什么时候后悔？**

1. **要做跨时区**（海外分公司、用户遍布多时区）。`DATETIME` 里的 `2026-07-15 12:00:00` **不带任何时区信息**——你不知道它是北京时间还是伦敦时间，只能靠"我们约定都是东八区"这个口头契约。一旦有一台服务器时区配错，数据就永久性地无法分辨。改造成本极高（要么全表加时区列，要么全量转 UTC 重刷）。
2. **服务器迁移到别的时区**。`DATETIME` 存的是墙上时钟，迁到 UTC 机器后，老数据还是 `12:00`（本意是北京 12 点），新数据写进去的 `12:00` 却是 UTC 12 点（北京 20 点）。**新老数据混在一列里，且无法区分。** 这是真实事故的常见成因。

实测证明这个差异：
```sql
SET time_zone='+00:00';
SELECT * FROM tz;
-- dt: 2026-07-15 12:00:00   ← 纹丝不动
-- ts: 2026-07-15 04:00:00   ← 自动转了
```

`TIMESTAMP` 换时区后能给出正确答案，`DATETIME` 给出的是原始数字——**在单时区系统里这没区别，在多时区系统里这是灾难。**

</details>

<details>
<summary>自检 7：`TINYINT(1)` 的 1 是什么？</summary>

**是显示宽度，和存储范围毫无关系。**

最常见的误解是以为 `TINYINT(1)` 只能存 0/1。实际上 `TINYINT(1)` 和 `TINYINT(4)`、`TINYINT` 的**存储和取值范围完全一样**：1 字节，`-128 ~ 127`（无符号 `0 ~ 255`）。

括号里的数字只是给客户端的一个"显示时补零到几位"的提示（配合 `ZEROFILL` 才有实际效果），**绝大多数客户端根本不理它**。

MySQL 8.0.17 起，整数类型的显示宽度已被**废弃**（deprecated），`SHOW CREATE TABLE` 也不再显示它。实测本项目的 `sys_user`：

```
`deleted` tinyint NOT NULL DEFAULT '0' COMMENT '逻辑删除 0/1',
```

**就是不带括号的 `tinyint`**，因为 `schema.sql` 里写的就是 `TINYINT`（没写宽度），是正确写法。

顺带：`BOOLEAN` / `BOOL` 是 `TINYINT(1)` 的别名——**MySQL 没有真正的布尔类型**。你写 `BOOLEAN`，`SHOW CREATE TABLE` 出来还是 `tinyint(1)`。项目直接写 `TINYINT`，诚实且无歧义。

</details>
