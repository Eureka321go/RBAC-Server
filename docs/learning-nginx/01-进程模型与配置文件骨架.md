## 一、承上：把最外层这 8 行摊开

`00` 结尾埋了两个问号，现在还。这是 `frontend/nginx.conf` 的前 8 行，一字不差：

```nginx
user  nginx;
worker_processes  auto;
error_log  /var/log/nginx/error.log warn;
pid        /var/run/nginx.pid;

events {
    worker_connections  1024;
}
```

八行里有两个进程相关的配置（`worker_processes`、`worker_connections`），一个权限配置（`user`），一个日志配置（`error_log`），一个运行时文件（`pid`）。要看懂它们，得先知道 nginx 启动之后到底变成了几个进程。

## 二、master-worker：nginx 启动后是几个进程

### 2.1 一个 master + N 个 worker

nginx 跑起来之后**不是一个进程，是一窝**。结构是固定的：

```
nginx: master process          ← 1 个，root 身份运行
 ├── nginx: worker process     ← N 个，用 user 指令指定的身份运行
 ├── nginx: worker process
 ├── nginx: worker process
 └── nginx: worker process
```

分工非常清楚，且**互不重叠**：

| | master 进程 | worker 进程 |
|---|---|---|
| 有几个 | 恒定 1 个 | N 个（`worker_processes` 决定） |
| 身份 | root（需要绑定 80 这类特权端口） | `user` 指令指定的普通用户 |
| 处理请求吗 | **不处理**，一个请求都不碰 | **全部请求都是它们处理的** |
| 干什么 | 读配置、绑端口、fork worker、管理 worker 生死、接收信号 | 抢连接、收请求、发响应 |
| 挂了会怎样 | 全站完蛋 | master 立刻 fork 一个新的补上 |

这个模型解决了一个矛盾：**绑定 80 端口需要 root 权限，但用 root 处理来自公网的请求太危险**（一旦 worker 被攻破，攻击者直接拿到 root）。

nginx 的解法是把这两件事拆给两个角色：master 用 root 身份把端口绑好，然后 fork 出 worker 并把身份**降级**成普通用户。worker 继承了已经绑好的端口（文件描述符），所以它不需要 root 也能在 80 上收请求。

这就是第一行的意思：

```nginx
user  nginx;      # worker 进程降权后的身份 —— nginx 镜像里预置的一个普通用户
```

> 🔑 `user nginx` 管的是 **worker** 的身份，master 始终是 root。所以配置里的这一行，和"nginx 以什么权限读文件"直接相关——如果 `/usr/share/nginx/html` 底下的文件 `nginx` 这个用户读不了，你会拿到 **403 Forbidden**，而不是 404。这是静态文件 403 的头号原因。

### 2.2 `worker_processes auto` 是几个

```nginx
worker_processes  auto;
```

`auto` 的解析规则很简单：**等于 CPU 核心数**。

为什么是核心数而不是"越多越好"？因为 nginx 的 worker 是**单线程 + 事件驱动**的：一个 worker 用一个线程，靠 epoll 这类 I/O 多路复用机制，在一个线程里同时盯着成千上万个连接，哪个有数据就处理哪个，从不阻塞等待。

这种模型下，worker 数量超过核心数没有任何好处——它们不会"更并行"，只会互相抢 CPU、增加上下文切换开销。所以最优解就是**一核一个 worker**，让每个 worker 独占一个核心跑满。

> 🔑 nginx 的高并发**不是靠多进程/多线程堆出来的**，是靠单线程内的事件循环。这和 Spring Boot 默认的"一个请求一个线程"模型是两种完全不同的思路——这也解释了为什么 nginx 能用几个进程扛住几万连接，而 backend 那边 200 个线程就到顶了。

本项目跑在阿里云轻量服务器上，几核就起几个 worker。写 `auto` 而不是写死数字的好处是：**换机器不用改配置**。

### 2.3 `error_log` 和 `pid`

```nginx
error_log  /var/log/nginx/error.log warn;    # 错误日志：写哪、记多细
pid        /var/run/nginx.pid;               # master 进程号存哪
```

`error_log` 第二个参数 `warn` 是**日志级别**，nginx 有八级，从啰嗦到安静：

```
debug → info → notice → warn → error → crit → alert → emerg
 最细                    ↑                          最粗
                    本项目在这
```

规则是"**记录该级别及以上**"。写 `warn` 就是：warn / error / crit / alert / emerg 都记，debug / info / notice 不记。

这是个中庸的选择：生产环境写 `debug` 会把磁盘刷爆（而且默认的 nginx 二进制通常没编译 debug 支持，写了也没用），写 `error` 又会漏掉"上游响应慢""连接被重置"这类**还没到报错、但已经不对劲**的信号。`warn` 正好卡在"值得你半夜被叫起来看一眼"的那条线上。

`pid` 存的是 master 的进程号。它的用途是**给 `nginx -s reload` 这类信号命令找到 master**——待会儿第五节会讲，而且会讲清楚为什么本项目用不上它。

日志和 `error_log` 的完整体系（包括本项目**没配**的 `access_log`）放在 `05` 讲，那里会把它和 `docker logs` 串起来。

## 三、`events` 块与 `worker_connections`：一个经典误解

```nginx
events {
    worker_connections  1024;
}
```

### 3.1 它不是"最多 1024 个人同时访问"

这是 nginx 配置里最容易被误读的一个指令。三个必须同时记住的限定：

**第一，它是"每个 worker"的上限，不是全局的。**

```
理论最大连接数 = worker_processes × worker_connections
```

4 核机器就是 `4 × 1024 = 4096` 个**连接**。

**第二，它算的是"连接"，不是"人"，也不是"请求"。**

HTTP/1.1 默认开 keep-alive（本项目的 `keepalive_timeout 65` 就是在配这个，`02` 细讲）：一个浏览器打开你的页面，会保持好几条 TCP 连接不断开，用来陆续加载 JS、CSS、图片。所以**一个用户 ≠ 一个连接**，往往是好几个。

**第三，也是最要命的一条：反向代理场景下，一个请求吃掉的是两个连接。**

```
浏览器 ──连接A──► nginx ──连接B──► backend:8080
        ↑ 算一个            ↑ 又算一个
```

nginx 转发 `/api/users` 时，客户端那侧占一个连接，它自己去连 backend 又占一个连接，**两个都算在 `worker_connections` 的账上**。

所以对本项目这种"既发静态文件又反代"的场景，真实的并发能力大概是：

```
纯静态请求：           4 × 1024 = 4096 个连接
纯 /api 反代请求：      4 × 1024 ÷ 2 = 2048 个并发请求
实际是两者混合，落在中间某处
```

> 🔑 `worker_connections 1024` **不是并发用户数**。它是"每个 worker 能同时持有的文件描述符数量"，而反向代理的每一次转发都要吃掉两个。把它当成用户数来估算容量，会高估到离谱。

### 3.2 那 1024 够不够

对本项目：**绰绰有余，而且短期内不会成为瓶颈**。

理由不是 1024 这个数字大，而是**瓶颈根本不在 nginx 这一层**。链路上真正先趴下的是 backend 的线程池和 MySQL 的连接数——一个后台管理系统，同时在线几十个管理员就算多的了，离 2048 个并发请求差着两个数量级。

值得注意的是：`worker_connections` 还受**系统层面文件描述符上限**（`ulimit -n`）的约束。如果把它调到 65535 但系统的 `ulimit -n` 只有 1024，那实际上限还是 1024，nginx 启动时会在 error.log 里报 warning。**调这个值必须同时调 `worker_rlimit_nofile` 和系统 ulimit，只改一个是自欺欺人**。

## 四、配置文件的组织方式

前面那 8 行读完了，但要读懂后面 37 行，得先建立"配置文件长什么样"的骨架。

### 4.1 只有两种东西：简单指令和块指令

nginx 配置的语法极简，全文只由两种元素构成：

**简单指令**：名字 + 参数，分号结尾。

```nginx
worker_processes  auto;
                       ↑ 分号是强制的，漏了直接语法错误
```

**块指令**：名字 + 参数 + 一对花括号，**花括号后面不加分号**。

```nginx
events {
    worker_connections  1024;
}
                        ↑ 这里没有分号
```

块指令的花括号里可以放别的指令，于是就有了嵌套。**能容纳其他指令的块，叫做「上下文」（context）**。

### 4.2 五层上下文

本项目的配置，把缩进抽出来看，是这样一个嵌套结构：

```nginx
                                    # ← main 上下文（最外层，没有花括号，整个文件就是它）
user  nginx;
worker_processes  auto;

events { ... }                      # ← events 上下文：连接处理相关

http {                              # ← http 上下文：所有 HTTP 相关配置的家
    include /etc/nginx/mime.types;
    gzip on;

    upstream rbac_backend { ... }   # ← upstream 上下文：定义后端服务器组

    server {                        # ← server 上下文：一个虚拟主机
        listen 80;

        location /api/ { ... }      # ← location 上下文：一组 URL 的处理规则
        location / { ... }          # ← 另一个 location
    }
}
```

各层的职责：

| 上下文 | 管什么 | 本项目里有几个 |
|---|---|---|
| main | 进程、用户、全局日志 —— 影响整个 nginx 实例 | 1（就是文件本身） |
| `events` | 连接处理模型、每 worker 连接数 | 1 |
| `http` | 所有 HTTP 层配置：MIME、压缩、超时 | 1 |
| `upstream` | 定义一组后端服务器（在 `http` 内） | 1（`rbac_backend`） |
| `server` | 一个虚拟主机：监听哪个端口、响应哪个域名 | 1 |
| `location` | 一组 URL 路径的处理规则 | 2（`/api/` 和 `/`） |

> 🔑 **一个 `http` 里可以有多个 `server`（多个网站共用一个 nginx），一个 `server` 里可以有多个 `location`（一个网站的不同路径不同处理）。** 本项目只有一个网站、两条分流规则，所以是 1 个 server + 2 个 location——这个结构就是 `00` 说的"按 URL 分流"的落地形态。

### 4.3 继承规则：子上下文继承父上下文

这是配置里最省事、也最容易踩坑的机制：

**内层上下文自动继承外层的指令；内层重新写一遍，就覆盖外层。**

看本项目的实例：

```nginx
http {
    sendfile        on;             # ← 写在 http 层
    keepalive_timeout  65;

    server {
        listen 80;
        root /usr/share/nginx/html; # ← 写在 server 层

        location /api/ {
            # 这里没写 sendfile，但它继承了 http 层的 on
            # 这里没写 root，但它继承了 server 层的 /usr/share/nginx/html
            proxy_pass http://rbac_backend;
        }
    }
}
```

`location /api/` 里虽然一个字都没提 `sendfile` 和 `root`，但它们**都生效**——从上面继承下来的。

这解释了本项目为什么把 `gzip on`、`sendfile on` 写在 `http` 层：**写一次，所有 server、所有 location 全都生效**。

**坑在哪**：继承是"整体覆盖"，不是"合并"。如果某个 `location` 里写了一条同名指令，外层那条对它就**完全失效**了，不是叠加。这个坑在 `proxy_set_header` 上最要命——`04` 会专门讲这个杀伤力惊人的细节。

### 4.4 `include`：本项目唯一的一次配置拆分

```nginx
http {
    include       /etc/nginx/mime.types;
```

`include` 就是"把另一个文件的内容原地展开到这里"，和 C 语言的 `#include` 是一个意思。

`/etc/nginx/mime.types` 是 nginx 官方镜像自带的文件，里面是几百行**文件后缀 → MIME 类型**的对照表：

```nginx
types {
    text/html                             html htm shtml;
    text/css                              css;
    application/javascript                js;
    image/png                             png;
    ...约 90 行
}
```

这种东西没人愿意抄到自己配置里，所以官方拆成单独文件，用 `include` 引进来。它到底影响什么，`02` 讲。

**为什么本项目是单文件，而不是 `conf.d/*.conf`？**

你在网上会大量看到这种结构：

```nginx
http {
    include /etc/nginx/conf.d/*.conf;    # ← 通配符：把这个目录下所有 .conf 都引进来
}
```

然后每个网站一个 `conf.d/xxx.conf`。nginx 官方镜像**默认就是这么组织的**（默认配置里有 `include /etc/nginx/conf.d/*.conf;`，而 `conf.d/default.conf` 里放着那个欢迎页 server）。

本项目没这么干，直接一个 `nginx.conf` 全写完，原因很简单：**只有一个网站**。拆成多文件是为了管理几十个虚拟主机时不打架，一个站点拆文件只会增加"要跳着看两个文件"的心智负担。

**注意一个后果**：`frontend/Dockerfile:18` 那句 `COPY nginx.conf /etc/nginx/nginx.conf` 是**整个覆盖**了官方镜像的默认配置。所以官方默认的 `include /etc/nginx/conf.d/*.conf` 也一并没了，`conf.d/default.conf` 里那个欢迎页 server **不会生效**。这是好事——否则那个 server 会和我们的 server 争夺 80 端口的默认权（`03` 讲 `default_server` 时会回到这里）。

## 五、改了配置怎么生效：`nginx -t` 和 `reload`

### 5.1 通用做法

标准的 nginx 运维循环是三步：

```bash
# ① 改配置
vim /etc/nginx/nginx.conf

# ② 先验语法！这一步不能省
nginx -t
# 输出 syntax is ok + test is successful 才算过

# ③ 热加载
nginx -s reload
```

`nginx -t` 只做一件事：**解析配置文件，报语法错误，然后退出**。它不会重启任何东西。这条命令的价值在于——如果配置有语法错误，`reload` 会失败，而**老配置继续跑**（不会宕机）；但如果是重启（`restart`），语法错误就意味着**起不来了，站点直接下线**。

> 🔑 `nginx -t` 是免费的保险。改完不验就 reload，等于闭着眼睛按核按钮。

### 5.2 `reload` 不是重启

这是 nginx 设计得最漂亮的地方之一。`nginx -s reload` 实际上是给 master 发一个 `HUP` 信号（`pid` 文件就是用来找到 master 的），然后发生的事是：

```
① master 收到 HUP 信号
② master 重新读配置文件、重新解析
   └─ 如果配置有错：放弃，打日志，什么都不变（老 worker 继续跑）✔
③ 配置没问题 → master fork 出一批【新 worker】，用新配置
④ master 通知【老 worker】："别接新连接了"
⑤ 老 worker 停止接受新连接，但【把手上正在处理的请求处理完】
⑥ 老 worker 处理完存量请求 → 自己退出
```

关键在第 ⑤ 步：**已经连上来的请求不会被打断**。所以 reload 是**零停机**的——用户完全无感，不会有任何一个请求失败。

对比一下重启：直接杀掉所有进程再启动，**正在处理的请求全部被掐断**，用户看到连接重置；而且如果新配置有语法错误，就是彻底起不来。

| | `reload` | 重启 |
|---|---|---|
| 存量请求 | 处理完才退出 ✔ | 直接掐断 ✘ |
| 停机时间 | 0 | 有（毫秒到秒级） |
| 配置有错时 | 拒绝加载，老配置继续跑 ✔ | 起不来，站点下线 ✘ |
| 换了 nginx 版本/二进制 | 不生效 | 才生效 |

### 5.3 但本项目根本用不上 reload

上面这套是通用做法。**本项目一条都用不上**，原因在 `frontend/Dockerfile`：

```dockerfile
FROM nginx:1.27
COPY nginx.conf /etc/nginx/nginx.conf     # ← 配置被【烤进镜像】了
COPY --from=build /app/dist /usr/share/nginx/html
```

`COPY` 发生在**构建镜像**的时候。也就是说，`/etc/nginx/nginx.conf` 是镜像的一部分，**和镜像一起被固化了**。

所以本项目改 nginx 配置的正确循环是：

```bash
# ① 开发机改 frontend/nginx.conf
# ② 提交推送
git add frontend/nginx.conf && git commit -m "..." && git push origin feat/rbac-mvp

# ③ 服务器拉取
cd /root/project/RBAC-Server && git pull origin feat/rbac-mvp

# ④ 【重新构建镜像】并重建容器 —— 注意 --build 不能省
cd deploy && docker compose up -d --build
```

改了 `frontend/nginx.conf` 却只跑 `docker compose restart frontend`？**一点用都没有**。restart 只是把老容器重启，而老容器里那个 `/etc/nginx/nginx.conf` 还是旧镜像烤进去的旧内容——你改的是宿主机上的源文件，容器里那份根本不知道。

> 🔑 **配置烤进镜像 → 改配置 = 重新构建镜像。** 这是本项目 nginx 运维和网上教程最大的差异点，也是"我明明改了配置怎么没生效"的头号原因。判断依据很简单：看这份配置是 `COPY` 进去的（要 rebuild）还是 `volumes` 挂进去的（restart 即可）。

有意思的是，那份**遗留**的 `deploy/config/nginx/nginx.conf` 恰恰是相反的：

```yaml
  nginx:
    volumes:
      - ./config/nginx/nginx.conf:/etc/nginx/nginx.conf:ro    # ← 挂载，不是 COPY
```

它是 **bind mount 挂进去的**，所以改它只需要 `docker compose restart nginx` 就生效，不用重新构建（`learning-docker 05` 讲过挂载与 `:ro`）。

**两份配置，连"怎么改才生效"都是相反的。** 这就是 `00` 说"看到 nginx.conf 先确认是哪一份"的原因之一。`06` 会把这笔账彻底算清。

## 附：答案与解析

> 建议先自己想一遍再点开。想不出来不丢人，但直接看答案，这节就白读了。

### 自检问题

<details>
<summary><b>1. nginx 启动后是几个进程？master 处理请求吗？</b></summary>

**1 个 master + N 个 worker**，N 由 `worker_processes` 决定（本项目是 `auto` = CPU 核心数）。

**master 一个请求都不处理。** 它只负责：读配置、绑定端口、fork worker、监控 worker 生死、接收信号（如 reload 的 HUP）。所有实际的请求处理**全部由 worker 完成**。

所以 master 是个纯管理者。这也是为什么 worker 崩溃不致命——master 还活着，立刻 fork 一个新的补上；而 master 挂了才是真完蛋。
</details>

<details>
<summary><b>2. <code>user nginx</code> 管的是 master 还是 worker 的身份？为什么要有这个降权设计？</b></summary>

管 **worker**。master 始终是 root。

设计动机是解决一个矛盾：**绑 80 端口需要 root 权限**（Linux 上 1024 以下是特权端口），**但用 root 处理公网请求太危险**——worker 是直接接触不可信输入的那一层，一旦被攻破，攻击者就拿到了 root。

nginx 的解法是拆分：master 用 root 把端口绑好（这是一次性动作），fork 出 worker 后把身份降级成 `nginx` 这个普通用户。worker 继承了已绑好的端口文件描述符，不需要 root 也能在 80 上收请求。

**实践后果**：worker 是以 `nginx` 用户身份去读 `/usr/share/nginx/html` 下的文件的。如果那些文件的权限不允许 `nginx` 用户读，请求会返回 **403 Forbidden**（不是 404）。看到静态文件 403 先查权限，这是第一嫌疑人。
</details>

<details>
<summary><b>3. <code>worker_processes auto</code> 起几个 worker？为什么不是越多越好？</b></summary>

**等于 CPU 核心数。**

不是越多越好，因为 nginx 的 worker 是**单线程 + 事件驱动（epoll）**的：一个 worker 用一个线程就能同时盯着上万个连接，谁有数据处理谁，从不阻塞。

在这种模型下，worker 数量超过核心数**不会带来任何并行度提升**——CPU 就那么多核，多出来的 worker 只会互相抢 CPU、增加上下文切换开销，净负收益。最优解就是一核一个 worker，各自跑满一个核。

写 `auto` 而不是写死数字的好处：换机器（比如从 2 核升到 4 核）不用改配置。
</details>

<details>
<summary><b>4. <code>worker_connections 1024</code> 是"最多 1024 个用户同时访问"吗？反向代理场景下有什么特殊之处？</b></summary>

**不是。** 三层误解要一起破：

1. **它是每个 worker 的上限**，不是全局。全局理论上限 = `worker_processes × worker_connections`。
2. **它算连接，不算用户**。HTTP keep-alive 下一个浏览器会保持多条连接不断开，一个用户往往占好几个。
3. **反向代理时一个请求吃两个连接**：客户端 → nginx 占一个，nginx → backend 又占一个，两个都算在同一个 worker 的账上。

所以纯反代场景下，实际并发请求上限要**除以 2**。

还有个隐藏约束：`worker_connections` 受系统 `ulimit -n`（文件描述符上限）制约。调大它却不调 `worker_rlimit_nofile` 和系统 ulimit，实际上限不会变，nginx 只会在 error.log 里给你一条 warning。
</details>

<details>
<summary><b>5. nginx 配置里，块指令的花括号后面要不要加分号？</b></summary>

**不加。**

- 简单指令：`worker_processes auto;` —— 分号强制。
- 块指令：`events { ... }` —— 花括号后面**没有分号**。

这是 nginx 配置最常见的低级语法错误之一。好消息是 `nginx -t` 会当场抓住它，所以这个错误几乎不可能上线——**前提是你真的跑了 `nginx -t`**。
</details>

<details>
<summary><b>6. 什么是上下文继承？如果 <code>http</code> 层写了 <code>sendfile on</code>，<code>location</code> 里能用上吗？</b></summary>

**能。** 内层上下文自动继承外层的指令，不用重写。

本项目的 `location /api/` 里一个字都没提 `sendfile`、`keepalive_timeout`、`root`、`gzip`，但它们全都生效——分别从 `http` 层和 `server` 层继承下来。

这就是为什么本项目把 `gzip on`、`sendfile on` 这类全局设置写在 `http` 层：**写一次，所有 server 所有 location 通吃**。

**关键的坑**：继承是**整体覆盖**，不是合并。内层一旦写了同名指令，外层那条对它就完全失效——不是叠加，是替换。这个坑在 `proxy_set_header` 上杀伤力最大（`04` 详谈）。
</details>

<details>
<summary><b>7. <code>nginx -s reload</code> 和重启最本质的区别是什么？</b></summary>

**reload 不打断存量请求，且配置出错时能安全回退。**

reload 的流程：master 收 HUP → 重读配置（有错就放弃，老 worker 照常跑）→ fork 新 worker 用新配置 → 通知老 worker 停止接新连接 → **老 worker 把手上的请求处理完再退出**。

所以 reload 是**零停机**的，用户完全无感，一个请求都不会失败。

重启则是把进程全杀了再起：正在处理的请求**直接掐断**，用户看到连接重置；配置有语法错误时**根本起不来，站点下线**。

唯一必须用重启的场景：换了 nginx 二进制/版本本身——reload 只重读配置，不会换掉正在跑的程序。
</details>

<details>
<summary><b>8. 你改了 <code>frontend/nginx.conf</code>，然后跑了 <code>docker compose restart frontend</code>。生效了吗？</b></summary>

**没生效。**

因为 `frontend/Dockerfile:18` 是 `COPY nginx.conf /etc/nginx/nginx.conf`——配置在**构建镜像时**就被烤进镜像了。容器里的那份是镜像的一部分。

`restart` 只是把老容器停掉再启动，用的**还是同一个老镜像**，里面还是老配置。你在宿主机上改的那个源文件，容器根本不知道。

正确做法是重新构建镜像：

```bash
docker compose up -d --build
```

（线上还要先 `git push` + 服务器 `git pull`，见 `docs/09:302` 记的标准循环。）

**判断通则**：配置是 `COPY` 进去的 → 必须 rebuild；配置是 `volumes` 挂进去的 → restart 即可。本项目两份 nginx.conf 恰好一个 COPY 一个挂载，**生效方式正好相反**。
</details>

<details>
<summary><b>9. 为什么本项目是单文件，而不是官方默认的 <code>conf.d/*.conf</code>？</b></summary>

因为**只有一个网站**。

`conf.d/*.conf` 那套拆分是为了管理多个虚拟主机时互不打架——几十个站点各占一个文件，加站删站不用碰主配置。本项目就一个 server + 两个 location，拆成多文件只会让你跳着看两个文件，纯增加心智负担。

一个重要的连带后果：`frontend/Dockerfile:18` 的 `COPY nginx.conf /etc/nginx/nginx.conf` **整个覆盖**了官方镜像的默认配置，所以官方那句 `include /etc/nginx/conf.d/*.conf;` 也一起没了，`conf.d/default.conf` 里的欢迎页 server **不会生效**。

这是好事——不然那个 server 会和我们的 server 争 80 端口的默认权（`03` 讲 `default_server` 会回到这里）。
</details>

### 练习 1（数进程）

<details>
<summary><b>点开看答案</b></summary>

2 核 → `worker_processes auto` → **2 个 worker**，加上 1 个 master，共 **3 个进程**：

```
nginx: master process nginx -g daemon off;    ← root 身份
 ├── nginx: worker process                     ← nginx 用户身份
 └── nginx: worker process                     ← nginx 用户身份
```

（`daemon off;` 是官方镜像的启动参数——容器里主进程不能后台化，否则容器会立刻退出。这一点 `learning-docker` 讲容器主进程时提过。）

**一个 worker 崩溃**：master 会立刻 fork 一个新 worker 补上，站点**不受影响**（那个 worker 上正在处理的请求会失败，但新请求正常）。这正是 master-worker 模型的容错价值。

顺带：如果是 **master 崩溃**，容器主进程就没了，容器退出。这时 `restart: unless-stopped`（`deploy/docker-compose.yml:96`）会把整个容器重新拉起——这是第二道保险。
</details>

### 练习 2（算连接）

<details>
<summary><b>点开看答案</b></summary>

分两部分算：

**客户端侧连接**：100 人 × 6 条 = **600 个连接**。

**上游侧连接**：每人平均 2 条正在请求 `/api/**`，每条反代请求会让 nginx 额外建一条到 backend 的连接 → 100 × 2 = **200 个连接**。

**合计：600 + 200 = 800 个连接。**

**上限**：2 核 × 1024 = **2048**。

所以占用约 **800 / 2048 ≈ 39%**，还有六成余量。

但真正该说的是：**这个计算本身就是学院派的**。100 个管理员同时在线的后台系统，先趴下的一定不是 nginx，而是 backend 的线程池（Spring Boot 默认 Tomcat 200 线程）或 MySQL 的连接数。nginx 在本项目里离成为瓶颈还差得远——它扛住的连接数比后面那些能处理的多一个数量级。

**这才是关键结论**：调 `worker_connections` 从来不是本项目的性能优化方向。真要优化，往 backend 和 MySQL 看。
</details>

### 练习 3（找继承）

<details>
<summary><b>点开看答案</b></summary>

`location /` 里只写了 `try_files`，但它继承到的指令至少有 8 条：

| 继承来的指令 | 来源上下文 | 行号 |
|---|---|---|
| `default_type application/octet-stream` | `http` | 12 |
| `sendfile on` | `http` | 13 |
| `keepalive_timeout 65` | `http` | 14 |
| `gzip on` | `http` | 16 |
| `gzip_min_length 1k` | `http` | 17 |
| `gzip_types text/plain text/css ...` | `http` | 18 |
| `root /usr/share/nginx/html` | `server` | 28 |
| `index index.html` | `server` | 29 |

（外加 `include mime.types` 在第 11 行展开出来的那张 types 表。）

**其中 `root` 是最关键的一条**——`try_files $uri` 要去哪个目录底下找文件，全靠继承来的这个 `root`。`location /` 里压根没提 root，但没有它 `try_files` 就无从谈起。

这就是继承机制的价值：`root` 写在 server 层一次，两个 location 都能用。

**顺带留个伏笔**：`location /api/` 也继承了同一个 `root`，但它**根本用不上**——因为 `proxy_pass` 一旦生效，请求就转走了，压根不会去读磁盘。继承过来的指令**不一定会被用到**，这取决于这个 location 走的是哪条处理路径。`04` 会讲这个分岔。
</details>

### 练习 5（为什么先 `-t`）

<details>
<summary><b>点开看答案</b></summary>

**对了一半，而且错的那一半会要命。**

**对在哪**：`reload` 时如果配置有语法错误，master 确实会拒绝加载、保持老配置继续跑。这个保护是真实存在的，站点不会挂。

**错在哪**——三条：

1. **`reload` 的保护只覆盖 `reload` 这条路径。** 如果这次是**重启**（容器重建、机器重启、OOM 被杀后自动拉起），语法错误就意味着 **nginx 起不来，站点直接下线**。而你不知道下一次重启什么时候发生——可能是凌晨三点。**配置错误会静静潜伏，直到最坏的时机爆炸。**

2. **本项目更严重：根本没有 `reload` 这条路径。** 配置烤进镜像，改配置走的是 `up -d --build`——那是**重建容器**，等于重启。语法错了容器就起不来，**没有任何"老配置继续跑"的保护网**。所以对本项目来说，那句话的前提完全不成立。

3. **"没生效"和"生效了但不对"是两回事。** `nginx -t` 只查语法，不查逻辑。它拦不住"`proxy_pass` 手滑加了个斜杠"这种语法完全合法、行为完全错误的改动（`04` 会讲这个）。但它至少能把语法这一层的错挡在门外——这是最便宜的一道防线，没有理由不要。

**结论**：`nginx -t` 是零成本的保险。本项目由于配置烤进镜像，更实际的做法是**在开发机上先验证配置**，而不是推上去让服务器的 `--build` 来当试错场——那时候失败的代价是站点下线。
</details>
