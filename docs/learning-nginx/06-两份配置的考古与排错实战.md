## 二、并排 diff

两份文件都很短，直接摆一起看。**开头 15 行一模一样**（`user` / `worker_processes` / `error_log` / `pid` / `events` / `include` / `default_type` / `sendfile` / `keepalive_timeout`），从第 16 行开始分岔。

### 2.1 四处差异

| # | 位置 | `frontend/nginx.conf`（**线上跑的**） | `deploy/config/nginx/nginx.conf`（**遗留**） |
|---|---|---|---|
| 1 | **gzip** | ✅ 有（第 16-18 行，三条） | ❌ **完全没有** |
| 2 | **upstream 目标** | `server backend:8080;` | `server host.docker.internal:8080;` |
| 3 | **server_name** | `_` | `localhost` |
| 4 | **root / index** | ✅ 有（`/usr/share/nginx/html`） | ❌ **没有** |
| 5 | **`location /`** | `try_files $uri $uri/ /index.html;` | `return 200 'RBAC Nginx is up\n';`<br>`add_header Content-Type text/plain;` |

（`location /api/` 那一整段**两份完全相同**，一个字都不差——四个 `proxy_set_header` 加 `proxy_pass`，连缩进和对齐的空格数都一样。这本身就是证据，见 `§3.4`。）

### 2.2 这四处差异说明了什么

单看每一处都很平常，**合起来看就是一部编年史**：

```
差异 2（host.docker.internal → backend）
    ↑ 说的是："后端从【宿主机进程】变成了【容器】"

差异 4+5（没有 root、return 200  →  有 root、try_files）
    ↑ 说的是："这个 nginx 从【纯反代】变成了【发静态文件 + 反代】"

差异 1（没 gzip → 有 gzip）
    ↑ 说的是："它开始发大文件了，需要压缩了"（纯反代时没什么好压的）

差异 3（localhost → _）
    ↑ 说的是："从【本机开发】变成了【对外服务，不挑域名】"
```

**四处差异，四条独立的证据，全都指向同一个结论。** 这不是巧合。

## 三、考古：三个阶段

### 3.1 阶段一：中间件在容器，应用在宿主机

**这是 `deploy/config/nginx/nginx.conf` 诞生的年代。**

那时候的架构：

```
开发者的 Mac
├── docker: mysql:3306, redis:6379          ← 只有中间件在容器里
├── 宿主机进程: Spring Boot :8080            ← 后端直接 mvn spring-boot:run
└── 宿主机进程: Vite dev server :5173        ← 前端 npm run dev
```

**证据链**（每一条都能在仓库里查到）：

1. **`docs/01-环境搭建.md`** 把 nginx 列在 `--profile extra` 的"**扩展层**"里，和 rabbitmq 并列——**它当时不是必需品，是个可选的玩具**。
2. **`deploy/docker-compose.yml:6-9`** 那段注释至今还写着：
   ```
   #   核心层（默认，无 profile）：mysql、redis
   #   扩展层（--profile extra）  ：nginx、rabbitmq
   ```
   **核心层里没有 backend 和 frontend** —— 因为那时候它们根本不在容器里！
3. **`host.docker.internal:8080`** 这个地址是**决定性证据**。这是 Docker Desktop 提供的特殊域名，专门用来让**容器访问宿主机**。用它就等于宣告："我要连的那个后端，**跑在宿主机上，不在容器里**"。
4. **`server_name localhost`**（`03 §3.5` 提过）：访问方式是 `http://localhost`，Host 头就是 `localhost`，精确匹配。
5. **没有 `root`，`location /` 返回 `RBAC Nginx is up`**：它**根本不发前端**（前端在 Vite dev server 上），所以根路径没东西可发，就返回一句话证明自己活着。**它是个纯反代 + 健康探针**。
6. **没有 gzip**：纯反代，没有大的静态文件要压。

**这份配置在它的年代是完全正确的。** 每一行都恰如其分。

### 3.2 阶段二：前后端全部容器化

**这是 `frontend/nginx.conf` 诞生的年代**（2026-07-14 前后，见 `docs/09` 的记录时间）。

要上线了，于是：

- 后端打成 jar 塞进容器 → `backend` 服务
- 前端 `npm run build` 打成 dist，塞进 nginx 镜像 → `frontend` 服务
- compose 里新增这两个服务（`docs/09:83` 的改动清单第 5 项）

**于是每一处差异都有了解释**：

| 差异 | 为什么变 |
|---|---|
| `host.docker.internal:8080` → `backend:8080` | 后端进容器了，**在同一个 `rbac-net` 里，用服务名直连**（`04 §2.1`）。`host.docker.internal` 不但没必要，而且**指向的宿主机上根本没有 8080**（`docker-compose.yml:87` 那行注释：不映射 8080 到宿主机） |
| 没有 root → `root /usr/share/nginx/html` | 前端 dist 被 `COPY` 进镜像了（`frontend/Dockerfile:19`），**这个 nginx 现在要发静态文件了** |
| `return 200 'RBAC Nginx is up'` → `try_files $uri $uri/ /index.html` | 从"健康探针"升级成"SPA 服务器"。`try_files` 是 SPA 的命门（`03 §5.3`） |
| 没有 gzip → 有 gzip | 现在要发几百 KB 的 Vue bundle 了，**压缩的收益突然变得巨大**（`02 §6.2`） |
| `localhost` → `_` | 要对外服务了，用 IP 或域名访问，Host 五花八门，**索性不挑**（`03 §3.3`） |

**关键问题：为什么不直接改那份旧的，而要新建一份？**

答案在 `docs/09-部署上线指南.md:123`，这句话是整个考古的**核心物证**：

> 说明：前端镜像里内置 nginx 并托管 `dist`，同时承担 `/api/` 反代。也可让前端只发静态文件、由独立 nginx 容器统一入口——**两种都行，本指南按「前端镜像即入口」写**。

**这就是分家的那一刻。**

作者在这里面临一个选择，而且他**明确意识到了这是个选择**：

```
方案 A：独立 nginx 容器统一入口       → 继续用 deploy/config/nginx/nginx.conf
方案 B：前端镜像内置 nginx           → 需要一份新配置，放在 frontend/ 下
                                       （因为 Dockerfile 的构建上下文是 frontend/）
```

**他选了 B**，于是诞生了 `frontend/nginx.conf`。

**而方案 A 的那份配置，没有被删。**

它就那么留在原地。compose 里那个 `nginx` 服务（`profiles: ["extra"]`）也留着。**它们不是被遗忘的，是被"暂时留着以防万一"的**——这是所有技术债最常见的出生方式。

> 🔑 **两份配置不是失误，是一次「选了 A 但没删 B」的技术债。** 那句"两种都行"是它的出生证明——作者当时确实在两个方案之间做选择，选完之后**没有回头清理未被选中的那个**。
>
> 而 `location /api/` 那一整段两份**一字不差**（连空格对齐都一样），说明 `frontend/nginx.conf` 是**从那份复制过来改的**——这是它们血缘关系的 DNA 证据。

### 3.3 阶段三：caddy 前置

**2026-07-14 晚些时候**，要上 HTTPS 了（见 `docs/ops/02-域名与HTTPS配置.md`）。

这次的改动**没有碰任何 nginx 配置**，只改了 compose（`docs/ops/02:47-50` 记得清清楚楚）：

> ### `deploy/docker-compose.yml`（关键改动）
> - `frontend` 服务：`ports: ["80:80"]` → 改为 `expose: ["80"]`（收进内网）。
> - 新增 `caddy` 服务：对外 `80:80` + `443:443`，挂载 Caddyfile，用 `caddy-data` / `caddy-config` 卷持久化证书。

**`frontend/nginx.conf` 一个字都没改。** 这正是 `00 §6` 说的那次演进的态度：**已经能跑的部分一个字都不动，只在前面加一层**。

**但代价来了**——`04 §4.5` 和 `05 §3.1` 已经详细讲过：

```nginx
proxy_set_header X-Forwarded-Proto $scheme;
```

这一行在**阶段二是完全正确的**（nginx 直接对外，$scheme 就是用户的协议）。到了**阶段三就静默地错了**（caddy 终结 TLS，nginx 收到的永远是 http）。

> 🔑 **没有任何一次提交引入了这个 bug。** `git blame` 会显示这一行从阶段二写下来就没动过，而且**当时是对的**。引入 bug 的是**一次它没有参与的架构变更**。
>
> 这就是配置漂移的本质：**代码没动，正确性却悄悄失效了**。它比"写错了"难发现一万倍——因为所有的代码审查、所有的 git 历史、所有的测试，都不会指向它。

## 四、真实的坑：抢 80 端口

这是那份遗留配置**现在的实际危害**——它不只是"没用"，它是**会炸的**。

### 4.1 证据

`deploy/docker-compose.yml` 里，两个服务都要宿主机的 80：

```yaml
  # ==================== 扩展层（--profile extra） ====================
  nginx:
    image: nginx:1.27
    container_name: rbac-nginx
    profiles: ["extra"]
    restart: unless-stopped
    ports:
      - "80:80"                    # ← 它要 80
    volumes:
      - ./config/nginx/nginx.conf:/etc/nginx/nginx.conf:ro
    networks: [rbac-net]
```

```yaml
  caddy:
    image: caddy:2.8
    container_name: rbac-caddy
    restart: unless-stopped
    ports:
      - "80:80"                    # ← 它也要 80
      - "443:443"
```

**一台机器上，同一个端口只能有一个进程监听。**

### 4.2 什么时候会炸

`nginx` 服务带着 `profiles: ["extra"]`，所以**默认不启动**。只有显式激活 extra profile 才会起：

```bash
docker compose --profile extra up -d
```

而 `docker-compose.yml:13` 的注释里，**明明白白写着这条命令**：

```
#   核心+扩展   : docker compose --profile extra up -d
```

**在生产机上跑这条命令**（比如某天想起来"要不加个 rabbitmq 试试"，因为 rabbitmq 也在 extra 里）：

```
Error response from daemon: driver failed programming external connectivity
on endpoint rbac-nginx: Bind for 0.0.0.0:80 failed: port is already allocated
```

**`port is already allocated`** —— 这个错误 `learning-docker 01` 的课堂答疑 Q1 就讲过，学习者本人也在做 `docker run mysql` 实验时**亲手踩过**（3306 被占，换成 13306）。

**这次的区别是**：那次是实验，这次是**生产机**。

### 4.3 最坏的情况

`docker compose --profile extra up -d` 失败时，**它已经做了一部分事**。具体行为取决于 compose 版本和启动顺序，但存在这样的风险：

- 如果 compose 决定先停掉/重建某些容器再启动 nginx，而 nginx 起不来 → **部分服务处于停止状态**
- 如果 caddy 因为某种原因被重建 → **证书重新申请** → 可能触发 LE 限流（`05 §3.4`）

**更现实的场景**：运维看到报错，第一反应是"80 被占了？那是谁占的？" → 一查是 caddy → "那我先停了 caddy 再起"：

```bash
docker compose stop caddy               # ← 站点【立刻全站下线】
docker compose --profile extra up -d    # 现在 nginx 起来了
# → 但 caddy 停了 → 没有 HTTPS → 没有对外入口 → 站点还是打不开
# → 而且 rbac-nginx 用的是那份【指向 host.docker.internal 的遗留配置】
# → 就算你访问 http://IP，也是 502（宿主机上根本没有 8080）
```

**一步错，步步错。** 而这一切的起点，只是想加个 rabbitmq。

### 4.4 已有的记录

`learning-docker 06 §2.6` **已经把这个坑写成过一节**，标题就叫「一个真实的坑：nginx 和 caddy 抢 80」。`learning-docker 07:451` 排错清单里也有端口冲突这一条。

**所以这个坑是已知的、被记录过的、但至今没修的。**

> 🔑 **一个"默认不启动"的服务，看起来无害，实际上是个地雷**——因为 `profiles` 只是让它"不自动启动"，**不是让它"不能启动"**。而 compose 文件的注释里还**主动教你怎么启动它**（`:13`）。
>
> 这是技术债最阴险的形态：**它不会自己爆炸，它等着某个不知情的人来踩**。而那个人手里拿着的，正是这份 compose 文件的注释当说明书。

## 五、文档漂移：`docs/09` 至今在指错路

`00 §3.2` 提过一次，这里集中清算。

### 5.1 四处漂移

| # | 位置 | 文档说 | 实际是 | 危害 |
|---|---|---|---|---|
| 1 | `docs/09:22-26` | 架构图：`浏览器 ──80/443──> nginx 容器` | **caddy 才是入口**，nginx 在内网 | 建立错误的心智模型 |
| 2 | `docs/09:42` | 「nginx 是整个部署的唯一入口（占 80/443）」 | 同上 | 同上 |
| 3 | `docs/09:47` `:81` | 指导你去改 **`deploy/config/nginx/nginx.conf`**：「上服务器要把反代目标改成后端服务名 `backend:8080`，并补上发前端的 `location /`」 | **那是遗留文件，改了完全没用** | ⚠️ **最严重** |
| 4 | `docs/09:119` | `COPY deploy/config/nginx/nginx.conf /etc/nginx/nginx.conf`<br>配合 `:173-174` 的 `context: ..` + `dockerfile: frontend/Dockerfile` | 实际是 `frontend/Dockerfile:18` 的 `COPY nginx.conf ...`<br>配合 `docker-compose.yml:92-93` 的 `context: ../frontend` | 照抄会构建失败 |
| 5 | `docs/09:178` | `frontend` 服务 `ports: - "80:80"  # 唯一对外暴露的端口` | 已改为 `expose: ["80"]` | 照抄会和 caddy 抢 80 |

### 5.2 第 3 条为什么最严重

设想一个新人接手这个项目。他做了**完全正确**的事：

```
① 读 docs/09-部署上线指南.md（这是项目的官方部署文档，还能读什么？）
② 读到 §3.2（:47）："现有 deploy/config/nginx/nginx.conf 里已有 /api/ 反代那段，
   但：① 缺发前端静态文件的部分；② upstream 指向 host.docker.internal:8080
   （本地开发接法）。上服务器要把反代目标改成后端服务名 backend:8080，
   并补上发前端的 location /。"
③ 他打开那个文件一看：【全对上了！】
   - 确实有 /api/ 反代那段 ✔
   - 确实缺 location / 发静态文件 ✔
   - 确实指向 host.docker.internal ✔
   → 文档描述得【分毫不差】，他有 100% 的理由相信这就是要改的文件
④ 他认认真真改好，加上 root、try_files、把 upstream 改成 backend:8080
⑤ 提交、推送、服务器 git pull、docker compose up -d --build
⑥ 【什么都没变】
```

**为什么什么都没变？** 因为线上跑的是 `frontend/nginx.conf`，他改的那份**根本没被任何正在运行的容器加载**（那个 `nginx` 服务是 `profiles: ["extra"]`，默认不启动）。

**他现在的处境**：

- 改动是**正确的**（他改对了每一处）
- 文档是**支持他的**（每一句都对上了）
- 文件是**真实存在的**（不是他找错了）
- 结果是**零效果**（一点变化都没有）

**他会怀疑什么？** 会怀疑构建缓存、怀疑 git 没推上去、怀疑 docker 没重新构建、怀疑挂载没生效……

**他唯一不会怀疑的，是"文档指错了文件"。**

> 🔑 **文档漂移比代码 bug 更坑人，因为 bug 只是不工作，漂移的文档会主动把人带进沟里。**
>
> 更要命的是：**这份文档的描述和那个文件完美吻合**（确实缺 location /、确实指向 host.docker.internal）。这种"局部完全自洽"制造了**极强的确信感**——它不是模糊地误导，它是**精确地误导**。
>
> 文档没说谎，它只是**停在了 2026-07-14 的上午**。而世界在那天下午变了两次（阶段二、阶段三）。

### 5.3 为什么会漂移

不是因为作者不负责。看时间线：

```
2026-07-14 上午：写 docs/09（记录时间就写在 :3）  ← 那时描述的架构是【计划中的】
2026-07-14 白天：实施阶段二 —— 但实施时【选了另一个方案】（:123 那句"两种都行"）
                  → 文档写的是方案 A，实施的是方案 B
                  → 【文档在落地的那一刻就已经和现实分叉了】
2026-07-14 晚上：实施阶段三（caddy）
                  → 另写了 docs/ops/02 记录，【但没回头改 docs/09】
                  → 分叉扩大
```

**第一次漂移发生在"写文档"和"写代码"之间**——文档是**设计意图**，代码是**实施结果**，而实施时改了主意（`:123` 那句"两种都行，本指南按前端镜像即入口写"其实是**文档在为自己开脱**：它意识到有两种方案，但它描述的部署步骤（`:47`、`:81`）却还停在方案 A 上）。

**第二次漂移发生在架构变更时**——写了新文档（`docs/ops/02`）记录新架构，**但没有回头更新旧文档**。于是仓库里同时存在两份互相矛盾的权威文档，**而且都没标注哪份是最新的**。

> 🔑 **文档漂移的根因不是"忘了改"，是"没有单一事实来源"。** `docs/09` 和 `docs/ops/02` 描述的是同一个系统的**同一件事**（部署架构），但它们是两个独立的文件，各自记录自己那一刻的真相。**没有任何机制让它们保持一致。**
>
> **配置文件不会漂移**——因为它就是运行的那个东西，它不可能和自己不一致。**这就是为什么本系列反复强调"以配置文件为准，文档只是旁证"**（`00` 自检 5 的结论）。

## 六、排错实战

不敲命令，练的是**定位思路**。核心方法：**从症状反推到链路上的哪一跳**。

### 6.1 先建立链路地图

排任何问题之前，先把这张图摆在面前：

```
浏览器 ──①──► caddy ──②──► nginx ──③──► backend ──④──► mysql/redis
        :443          :80          :8080
```

**每个症状都对应链路上的某一段。** 第一步永远是**缩小到哪一跳**。

### 6.2 症状 → 怎么查

| 症状 | 最可能的一跳 | 第一步查什么 | 常见原因 |
|---|---|---|---|
| **整站打不开**（连接超时/拒绝） | ① | 安全组、caddy 容器状态 | caddy 没起 / 端口没放行 / DNS 没解析 |
| **证书错误/不安全警告** | ① | `docker compose logs caddy` | 证书申请失败（DNS 没生效、80 没开）/ 续期失败 / LE 限流 |
| **页面正常，API 全 502** | ③ | **`docker compose logs frontend`**（nginx 的 error.log） | backend 没起 / 还在启动 / DNS 解析不了 / 用错了配置文件 |
| **页面正常，API 全 404** | ③ | **后端收到的路径是什么** | ⚠️ `proxy_pass` 加了尾斜杠（`04 §3.3`）/ context-path 变了 |
| **API 慢，最后 504** | ③④ | `$upstream_response_time`（如果配了 log_format） | 慢 SQL / 连接池耗尽 / 死锁 |
| **刷新页面 404，点链接正常** | ② | nginx 有没有 `try_files` | SPA 回退没配（`03 §5.3`）|
| **静态资源 403** | ② | 文件权限 | `nginx` 用户读不了（`01 §2.1`）/ 目录没有 x 权限 |
| **访问站点变成下载文件** | ② | 响应头的 `Content-Type` | `include mime.types` 丢了（`02` 练习 1）|
| **看到 "Welcome to nginx!"** | ② | 镜像里 `/usr/share/nginx/html` 有什么 | dist 没 COPY 进去（`03` 练习 5）|
| **上传大文件 413** | ② | `client_max_body_size` | 默认 1m（`05 §4.4`）|
| **改了配置没生效** | ② | **是 COPY 还是 mount** | 没 `--build`（`01 §5.3`）|
| **JS 报 `Unexpected token '<'`** | ② | 那个 JS 请求的响应体 | 静态资源 404 被 `try_files` 兜底成了 index.html（`03` 练习 6）|

### 6.3 三条通用原则

**原则一：先看 nginx 的 error.log，它通常把答案写在脸上。**

```bash
docker compose logs --tail=50 frontend
```

502 时它会明确告诉你：

| error.log 里的话 | 意思 |
|---|---|
| `connect() failed (111: Connection refused)` | 地址对，但**没人监听**（backend 没起 / 端口不对） |
| `backend could not be resolved` | **DNS 问题**（不在同一网络 / 服务名拼错） |
| `no live upstreams` | 所有上游都被标记失败 |
| `upstream timed out` | 这是 **504**，不是 502 —— 连上了但太慢 |
| `client intended to send too large body` | **413**，`client_max_body_size` 拦的 |

`04` 练习 6 的结论：**排 502 别急着猜，先看 error.log。**

**原则二：确认"上游到底收到了什么"。**

`04` 练习 1 的结论。不要从"后端为什么这么响应"开始猜，先确认**它收到的请求是不是你以为的那个**。这一步能省掉 90% 的弯路——尤其是 `proxy_pass` 斜杠那类"路径在半路被改了"的问题。

**原则三：机器全绿不代表没事。**

本系列出现过至少四个"**所有指标健康、但提供的是错误的东西**"的故障：

| 故障 | `docker compose ps` | `nginx -t` | error.log | 用户看到 |
|---|---|---|---|---|
| `proxy_pass` 多个斜杠（`04` 练习 1） | ✅ Up | ✅ ok | ✅ 干净 | ❌ API 全 404 |
| dist 没 COPY 进去（`03` 练习 5） | ✅ Up | ✅ ok | ✅ 干净 | ❌ Welcome to nginx! |
| `mime.types` 丢了（`02` 练习 1） | ✅ Up | ✅ ok | ✅ 干净 | ❌ 站点变下载器 |
| keepalive 少两行（`04` 练习 7） | ✅ Up | ✅ ok | ✅ 干净 | 😐 性能没变（永远发现不了） |

> 🔑 **`nginx -t` 只查语法，不查逻辑**（`01` 练习 5）。**容器 Up 只说明进程活着，不说明它在干对的事。** 验证配置的唯一可靠手段是**观察实际行为**：`curl -I` 看响应头、看后端收到的路径、看实际的连接状态。**配置文件不是事实，运行时行为才是**（`04` 练习 7 / `05` 练习 6 的共同结论）。

### 6.4 本项目特有的第一嫌疑人

```
❓ 改了 nginx 配置没生效
   → 你改的是哪份？（frontend/ 还是 deploy/config/？）
   → 是 COPY 还是 mount？→ COPY 就必须 --build（01 §5.3）

❓ 502
   → 先 logs frontend 看 error.log
   → 如果 upstream 指向 host.docker.internal → 【你用错配置文件了】

❓ 端口被占
   → 是不是跑了 --profile extra？→ nginx 服务在跟 caddy 抢 80（§4）
```

`learning-docker 07:459` 排 502 时的原话，可以当口诀：

> **"那两个 nginx.conf 别弄混"**

### 7.2 逐条展开

---

**① 删除遗留 nginx 服务与配置** —— 优先级：**高**

- **改什么**：删 `deploy/config/nginx/` 整个目录；删 `deploy/docker-compose.yml:121-130` 的 `nginx` 服务；改 `:8` 那行注释（扩展层里去掉 nginx）。
- **理由**：它**没有任何用途**（线上从没跑过），但**有真实危害**（和 caddy 抢 80，`§4`），还**持续制造混淆**（`docs/09` 指错路的根源之一，`learning-docker 07` 都要专门叮嘱"别弄混"）。**纯负债，零资产。**
- **影响面**：无。它从来没被启动过。
- **风险**：**极低**。唯一要确认的是没有别的地方引用它——已确认没有（只有 `docs/01` 和 `docs/09` 提到，那些正好也要改）。
- **注意**：`rabbitmq` 也在 `extra` profile 里，删 nginx 服务时**别误删 rabbitmq**，profile 本身要保留。

---

**② 修 `docs/09` 的四处漂移** —— 优先级：**高**

- **改什么**：见 `§5.1` 那张表的五处（架构图、"唯一入口"、指错文件 ×2、Dockerfile 示例、compose 示例）。
- **理由**：**它正在主动误导任何一个接手项目的人**（`§5.2` 那个推演）。而且这是**唯一的官方部署文档**，新人一定会读它。
- **影响面**：纯文档。
- **风险**：**零**。
- **建议做法**：与其逐条修补，不如在 `docs/09` 开头加一个醒目的**架构变更说明**，指向 `docs/ops/02`，然后修掉那几处会导致"改错文件"的致命项（`:47`、`:81`）。**根治的办法是让架构描述只有一个来源**——但那是更大的重构。

---

**③ 修 IP 传递链路** —— 优先级：**中高**（是三个功能的共同地基）

- **问题**：nginx 的 `$remote_addr` 恒等于 caddy 的 IP（`04 §4.3`）；`X-Forwarded-For` 可被任意伪造（`04` 练习 4）。**当前没有任何一个可信的真实客户端 IP 来源。**
- **卡住了三个功能**：
  - **登录限流**（`05` 练习 4）：用 `$remote_addr` → 一键 DoS 自己；用 XFF → 可绕过。两条路都不通。
  - **操作日志的 IP 审计**：现在记的要么是 caddy 的内网 IP（无意义），要么是可伪造的 XFF（**可栽赃**）。对一个 RBAC 系统，**审计日志的 IP 不可信 = 这个字段在法律意义上归零**。
  - **未来的 IP 白名单 / 异地登录告警**：同样不可信。
- **推荐方案**：**在 caddy 那一层做需要真实 IP 的事**。caddy 是唯一见得到真实 `$remote_addr` 的跳（那是 TCP 连接的源地址，**伪造不了**）。
  - 限流直接在 caddy 做。
  - 需要传给后端的话，让 caddy 写一个**下游不可覆盖的专用头**（如 `X-Client-IP`，强制覆盖而非追加），nginx 原样透传，后端只信这个头。
- **影响面**：caddy 配置 + nginx 配置 + 后端读 IP 的代码。
- **风险**：中。改动跨三个组件，需要一起验证。
- **原则**：**把判断收敛到唯一有资格判断的那一跳。**

---

**④ 修 `X-Forwarded-Proto`** —— 优先级：**中**（前置债务）

- **问题**：`proxy_set_header X-Forwarded-Proto $scheme;` 恒为 `http`（`04 §4.5`）。已被 `docs/ops/02:97` 记录在案。
- **当前无害**：JWT 放请求头，没人读这个头。
- **什么时候必须修**：上 **Secure Cookie**（登录会直接失效）或**后端生成绝对 URL**（OAuth 回调会硬失败）之前。
- **改法**：
  ```nginx
  map $http_x_forwarded_proto $real_scheme {
      default $http_x_forwarded_proto;   # 优先用 caddy 传来的
      ""      $scheme;                   # caddy 没传时回落
  }
  ...
  proxy_set_header X-Forwarded-Proto $real_scheme;
  ```
  （caddy 的 `reverse_proxy` 默认就会设 `X-Forwarded-Proto: https`，caddy 侧不用改。）
- **影响面**：只有 nginx 配置。
- **风险**：**低**。当前没人读这个头，改了也不会破坏任何现有功能。
- **建议**：**现在就改**。风险极低，而且能消除一个"等着坑未来的自己"的定时炸弹。改完在注释里写清为什么。

---

**⑤ 静态资源 `expires` 缓存** —— 优先级：中

- **改法**（`02 §7.3` + `03` 练习 6）：
  ```nginx
  # ⚠️ 依赖 Vite 的内容哈希文件名，改 Vite 打包策略前先回来看这里
  location ^~ /assets/ {
      expires 1y;
      add_header Cache-Control "public, immutable";
  }
  location = /index.html {
      expires -1;
      add_header Cache-Control "no-cache";
  }
  ```
- **理由**：`docs/09:220` 早就提过要做。收益是**老用户回访时零请求**（连 304 都不发）。
- **影响面**：只有 nginx 配置。
- **风险**：**中，且有个隐藏的大坑**。`immutable` 是**不可撤销的支票**（`02` 练习 6）——它的全部安全性建立在"Vite 打包带内容哈希"这个**外部前提**上。哪天有人改了 Vite 配置去掉哈希，这套配置会造成**新旧混搭的白屏**，而且**没有解药**（用户不会自愈，你也收不回已经发出去的缓存）。
- **必须做的**：注释里写死这个依赖前提。
- **顺带收益**：`/assets/` 脱离 `try_files` 之后，缺失的静态资源会**老实 404**，而不是返回 index.html 导致 `Unexpected token '<'` 那个著名的迷惑报错（`03` 练习 6）。

---

**⑥ 零代价安全加固** —— 优先级：低（但便宜）

- **改法**：
  ```nginx
  http {
      server_tokens off;
  }
  server {
      add_header X-Content-Type-Options "nosniff" always;
      add_header X-Frame-Options        "SAMEORIGIN" always;
  }
  ```
- **理由**：当前收益接近零（nginx 在内网，响应经过 caddy）。**但代价也接近零**，而且是**纵深防御**——`05` 练习 7 演示过：只要有人把 `expose` 改成 `ports`（一次调试的手滑），nginx 立刻裸奔，这几行当场值钱。
- **风险**：**低，但有一个必须注意的坑**。`add_header` 是**整层覆盖**（`05` 练习 6）——写在 `server` 层的话，`location /api/` 里如果有任何 `add_header`，server 层这组就**全部失效**。本项目当前两个 location 都没写 `add_header`，所以直接加在 server 层是安全的。**但以后谁在 location 里加了一条 `add_header`，这些安全头就静默消失了。**
- **注意**：`always` 不能省，否则错误页不带这些头。

---

**⑦ 自定义 `log_format`** —— 优先级：低

- **改法**（`05 §2.3`）：
  ```nginx
  log_format main '$http_x_forwarded_for - $remote_user [$time_local] '
                  '"$request" $status $body_bytes_sent '
                  '"$http_referer" "$http_user_agent" '
                  'rt=$request_time urt=$upstream_response_time';
  access_log /var/log/nginx/access.log main;
  ```
- **理由**：现在日志里的 IP **全是 caddy 的内网 IP，完全没有价值**（`05` 练习 1）。加上 `$request_time` / `$upstream_response_time` 后，排查"慢"的问题时一眼就知道该找 nginx 还是找后端。
- **风险**：低。
- **注意**：日志里的 XFF **可伪造**，能用来排查，**不能用来追责**（除非先做 ③）。

---

**⑧ upstream `keepalive`** —— 优先级：**很低**

- **改法**（`04 §6.2`，三件套缺一不可）：
  ```nginx
  upstream rbac_backend {
      server backend:8080;
      keepalive 32;
  }
  location /api/ {
      proxy_http_version 1.1;
      proxy_set_header Connection "";
      ...
  }
  ```
- **理由**：现在每个 API 请求都新建 TCP 连接。
- **风险**：低。
- **但收益也极低**：内网 RTT 只有几十微秒，而本项目的量级（几十个管理员）离 `TIME_WAIT` 堆积差得远。
- **结论**：**正确但没必要。** 列在这里主要是为了说明"知道该怎么做"和"值得做"是两回事。真要做，**三件套一个都不能少**，否则是静默失效（`04` 练习 7）。

### 7.3 一个元建议

上面 8 条里，**①②** 是清理债务（该做），**③④** 是修正错误（该做），**⑤⑥⑦** 是优化（可做），**⑧** 是知识（不必做）。

但更重要的是 `05 §4.6` 和 `05` 练习 7 反复指向的那件事：

> 🔑 **本项目 nginx 的安全，依赖两个不在 nginx 配置文件里的前提**：`docker-compose.yml:97-98` 的 `expose`（而非 `ports`），以及阿里云安全组只开 22/80/443。
>
> **这两个前提没有任何机制保护自己，也不会在被违反时报警。** 而改它们的人（想调试、想加个服务），**根本不会想到自己让 nginx 裸奔了**。
>
> `learning-docker 07` 第八节已经就数据库挖出过**完全相同的模式**（mysql/redis 的安全也吊在安全组这根弦上）。**同一个故事，两个受害者** —— 这说明它是**系统性的**，不是偶发的。
>
> **最有价值的一条建议，可能是在 `docker-compose.yml` 的 `expose` 旁边加一行注释**，写清"⚠️ 改成 ports 会让 nginx 直接暴露公网且无 TLS"。它不修任何代码，但它**让下一个想改的人在改之前就看见**。

<details>
<summary><b>2. <code>host.docker.internal:8080</code> 说明了什么架构？</b></summary>

它是 Docker Desktop 提供的特殊域名，专门用来让**容器访问宿主机**。

用它就等于宣告：**"我要连的那个后端，跑在宿主机上，不在容器里。"**

这是**阶段一**的决定性证据：那时候只有 mysql/redis 在容器里，Spring Boot 是 `mvn spring-boot:run` 直接跑在开发机上的。

佐证：`deploy/docker-compose.yml:6-9` 的注释至今写着"核心层：mysql、redis"——**核心层里没有 backend 和 frontend**。
</details>

<details>
<summary><b>3. 为什么阶段二不直接改旧配置，而是新建一份？证据在哪？</b></summary>

证据是 **`docs/09-部署上线指南.md:123`**：

> 说明：前端镜像里内置 nginx 并托管 `dist`，同时承担 `/api/` 反代。也可让前端只发静态文件、由独立 nginx 容器统一入口——**两种都行，本指南按「前端镜像即入口」写**。

**这就是分家的那一刻。** 作者面临两个方案：

- 方案 A：独立 nginx 容器统一入口 → 继续用 `deploy/config/nginx/nginx.conf`
- 方案 B：前端镜像内置 nginx → **需要一份新配置放在 `frontend/` 下**（因为 Dockerfile 的构建上下文是 `frontend/`，`docker-compose.yml:92-93` 的 `context: ../frontend`）

**他选了 B**，于是诞生了 `frontend/nginx.conf`。而方案 A 那份**没被删**。
</details>

<details>
<summary><b>4. 为什么说"两份配置不是失误，是技术债"？</b></summary>

因为**作者明确知道自己在做选择**（`docs/09:123` 那句"两种都行"就是证明），他不是搞错了，是**选了 A 但没删 B**。

这是技术债最常见的出生方式：**"暂时留着以防万一"**。不是遗忘，是**主动的、看起来很谨慎的、但从未被兑现的保留**。

区别很重要：**失误**是不知道，**技术债**是知道但推迟。前者靠 review 能防，后者只能靠纪律——**而纪律通常输给"以后再说"**。
</details>

<details>
<summary><b>5. <code>location /api/</code> 两份一字不差说明什么？</b></summary>

说明 **`frontend/nginx.conf` 是从那份复制过来改的**。

**连四个 `proxy_set_header` 的空格对齐都完全一样**——这种程度的一致性不可能是独立写出来的，只能是复制粘贴。

这是它们**血缘关系的 DNA 证据**：两份配置是父子，不是兄弟。也印证了阶段二的做法是"拿旧的改"，而不是"从头写"。
</details>

<details>
<summary><b>6. 阶段三改了 nginx 配置吗？那 <code>X-Forwarded-Proto</code> 为什么变错了？</b></summary>

**没改。一个字都没改。**

`docs/ops/02:47-50` 记录得清清楚楚，阶段三只改了 compose：`frontend` 的 `ports` → `expose`，新增 `caddy` 服务。

**那为什么变错了？** 因为 `$scheme` 的语义是"**nginx 自己这一跳收到的协议**"：

- 阶段二：nginx 直接对外，用户用 HTTPS 直连它 → `$scheme` = `https` ✅ **正确**
- 阶段三：caddy 终结 TLS，用明文 http 转给 nginx → `$scheme` = `http` ❌ **错了**

> 🔑 **没有任何一次提交引入了这个 bug。** `git blame` 显示这一行从阶段二写下来就没动过，而且当时是对的。引入 bug 的是**一次它没有参与的架构变更**。
>
> 这就是配置漂移的本质：**代码没动，正确性却悄悄失效了**。所有的 code review、git 历史、测试，都不会指向它。
</details>

<details>
<summary><b>7. 遗留的 <code>nginx</code> 服务默认不启动，那还有什么危害？</b></summary>

**三条，一条比一条实在**：

1. **`profiles` 只是"不自动启动"，不是"不能启动"。** 跑 `docker compose --profile extra up -d` 它就起来了——而**这条命令就写在 `docker-compose.yml:13` 的注释里**，等于说明书在教你怎么引爆。
2. **和 caddy 抢 80**（`§4`）。两个服务都要 `ports: "80:80"`，生产机上必然 `port is already allocated`。而 rabbitmq 也在 extra 里，所以"想加个 rabbitmq"是个**非常自然的引爆动机**。
3. **持续制造混淆**。它是 `docs/09` 指错路的根源之一，`learning-docker 07:459` 排 502 时甚至要专门叮嘱"那两个 nginx.conf 别弄混"。

**一个"默认不启动"的服务，看起来无害，实际是个等人来踩的地雷。**
</details>

<details>
<summary><b>8. <code>docs/09</code> 哪一处漂移最严重？为什么？</b></summary>

**`:47` 和 `:81`** —— 指导你去改 `deploy/config/nginx/nginx.conf`。

因为它**不是模糊地误导，是精确地误导**。文档说那个文件"缺 location /、upstream 指向 host.docker.internal"——**打开一看全对上了**！

于是新人有 **100% 的理由**相信这就是要改的文件：文档是官方的、描述是精确的、文件是真实存在的、他的改动也是正确的。**唯一的问题是这个文件根本没被任何运行中的容器加载。**

这种"**局部完全自洽**"制造了极强的确信感。他会怀疑构建缓存、怀疑 git、怀疑 docker——**唯独不会怀疑文档指错了文件**。
</details>

<details>
<summary><b>9. 为什么说"文档漂移比代码 bug 更坑人"？</b></summary>

**因为 bug 只是不工作，漂移的文档会主动把人带进沟里。**

- **bug**：你做对的事，它失败了 → 你知道出问题了，开始查。
- **漂移的文档**：你按它做对了每一步，结果什么都没发生 → **你不知道自己在沟里**，你以为是别的地方出了问题，然后往错误的方向查一整天。

更要命的是**文档没说谎**——它只是停在了 2026-07-14 的上午，而世界在那天下午变了两次。它的每一句在当时都是对的。
</details>

<details>
<summary><b>10. 文档漂移的根因是什么？为什么配置文件不会漂移？</b></summary>

**根因：没有单一事实来源（single source of truth）。**

`docs/09` 和 `docs/ops/02` 描述同一个系统的同一件事（部署架构），但它们是**两个独立文件，各自记录自己那一刻的真相**，而且**没有任何机制让它们保持一致**，也没标注哪份最新。

**配置文件不会漂移**，因为**它就是运行的那个东西**——它不可能和自己不一致。运行时行为直接由它决定，它一改，行为立刻跟着变。

**这就是本系列反复强调"以配置文件为准，文档只是旁证"的根本原因**（`00` 自检 5 的结论）。

（顺带：`§5.3` 还揭示了第一次漂移发生在"写文档"和"写代码"之间——文档是**设计意图**，代码是**实施结果**，而实施时改了主意。所以漂移不只发生在"架构变更后忘了改文档"，也发生在"文档写完后实施走了另一条路"。）
</details>

<details>
<summary><b>11. 排 502 的第一步应该做什么？</b></summary>

**看 nginx 的 error.log**：`docker compose logs --tail=50 frontend`

它通常把答案直接写在脸上：

| error.log | 意思 |
|---|---|
| `connect() failed (111: Connection refused)` | 地址对但没人监听（backend 没起） |
| `backend could not be resolved` | DNS 问题（不在同一网络） |
| `no live upstreams` | 上游全被标记失败 |
| `upstream timed out` | 这其实是 504，连上了但太慢 |

**别急着猜。** 猜的成本是几小时，看日志的成本是十秒。（`04` 练习 6 的结论。）
</details>

<details>
<summary><b>12. "容器 Up + <code>nginx -t</code> 通过 + error.log 干净"能证明配置对吗？</b></summary>

**完全不能。**

本系列出现过至少四个"所有指标健康、但提供的是错误的东西"的故障：

| 故障 | ps | `nginx -t` | error.log | 用户看到 |
|---|---|---|---|---|
| `proxy_pass` 多个斜杠 | ✅ | ✅ | ✅ | ❌ API 全 404 |
| dist 没 COPY 进去 | ✅ | ✅ | ✅ | ❌ Welcome to nginx! |
| `mime.types` 丢了 | ✅ | ✅ | ✅ | ❌ 站点变下载器 |
| keepalive 少两行 | ✅ | ✅ | ✅ | 😐 性能没变（永远发现不了） |

**`nginx -t` 只查语法不查逻辑**（`01` 练习 5）；**容器 Up 只说明进程活着，不说明它在干对的事**。

唯一可靠的验证是**观察实际行为**：`curl -I` 看响应头、看后端收到的路径、看连接状态。

> 🔑 **配置文件不是事实，运行时行为才是。**（`04` 练习 7 / `05` 练习 6 的共同结论。）
</details>

<details>
<summary><b>13. 整改清单里哪条是"三个功能的共同地基"？</b></summary>

**③ 修 IP 传递链路。**

它同时卡住三个功能：

1. **登录限流**：用 `$remote_addr` → 全站共享配额，一键 DoS 自己；用 XFF → 可伪造绕过。**两条路都不通。**
2. **操作日志 IP 审计**：记的要么是 caddy 内网 IP（无意义），要么是可伪造的 XFF（**可栽赃**）。对 RBAC 系统，审计 IP 不可信 = 这个字段在法律意义上归零。
3. **未来的 IP 白名单 / 异地登录告警**：同样不可信。

**推荐解法**：在 caddy 那层做需要真实 IP 的事——它是唯一见得到真实 `$remote_addr` 的跳，而 TCP 连接的源地址**伪造不了**。

**原则：把判断收敛到唯一有资格判断的那一跳。**
</details>

<details>
<summary><b>14. 本项目 nginx 的安全依赖哪两个前提？</b></summary>

**两个都不在 nginx 的配置文件里**：

1. `deploy/docker-compose.yml:97-98` 是 `expose: ["80"]` 而非 `ports`（只在内网可达）
2. 阿里云安全组只放行 22/80/443

**任何一条被改掉，nginx 立刻裸奔**：没 TLS（token 明文传输）、没限流（可暴力破解）、没安全头、版本号暴露。（`05` 练习 7 详细推演过。）

**最可怕的是**：改这两处的人根本不会想到自己让 nginx 裸奔了——他只是想调试个东西，他改的是 compose，**在他的心智模型里这跟 nginx 的安全毫无关系**。

`learning-docker 07` 第八节就数据库挖出过**完全相同的模式**（mysql/redis 也吊在安全组这根弦上）。**同一个故事，两个受害者** —— 说明它是系统性的。
</details>

<details>
<summary><b>点开看答案</b></summary>

**A. 他会依次怀疑什么？**

| 顺序 | 怀疑 | 他会做什么 | 为什么会怀疑这个 |
|---|---|---|---|
| 1 | **Docker 构建缓存** | `docker compose build --no-cache` | 这是"改了没生效"的头号民间解法，几乎是肌肉记忆 |
| 2 | **git 没推上去 / 服务器没拉到** | `git log` 对比本地和服务器 | 第二常见。`docs/09:262` 还专门警告过这个坑 |
| 3 | **挂载没生效 / 路径不对** | `docker exec rbac-nginx cat /etc/nginx/nginx.conf` | 他会去 `rbac-nginx` 容器里看——**但那个容器根本没跑**！`docker exec` 会报 "No such container"，这会让他更困惑 |
| 4 | **自己改错了地方** | 反复检查自己的改动 | 但他改的每一处都对（文档说什么他改什么），**越查越确信自己没错** |

**注意第 3 条那个转折**：他去 `docker exec rbac-nginx` 时会撞上 "No such container"。**这其实是最接近真相的一刻**——如果他追问"为什么这个容器不存在"，就会发现 `profiles: ["extra"]`，进而发现线上跑的是 `rbac-frontend`。

**但更可能的是**：他以为自己记错了容器名，然后 `docker compose ps` 一看有个 `rbac-frontend`，就去 exec 那个——**然后看到一份完全陌生的配置**（有 root、有 try_files、有 gzip）。

**那一刻他就该醒了。** 但也可能他会想"哦原来构建时会自动加这些"，然后继续在错误的路上狂奔。

**B. 什么样的单一动作能让他立刻发现真相？**

```bash
docker exec rbac-frontend cat /etc/nginx/nginx.conf
```

**看线上容器里实际加载的配置**。

一眼就能看出：这份配置和他改的那份**完全不是一个东西**（有 root、有 try_files、有 gzip、upstream 指向 `backend`）。

**通则**：**"我改的文件" ≠ "它加载的文件"。** 排查任何"改了没生效"的问题，第一步永远是**去运行时确认它实际用的是什么**，而不是在源文件这边反复检查。

（这也是 `§6.3` 原则三"配置文件不是事实，运行时行为才是"的又一次印证。）

**C. 加一道什么防线？**

**最便宜有效的：在遗留文件的开头加一个大写警告。**

```nginx
# ⚠️⚠️⚠️ 这份配置【线上没有使用】！⚠️⚠️⚠️
#
# 线上跑的是 frontend/nginx.conf（被 frontend/Dockerfile COPY 进 rbac-frontend 镜像）。
# 这份是 --profile extra 的历史遗留（后端还跑在宿主机的年代），且它的 ports:80:80
# 会和 caddy 抢端口，在生产机上启动会失败。
#
# 改这个文件【不会对线上产生任何影响】。你要找的多半是 frontend/nginx.conf。
# 详见 docs/learning-nginx/06-两份配置的考古与排错实战.md
user  nginx;
...
```

**为什么这比改文档更有效**：

- **它在人一定会看的地方**。新人可以不读 docs，但他**必须打开这个文件才能改它**——警告直接怼在他脸上。
- **它零维护成本**。文档会漂移（这整节就是在讲这个），但这行注释**和它警告的那个文件在同一个文件里**，不可能分家。
- **它防的是动作，不是知识**。文档试图让人"知道"，注释直接拦住"做"。

**当然，最好的防线是 ①：直接删掉这个文件。** 不存在的文件不需要警告。

但如果因为某种原因暂时不能删（比如要留着参考），那这个警告就是**次优解**——而且它**五秒钟就能加上**。

> 🔑 **把警告放在"人一定会经过的地方"，而不是"人应该去读的地方"。** 这是防呆设计的核心：**不要依赖别人先读文档**。

### 练习 3（抢 80 的连锁反应）

<details>
<summary><b>点开看答案</b></summary>

**完整故障链**：

```
① 运维想加 rabbitmq，跑：docker compose --profile extra up -d
   （这条命令就写在 docker-compose.yml:13 的注释里，他没做错任何事）

② compose 开始处理所有服务。rabbitmq 起来了 ✔
   轮到 nginx：
   Error: Bind for 0.0.0.0:80 failed: port is already allocated ✘

③ 运维看到报错，第一反应："80 被谁占了？"
   docker compose ps → 看到 rbac-caddy 占着 0.0.0.0:80->80/tcp

④ 【转折点】运维决定："那我先把 caddy 停了，让 nginx 起来"
   docker compose stop caddy
   ↓
   ★★★ 站点【立刻全站下线】★★★
   （caddy 是【唯一】对外入口。它一停，443 没人听，80 也没人听）

⑤ docker compose --profile extra up -d
   → nginx 起来了，占住了 80

⑥ 运维访问 http://IP 想验证
   → nginx 收到请求 → location /api/ → upstream host.docker.internal:8080
   → 宿主机上【根本没有 8080】（docker-compose.yml:87 明确写了不映射）
   → 502 Bad Gateway
   → 而且 location / 是 return 200 'RBAC Nginx is up'
   → 他看到一行纯文本 "RBAC Nginx is up"，【没有前端页面】

⑦ 此时的状态：
   - HTTPS：❌ 没了（caddy 停了）
   - 前端：❌ 没了（nginx 那份配置不发静态文件）
   - API：❌ 502（upstream 指向不存在的宿主机 8080）
   - 用户：❌ 全部无法访问
   - 而运维本来只是想加个 rabbitmq
```

**转折点是第 ④ 步：`docker compose stop caddy`。**

**为什么这是转折点**：

- 第 ②③ 步只是**启动失败**——什么都没坏，站点还好好的，rabbitmq 也起来了。**如果他到此为止，损失为零。**
- 第 ④ 步是**主动破坏了一个正在正常工作的东西**，为了让一个**本来就不该启动的东西**启动。

**他为什么会这么做？** 因为他的心智模型里，"nginx 起不来"是个**需要解决的问题**。而他不知道：

1. 那个 nginx **根本不该启动**（它是历史遗留）
2. caddy 是**唯一对外入口**（停它 = 全站下线）
3. 就算 nginx 起来了也**没用**（配置指向不存在的宿主机 8080）

**三个关键认知，他一个都没有。** 而 `docker-compose.yml` 里**没有任何一行注释告诉他这些**——恰恰相反，`:13` 那行注释还在**主动教他跑这条命令**。

**如果还要更糟**：

第 ④ 步如果他用的是 `docker compose down` 而不是 `stop caddy`，那 `caddy-data` 卷虽然还在（`down` 不删卷），但**如果他手滑加了 `-v`**（`docs/09:202` 警告过），证书就没了 → 重建后重新申请 → **反复几次触发 LE 限流** → **等一周**（`05 §3.4`）。

**从"想加个 rabbitmq"到"站点一周内无法上 HTTPS"，中间只隔了三个看起来都很合理的决定。**

> 🔑 **这道题的意义**：`§4` 说那个遗留服务"是个等人来踩的地雷"。这就是踩响的全过程——而**踩的人没做错任何事**，他跑的命令就写在项目自己的注释里。
>
> **技术债的伤害不是它自己造成的，是它诱导正常人做出的连锁决定造成的。**
</details>

### 练习 4（给整改清单排序）

<details>
<summary><b>点开看答案</b></summary>

**半天，只能做 3 条。我选 ①②④。**

**① 删除遗留 nginx 服务与配置** —— 半小时

- **理由**：**它是纯负债，零资产**。删了立刻消除：抢 80 的地雷（练习 3 那整条故障链）、`docs/09` 指错路的根源、"两个 nginx.conf 别弄混"的持续混淆。
- **风险最低**：它从来没被启动过，删了不可能破坏任何东西。
- **收益/风险比最高**，没有之一。

**② 修 `docs/09` 的漂移** —— 一小时

- **理由**：它**正在主动误导每一个接手项目的人**（`§5.2`）。而且这是**唯一的官方部署文档**，新人一定会读。
- **和 ① 是配套的**：删了那个文件，`docs/09:47` 指向的东西就不存在了——**必须一起改，否则文档会从"指错文件"变成"指向不存在的文件"**（虽然那样反而更容易发现，但太恶劣了）。
- **风险为零**（纯文档）。

**④ 修 `X-Forwarded-Proto`** —— 一小时（含验证）

- **理由**：改动极小（加个 `map` + 改一行），**风险极低**（当前没人读这个头，改了不可能破坏现有功能），但它**拆掉了一个等着坑未来的定时炸弹**。
- **关键判断**：这是**唯一一条"现在改零风险、以后改可能已经出事了"的**。等到上 Secure Cookie 那天再改，就是在**一边调试登录失效一边改 nginx**——那时候压力大得多，而且很可能根本想不到是这里。
- **现在改，还能在注释里从容地写清为什么。**

**为什么不选 ③（修 IP 传递链路）？**

它优先级更高（中高 > 中），但：

- **改动跨三个组件**（caddy + nginx + 后端代码），半天做不完，做一半更危险
- **需要仔细验证**，否则可能把日志/限流搞得更乱
- **它是"地基"，适合作为一个独立的、有充分时间的任务**

**半天时间做 ③ 属于"时间不够但硬上"**，违反了"要么做完要么别开始"的原则。

---

**如果产品明天要上"记住我"（Secure Cookie），选择怎么变？**

**④ 从"该做"变成"必须做，且是第一优先级"，甚至 ③ 也要跟上。**

推演一下不做会怎样：

```
① 后端下发 Secure Cookie
② Spring Security 检查 X-Forwarded-Proto → 看到 "http"
③ → 判定连接不安全 → 【拒绝下发 Secure Cookie】
④ → 用户登录后拿不到 token → 【"记住我"功能完全不工作】
⑤ → 更糟：可能连普通登录都跟着挂（如果一起改成了 Cookie 认证）
```

**而且这个故障极难定位**：前端开发会说"后端没返回 Cookie"，后端开发会说"我明明 set 了"——**因为 Spring 是在框架层静默丢弃的，业务代码里看不到**。查到 nginx 那一行要绕一大圈。

**新的排序**：

| | 做什么 | 理由 |
|---|---|---|
| 1 | **④ 修 `X-Forwarded-Proto`** | **不做的话"记住我"根本不工作。这是硬阻塞。** |
| 2 | **① 删遗留配置** | 半小时，顺手清掉，避免改 nginx 时又把两份搞混（**这时候尤其危险**：正在改 nginx 配置的人最容易改错文件） |
| 3 | **③ 修 IP 传递链路** | Cookie 认证会让"会话劫持"的风险上升 → 需要能审计"这个会话从哪个 IP 来" → **而现在的 IP 是不可信的**。虽然半天不够，但**必须立刻排期** |

**② 修文档**这时候反而可以往后放——它重要，但它不阻塞明天的功能。

> 🔑 **这道题的意义**：整改清单的优先级**不是固定的，它是需求的函数**。
>
> ④ 在今天是"中优先级、可选"，在明天上 Cookie 时就是"**硬阻塞、必须先做**"。而它的**改动内容一个字都没变**——变的只是"什么时候做"的代价。
>
> **这就是"前置债务"的定义**：它现在很便宜，以后会变得很贵，而且**变贵的那一刻恰好是你最忙的时候**。
</details>

### 练习 5（漂移检测）

<details>
<summary><b>点开看答案</b></summary>

**方案 A：让文档引用配置，而不是复制配置**

**做法**：`docs/09` 里不再**粘贴** nginx.conf / Dockerfile / compose 的片段，改为**引用**：

```markdown
### nginx.conf 关键片段

见 `frontend/nginx.conf` —— 逐行讲解见 docs/learning-nginx/。
不要在这里复制配置内容。
```

**为什么有效**：`docs/09:125-150` 那 26 行粘贴的 nginx.conf、`:107-121` 粘贴的 Dockerfile、`:154-181` 粘贴的 compose——**它们全都是漂移的载体**。粘贴的那一刻就产生了副本，而副本**必然会和原件分叉**（只是时间问题）。

**代价**：
- 文档的**自包含性下降**——读者要跳去看另一个文件，不能一口气读完。
- 对"设计文档"这个体裁是**减分**的：`docs/09` 的价值之一就是"给你一个可以照抄的模板"。引用之后，这个价值没了。

**方案 B：CI 校验**

**做法**：加一个 CI 检查，如果 `frontend/nginx.conf`、`frontend/Dockerfile`、`deploy/docker-compose.yml` 有改动，而 `docs/09-部署上线指南.md` 没有同步改动 → **CI 失败**（或至少打个 warning）。

```yaml
# 伪代码
- name: 检查部署文档是否同步
  run: |
    if git diff --name-only origin/main | grep -qE '(frontend/nginx.conf|frontend/Dockerfile|deploy/docker-compose.yml)'; then
      if ! git diff --name-only origin/main | grep -q 'docs/09-部署上线指南.md'; then
        echo "::warning::改了部署相关配置，但没改 docs/09。确认文档是否需要同步？"
      fi
    fi
```

**为什么有效**：它**在漂移发生的那一刻就抓住**，而不是等半年后某个新人踩坑。它把"记得改文档"这件事从**人的美德**变成了**流水线的约束**。

**代价**：
- **误报**：改个空格、改个注释也会触发 → 久而久之大家学会无视这个 warning → **失效**（这是所有"提醒型"CI 检查的宿命）。
- **它检查不了正确性**：它只能确认"文档被改过了"，不能确认"改对了"。有人可以改个错别字来糊弄它。

**方案 C（我更推荐）：标注时效性 + 单一入口**

**做法**：

1. **每份架构类文档开头强制标注适用版本/日期**（`docs/09:3` 其实已经有"记录时间：2026-07-14"了 —— **但没人当回事，因为没有对照物**）。
2. **建一个 `docs/00-架构现状.md` 作为唯一入口**，它是**唯一**描述"当前架构长什么样"的文档。其他所有文档（包括 `docs/09`、`docs/ops/02`）都降级为"**某次变更的施工记录**"，开头统一写：

   ```markdown
   > ⚠️ 这是 2026-07-14 那次部署的施工记录，不代表当前架构。
   > 当前架构见 `docs/00-架构现状.md`。
   ```

**为什么有效**：它**承认了施工记录必然会过期**，然后把"当前是什么样"这个问题**收敛到唯一一个地方**。

`docs/09` 和 `docs/ops/02` 都不再假装自己描述现状——它们只是历史。**历史是不会漂移的，因为历史本来就不该更新。**

**代价**：
- 要新写一份文档，并且**维护它**（但只有一份，成本可控）。
- 需要一次性给所有存量文档加免责声明。

---

> 🔑 **三个方案的共同思路：不要试图让人"更认真"，要让漂移在结构上变得不可能或立刻可见。**
>
> - A 让副本不存在（**没有副本就没有分叉**）
> - B 让分叉立刻报警（**但会被无视**）
> - C 让"现状"只有一个来源，其余的**明确降级为历史**（**而历史不需要同步**）
>
> **C 最贴合本项目的实际**：因为 `docs/09` 和 `docs/ops/02` 的真实身份**本来就是施工记录**（它们详细记录了"那天踩了哪些坑、怎么解决的"——`docs/09:283-296` 那张踩坑表就是纯历史，**极有价值且不该更新**）。
>
> **它们的问题不是"过期了"，是"假装自己是现状"。** 给它们一个诚实的身份，问题就解决了一大半。
</details>

### 练习 6（排错推演）

<details>
<summary><b>点开看答案</b></summary>

**关键信息：页面正常 + API 全 404（不是 502）。**

这两条信息价值极大：

- **页面正常** → caddy ✔、nginx ✔、`location /` ✔、dist ✔、静态链路完好
- **API 是 404 而不是 502** → nginx **连上 backend 了**（连不上是 502）→ **backend 活着**
- **404 是谁返回的？** → 要么是 backend 说"没这个路由"，要么是 nginx 当静态文件找不到

**范围已经缩到：nginx → backend 这一跳的"路径"上。**

**第一嫌疑人：`proxy_pass` 的尾斜杠**（`04 §3.3`）。

**排查步骤**：

```
① 确认后端收到的路径是什么   ← 【最关键的一步】
   docker compose logs --tail=50 backend
   → 看 Spring Boot 的访问日志里，请求路径是 /api/users 还是 /users？
   → 如果是 /users → 【破案】：proxy_pass 多了个斜杠
   → 如果是 /api/users → 那是后端自己的问题，转 ④

② 如果后端日志里【什么都没有】
   → 说明请求压根没到 backend
   → 那这个 404 是 nginx 自己返回的！
   → 检查 location 匹配：是不是有人加了正则 location 把 /api/ 截胡了？（03 练习 2）
   → docker exec rbac-frontend cat /etc/nginx/nginx.conf

③ 确认线上加载的配置
   docker exec rbac-frontend cat /etc/nginx/nginx.conf | grep -A2 proxy_pass
   → 一眼看出斜杠有没有

④ 如果路径确实是 /api/users 但后端还是 404
   → 是后端的问题：context-path 改了？Controller 没注册？
   → 查 application.yml 的 context-path 和 Controller 注解
```

**为什么第 ① 步最关键**：

`04` 练习 1 的结论——**排查反代问题的第一原则：确认"上游到底收到了什么"。**

不要从"后端为什么 404"开始猜（那会让你去查 Controller、查注解、查 Security 配置，一整天）。**先确认它收到的请求是不是你以为的那个**。

一旦看到"后端收到的是 `/auth/login` 而不是 `/api/auth/login`"，方向立刻就对了——**路径在半路被改了，那只能是 nginx 干的**。

**三个最可能的原因**（按可能性排序）：

| # | 原因 | 特征 |
|---|---|---|
| 1 | **`proxy_pass` 多了尾斜杠**（`04 §3.3`） | 后端收到的路径**少了 `/api` 前缀** |
| 2 | **后端 `context-path` 被改了** | 后端收到 `/api/users`，但它现在期望 `/v2/users` 之类 |
| 3 | **有人加了正则 location 截胡**（`03` 练习 2） | 后端**完全没收到请求**，nginx 自己 404 了 |

**注意第 1 和第 2 是同一个契约的两端**（`04 §3.3` 讲的那对配套设计）：**改任何一边而不改另一边，症状完全一样**。所以第 ① 步看到"路径不对"之后，还要判断是 nginx 改了路径，还是后端改了期望。

**"页面正常"这个信息为什么这么值钱**：

它一口气排除了：caddy、DNS、证书、安全组、nginx 进程、dist、`location /`、`try_files`、静态文件权限……

**排错的第一步永远是"用症状缩小范围"，而不是"从头查一遍"。** 一个"页面正常"就砍掉了链路的一大半。
</details>
