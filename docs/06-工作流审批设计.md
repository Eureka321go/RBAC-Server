# RBAC 系统 —— 工作流 / 审批流程设计文档

> 记录时间：2026-07-08
> 当前基础：Spring Boot 3.4.1 / JDK 21 / Spring Security / MyBatis-Plus / MySQL / Redis
> 本阶段目标：在现有 RBAC 底座上，扩展一套轻量、可扩展、与权限体系深度集成的审批工作流模块

---

## 一、设计目标与定位

本模块为通用后台补齐"审批"能力，服务于请假、报销、采购、用印、变更申请等常见场景。

设计原则：

- **轻量优先**：不追求 BPMN 2.0 全功能，先实现串行 / 会签 / 或签 + 条件分支的可用引擎。
- **与 RBAC 深度集成**：审批人来源直接复用现有用户、角色、岗位、部门数据；审批操作走统一鉴权与操作日志。
- **表单与流程解耦**：流程定义描述"谁审、怎么审"，业务表单数据独立存储，通过 `businessKey` 关联。
- **可扩展**：预留 Flowable 平滑替换路径，业务侧只依赖流程服务接口，不直接耦合引擎实现。

**非目标（首期不做）**：可视化拖拽流程设计器、跨系统消息编排、复杂网关（并行网关 + 汇聚）、流程版本灰度。

---

## 二、选型对比

| 方案 | 优点 | 缺点 | 适用 |
|------|------|------|------|
| **自研轻量引擎（推荐）** | 表结构可控、与 RBAC 数据零阻抗、学习成本低、易审计 | 复杂流程能力有限，需自行维护状态机 | 中小型后台、审批规则相对固定 |
| **集成 Flowable** | BPMN 标准、功能完备、社区成熟 | 表结构庞大（40+ 表）、与现有权限模型需适配层、上手成本高 | 复杂企业流程、需要流程图导出/仿真 |

**结论**：首期自研轻量引擎，通过 `WorkflowEngine` 接口隔离实现。若后续流程复杂度上升，可将实现替换为 Flowable 适配器而不影响业务模块。

---

## 三、核心概念

| 概念 | 说明 |
|------|------|
| 流程定义 `ProcessDefinition` | 一类审批的模板，如"请假审批"。包含有序的节点列表 |
| 流程节点 `ProcessNode` | 定义中的单个审批环节，指定审批人来源与会签策略 |
| 流程实例 `ProcessInstance` | 一次具体发起，绑定发起人、业务数据、当前节点、状态 |
| 审批任务 `ProcessTask` | 分派给某审批人的待办，一个节点可产生多条（会签） |
| 审批记录 `ProcessRecord` | 每次审批动作（同意/驳回/转办/加签/撤回）的留痕 |
| 抄送 `ProcessCc` | 无需审批、仅知会的接收人 |

### 审批人来源（`assigneeType`）

复用现有 RBAC 数据，避免二次建模：

| 类型 | 含义 | 取值来源 |
|------|------|---------|
| `USER` | 指定用户 | `sys_user.id` |
| `ROLE` | 指定角色下全部用户 | `sys_role` + 用户角色关联 |
| `POST` | 指定岗位 | `sys_post` + 用户岗位关联 |
| `DEPT_LEADER` | 发起人所在部门负责人 | `sys_dept.leader_id` |
| `INITIATOR_SELF` | 发起人本人（销假、确认类） | 流程实例发起人 |
| `INITIATOR_LEADER` | 发起人直属上级 | 组织架构上溯 |

### 会签策略（`approveMode`）

| 模式 | 含义 |
|------|------|
| `ANY`（或签） | 任一审批人同意即节点通过 |
| `ALL`（会签） | 全部审批人同意才通过，任一驳回即节点驳回 |
| `SEQUENTIAL`（顺序会签） | 按顺序逐个审批 |

## 四、状态机

流程实例状态 `instanceStatus`：

```
DRAFT ──提交──▶ RUNNING ──全部节点通过──▶ APPROVED
                  │  │
       撤回/撤销  │  └──任一节点驳回──▶ REJECTED
                  ▼
               CANCELED
```

- `DRAFT` 草稿：已保存未提交。
- `RUNNING` 审批中：存在未完成任务。
- `APPROVED` 通过 / `REJECTED` 驳回 / `CANCELED` 已撤销：终态。

审批任务状态 `taskStatus`：`PENDING`（待办）/ `APPROVED` / `REJECTED` / `TRANSFERRED`（已转办）/ `CANCELED`。

**驳回策略**：支持"驳回到发起人"（重新编辑再提交）与"驳回到上一节点"，由节点配置 `rejectStrategy` 决定。

## 五、数据模型

所有表继承 `BaseEntity`（id / createdBy / createdAt / updatedBy / updatedAt / deleted 逻辑删除）。落库枚举用 varchar，API 层输出上表中的固定字符串。

### 1. 流程定义 `wf_process_definition`

| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint | 主键 |
| process_key | varchar(64) | 流程标识，唯一，如 `leave` |
| name | varchar(128) | 流程名称 |
| category | varchar(64) | 分类（关联字典 `wf_category`） |
| form_key | varchar(64) | 关联业务表单标识 |
| version | int | 版本号 |
| status | varchar(16) | `ENABLED` / `DISABLED` |
| remark | varchar(255) | 说明 |

### 2. 流程节点 `wf_process_node`

| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint | 主键 |
| definition_id | bigint | 所属定义 |
| node_order | int | 节点顺序（从 1 递增） |
| node_name | varchar(128) | 节点名称，如"部门经理审批" |
| assignee_type | varchar(32) | 审批人来源，见上表 |
| assignee_value | varchar(255) | 来源取值（用户/角色/岗位 id，多个逗号分隔） |
| approve_mode | varchar(16) | `ANY` / `ALL` / `SEQUENTIAL` |
| reject_strategy | varchar(16) | `TO_INITIATOR` / `TO_PREV` |
| condition_expr | varchar(255) | 分支条件（如 `amount > 5000`），空则必经 |

### 3. 流程实例 `wf_process_instance`

| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint | 主键 |
| definition_id | bigint | 流程定义 |
| process_key | varchar(64) | 冗余，便于查询 |
| business_key | varchar(64) | 业务单据 id（与业务表关联） |
| title | varchar(255) | 单据标题，如"张三的请假申请" |
| initiator_id | bigint | 发起人 |
| initiator_dept_id | bigint | 发起人部门（冗余，用于数据权限） |
| current_node_order | int | 当前节点 |
| instance_status | varchar(16) | 见状态机 |
| form_data | json | 表单快照（可选，便于历史留痕） |
| submit_time | datetime | 提交时间 |
| end_time | datetime | 结束时间 |

### 4. 审批任务 `wf_process_task`

| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint | 主键 |
| instance_id | bigint | 流程实例 |
| node_order | int | 所属节点 |
| node_name | varchar(128) | 节点名称快照 |
| assignee_id | bigint | 审批人 |
| task_status | varchar(16) | `PENDING` 等 |
| approve_time | datetime | 处理时间 |

> 索引建议：`(assignee_id, task_status)` 支撑"我的待办"高频查询。

### 5. 审批记录 `wf_process_record`

| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint | 主键 |
| instance_id | bigint | 流程实例 |
| node_order | int | 节点 |
| operator_id | bigint | 操作人 |
| action | varchar(16) | `SUBMIT` / `APPROVE` / `REJECT` / `TRANSFER` / `ADD_SIGN` / `WITHDRAW` |
| comment | varchar(500) | 审批意见（限长，同操作日志红线） |
| operate_time | datetime | 操作时间 |

### 6. 抄送 `wf_process_cc`

| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint | 主键 |
| instance_id | bigint | 流程实例 |
| user_id | bigint | 抄送人 |
| read_flag | tinyint | 是否已读 |

## 六、后端模块与包结构

在 `com.rbac` 下新增 `workflow` 顶层模块（与 `system` 平级）：

```
com.rbac.workflow
├── definition   # 流程定义 + 节点：controller/service/mapper/entity/dto/vo
├── instance     # 流程实例 + 发起/查询
├── task         # 审批任务：待办/已办/审批动作
├── engine       # WorkflowEngine 接口 + 轻量实现（节点流转、审批人解析、状态机）
└── support      # 审批人解析器 AssigneeResolver、条件表达式求值 ConditionEvaluator
```

**引擎核心接口**（隔离实现，便于后续替换）：

```java
public interface WorkflowEngine {
    Long start(String processKey, String businessKey, String title, Map<String,Object> formData);
    void approve(Long taskId, String comment);
    void reject(Long taskId, String comment);
    void transfer(Long taskId, Long targetUserId, String comment);
    void withdraw(Long instanceId, String comment);   // 发起人撤回
}
```

**审批人解析** `AssigneeResolver`：根据 `assigneeType` + `assigneeValue` + 流程实例上下文，解析出实际审批人 id 列表；`DEPT_LEADER` / `INITIATOR_LEADER` 依赖 `sys_dept` 组织树上溯。

## 七、接口规划

统一前缀 `/api`，camelCase，`Result<T>` 包裹，`@PreAuthorize` 权限码控制。

### 流程定义（管理端）

| 方法 | 路径 | 权限码 | 说明 |
|------|------|--------|------|
| GET | `/workflow/definition/page` | `workflow:definition:list` | 分页查询 |
| GET | `/workflow/definition/{id}` | `workflow:definition:query` | 详情（含节点） |
| POST | `/workflow/definition` | `workflow:definition:add` | 新增定义 + 节点 |
| PUT | `/workflow/definition` | `workflow:definition:edit` | 编辑 |
| PUT | `/workflow/definition/{id}/status` | `workflow:definition:edit` | 启用/停用 |
| DELETE | `/workflow/definition/{id}` | `workflow:definition:remove` | 删除 |

### 流程实例与任务（业务端）

| 方法 | 路径 | 权限码 | 说明 |
|------|------|--------|------|
| POST | `/workflow/instance/start` | `workflow:instance:start` | 发起审批 |
| POST | `/workflow/instance/{id}/withdraw` | — | 发起人撤回（Service 校验本人） |
| GET | `/workflow/instance/mine` | — | 我发起的（数据权限：本人） |
| GET | `/workflow/instance/{id}/detail` | — | 实例详情 + 审批记录时间线 |
| GET | `/workflow/task/todo` | — | 我的待办（`assignee=当前用户` + `PENDING`） |
| GET | `/workflow/task/done` | — | 我的已办 |
| POST | `/workflow/task/{id}/approve` | — | 同意 |
| POST | `/workflow/task/{id}/reject` | — | 驳回 |
| POST | `/workflow/task/{id}/transfer` | — | 转办 |
| GET | `/workflow/cc/mine` | — | 抄送我的 |

> 任务处理接口不用静态权限码，改为 Service 层二次校验"当前用户是否为该任务的合法审批人"，符合安全红线"敏感操作后端必须再鉴权"。

## 八、与现有模块集成

- **RBAC 权限**：新增 `workflow:*` 权限码，纳入菜单权限树；管理端菜单挂"系统管理/工作流"，业务端菜单挂"办公/我的审批"。
- **数据权限**：`/workflow/instance/mine`、`todo`、`done` 均按发起人/审批人 = 当前用户过滤，管理员查询走 `DataScope`（`instance.initiator_dept_id`）。不可绕过（安全红线）。
- **操作日志**：审批动作复用现有操作日志切面记录，`comment` 限长。
- **通知（依赖 P0 通知模块）**：任务分派、审批通过/驳回时触发站内消息 → 打通"办结即通知"。若通知模块未就绪，先落 `wf_process_task` 待办，前端轮询/角标展示。
- **字典**：流程分类 `wf_category`、审批动作展示文案走 `sys_dict`。

## 九、前端设计

遵循动态路由 + `import.meta.glob` 白名单、按钮权限 `v-permission`。

新增视图（`frontend/src/views/workflow/`）：

| 视图 | 说明 |
|------|------|
| `definition/DefinitionView.vue` | 流程定义管理：列表 + 节点编辑（表单式配置节点顺序/审批人来源/会签策略，非拖拽） |
| `task/TodoView.vue` | 我的待办：列表 + 审批抽屉（意见输入、同意/驳回/转办） |

- 节点审批人选择器复用用户/角色/岗位/部门选择组件。

## 十、实施顺序

1. **数据层**：建 6 张 `wf_*` 表 + 种子数据（内置"请假审批"示例定义）。
2. **引擎**：`WorkflowEngine` 接口 + 轻量实现（先支持串行 + 或签/会签，条件分支后置）；`AssigneeResolver`。
3. **流程定义管理**：后端 CRUD + 前端配置页。
4. **发起与待办**：`start` / `todo` / `approve` / `reject` 打通最小闭环。
5. **实例详情与时间线**：审批记录留痕展示。
6. **转办、加签、撤回、抄送**：补齐动作。
7. **条件分支 `condition_expr`**：接入表达式求值（如 Aviator / SpEL）。
8. **通知联动**：接入通知模块（依赖 P0）。
9. **示例业务表单**：以"请假申请"打样，验证表单 ↔ 流程解耦。

## 十一、风险与注意

- **并发审批**：会签场景多人同时处理同一节点，需对 `wf_process_task` / 节点流转加乐观锁或行锁，避免重复推进。
- **审批人为空**：解析结果为空时（如部门未设负责人）必须阻断并提示，不可静默跳过节点（安全）。
- **流程定义变更**：运行中实例应锁定其发起时的定义版本，编辑定义生成新 `version`，不影响在途实例。
- **超管兜底**：预留管理员强制终止/转交能力，防止流程因人员离职卡死。
