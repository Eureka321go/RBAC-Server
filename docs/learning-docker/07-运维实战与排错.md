## 二、日常命令：别背表，按"你想知道什么"反查

命令速查表最大的问题是：**出事的时候你不知道该查哪一条**。所以先建立索引——从你脑子里冒出的那个问句，找到对应的命令。

| 你心里在想 | 敲这个 |
|---|---|
| 现在有啥在跑？健康吗？ | `docker compose ps` |
| 刚才那个容器**死哪去了**？ | `docker compose ps -a`（`-a` = 连死掉的一起列） |
| 它为什么起不来 / 为什么报错？ | `docker compose logs --tail=50 backend` |
| 我想盯着日志看它启动 | `docker compose logs -f backend` |
| 我想进去看看容器里到底长啥样 | `docker compose exec backend bash` |
| 谁在吃我的内存/CPU？ | `docker stats` |
| 这条命令会起哪些服务？ | `docker compose config --services`（`06` 学的） |
| 磁盘被谁吃了？ | `docker system df` |
| 改完代码怎么上线？ | `docker compose up -d --build` |

> 🔑 **`ps` 和 `logs` 是你 90% 的时间会用到的两条。** 其他都是特定场景。**先把这两条焊在手上**，剩下的用到再查。

注意一个贯穿的区别，`03` 提过，这里再强调一次：

| | `docker xxx` | `docker compose xxx` |
|---|---|---|
| 作用范围 | **整个 Docker**，所有容器 | **只管当前项目**（靠 `name: rbac-server` 圈定，`03` 学的） |
| 怎么指名容器 | 用容器名 `rbac-backend` | 用**服务名** `backend` |
| 要在哪跑 | 任意目录 | **必须在 `deploy/`**（要能读到 compose 文件） |

所以 `docker compose logs backend` 和 `docker logs rbac-backend` 是同一份日志的两种问法。**`docker stats` 和 `docker system df` 没有 compose 版本**——磁盘和内存是全局的，不分项目。

## 三、看日志：排错的第一步，通常也是最后一步

### 3.1 基本用法

```bash
cd deploy
docker compose logs backend            # 全部日志，一次性打完
docker compose logs -f backend         # -f = follow，跟着刷（Ctrl+C 退出）
docker compose logs --tail=50 backend  # 只看最后 50 行 ← 最常用
docker compose logs --since=10m        # 只看最近 10 分钟（所有服务）
```

不带服务名 = **所有服务混在一起**，每行前面带服务名前缀。这是你本机的**真实输出**：

```
rbac-redis  | 62711:C 14 Jul 2026 06:17:57.086 * DB saved on disk
rbac-redis  | 62711:C 14 Jul 2026 06:17:57.087 * Fork CoW for RDB: current 0 MB, peak 0 MB
rbac-redis  | 1:M 14 Jul 2026 06:17:57.179 * Background saving terminated with success
```

前缀 `rbac-redis |` 就是告诉你这行是谁喊的。混流看着乱，但排查**跨服务问题**时特别有用——比如「backend 报连不上 mysql」，你想知道那一刻 mysql 在干嘛，混着看时间戳一对就清楚了。

> 🔑 **`--tail=50` 应该是你的默认习惯，而不是裸 `logs`。**
>
> Spring Boot 启动能刷几百行，MySQL 跑一天几万行。裸 `logs` 会把终端刷爆，你还得往回翻。`docs/09-部署上线指南.md` 第 270 行那条 `docker compose logs --tail=30 backend` 就是这个习惯。

### 3.2 容器起不来时：两步定位

这是最高频的场景。**流程固定**：

```
docker compose ps -a          ← 第 1 步：它是什么状态？
      │
      ├── Exited (1)   ──▶ 启动就崩了 → 看 logs，原因一定在里面
      ├── Restarting   ──▶ 崩了又被 restart: unless-stopped 拉起来，反复循环 → 看 logs
      └── Up (unhealthy) ─▶ 进程活着但健康检查不过（04 的内容）→ 看 logs + 手动跑一次探针
      │
docker compose logs --tail=50 <服务名>    ← 第 2 步：原因
```

**为什么必须是 `ps -a`？** 因为 `docker compose ps` **只列活着的**。一个启动就崩的容器，在 `ps` 里**根本看不见**——很多人到这一步就懵了，以为"容器压根没创建"，其实它创建了、崩了、躺在那儿等你 `-a`。

注意 `Restarting` 这个状态，它是 `03` 学的 `restart: unless-stopped` 的副作用：**容器崩了会被自动拉起来，然后再崩**。表现是 `ps` 里它一会儿在一会儿不在，看着像"时好时坏"，其实是**一直在死**。日志会看到同样的报错一遍遍重复——**那不是三个问题，是同一个问题的第 3、4、5 次**。

> 🔑 **容器死了，日志是唯一的现场。** 而且这个现场**会随容器重建而消失**——`docker compose up -d --build` 一敲，旧容器被删，日志跟着没了。**所以顺序永远是：先 `logs` 看明白，再动手重建。** 反过来做，你就把证据自己销毁了，然后对着一个"复现不了"的问题发呆。

### 3.3 日志存在哪？为什么它会吃磁盘

容器的 stdout/stderr 被 Docker 默认的 `json-file` 驱动接走，写成宿主机上的 JSON 文件。

**默认没有大小限制。** 一个话痨服务跑上几个月，几个 G 是常事——这是服务器磁盘被吃满的**经典原因之一**，而且特别隐蔽：你 `du -sh /root/project` 看项目目录明明没多大。

（限制大小要在 compose 里配 `logging.options.max-size`，本项目**没配**——个人项目问题不大，但你该知道这根弦在哪。第六节讲磁盘时会再碰到它。）

## 四、进容器：为什么 caddy 里没有 `bash`

### 4.1 基本用法

```bash
docker compose exec backend bash          # 开个交互 shell
docker compose exec mysql mysql -uroot -p # 直接跑一条命令（05 用过很多次）
```

`exec` = 在**已经在跑的**容器里执行命令。`05` 你已经用过好多次了（`docker exec rbac-mysql ls -la /var/lib/mysql`）。

### 4.2 一个真实的坑：`bash: not found`

```bash
docker compose exec caddy bash
# OCI runtime exec failed: exec: "bash": executable file not found in $PATH
```

**不是容器坏了，是那个镜像里真的没有 bash。**

镜像为了瘦身，用的基础发行版不同。这是**在你本机实测出来的真实结果**：

| 服务 | 镜像 | 底层发行版 | 有 `bash` 吗 |
|---|---|---|---|
| `mysql` | `mysql:8.4` | Oracle Linux | ✅ 有 |
| `redis` | `redis:7.4` | Debian 12 (bookworm) | ✅ 有 |
| `backend` | `eclipse-temurin:21-jre` | Ubuntu | ✅ 有 |
| `frontend` | `nginx:1.27` | Debian | ✅ 有 |
| `caddy` | `caddy:2.8` | **Alpine Linux** | ❌ **没有** |

Alpine 是个极简发行版（整个镜像才 18MB，看 `docker images` 里 caddy 的 CONTENT SIZE），它不带 bash，只有 **BusyBox 提供的 `sh`**。

> 🔑 **`exec` 的时候用 `sh`，不用 `bash`。**
>
> ```bash
> docker compose exec caddy sh    # ✅ 这个几乎总能成
> ```
>
> `sh` 是 POSIX 标准，**任何 Linux 镜像都有**（除了 `scratch` 那种连 shell 都没有的极限精简镜像）。`bash` 是增强版，可能有可能没有。**先 `sh`，需要补全和历史再换 `bash`**——排错时你也不需要那些。

### 4.3 在容器里改的东西，留不住

这条比命令本身重要得多。

假设 caddy 配置有问题，你想快点验证一个改法：

```bash
docker compose exec caddy sh
vi /etc/caddy/Caddyfile     # ← 白干
```

**两个原因，一个比一个致命：**

1. **改不动**。`05` 讲的 `:ro`——第 113 行 `./config/caddy/Caddyfile:/etc/caddy/Caddyfile:ro`，只读挂载，`vi` 存不下去。（`05` 练习 3 你亲手试过。）
2. **就算改得动，也留不住**。容器里的改动写在**可写层**（`05` 第二节），`docker compose up -d --build` 一重建，容器是**全新的**，改动全没。

第 2 条的可怕之处在于它**延迟生效**：你改完，重启，"咦好了！"，然后过两周为了别的事重建一次容器，问题**毫无征兆地回来了**，而你早忘了当初改过什么。

> 🔑 **容器是可重建的，所以任何"想留住的改动"都必须在源头。**
>
> - 改配置 → 改**你项目里**的 `Caddyfile` / `nginx.conf`（bind mount 送进去，`05` 讲的）
> - 改环境变量 → 改 `.env` 或 compose
> - 改代码 → 改代码，然后**重新构建镜像**
>
> `docs/09-部署上线指南.md` 第 301 行那条经验，说的就是这件事：
>
> > **部署机（服务器）当成一次性可重建**：出问题优先 `git reset --hard` 对齐远程、`docker compose down` 重来，**别在上面手改**。

**`exec` 是用来"看"的，不是用来"改"的。** 查日志、看文件、连数据库、跑诊断——都行。**改**？回源头改。

## 五、更新上线：那个你会敲几百遍的循环

### 5.1 标准循环

`docs/09-部署上线指南.md` 第 302 行定死了：

```bash
# ① 开发机
git add . && git commit -m "feat: xxx" && git push origin feat/rbac-mvp

# ② 服务器
ssh root@106.15.89.180
cd /root/project/RBAC-Server && git pull origin feat/rbac-mvp
cd deploy && docker compose up -d --build

# ③ 验证
docker compose ps
docker compose logs --tail=30 backend    # 看到 Started RbacServerApplication = 就绪
```

**为什么必须先 push？** 因为服务器是 `git clone` 来的（`09` 第 8.2 节），它只认 GitHub 上的东西。`09` 踩坑表第 10 条就是这个：「服务器拉到的代码没有部署文件」——本地改了没 push，服务器 pull 个寂寞。

### 5.2 `up -d` 是**增量**的

一个关键理解：**`docker compose up -d` 不是"全部重启"。**

它的逻辑是**比对**：

```
docker compose up -d
  │
  ├─▶ 对每个服务，算一遍「它现在该长什么样」（镜像 + 环境变量 + 挂载 + 网络 + ...）
  │
  ├─▶ 和「正在跑的那个容器实际长什么样」比一比
  │
  ├── 一样 ──▶ 不动它 ✅ 输出 "Container rbac-mysql  Running"
  │
  └── 不一样 ──▶ 删掉旧容器，用新配置建一个 🔄 输出 "Container rbac-backend  Recreated"
```

所以你只改了后端代码，`up -d --build` **不会重启 mysql**——它算出来 mysql 该长的样子没变，就不碰。**你的数据库连接、缓存都不受影响，只有 backend 那零点几秒的中断。**

> 🔑 **`up -d` 是幂等的：敲一次和敲十次结果一样。** 什么都没改的情况下再敲一遍，它会告诉你所有服务 `Running` 然后什么都不做。**所以不确定线上状态时，敲 `up -d` 永远是安全的**——它只会把现实拉回到配置文件描述的样子。这就是"声明式"的含义（`03` 第一节讲的）。

### 5.3 `--build` 到底什么时候要加

这里要精确，因为很多人（包括本项目的文档）习惯性无脑加 `--build`：

| 你改了什么 | 要 `--build` 吗 | 为什么 |
|---|---|---|
| **后端/前端代码** | ✅ **必须** | 代码是 `COPY` 进镜像的（`02` 讲的）。**不重新构建镜像，改动根本进不去** |
| `Dockerfile` | ✅ **必须** | 同上 |
| `.env` 里的密码 | ❌ 不用 | 环境变量是**运行时**注入的，`up -d` 检测到变化就会重建容器 |
| `docker-compose.yml` | ❌ 不用 | 同上，`up -d` 自己会重建 |
| `Caddyfile` / `nginx.conf` | ❌ 不用 | bind mount 送进去的（`05`），文件改了容器里立刻就是新的（但要 `restart` 让进程重读） |

> 🔑 **`--build` 管的是"镜像"，`up -d` 管的是"容器"。**
>
> 一句话判据：**改的东西在镜像里（代码），就要 `--build`；在镜像外（环境变量、挂载的配置），`up -d` 就够。**

`docs/ops/01-更换默认密码与密钥.md` 第 85-86 行写的是「环境变量变了，backend 要 `--build` 重建」——**严格说 `--build` 是多余的**，`up -d` 就会重建容器。但**加了也不亏**：`02` 讲的构建缓存会让它秒过，几乎不花时间。**无脑加 `--build` 是个成本很低的保险**，代价只是你可能一直没搞清楚这两件事的区别——而现在你搞清楚了。

> ⚠️ 一个例外：`Caddyfile` 这种 bind mount 的配置改了，容器里的文件立刻是新的，**但进程不会自动重读**。要 `docker compose restart caddy`（或 `docker compose exec caddy caddy reload --config /etc/caddy/Caddyfile`）。**文件新了 ≠ 生效了**，这也是个高频困惑。

### 5.4 为什么第一次那么慢

`09` 踩坑表第 11 条：**首次 `up --build` 约 13 分钟**。因为服务器在**现场编译**——Maven 下全部依赖打 jar，npm 装全部依赖跑 vite build（`02` 逐行读过这两个 Dockerfile）。

后续快得多，靠的是 `02` 讲的**构建缓存**：`pom.xml` / `package*.json` 没变 → 依赖层直接复用 → 只重跑编译。

**这正是那两个 Dockerfile 都先 `COPY pom.xml` / `COPY package*.json` 再 `COPY src` 的原因**（`02` 的核心教学点）。改一行 Java 代码，只有最后那层失效。

> 顺带解释 `09` 的待办 #5（CI/CD）：**服务器既是构建机又是运行机**，编译时 CPU 打满，跑着的服务会卡。正经做法是 CI 构建好镜像推仓库，服务器只 `pull`。个人项目现在这样够用，但你该知道为什么它不是终局。

## 六、磁盘：`docker system df` 与你机器上的考古

### 6.1 先看真实数据

这是**你这台 Mac mini 上刚跑出来的真实输出**：

```
$ docker system df
TYPE            TOTAL     ACTIVE    SIZE      RECLAIMABLE
Images          4         2         2.494GB   1.186GB (47%)
Containers      2         2         49.15kB   0B (0%)
Local Volumes   4         2         426.7MB   204.9MB (48%)
Build Cache     2         0         16.38kB   16.38kB
```

读法：

| 列 | 含义 |
|---|---|
| `TOTAL` | 一共有几个 |
| `ACTIVE` | 其中**正在被使用**的有几个 |
| `SIZE` | 占了多少磁盘 |
| `RECLAIMABLE` | **能回收多少**（= 没在用的那些占的空间） |

**你只跑着 2 个容器（mysql + redis），却有 4 个镜像、4 个卷，其中将近一半是垃圾。** 这就是 Docker 用久了的常态——**它从不主动帮你打扫**。

### 6.2 那个 1.12GB 的"无名镜像"

```
$ docker images -f "dangling=true"
IMAGE        ID             DISK USAGE   CONTENT SIZE
<untagged>   d36d39a64cd1       1.12GB          249MB
```

`<untagged>` 叫**悬空镜像**（dangling image）：**有内容，但没有名字。**

它是怎么来的？还记得你 `docker compose ps` 的输出吗——`rbac-mysql` 那行的 IMAGE 列不是 `mysql:8.4`，而是 `sha256:d36d39a64cd1...`。**就是它。**

故事是这样的：

```
你当初 pull 了 mysql:8.4  →  这个镜像叫「mysql:8.4」，容器基于它启动
        │
        ▼
后来 mysql:8.4 这个标签被更新了（官方发了新版，或你重新 pull 过）
        │
        ▼
「mysql:8.4」这个名字被贴到了新镜像上
        │
        └─▶ 老镜像的名字被抢走了，成了 <untagged>
              但它不能删 —— 你的 rbac-mysql 容器还基于它在跑！
              所以它以 ACTIVE 的身份，占着 1.12GB
```

> 🔑 **标签（`mysql:8.4`）是可以移动的指针，不是镜像的身份证。** 镜像的真身份是那串 sha256。这就是**为什么生产环境不该只写 `mysql:8.4`**——同一个标签，今天和三个月后 `pull` 到的可能不是同一个镜像。真正较真的做法是锁到摘要（`mysql:8.4@sha256:...`）。

### 6.3 考古：`01` 那个实验的数据，其实还在你硬盘上

**这段是本节的重点，而且是在你机器上现挖出来的。**

看卷列表（真实输出）：

```
$ docker volume ls
DRIVER    VOLUME NAME
local     53cccfa09a90a301b13ac192669ae98a539460a9ec70713ed0f6ad5399e43daf
local     a465742502d49cd2a74fa3eb1259ba05acf137cc2ccfeac3703416f217b6e74a
local     rbac-server_mysql-data
local     rbac-server_redis-data
```

下面两个你认识（`05` 查过）。**上面那两串哈希是什么？**

查一下创建时间：

```
53cccfa0... | 创建于 2026-07-14T07:43:14Z
a4657425... | 创建于 2026-07-14T07:37:14Z
```

**`01` 那天，你做 `docker run mysql` 实验的时间。** 相差 6 分钟——你跑了两次。

挖开看看里面装的什么：

```
$ docker run --rm -v 53cccfa0...:/probe:ro alpine ls /probe
ibdata1     mysql.ibd    performance_schema   rbac        undo_001
mysql       mysql.sock   private_key.pem      sys         undo_002
```

**这是一个完整的 MySQL 数据目录。** 你在 `01` 里以为"随着 `docker rm -f` 一起蒸发了"的那些数据——**它一直躺在你硬盘上，占着 200 多 MB，到今天。**

### 6.4 为什么？—— 一个 `05` 讲得不够准的机制

`05` 说：不挂卷，数据写在**容器可写层**，`docker rm` 就跟着没了。

**这个说法在 mysql 这个具体案例上是错的。** 真相是：

```
$ docker image inspect mysql:8.4 --format '{{json .Config.Volumes}}'
{"/var/lib/mysql":{}}

$ docker image inspect redis:7.4 --format '{{json .Config.Volumes}}'
{"/data":{}}

$ docker image inspect caddy:2.8 --format '{{json .Config.Volumes}}'
null
```

**mysql 和 redis 的镜像里，写死了 `VOLUME` 声明。**（`02` 读 Dockerfile 时见过 `EXPOSE`，`VOLUME` 是同一类指令。）

它的效果是：

```
docker run mysql:8.4          ← 你没写任何 -v
     │
     ├─▶ Docker 一看镜像声明了 VOLUME /var/lib/mysql
     │     "这个路径的数据不该待在可写层"
     │
     └─▶ 自动创建一个【匿名卷】（就是那串哈希），挂到 /var/lib/mysql
           │
           └─▶ 你的数据其实写进了一个真正的卷 ✅

docker rm -f my-test-mysql    ← 没加 -v
     │
     └─▶ 容器删了，但匿名卷【留下了】
           它没有名字，没有容器引用它 → 成了孤儿
           └─▶ 你找不回来，但它占着磁盘 💾
```

所以精确的说法是：

> 🔑 **`05` 的结论对，机制说错了。**
>
> | | `05` 的说法 | 实际 |
> |---|---|---|
> | 数据写在哪 | 容器可写层 | **匿名卷**（因为 mysql 镜像有 `VOLUME` 声明） |
> | `docker rm` 之后 | 数据被删除了 | 数据**还在**，但卷成了没人认领的孤儿 |
> | 你重新 `run` 一个 | 数据没了 ✅ | 数据没了 ✅（因为**新建了另一个新的匿名卷**） |
>
> **表现完全一样**（新容器看到空数据库），所以 `05` 的教训一个字都不用改：**不挂命名卷，数据就活不长。**
>
> **但后果更糟**：数据不是被清理了，而是变成了**你看不见、找不回、还占着磁盘的垃圾**。你每跑一次这种实验，硬盘上就多 200MB 永久垃圾。

而 `caddy:2.8` 输出 `null`——**它没有 `VOLUME` 声明**。所以 `06` 讲的"不挂 `caddy-data` 证书就没了"，那个才是货真价实的可写层丢失。**同一个项目里两种机制都有，正好对照。**

> 🔑 **命名卷 vs 匿名卷：差别只在你有没有给它起名字。**
>
> - `-v mysql-data:/var/lib/mysql` → **命名卷**，你能 `ls` 到、能复用、能管理。
> - 什么都不写 + 镜像有 `VOLUME` → **匿名卷**，Docker 给个哈希名，容器一删就成孤儿。
>
> `docker run -v ...` 和 `docker rm -v`（删容器时连匿名卷一起删）里那两个 `-v`，管的就是这件事。

### 6.5 打扫：从最安全到核按钮

```bash
# ① 最安全：只删悬空镜像（没名字、也没容器在用的）
docker image prune

# ② 安全：构建缓存（02 讲的那个，删了只是下次构建慢点）
docker builder prune

# ③ 要看清楚：删所有「没有容器在用」的镜像
docker image prune -a
#    ⚠️ 包括你 --profile 里那些没在跑的服务的镜像，下次要重新 pull

# ④ 孤儿卷（就是上面挖出来那两个）
docker volume ls                        # 先看
docker volume rm <那串哈希>              # 确认过再一个个删
```

> ⚠️ **`docker system prune -a --volumes` 是核按钮，比 `down -v` 还狠。**
>
> `05` 讲的 `down -v` 只删**本项目**的卷。而 `system prune --volumes` 删的是**整台机器上所有没被使用的卷**——包括你临时停掉的别的项目的数据库。
>
> **特别注意 `--volumes` 对本项目意味着什么**：如果哪天你 `docker compose down` 之后（容器没了，卷还在，`05` 讲过）顺手来一发 `system prune -a --volumes`，那 `rbac-server_mysql-data` 就是"没有容器在用的卷" ——**它会被删掉**。你以为你在打扫，其实在清库。
>
> **日常打扫用 `docker image prune` + `docker builder prune` 就够了**，这两个删的都是能重新生成的东西。

**回到服务器**：`09` 记录的编译要 13 分钟，意味着每次 `--build` 都在产生新镜像层和构建缓存。轻量服务器磁盘通常只有 40-60GB，**`--build` 几十次之后磁盘告警是必然的**。定期上去 `docker system df` 看一眼，`image prune` 一下——**这是运维日常，不是出事才做的**。

## 七、症状 → 怎么查

把前七节的知识按"你看到的现象"重新索引一遍。**出事时从这张表进。**

| 症状 | 大概率原因 | 怎么查 / 怎么办 | 哪节讲的 |
|---|---|---|---|
| `port is already allocated` | 宿主机端口被占了 | `lsof -i :80` 或 `docker ps` 找占用者；换端口或停掉它 | `01`、`06`（nginx↔caddy 抢 80） |
| 容器 `Exited (1)`，`ps` 里看不见 | 启动就崩 | **`ps -a`** 看状态 → `logs --tail=50` 看原因 | 本节 |

| 改了 `.env` 密码不生效 | **出厂设置**：数据卷不空，mysql 不读环境变量 | `down -v` 重建（丢数据）或进容器 `ALTER USER`（保数据） | `05`、`docs/ops/01` |
| 改了 `Caddyfile` 没生效 | 文件新了，但进程没重读 | `docker compose restart caddy` | 本节 5.3 |
| 改了代码没生效 | 忘了 `--build`，镜像还是旧的 | `up -d --build` | `02`、本节 5.3 |
| 网页 502 / 网关错误 | 上游没起，或 upstream 指错了 | `ps` 看 backend 是否 Up；`06` 那两个 nginx.conf 别弄混 | `06` |
| 刷新页面 404 | SPA 路由回退没配 | `try_files $uri $uri/ /index.html`（本项目已配） | `06`、`docs/09` 第 38 行 |
| HTTPS 证书签不下来 | DNS 没生效 / 80 没放行 | `logs caddy` 看 ACME 报错；`ping 域名` 验解析 | `06`、`docs/ops/02` |
| 证书突然签不出来了 | **LE 限流**（一周 5 张） | 等一周。别删 `caddy-data` 卷 | `05`、`06` |
| 磁盘满了 | 悬空镜像 / 构建缓存 / 孤儿卷 / **日志** | `docker system df` → `image prune`、`builder prune` | 本节 |
| 容器里 `bash: not found` | Alpine 镜像没 bash | 用 `sh` | 本节 |
| 在容器里改的东西过两周没了 | 可写层随容器重建蒸发 | 回源头改（配置文件 / `.env` / 代码） | `05`、本节 |

>
> 镜像层（代码）、容器层（环境变量）、挂载层（配置文件）、卷（数据）——**四层，各有各的生效方式**。搞不清"我这个改动住在哪一层"，就会一直踩这类坑。这也是为什么前六节要一层一层地讲。

## 八、收掉两根弦：本项目线上此刻的真实安全状况

`06` 说好了这节回来收。**这不是假设题，是你线上正在跑的东西。**

### 8.1 弦一：mysql / redis 的 `ports` 是真实暴露面

`docs/09-部署上线指南.md` 第 209 行的**安全红线**写得清清楚楚：

> **数据库/Redis 端口不出内网**：compose 里 `mysql`/`redis` 服务去掉 `ports:` 映射（容器间靠服务名通信不需要映射到宿主机），只保留 nginx 的 80/443。

**而 `deploy/docker-compose.yml` 第 25-26、51-52 行现在是这样的：**

```yaml
  mysql:
    ports:
      - "3306:3306"     # ← 红线说该删，它还在
  redis:
    ports:
      - "6379:6379"     # ← 同上
```

**文档的红线和文件的现状不一致。** 这不是谁犯了错——是**一份 compose 文件同时服务两个环境**的必然结果：本地你要用 Navicat 连 3306（`04` 讲过），服务器上这行就成了暴露面。

### 8.2 弦二：唯一挡着的，是 compose 之外的一条防火墙规则

那为什么线上没出事？因为 `09` 第 246 行：

> 阿里云防火墙只放行 **22（SSH）** 和 **80（网页）**；`3306 / 6379` 不对公网开放。

（`docs/ops/02` 上 HTTPS 时又加了 443。）

`docs/ops/01-更换默认密码与密钥.md` 第 124 行也承认了这个结构：

> MySQL/Redis 端口虽在 compose 里映射到宿主机（3306/6379），但防火墙只放行 22/80，外网连不进来，**这层是安全的**。

这句话对——**但它的"安全"全部押在一个 compose 文件里看不到的地方。**

### 8.3 把两根弦并起来看

现在把 `handoff.md` 第 76 行的待办 #1 拿过来：

> 1. **[安全] 换掉默认密码**（当前仍是 `rbac_123` / `rbac_redis_123` / 默认 JWT secret）。

而 `docs/ops/01` 第 43 行解释了为什么：

> 本地 `deploy/.env` 已被 `.gitignore`，**不会推到服务器**。所以服务器原本没有 `.env`，用的是 compose 里的 `:-默认值` 兜底。

**三个事实串起来**（每一条你都在前面的文档里读到过）：

```
① compose 把 3306 映射到了阿里云主机（第 25-26 行）
② 服务器没有 .env → mysql 用的是 compose 里的兜底默认值 rbac_123（03 讲的 ${VAR:-默认}）
③ 3306 没被公网访问到，纯粹因为阿里云防火墙没放行

   ⇒ 一个公网 IP 上，跑着密码是 rbac_123 的 MySQL，
     和外面之间隔着【一条防火墙规则】。
```

**这就是"纵深防护"的反面。** `06` 那套设计——backend 连 `ports` 都不写、frontend 只 expose、caddy 独占入口——是**结构上不可达**：想攻击 backend，你得先攻破 caddy 和 frontend。而 3306 这里是**规则上不可达**：只要有人为了排查问题临时放行 3306 然后忘了关，`rbac_123` 就是全世界都能试的密码。

> 🔑 **判断一道防线好不好，问一句：它失效需要几步？**
>
> - backend 那种：需要**攻破两层反代**。
> - 3306 这种：需要**一次手滑**。
>
> 好的安全设计里，**没有任何一环的失效是一步之遥**。这就是 `handoff.md` 把"换默认密码"排在待办 #1 的原因——它不是让密码变复杂，是**让最后一根弦断了也不至于当场丢库**。

### 8.4 那怎么两全？

问题回到：**本地开发要 3306，生产不要，一份文件怎么办？**

三条路，从简单到正经：

| 方案 | 怎么做 | 评价 |
|---|---|---|
| **现状** | 都留着，靠防火墙 | 能跑，但防线在文件之外 |
| **override 文件** | compose 主文件里**不写** mysql 的 `ports`；本地额外放一个 `docker-compose.override.yml` 补上（Compose 会**自动**合并同目录的 override，且它已被 `.gitignore` 的话不上服务器） | **正经做法**：默认安全，本地按需开洞 |
| **profile** | 把"本地调试用的端口映射"单独拆个服务/层 | `06` 学的机制，但 `ports` 属于服务级配置，用 profile 表达不自然 |

> ⚠️ **本项目现在没有 `docker-compose.override.yml`**，上面第二行是**可选方案**，不是现状。真要改，属于一次独立的动手改造——`docs/ops/` 下再开一篇更合适。

**眼下最该做的仍然是待办 #1**：把默认密码换掉（`docs/ops/01` 有完整的方案 A/方案 B）。**那是成本最低、收益最大的一步。**

<details>
<summary>点开看答案</summary>

**第一条命令：`docker compose logs --tail=50 backend`。**

**关键在于：先看日志，别先重启。**

- `Restarting` 说明 `restart: unless-stopped` 正在反复拉它（`03`），日志里那个错**已经重复了 N 遍**——那是**一个**问题，不是 N 个。

| 日志说什么 | 大概率是 | 下一步 |
|---|---|---|
| `Access denied for user 'rbac'` | 密码不一致（`05` 的出厂设置坑） | `docs/ops/01` 的方案 B |
| `Communications link failure` | mysql 没 ready 或挂了 | `docker compose ps` 看 mysql 健康状态（`04`） |
| `OutOfMemoryError` | 内存不够 | `docker stats`；轻量服务器容易中 |
| 磁盘相关的错 | 盘满了 | `docker system df` + `df -h` |

> 🔑 **排错的第一动作永远是"读"，不是"改"。** 你只有一次看现场的机会。
</details>

## 附：答案与解析

> 建议先自己想一遍再点开。

<details>
<summary><b>1. `ps` 和 `ps -a` 差在哪？</b></summary>

**`docker compose ps` 只列活着的容器，`-a` 连死掉的一起列。**

**后者不可替代的场景：容器启动就崩了。**

它在 `ps` 里**根本看不见**——很多人到这就懵了，以为"容器压根没创建"。其实它创建了、崩了、以 `Exited (1)` 的状态躺着等你 `-a`。

而且 `Exited` 后面的**退出码**很有用：`Exited (0)` 是正常结束，`Exited (1)` 是报错退出，`Exited (137)` 通常是被 OOM Killer 干掉了（内存不够）。

> 🔑 **排错第一步：`ps -a`，不是 `ps`。**
</details>

<details>
<summary><b>2. 为什么先 `logs` 再重建？</b></summary>

> 🔑 **容器死了，日志是唯一的现场——而这个现场会随容器重建而消失。**

`docker compose up -d --build` 会**删掉旧容器建新的**（本节 5.2 的比对逻辑）。旧容器一删，它的日志跟着没了。

反过来做的两种结局：
- **"重启后好了"**：但你不知道为什么，也不知道它会不会再来（大概率会）。
- **"重启后还是坏"**：现在你既有新错误、又永远看不到原来那个了。

**你只有一次看现场的机会。第一动作永远是"读"，不是"改"。**
</details>

<details>
<summary><b>3. `bash: not found` 为什么？</b></summary>

**因为 `caddy:2.8` 是 Alpine Linux 基础镜像，它不带 bash**，只有 BusyBox 的 `sh`（整个镜像才 18MB，瘦身瘦掉的）。

**解决：用 `sh`。**

```bash
docker compose exec caddy sh
```

`sh` 是 POSIX 标准，几乎所有 Linux 镜像都有；`bash` 是增强版，不保证有。

本项目实测：mysql（Oracle Linux）、redis（Debian 12）、backend（`eclipse-temurin:21-jre`，Ubuntu）、frontend（`nginx:1.27`，Debian）**都有 bash**，只有 caddy 没有。

> 🔑 **默认敲 `sh`。** 排错时你不需要 bash 那些补全和历史功能。
</details>

<details>
<summary><b>4. 容器里改的配置，两周后没了？</b></summary>

**因为你改在了容器的可写层**（`05` 第二节），而**容器是可重建的**。

两周后你为了别的事敲了一次 `up -d --build` → 旧容器被删、新容器从镜像重建 → **那个改动从来没进过镜像，自然不会出现在新容器里**。

**这个坑的可怕之处是延迟生效**：改完当场"好了"，问题在两周后毫无征兆地回来，而你早忘了改过什么。

> 🔑 **任何想留住的改动必须在源头**：配置 → 改项目里的文件（bind mount 送进去）；环境变量 → 改 `.env`；代码 → 改代码再 `--build`。
>
> **`exec` 是用来"看"的，不是用来"改"的。**（`docs/09` 第 301 行那条经验：部署机当成一次性可重建，别在上面手改。）
</details>

<details>
<summary><b>5. 改一行 Java 代码，会重启 mysql 吗？</b></summary>

**不会。**

`up -d` 是**增量**的，逻辑是**比对**：算出每个服务"该长什么样"，和正在跑的容器"实际长什么样"比——**一样就不动它**。

你改的是后端代码 → 只有 `backend` 的镜像变了 → 只有它被 `Recreated`。mysql 该长的样子一个字没变，Compose 碰都不碰，输出 `Container rbac-mysql  Running`。

**你的数据库连接、Redis 缓存都不受影响**，只有 backend 那零点几秒的中断。

> 🔑 **`up -d` 是幂等的**：什么都没改时敲十遍和敲一遍一样。**所以不确定线上状态时，敲 `up -d` 永远安全**——它只会把现实拉回配置描述的样子。这就是"声明式"（`03`）。
</details>

<details>
<summary><b>6. 什么时候必须 `--build`？</b></summary>

> 🔑 **判据：改的东西在镜像里，就要 `--build`；在镜像外，`up -d` 就够。**

| 改了什么 | 要 `--build` 吗 |
|---|---|
| 前后端**代码**、`Dockerfile` | ✅ **必须**（代码是 `COPY` 进镜像的，不重建镜像进不去） |
| `.env`、`docker-compose.yml` | ❌ 不用（运行时注入，`up -d` 自己会重建容器） |
| `Caddyfile` / `nginx.conf` | ❌ 不用（bind mount，文件即时生效……但进程要 `restart` 才重读） |

**`--build` 管镜像，`up -d` 管容器。**

无脑加 `--build` 也不亏（`02` 的构建缓存会让它秒过），但你得知道自己在干嘛——`docs/ops/01` 第 85 行写的「环境变量变了要 `--build`」严格说是多余的。

⚠️ 最容易忘的是那个例外：**改了 `Caddyfile`，容器里文件立刻是新的，但 caddy 进程不会自己重读**。要 `docker compose restart caddy`。**文件新了 ≠ 生效了。**
</details>

<details>
<summary><b>7. `<untagged>` 的 1.12GB 是什么？</b></summary>

**悬空镜像**（dangling image）：**有内容，但没有名字。**

来历：你的 `rbac-mysql` 容器就是基于它跑的（`docker compose ps` 里那行 IMAGE 显示 `sha256:d36d39a6...` 而不是 `mysql:8.4`，就是证据）。后来 `mysql:8.4` 这个**标签被贴到了新镜像上**，老镜像的名字被抢走，成了 `<untagged>`。

**为什么删不掉**：`docker image prune` 只删"没有容器在用的悬空镜像"。这个还有 `rbac-mysql` 在跑，所以它以 ACTIVE 的身份占着 1.12GB。等你哪天重建 mysql 容器用上新镜像，它就变成可回收的了。

> 🔑 **标签是可移动的指针，不是身份证。** 镜像的真身份是那串 sha256。所以 `mysql:8.4` 今天和三个月后 `pull` 到的**可能不是同一个东西**——生产环境较真的做法是锁摘要（`mysql:8.4@sha256:...`）。
</details>

<details>
<summary><b>8. `01` 的数据丢没丢？`05` 哪里不准？</b></summary>

**没丢。它还在你硬盘上，占着 200 多 MB。**

`05` 说「数据写在容器可写层，`docker rm` 就跟着没了」——**结论对，机制错**。

真相是 **mysql 镜像声明了 `VOLUME /var/lib/mysql`**（`docker image inspect mysql:8.4 --format '{{json .Config.Volumes}}'` 输出 `{"/var/lib/mysql":{}}`）。效果是：

```
docker run mysql:8.4（没写 -v）
  └─▶ Docker 自动建一个【匿名卷】挂到 /var/lib/mysql
        └─▶ 数据其实写进了真正的卷

docker rm -f（没加 -v）
  └─▶ 容器删了，匿名卷【留下】→ 没名字、没人引用 → 孤儿
```

| | `05` 的说法 | 实际 |
|---|---|---|
| 数据写在 | 可写层 | **匿名卷** |
| `rm` 之后 | 被删除 | **还在**，成了孤儿 |
| 重新 `run` | 数据没了 ✅ | 数据没了 ✅（**新建了另一个**匿名卷） |

**表现完全一样**，所以 `05` 的教训不用改：**不挂命名卷，数据活不长。**

**但后果更糟**：数据不是被清理了，是变成了**看不见、找不回、还占磁盘**的垃圾。每跑一次这种实验多 200MB 永久垃圾——你跑了两次，所以有两个。

对照：`caddy:2.8` 的 `Config.Volumes` 是 `null`（**没有 `VOLUME` 声明**），所以 `06` 讲的"不挂 `caddy-data` 证书就没了"**才是**货真价实的可写层丢失。**同一个项目里两种机制都有。**
</details>

<details>
<summary><b>9. `system prune -a --volumes` 为什么比 `down -v` 更危险？</b></summary>

**范围不同：`down -v` 只删本项目的卷，`system prune --volumes` 删【整台机器上所有没被使用的卷】。**

包括你临时停掉的别的项目的数据库。

**对本项目最阴的场景**：

```
docker compose down                    # 容器没了，卷还在（05 讲的，这步很安全）
docker system prune -a --volumes       # 💀 rbac-server_mysql-data 现在"没有容器在用"
                                       #    → 被当垃圾删掉
```

**你以为你在打扫，其实在清库。** 而且 `down -v` 好歹名字里带个 `down`，你知道自己在停服务；`system prune` 听起来就像"清理系统"，特别容易手滑。

> 🔑 **日常打扫只用 `docker image prune` + `docker builder prune`。** 这两个删的都是**能重新生成**的东西（重新 pull、重新构建），最坏结果是下次慢一点。**碰卷的命令，每一个都要停下来想三秒。**
</details>

<details>
<summary><b>10. 线上 3306 现在靠什么挡着？和 backend 那道防线差在哪？</b></summary>

**挡着的是：阿里云防火墙只放行 22 / 80 / 443**（`docs/09` 第 246 行 + `docs/ops/02` 加的 443）。

**完整的现状是三个事实叠在一起：**

1. compose 第 25-26 行把 3306 映射到了公网主机上（`docs/09` 第 209 行的红线明说该删，还没删）。
2. 服务器上**没有 `.env`**（被 `.gitignore` 了，`docs/ops/01` 第 43 行），所以 mysql 用的是 compose 里的兜底默认值 `rbac_123`（`03` 讲的 `${VAR:-默认}`）。
3. 外面连不进来，**纯粹因为防火墙没放行**。

**⇒ 一个公网 IP 上跑着密码是 `rbac_123` 的 MySQL，和外面之间隔着一条防火墙规则。**

**和 backend 那道防线的差别：**

| | backend（`06` 的设计） | mysql 的 3306 |
|---|---|---|
| 防护类型 | **结构上**不可达（压根没写 `ports`） | **规则上**不可达（写了 `ports`，靠防火墙挡） |
| 失效需要几步 | 攻破 caddy + frontend 两层反代 | **一次手滑**（临时放行 3306 忘了关） |
| 防线在哪 | **compose 文件里**，看得见、进 git、可 review | **compose 之外**，云控制台里，没人 review |

> 🔑 **判断一道防线好不好，问一句：它失效需要几步？** 好的安全设计里，**没有任何一环的失效是一步之遥**。

这就是 `handoff.md` 待办 #1 的意义：换掉默认密码**不是让密码变复杂**，是**让最后一根弦断了也不至于当场丢库**。

**正经的结构性解法**：主 compose 里不写 mysql 的 `ports`，本地用 `docker-compose.override.yml`（Compose 自动合并、且不入库）补上——**默认安全，本地按需开洞**。⚠️ 本项目**现在没有**这个文件，那是可选改造，不是现状。
</details>
