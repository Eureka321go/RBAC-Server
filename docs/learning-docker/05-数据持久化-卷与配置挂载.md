## 二、先搞懂：容器里的数据本来是活不长的

### 2.1 容器是一次性的

回想 `00` 的类比：**镜像是菜谱，容器是按菜谱做出来的那盘菜。**

这个类比现在要往前推一步：**那盘菜吃完了，盘子是要洗掉的。**

容器的文件系统是**临时的**。你在容器里写的任何东西，都写在容器自己那一层"可写层"上。这一层的命运和容器绑死——**`docker rm` 把容器删了，这层跟着一起没**。

这就是 `01` 那个实验的全部真相：

```
docker run -d --name my-test-mysql -p 13306:3306 -e MYSQL_ROOT_PASSWORD=123456 mysql:8.4
     │
     ├─▶ 你建了库、插了数据 → 全都写在容器的可写层里
     │
docker rm -f my-test-mysql
     │
     └─▶ 可写层随容器一起蒸发 💨 数据全没
```

**不是 Docker 有 bug，这是设计。** 容器被设计成"用完即弃"的东西——正因为它随时能删能重建，你才敢随便升级、随便回滚。但代价是：**任何需要活得比容器长的东西，必须存到容器外面去。**

这个"存到外面去"的机制，就是 `volumes`。

### 2.2 挂载的语义：左盖右

`01` 答疑 Q3 讲过这个，复习一下：

```yaml
      - mysql-data:/var/lib/mysql
        └────┬───┘ └──────┬─────┘
          外部存储      容器内路径
```

**冒号左边是"外面的东西"，右边是"容器里的位置"。** 挂载的效果是**左边盖住右边**——容器内 `/var/lib/mysql` 这个路径，读写的实际上是外面那块存储。

> 沿用宴席类比：容器是**一次性的餐盘**，用完就扔。而卷是**后厨的储物柜**——菜品端上端下，柜子一直在那儿。你在 `/var/lib/mysql` 这个位置"开了个门"，门后面通向储物柜，而不是盘子本身。**盘子扔了，柜子里的东西还在。**

## 三、两种挂载：判断依据只有一个

看本项目 `mysql` 的 `volumes`（第 37-39 行，真实内容）：

```yaml
    volumes: #数据卷挂载（左=外部存储，右=容器内路径）
      - mysql-data:/var/lib/mysql # 我们手动实验时"缺"的那块，持久化数据
      - ./config/mysql/init:/docker-entrypoint-initdb.d # bind mount：注入你写的初始化 SQL
```

两行长得差不多，但**是两种完全不同的东西**。

### 3.1 一眼分辨

> 🔑 **判断依据只有一个：看冒号左边有没有"路径的样子"。**
>
> | 左边长什么样 | 是什么 | 例子 |
> |---|---|---|
> | 就是个名字，**没有斜杠** | **命名卷**（named volume） | `mysql-data:/var/lib/mysql` |
> | 以 `./` 或 `/` 或 `../` 开头 | **bind mount**（绑定挂载） | `./config/mysql/init:/docker-entrypoint-initdb.d` |
>
> 就这么简单。Docker 就是靠"**左边像不像一个路径**"来区分的。

### 3.2 两者的本质区别

| | 命名卷 `mysql-data` | bind mount `./config/mysql/init` |
|---|---|---|
| 谁管着它 | **Docker 管**（它自己找地方存） | **你管**（就是你项目里那个目录） |
| 存在哪 | Docker 的地盘：`/var/lib/docker/volumes/...` | 你指定的位置，你看得见摸得着 |
| 要不要先声明 | **要**（顶层 `volumes:` 登记过） | **不要**（路径就是一切） |
| 需要跟着 git 走吗 | 不能也不该（那是运行时数据） | **通常要**（那是配置，是代码的一部分） |
| 适合装什么 | **数据**：数据库文件、上传的图片、证书 | **配置**：conf 文件、初始化脚本 |
| 典型方向 | 容器**写**进去 | 容器**读**出来 |

一句话总结这个分工：

> 🔑 **命名卷装"容器产生的数据"，bind mount 送"你写好的配置"。**
>
> 前者是**出**——容器往里写，写完你不用管在哪，Docker 负责保管好。
> 后者是**进**——你把文件放好，容器进去读。你要能随时编辑它，所以必须放在你自己的目录里。

### 3.3 为什么数据不用 bind mount？

一个很自然的疑问：既然 bind mount 看得见摸得着，那 `mysql-data` 干嘛不也写成 `./data/mysql:/var/lib/mysql`？我还能直接 `ls` 看到，多方便。

**能这么干，但通常不该。** 三个理由：

1. **性能**。在 Mac 和 Windows 上，bind mount 要跨越"你的系统 ↔ Docker 的 Linux 虚拟机"这道墙，文件 IO 会**慢一个量级**。数据库这种疯狂读写的场景，差别非常明显。命名卷住在虚拟机里面，没有这个损耗。
2. **权限**。MySQL 容器里的进程是 `mysql` 用户（UID 999），它要往这个目录写东西。bind mount 会把宿主机的文件权限直接带进去，经常出现"容器里没权限写"的糟心事。命名卷是 Docker 建的，权限它自己搞定。
3. **误删**。数据目录躺在你项目里，某天 `git clean -fdx` 一把梭，或者手滑删了个文件夹——数据库就没了。放在 Docker 的地盘里，至少不会被日常操作误伤。

**反过来，配置为什么不用命名卷？** 因为配置需要你**随时编辑**。你要改 `Caddyfile`、改初始化 SQL，改完 `git commit` 让同事也拿到。塞进命名卷里，你连编辑它都费劲。

## 四、还债 1：`mysql-data` 到底在硬盘哪儿

`01` 答疑 Q2 你问过这个。现在把答案讲完整。

### 4.1 真名带前缀

`03` 讲过，`name: rbac-server` 会当前缀贴上去。所以顶层声明的 `mysql-data`，真名是：

```
rbac-server_mysql-data
```

自己看一眼：

```bash
docker volume ls
```

### 4.2 真实位置

```bash
docker volume inspect rbac-server_mysql-data
```

输出里的 `Mountpoint` 大概长这样：

```
/var/lib/docker/volumes/rbac-server_mysql-data/_data
```

**这就是数据的真实存放路径。**

### 4.3 但你在 Mac 上进不去

你去 Finder 里找 `/var/lib/docker`——**没有这个目录**。

原因 `04` 里提过：**Docker Desktop 的引擎跑在一个隐藏的 Linux 虚拟机里**。那个 `/var/lib/docker/...` 是**虚拟机内部的路径**，不是你 Mac 上的路径。你的 Mac 根本看不见它。

（在真正的 Linux 服务器上就不一样了——那儿 Docker 是原生跑的，`sudo ls /var/lib/docker/volumes/` 直接就能看到。你阿里云那台就是这样。）

> 🔑 **这正是命名卷的设计哲学：你本来就不该关心它在哪。**
>
> 你只需要知道"有个叫 `mysql-data` 的柜子，Docker 帮我保管着"。至于柜子在几楼哪个房间，那是 Docker 的事。**要看里面的东西，走正门**——用 `docker exec` 钻进容器里看，或者用 `mysqldump` 导出来。

想看看里面有什么，正门是这样走的：

```bash
docker exec rbac-mysql ls -la /var/lib/mysql
```

你会看到 `rbac` 数据库的目录、`ibdata1` 这些 InnoDB 文件——**这些就是躺在卷里的真实数据**。

## 五、还债 2：为什么改了 `MYSQL_DATABASE` 不生效

`03` 练习 3 那个思考题，现在正式展开——因为它牵出的是本节第二个主角。

### 5.1 神奇的 `docker-entrypoint-initdb.d`

看第二行挂载：

```yaml
      - ./config/mysql/init:/docker-entrypoint-initdb.d # bind mount：注入你写的初始化 SQL
```

`deploy/config/mysql/init/` 里躺着一个 `01-init.sql`（真实内容）：

```sql
-- MySQL 容器首次启动时自动执行（仅空数据卷时运行一次）
-- 确保数据库字符集为 utf8mb4，并给应用账号授权

CREATE DATABASE IF NOT EXISTS `rbac`
  DEFAULT CHARACTER SET utf8mb4
  DEFAULT COLLATE utf8mb4_unicode_ci;

-- rbac 账号已由 compose 的 MYSQL_USER 创建，这里补充授权
GRANT ALL PRIVILEGES ON `rbac`.* TO 'rbac'@'%';
FLUSH PRIVILEGES;
```

`docker-entrypoint-initdb.d` 是 **mysql 镜像约定好的一个魔法目录**：镜像的启动脚本会去这个目录里，把所有 `.sql`、`.sh`、`.sql.gz` 文件**按文件名排序依次执行**。

（这个约定不是 mysql 独有的，postgres 镜像也有一模一样的机制。文件名前面加 `01-`、`02-` 就是为了控制执行顺序。）

### 5.2 关键：它只在"第一次开张"时看一眼

**重点来了。** mysql 镜像的启动脚本，逻辑大致是这样：

```
容器启动
  │
  ├─▶ 看一眼 /var/lib/mysql 是不是空的？
  │
  ├── 空的 ──▶ 「首次初始化」流程：
  │              1. 建系统表
  │              2. 读 MYSQL_ROOT_PASSWORD 设置 root 密码
  │              3. 读 MYSQL_DATABASE 建库
  │              4. 读 MYSQL_USER / MYSQL_PASSWORD 建账号
  │              5. 跑一遍 /docker-entrypoint-initdb.d/ 里的脚本 ✅
  │              6. 完事，正常启动
  │
  └── 不空 ──▶ 「已经有数据了」：
                 直接启动，上面 1-5 步全部跳过 ⏭️
                 MYSQL_DATABASE 连看都不看一眼
```

**所以 `03` 那个思考题的答案是：不会。**

你的 `mysql-data` 卷里早就有数据了（你的 `rbac-mysql` 都跑了 30 多个小时），MySQL 一看"这儿已经有库了"，整个初始化流程直接跳过。你把 `MYSQL_DATABASE` 改成 `rbac_test`、改成 `hello_world`，它**根本不读**。

> 🔑 **`MYSQL_DATABASE`、`MYSQL_ROOT_PASSWORD`、`initdb.d` 里的脚本，全都是「出厂设置」，不是「每次启动都生效的配置」。**
>
> 这是个超级经典的坑，几乎人人都踩过一次：
> - "我明明改了 `MYSQL_ROOT_PASSWORD`，为什么还是老密码能登？"
> - "我在 `initdb.d` 里加了张表的 SQL，为什么重启后没有？"
>
> 答案都一样：**数据目录不空，它就不看。**

### 5.3 那怎么才能让它重新生效？

只有一个办法：**把数据目录清空**，让 MySQL 以为自己是全新的。

也就是——**删掉那个卷**。而删卷的命令，正好就是我们欠的第三笔债：`docker compose down -v`。

现在你应该能理解为什么这两件事是同一件事了：

```
docker compose down -v
      │
      └─▶ 删掉 rbac-server_mysql-data 卷
            │
            └─▶ 下次 up 时，/var/lib/mysql 是空的
                  │
                  └─▶ MySQL 触发「首次初始化」
                        ├─ MYSQL_DATABASE 生效了 ✅
                        ├─ MYSQL_ROOT_PASSWORD 生效了 ✅
                        └─ initdb.d 的脚本跑了 ✅

                        …代价是：原来的数据全没了 💀
```

**改配置生效**和**数据全丢**，是同一个动作的两面。这就是为什么 `down -v` 是核按钮。

## 六、`:ro` —— 只读挂载

看 `caddy` 服务的挂载（第 112-115 行，真实内容）：

```yaml
    volumes:
      - ./config/caddy/Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy-data:/data      # 证书持久化，重建容器不会重新申请（避免 LE 限流）
      - caddy-config:/config
```

第一行末尾多了个 `:ro`——**read-only，只读**。加上它之后，容器**只能读，不能写**这个文件。哪怕容器里的进程是 root，想改也会直接报错。

`nginx` 服务也是同样的写法（第 129 行）：

```yaml
      - ./config/nginx/nginx.conf:/etc/nginx/nginx.conf:ro
```

**为什么配置文件要加 `:ro`？**

因为 bind mount 是**双向的**——容器往这个路径写东西，会**真的改到你项目里的文件**。这就有风险了：

- 某个进程的 bug、或者容器里跑的脚本，可能悄悄把你的 `Caddyfile` 改了。
- 你 `git status` 一看，配置文件莫名其妙变了，还不知道是谁干的。

加上 `:ro`，等于告诉 Docker：**这文件是我给你看的，不是给你改的。**

> 🔑 **凡是"我给容器读的配置"，都该加 `:ro`。**
>
> 这是**最小权限原则**在挂载上的体现：不需要写权限，就别给写权限。成本是多打三个字符，收益是排除一整类"文件被容器偷偷改了"的诡异问题。

注意对比：**同一个服务里，`caddy-data:/data` 就没加 `:ro`**——因为那是命名卷，Caddy 要往里写证书，必须可写。**配置只读，数据可写**，界限很清楚。

顺便说一下 `caddy-data` 那行的注释，它藏着一个真实的生产教训：

```yaml
      - caddy-data:/data      # 证书持久化，重建容器不会重新申请（避免 LE 限流）
```

Caddy 会自动去 Let's Encrypt 申请 HTTPS 证书。而 **Let's Encrypt 有严格的频率限制**（同一域名每周只能申请几次）。如果不挂这个卷，你每次 `docker compose down && up` 证书就没了、又得重新申请——**折腾几次就会被限流，然后你的网站几小时内都签不出证书**。挂上卷，证书活得比容器长，重建容器直接复用。

**这就是"数据必须活得比容器长"最生动的例子。**（`06` 讲 Caddy 时会展开。）

## 七、还债 3：`down` vs `down -v` 实验

说好了要做的实验。**这个实验建议你亲手做一遍**——看见比听见管用得多。

> ⚠️ **先看清楚**：下面的实验会**真的删掉你 `rbac` 库里的数据**。你现在这个是本地开发库，删了也就重新初始化一下。但请务必确认你没有什么舍不得的数据。如果不放心，跳过第 3 步，只做第 1、2 步（那部分是安全的）。

### 第 1 步：先存点数据进去

```bash
docker exec -it rbac-mysql mysql -uroot -prbac_root_123 -e \
  "CREATE DATABASE IF NOT EXISTS test_persist; \
   CREATE TABLE test_persist.t (id INT, note VARCHAR(50)); \
   INSERT INTO test_persist.t VALUES (1, '我能活下来吗');"
```

确认一下写进去了：

```bash
docker exec rbac-mysql mysql -uroot -prbac_root_123 -e "SELECT * FROM test_persist.t;"
```

### 第 2 步：`down`（不带 `-v`）—— 数据应该还在

```bash
cd deploy
docker compose down          # 删容器、删网络，卷不动
docker volume ls | grep mysql-data    # 👀 卷还在！
docker compose up -d
```

等 mysql 变成 healthy（`docker compose ps` 看一眼），然后：

```bash
docker exec rbac-mysql mysql -uroot -prbac_root_123 -e "SELECT * FROM test_persist.t;"
```

**数据还在。** 容器被删了又重建，是个全新的容器——但它挂的是同一个卷，所以数据一点没少。

> 这就是日常运维的常规操作：升级镜像、改配置、重启服务，都是 `down` + `up`，**数据安然无恙**。

### 第 3 步：`down -v` —— 见证核按钮

```bash
docker compose down -v       # 💀 连卷一起删
docker volume ls | grep mysql-data    # 👀 没了！
docker compose up -d
```

等 mysql 起来（**这次会慢很多**，因为它在做首次初始化——正是第五节讲的那个流程），然后：

```bash
docker exec rbac-mysql mysql -uroot -prbac_root_123 -e "SELECT * FROM test_persist.t;"
```

```
ERROR 1049 (42000): Unknown database 'test_persist'
```

**数据没了。彻底没了。没有回收站，没有二次确认。**

顺便验证一下 `initdb.d` 确实又跑了一遍：

```bash
docker exec rbac-mysql mysql -uroot -prbac_root_123 -e "SHOW DATABASES;"
```

`rbac` 库回来了——那是 `01-init.sql` 和 `MYSQL_DATABASE` 重新执行的结果。**空数据目录 → 触发初始化**，第五节讲的流程，你刚刚亲眼看见了。

### 实验结论

| 命令 | 容器 | 网络 | **卷（数据）** | 什么时候用 |
|---|---|---|---|---|
| `docker compose stop` | 停但不删 | 保留 | ✅ 保留 | 临时停一下 |
| `docker compose down` | **删除** | **删除** | ✅ **保留** | 日常：升级、改配置、重启 |
| `docker compose down -v` | **删除** | **删除** | 💀 **删除** | 只在"我确实要从零开始"时 |

> 🔑 **把 `-v` 当核按钮看。**
>
> 它的合理用途只有一个：**本地开发时，我想要一个全新的、干净的数据库。**（比如你改了 `initdb.d` 的脚本想重新跑、或者数据被测试搞乱了想重置。）
>
> **在任何有真实数据的环境上，永远不要打这三个字符。** 而且注意——`-v` 挨着 `down` 很近，手快一点就出去了。

>
> 从 `01` 手动 `docker run` 一个 mysql 开始，到现在读懂一整套编排的核心层——回头看看 `01` 那条你觉得又长又难记的命令，是不是已经没什么神秘感了？

`redis` 的卷更简单，就一行（第 55 行）：

```yaml
    volumes:
      - redis-data:/data
```

命名卷，`/data` 是 redis 镜像存 AOF 文件的位置——正好对应 `03` 里 `command` 配的那个 `--appendonly yes`。**开了 AOF 持久化却不挂卷，等于白开**：容器一删，AOF 文件跟着没，重启照样丢数据。**两个配置必须配对出现**，这是个很容易漏的坑。

### 练习 5（思考题，不用敲命令）

假设你把 `mysql` 的卷配置从：

```yaml
      - mysql-data:/var/lib/mysql
```

改成：

```yaml
      - ./data/mysql:/var/lib/mysql
```

会发生什么？能跑吗？有什么后果？

<details>
<summary>点开看答案</summary>

**能跑，但一身毛病。**

1. **数据搬家了**：从 Docker 管理的卷，变成你项目目录下的 `deploy/data/mysql/`。你能 `ls` 看到一堆 MySQL 的数据文件了。
2. **性能变差**：Mac 上 bind mount 要跨越"你的系统 ↔ Docker 的 Linux 虚拟机"这道墙，数据库这种高频读写会明显变慢。
3. **可能起不来**：权限问题。容器里的 mysql 进程（UID 999）不一定有权限写你 Mac 上那个目录。
4. **git 灾难**：`deploy/data/` 会出现在 `git status` 里。你得赶紧加 `.gitignore`，不然几百兆的数据库文件就要进仓库了。
5. **误删风险**：一个 `git clean -fdx` 或者手滑删文件夹，数据库就没了。

**还有个隐蔽的**：`down -v` **不会删它**了！因为 `-v` 只删命名卷，管不着 bind mount。听起来像好事（数据更安全了），但也意味着你想重置数据库时，得手动 `rm -rf ./data/mysql`——**反而更容易出事**，因为 `rm -rf` 比 `down -v` 危险多了。

结论：**数据用命名卷，这不是随便选的。**
</details>

## 附：答案与解析

> 建议先自己想一遍再点开。想不出来不丢人，但直接看答案，这节就白读了。

<details>
<summary><b>1. Docker 靠什么区分命名卷和 bind mount？</b></summary>

**看冒号左边有没有"路径的样子"。**

| 左边长什么样 | 是什么 |
|---|---|
| 就是个名字，**没有斜杠**（`mysql-data`） | **命名卷** |
| 以 `./`、`/`、`../` 开头（`./config/mysql/init`） | **bind mount** |

就这么一条规则，没有别的。

这也意味着一个隐蔽的坑：你想挂当前目录下的 `data` 文件夹，**必须写 `./data`，不能写 `data`**——后者会被当成一个叫 `data` 的命名卷，Docker 会默默给你建一个空卷，然后你对着空目录怀疑人生。
</details>

<details>
<summary><b>2. `01` 的实验里数据丢在哪儿了？</b></summary>

丢在**容器的可写层**里。

容器的文件系统是临时的，你写的东西都落在容器自己那一层可写层上，**这层的命运和容器绑死**——`docker rm` 删掉容器，这层跟着一起蒸发。

加了 `-v mysql-data:/var/lib/mysql` 之后，容器内 `/var/lib/mysql` 这个路径被**卷盖住了**，MySQL 往那儿写的数据实际上落在卷里。卷是独立于容器存在的，**容器删了卷还在**。

一句话：**不是数据"没保存"，是它保存在了一个跟着容器一起死的地方。**
</details>

<details>
<summary><b>3. `mysql-data` 的真实路径？为什么 Mac 上打不开？Linux 上呢？</b></summary>

真实路径（`docker volume inspect rbac-server_mysql-data` 的 `Mountpoint`）：

```
/var/lib/docker/volumes/rbac-server_mysql-data/_data
```

注意卷的真名带着 `rbac-server_` 前缀，那是 `03` 学的 `name:` 贴上去的。

**Mac 上打不开**：Docker Desktop 的引擎跑在一个**隐藏的 Linux 虚拟机**里。这个路径是**虚拟机内部的路径**，你的 Mac 文件系统里压根没有 `/var/lib/docker` 这个目录。

**阿里云那台 Linux 上就能**：那儿 Docker 是原生跑的，没有中间的虚拟机，`sudo ls /var/lib/docker/volumes/` 直接看得到。

但即使能看，也**不建议直接去动**——要看内容走正门：`docker exec rbac-mysql ls /var/lib/mysql`。
</details>

<details>
<summary><b>4. 为什么数据用命名卷、配置用 bind mount？</b></summary>

**核心分工**：命名卷装"容器产生的数据"（往里**写**），bind mount 送"你写好的配置"（往外**读**）。

**数据为什么不用 bind mount**（任举其一）：
- **性能**：Mac/Windows 上 bind mount 要跨越"你的系统 ↔ Docker 虚拟机"这道墙，数据库高频读写会慢一个量级。
- **权限**：容器里 mysql 进程是 UID 999，bind mount 会把宿主机权限带进去，经常"没权限写"。
- **误删**：数据躺在项目目录里，`git clean -fdx` 一把梭就没了。

**配置为什么不用命名卷**：因为你需要**随时编辑**它——改 `Caddyfile`、改初始化 SQL，改完还要 `git commit` 让同事拿到。塞进命名卷里你连编辑都费劲。
</details>

<details>
<summary><b>5. `initdb.d` 里的脚本什么时候执行？改完重启会跑吗？</b></summary>

**只在数据目录 `/var/lib/mysql` 为空时执行一次。**

**改完重启不会跑。** 你的卷里早有数据了，MySQL 启动时一看"这儿已经有库了"，整个初始化流程（建系统表、读 `MYSQL_DATABASE`、跑 `initdb.d`）**全部跳过**。

想让它重新跑，只有一个办法：**把数据目录清空** → `docker compose down -v` → 下次 `up` 时触发首次初始化。

代价当然是**原有数据全没**。
</details>

<details>
<summary><b>6. 改了 `MYSQL_ROOT_PASSWORD` 为什么还是老密码能登？</b></summary>

和第 5 题**是同一个原因**：`MYSQL_ROOT_PASSWORD` 是**出厂设置**，只在首次初始化（数据目录为空）时被读取，用来设置 root 密码。

密码设好之后，它就**存进数据库的用户表里**了——那是卷里的数据。之后每次启动，MySQL 直接从表里读用户和密码，**环境变量看都不看**。

所以你改 `.env` 完全没用，数据库里那条记录纹丝不动。

**想生效的两条路**：
1. `docker compose down -v` 重新初始化 —— **代价：数据全没**。
2. 进数据库手动改：`ALTER USER 'root'@'%' IDENTIFIED BY '新密码';` —— **数据保住了**，生产环境改密码就得这么来（参见 `docs/ops/01-更换默认密码与密钥.md`）。

理解了"出厂设置 vs 运行时配置"这个区分，这类问题就再也不会困扰你了。
</details>

<details>
<summary><b>7. `:ro` 是什么？为什么 `Caddyfile` 加了、`caddy-data` 没加？</b></summary>

`:ro` = **read-only**，容器只能读、不能写。哪怕容器里是 root，想改也报 `Read-only file system`。

**`Caddyfile` 加**：它是 bind mount，而 bind mount 是**双向的**——容器往那个路径写东西，会**真的改到你项目里的文件**。加 `:ro` 就杜绝了"配置文件被容器偷偷改了、`git status` 里莫名其妙多出改动"这类诡异问题。这是**最小权限原则**：不需要写，就别给写。

**`caddy-data:/data` 不加**：那是命名卷，装的是 Caddy 自动申请的 **HTTPS 证书**。Caddy 必须能往里写，加了 `:ro` 它就没法保存证书了。

**配置只读，数据可写**——界限很清楚。
</details>

<details>
<summary><b>8. `stop` / `down` / `down -v` 分别做了什么？</b></summary>

| 命令 | 容器 | 网络 | **卷（数据）** | 用在什么时候 |
|---|---|---|---|---|
| `docker compose stop` | 停但**不删** | 保留 | ✅ 保留 | 临时停一下，待会还要起 |
| `docker compose down` | **删除** | **删除** | ✅ **保留** | 日常：升级镜像、改配置、重启 |
| `docker compose down -v` | **删除** | **删除** | 💀 **删除** | 只在"我确实要从零开始"时 |

`stop` 和 `down` 的区别：`stop` 之后容器还在（`docker ps -a` 看得到），`start` 就能原地复活；`down` 是把容器整个删了，`up` 是**造一个新的**。

但对**数据**来说这俩没区别——都保留。真正的分水岭是那个 `-v`。
</details>

<details>
<summary><b>9. redis 配了 `--appendonly yes` 但没挂卷会怎样？</b></summary>

**等于白开。**

`--appendonly yes` 开启 AOF 持久化，redis 会把每条写命令记进 AOF 文件，存放位置是容器内的 `/data`。

但如果不挂 `redis-data:/data`，这个 `/data` 就只是**容器可写层里的一个普通目录**——容器一删，AOF 文件跟着蒸发，重启后 redis 空空如也。

**你辛辛苦苦记了一路日志，日志本身却是一次性的。**

> 🔑 **持久化配置 和 卷挂载 必须配对出现。** 只做一半，等于没做——而且更糟：你会以为自己有持久化，直到出事那天才发现没有。

同理，mysql 也一样：镜像默认就往 `/var/lib/mysql` 写数据，但不挂卷，那个目录就是一次性的——**这正是 `01` 那个实验的真相**。
</details>
