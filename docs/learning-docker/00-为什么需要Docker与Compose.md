## 一、先讲痛点：没有 Docker 的世界有多难受

假设你今天要在一台新电脑上把咱们这个 RBAC 项目跑起来。后端要连数据库和缓存，于是你得：

1. 装 **MySQL 8.4**，配好账号密码、字符集、时区，建库建表。
2. 装 **Redis 7.4**，设好密码、开启持久化。
3. 万一以后还要加 **RabbitMQ、Kafka、Elasticsearch**……每个都要单独装、单独配。
4. 换一台电脑（比如上线用的阿里云服务器），上面 1、2、3 全部**再来一遍**。

这中间的坑你大概能想象：

- "我本地是 MySQL 8.0，服务器是 8.4，行为不一样，出 bug 了。"
- "同事装的 Redis 没开密码，我的开了，代码在他那儿能跑我这儿连不上。"
- "装 Elasticsearch 把系统环境搞乱了，卸载还卸不干净。"

这就是那句经典抱怨：**"在我电脑上明明是好的啊（works on my machine）。"**

> 🔑 根本矛盾：**软件运行需要一整套环境**（操作系统库、依赖、配置、端口、数据目录），而每个人、每台机器的环境都不一样。

## 二、Docker 是什么：用"集装箱"理解

Docker 的解法，和现实世界里**集装箱（container）**解决国际货运的思路一模一样。

在集装箱出现前，货物形状千奇百怪（桶装、袋装、箱装），装船、转火车、上卡车，每次都要重新搬运、重新捆扎，效率极低还容易坏。集装箱把货物**统一封装成标准尺寸的铁箱子**：无论箱子里装的是香蕉还是家具，船、火车、吊车只认这个标准箱子，怎么运都一样。

Docker 做的事就是：**把一个软件 + 它需要的整套环境，一起打包进一个标准"集装箱"里。** 这个箱子在你的 Mac 上、在同事的 Windows 上、在阿里云的 Linux 上，跑起来**行为完全一致**。

它带来三个直接好处：

| 好处 | 具体到我们项目 |
|------|----------------|
| **环境一致** | 你本地和阿里云跑的都是同一个 `mysql:8.4` 镜像，不会有版本差异 |
| **隔离干净** | MySQL、Redis 各在各的箱子里互不干扰，删掉箱子系统一点不脏 |
| **秒级启停** | 一条命令起一整套中间件，不用一个个手动安装配置 |

## 三、三个必须先分清的名词：镜像、容器、仓库

这三个词会贯穿整个学习过程，先用做菜来打个比方，混个脸熟即可（阶段 1 会正式讲）：

| 名词 | 一句话 | 生活类比 |
|------|--------|----------|
| **镜像（Image）** | 一个只读的"打包好的软件模板"，比如 `mysql:8.4` | **菜谱 + 备好的食材**，是死的、不会变 |
| **容器（Container）** | 由镜像**启动起来**的、正在运行的实例 | **按菜谱做出来的那盘菜**，是活的、能吃能改 |
| **仓库（Registry）** | 存放镜像、供人下载的地方，默认是 Docker Hub | **菜谱网站**，你从上面下载别人写好的菜谱 |

一句话串起来：**从仓库拉下镜像，用镜像启动出容器。**

```
  Docker Hub（仓库）          你的机器
 ┌──────────────┐   docker pull   ┌─────────────┐  docker run  ┌──────────────┐
 │  mysql:8.4   │ ──────────────► │  镜像(模板)  │ ───────────► │ 容器(运行中)  │
 │  redis:7.4   │                 │             │              │ 真的在跑数据库 │
 └──────────────┘                 └─────────────┘              └──────────────┘
```

> 🔑 同一个镜像可以启动出**多个**容器，就像同一份菜谱可以做出很多盘菜。

## 四、那 Compose 又是什么：从"一个箱子"到"一整套编排"

Docker 本身一次管**一个**容器。可我们项目要同时跑一堆：MySQL、Redis、后端、前端、Caddy……

如果只用原始 `docker` 命令，你得手动敲很多行：给每个容器起名字、连网络、设密码、挂数据目录、还要注意"先起 MySQL 再起后端"的顺序……敲一次就够呛，换台机器还得重来。

**Docker Compose** 就是来解决这个的：**把"要起哪些容器、每个怎么配、谁依赖谁"全部写进一个 `docker-compose.yml` 文件，然后一条命令 `docker compose up` 全部起来。**

打个比方：

- `docker run` 像是**你亲手一道菜一道菜地炒**。
- `docker compose` 像是**一张宴席菜单 + 一个总厨**：菜单（`docker-compose.yml`）写清楚上哪些菜、每道怎么做、上菜顺序，总厨照单全办。

> 🔑 Compose 的核心价值：**用一个文本文件，把一整套服务的编排"固化"下来，可复现、可版本管理、可一键启停。**

## 五、我们项目的 `deploy/` 目录鸟瞰

现在打开你项目的 `deploy/` 目录，它长这样：

```
deploy/
├── docker-compose.yml        ← 主角：整套服务的"宴席菜单"
├── .env                       ← 密码等变量（被 compose 自动读取）
└── config/                    ← 挂进容器里的各种配置文件
    ├── mysql/init/01-init.sql ← MySQL 首次启动时自动执行的建库脚本
    ├── nginx/nginx.conf        ← nginx 配置（扩展层才用）
    └── caddy/Caddyfile         ← Caddy 的 HTTPS 反代配置
```

`docker-compose.yml` 里定义的服务，被分成了三层，用一个叫 **profile** 的开关控制"这次起哪些"（阶段 6 细讲）：

| 层 | 包含的服务 | 什么时候起 |
|----|-----------|-----------|
| **核心层**（默认） | `mysql`、`redis`、`backend`、`frontend`、`caddy` | 平时开发、上线都要 |
| **扩展层**（`--profile extra`） | `nginx`、`rabbitmq` | 需要消息队列时 |
| **完整层**（`--profile full`） | `kafka`、`elasticsearch`、`kibana` | 需要搜索/日志分析时 |

对应的常用命令（现在只需眼熟，别急着敲）：

```bash
cd deploy
docker compose up -d                                  # 只起核心层
docker compose --profile extra up -d                  # 核心层 + 扩展层
docker compose --profile extra --profile full up -d   # 全部
docker compose down                                   # 停掉（数据还在）
docker compose down -v                                # 停掉并清空数据（慎用）
```

## 六、这套编排里，各个服务是怎么协作的

把核心层画成一张图，先感受一下"谁连谁"（细节后面每节展开）：

```
             外网用户
                │ HTTPS (443)
                ▼
        ┌───────────────┐
        │     caddy     │  唯一对外入口，自动申请 HTTPS 证书
        └───────┬───────┘
                │ 内网
                ▼
        ┌───────────────┐
        │   frontend    │  nginx 发前端页面 + 把 /api 转给后端
        └───────┬───────┘
                │ 内网 /api
                ▼
        ┌───────────────┐
        │    backend    │  Spring Boot 应用
        └───┬───────┬───┘
            │       │
     ┌──────▼──┐ ┌──▼──────┐
     │  mysql  │ │  redis  │   数据库 + 缓存
     └─────────┘ └─────────┘

     （这几个箱子都挂在同一个内网 rbac-net 上，靠"服务名"互相找到对方）
```

这里藏着一堆我们后面要逐个吃透的知识点，先埋个伏笔：

- 为什么 `backend` 连数据库时能直接写 `DB_HOST: mysql`，而不是写 IP？→ **阶段 4：服务名即 DNS**
- 为什么要保证 `mysql` 先"健康"了，`backend` 才启动？→ **阶段 4：healthcheck + depends_on**
- 为什么 `frontend` 不直接对外，非要藏在 `caddy` 后面？→ **阶段 6：expose vs ports**
- MySQL 容器删了，数据为什么还在？→ **阶段 5：命名卷**
- 后端、前端没有现成镜像，怎么变成容器的？→ **阶段 2：Dockerfile 多阶段构建**

## 动手练习（本节）

1. **确认 Docker 已装好**：打开终端，敲 `docker --version` 和 `docker compose version`，能打印出版本号就说明环境 OK（装不上先别慌，阶段 1 会处理）。
2. **通读一遍主文件**：用编辑器打开 `deploy/docker-compose.yml`，**不用看懂**，只做一件事——数一数 `services:` 下面一共定义了几个服务，把它们的名字抄下来，对照本文第五节的三层表格，看看每个属于哪一层。
