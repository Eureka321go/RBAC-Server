## 二、`networks`：给容器们拉一个内部对讲频道

### 2.1 先看声明

文件最底下（第 211-213 行）：

```yaml
networks: #声明服务通信网络
  rbac-net:
    driver: bridge
```

然后每个服务里都有一行：

```yaml
    networks: [rbac-net]
```

还是 `03` 讲过的"**声明 vs 使用**"那套分工：顶层 `networks:` 是去后勤登记"我要开一个叫 rbac-net 的频道"，服务里的 `networks: [rbac-net]` 是"把我也接进这个频道"。

`driver: bridge` 是网络类型，也是最常用的一种，你可以先粗暴理解成"**给这些容器接了一台虚拟交换机**"。接在同一台交换机上的容器，彼此能通；没接的，就在外面。

> 沿用 `00` 的宴席类比：`rbac-net` 就是**后厨内部的对讲频道**。凉菜台、热菜台、打荷位都戴着同一个频道的耳机，喊一声就能沟通；而餐厅大堂的客人不在这个频道上，听不见，也插不上话。

### 2.2 `driver` 还能填什么？

Docker 内置了这么几种网络驱动。**你 90% 的时候只会用 `bridge`**，但知道另外几个的存在，能帮你理解 `bridge` 到底在做什么——以及为什么它是这里的正确答案。

| driver | 一句话 | 容器有独立 IP？ | 典型场景 |
|---|---|---|---|
| **`bridge`** | 虚拟交换机，容器组成一个内网，和宿主机隔离 | ✅ 有 | **单机多容器互联——本项目、以及绝大多数 Compose 项目** |
| `host` | 容器**直接共用宿主机的网络栈**，没有隔离 | ❌ 就是宿主机的 | 极致性能、需要抓宿主机流量、UDP 广播类应用 |
| `none` | 完全没网，只有 `lo` 回环 | ❌ 没网 | 纯计算任务、刻意断网的沙箱 |
| `overlay` | **跨主机**组网，多台机器上的容器连成一个网 | ✅ 有 | Docker Swarm 集群，单机用不上 |
| `macvlan` | 容器在**物理局域网**上有自己的 MAC 和 IP，路由器看它就像一台真机 | ✅ 物理网段的 IP | 容器必须以独立设备身份出现在局域网（老旧设备对接、网络监控） |
| `ipvlan` | 和 `macvlan` 类似，但**共用宿主机的 MAC**，只分 IP | ✅ 物理网段的 IP | 交换机限制了 MAC 数量的环境 |

后三个（`overlay`/`macvlan`/`ipvlan`）你现阶段完全可以忽略——单机开发碰不到。真正值得对比一下的是 `host` 和 `none`。

#### `host` 模式：把隔离墙拆了

`host` 的意思是"**容器不要自己的网络了，直接用宿主机的**"。后果很直接：

```
bridge 模式（本项目）              host 模式
──────────────────                ──────────
容器有自己的 IP 172.18.0.2         容器就用宿主机的网络
容器内 :8080 是容器的 8080          容器内监听 :8080 == 宿主机的 8080
需要 ports: "8080:8080" 才能从      不需要 ports，因为压根没有"内外"之分
宿主机访问                          （写了也会被直接忽略）
```

听起来省事，但代价很大：

- **`ports` 完全失效**，端口是直接抢宿主机的。你的 mysql 容器一起来就霸占宿主机 3306，想改成 13306？做不到，得去改 MySQL 自己的配置。
- **容器之间没有隔离**，两个容器都想用 8080 就直接冲突，`01` 那个"端口已被占用"的错误会天天见。
- **服务名 DNS 没了**——大家都在宿主机网络上，`mysql` 这个名字没人认，只能写 `localhost` 或真实 IP。

> ⚠️ **Mac 上尤其别用 `host`。** Docker Desktop 的引擎跑在一个隐藏的 Linux 虚拟机里（这也是 `01` 答疑 Q2 里你找不到卷目录的原因）。所以 `host` 模式共享的是**那台虚拟机的网络**，不是你 Mac 的网络——行为跟 Linux 上完全不一样，是个经典的踩坑点。

那 `host` 什么时候有用？主要是**性能敏感**（少一层 NAT 转发）和**需要接收宿主机网卡上的广播/组播流量**（比如某些网络扫描、游戏服务器发现协议）的场景。日常 Web 应用用不上。

#### `none` 模式：真的一点网都没有

容器里只剩一个 `lo` 回环网卡，连 DNS 都没有。用途很窄，但很实在：跑一个**只做计算、不需要联网**的任务（比如批量图片处理），断网是最彻底的安全隔离——**它想偷偷外传数据都办不到**。

#### 所以本项目为什么是 `bridge`？

对着上面的表格看，答案就很显然了：

1. **单机部署** → 用不上 `overlay`。
2. **需要容器互联** → 排除 `none`。
3. **需要端口隔离和映射灵活性** → 排除 `host`（不然 `backend` 那个"不映射 8080、只让内网访问"的设计根本没法实现）。
4. **不需要容器直接暴露在局域网** → 用不上 `macvlan`。

`bridge` 是唯一同时满足"容器之间能通"+"和宿主机隔离"+"端口映射可控"的选项。**它不是默认所以被选中，而是选中了才是对的。**

### 2.3 一个大坑：`bridge` 和 `bridge` 不是一回事

这里有个 Docker 的历史包袱，非常容易踩：

Docker 自带一个**名字就叫 `bridge` 的内置网络**。你 `docker run` 时什么网络都不指定，容器就默认接到它上面——`01` 里你手动跑的那个 `my-test-mysql` 就在这个网络里。

而本项目的 `rbac-net` 是**你自己建的网络**（只是恰好也用 `bridge` 这个驱动）。这两者有一个**致命区别**：

| | 内置的 `bridge` 网络 | 自定义网络（如 `rbac-net`） |
|---|---|---|
| 容器之间能通吗 | 能（走 IP） | 能 |
| **能用服务名互相访问吗** | **❌ 不能！** | **✅ 能** |
| 怎么来的 | Docker 装好就有 | 你在 compose 里声明 |

> 🔑 **只有「自定义网络」才有内置 DNS。**
>
> 下一小节要讲的"服务名即域名"，**前提就是你用了自定义网络**。在 Docker 内置的那个 `bridge` 网络里，容器之间只能靠 IP 互相访问，写 `mysql` 是解析不出来的（老教程里那个已废弃的 `--link` 参数就是为了绕开这个限制才存在的）。
>
> 这就是为什么本项目要费劲声明一个 `rbac-net`，而不是图省事什么都不写——**声明自定义网络，换来的就是"服务名即域名"这个能力。**

（补充一句：如果你在 compose 里**完全不写 `networks`**，Compose 会自动帮你建一个叫 `项目名_default` 的**自定义**网络并把所有服务塞进去——所以那样也有 DNS，是能跑的。换句话说，Compose 从一开始就在替你规避这个坑。但**显式声明**网络仍然更好：意图清楚，而且后面 `06` 讲纵深防护时，你会需要"某些服务只在某个网络里"这种精确控制。）

### 2.4 关键：服务名就是域名

现在回答问题 1。

**只要两个容器在同一个自定义网络里，就能用对方的「服务名」当域名互相访问。** Docker 内置了一个 DNS 服务器，专门干这件事：`mysql` 这个词发出去，Docker 的 DNS 就告诉你"哦，它现在的 IP 是 172.18.0.2"。

```
backend 容器                                      mysql 容器
──────────                                        ──────────
Java 代码要连 "mysql:3306"
      │
      ├─▶ 问 Docker 内置 DNS："mysql 是谁？"
      │        │
      │        └─▶ 答："172.18.0.2"（都在 rbac-net 上，我认识它）
      │
      └─────────────── 连过去 ──────────────────▶  :3306 ✅
```

那**为什么非得搞这一套？直接写 IP 不行吗？**

不行，而且是三重不行：

| 直接写 IP 的问题 | 服务名怎么解决 |
|---|---|
| 容器 IP 是 Docker 动态分配的，**每次重建都可能变** | 服务名永远不变，Docker 自己去追踪 IP |
| 你没启动之前，根本不知道 IP 是多少，**没法提前写进配置** | 服务名你写 compose 的时候就定好了 |
| 换台机器部署，IP 全变，配置得重改 | 一份配置到处跑 |

> 🔑 **`DB_HOST: mysql` 里的 `mysql`，是 `services:` 下面那个服务名，不是 `container_name`。**
>
> 这个坑很多人踩。本项目里 `mysql` 服务的 `container_name` 是 `rbac-mysql`——但 `backend` 里写的是 `mysql`，不是 `rbac-mysql`。**Compose 的 DNS 认的是服务名。**（`container_name` 也能解析，但那是给人看的名字，别依赖它。）
>
> 所以 `03` 里我说"服务名很重要"，就是这个意思：它不只是个标签，它是**容器之间互相称呼的地址**。

### 2.5 顺便：`3306` 这个端口和 `ports` 没关系

一个高频困惑：`backend` 写 `DB_PORT: "3306"`，而 `mysql` 的 `ports` 是 `"3306:3306"`——是不是因为映射了才能连？

**不是。这俩毫无关系。**

回想 `01` 讲的端口映射方向：`ports: "3306:3306"` 是**宿主机端口 : 容器端口**，它解决的是"**我在 Mac 上用 Navicat 连数据库**"这个需求——把容器的端口捅到宿主机上。

而 `backend` 连 `mysql` 走的是**内部网络**，压根不经过宿主机：

```
你的 Mac（宿主机）
├── Navicat ──▶ localhost:3306 ──[ports 映射]──┐
│                                              ▼
└── Docker                            ┌─────────────┐
    └── rbac-net（内部频道）           │ mysql 容器  │
        ├── backend ──── mysql:3306 ──▶│   :3306     │
        └── ...                        └─────────────┘
                  ↑
          走内部网络，和 ports 完全无关
```

**证据**：看 `backend` 服务，它自己**根本没有 `ports` 字段**，最后还有一行注释写着：

```yaml
    networks: [rbac-net]
    # 不映射 8080 到宿主机，只让 frontend 容器走内网反代
```

`backend` 没对宿主机暴露任何端口，但 `frontend` 照样能反代到它。**只要在同一个网络里，容器的所有端口彼此都是通的**，不需要 `ports`。

> 🔑 **`ports` 是"对外开窗户"，不是"对内开门"。**
> - 容器之间互访 → 只要同网络，**什么都不用配**。
> - 宿主机/外网要访问容器 → 才需要 `ports`。
>
> 这个区分是**安全的基础**：本项目 `mysql` 映射了 3306 是为了本地开发方便，而 `backend` 故意不映射 8080——外界碰不到它，只有 `frontend` 能从内网找它。`06` 讲 Caddy 时会把这个思路推到极致。

## 三、`healthcheck`：怎么判断"这玩意儿真的能用了"

### 3.1 先讲那个经典事故

想象一下这个场景，几乎每个后端都撞过：

```
00:00  docker compose up -d
00:01  mysql 容器启动了 ✅（进程跑起来了）
00:01  backend 容器启动了 ✅
00:02  backend: 我要连数据库！
00:02  mysql: 我还在初始化数据目录呢，30 秒后再来
00:02  backend: 连不上，Connection refused 💥 挂了
00:30  mysql: 我好了，可以用了
       backend: （已经死了，没人告诉它）
```

**问题的根源**：容器"**启动了**"和服务"**能用了**"，是两回事。

MySQL 容器起来的一瞬间，`docker ps` 里它就是 `Up` 状态了——但它内部还在初始化数据目录、建系统表、跑你的初始化 SQL，可能要几十秒才真正能接受连接。这段时间它是"活着但不能干活"。

> 就像后厨的师傅：**人已经到岗了**（容器 Up），但他还在磨刀、烧水、备料，你这会儿冲进去喊"来份宫保鸡丁"，他只能瞪你一眼。**人到了 ≠ 能出菜了。**

### 3.2 `healthcheck` 就是"你好了没？"

`healthcheck` 的作用是：让 Docker **定期敲门问一句"你好了没"**，直到听见"好了"，才把这个容器标记成 `healthy`。

看 `mysql` 的（第 40-44 行，真实内容）：

```yaml
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost", "-p${MYSQL_ROOT_PASSWORD:-rbac_root_123}"]
      interval: 10s
      timeout: 5s
      retries: 10
```

四个字段逐个拆：

| 字段 | 值 | 什么意思 |
|---|---|---|
| `test` | `["CMD", "mysqladmin", "ping", ...]` | **敲门的方式**。Docker 会**在容器内部**执行这条命令；**退出码 0 = 健康**，非 0 = 不健康 |
| `interval` | `10s` | **多久敲一次**。每 10 秒问一遍 |
| `timeout` | `5s` | **等多久算超时**。一次敲门 5 秒没回应，这次就算失败 |
| `retries` | `10` | **连着失败几次才判死刑**。连续 10 次失败 → 状态变 `unhealthy` |

把这四个字段串起来读：**每 10 秒在容器里跑一次 `mysqladmin ping`，每次最多等 5 秒；连续失败 10 次就认定它废了。** 最长容忍时间大约是 10 × 10s = 100 秒，对 MySQL 冷启动来说是够用的。

再看 `test` 这条命令本身：

- `mysqladmin ping` —— MySQL 自带的探活工具，**它不查数据、不管业务，只问一句"服务端能应答吗"**，能应答就返回退出码 0。
- `-h localhost` —— 连本机。注意这是**在 mysql 容器内部**执行的，所以 `localhost` 就是 mysql 自己。
- `-p${MYSQL_ROOT_PASSWORD:-rbac_root_123}` —— 带密码。**注意这里又出现了 `03` 学的变量替换**，而且 `-p` 和值之间**不能有空格**（MySQL 命令行的历史包袱），所以只能这么紧挨着写。

`redis` 的同理，只是换了工具（第 56-60 行）：

```yaml
    healthcheck:
      test: ["CMD", "redis-cli", "-a", "${REDIS_PASSWORD:-rbac_redis_123}", "ping"]
      interval: 10s
      timeout: 5s
      retries: 10
```

`redis-cli ping` 正常会返回 `PONG`。`-a` 是密码参数（对应 `03` 里 `command` 设的那个 `--requirepass`）。

> 🔑 **`test` 要选"轻量但真实"的命令。**
> - **别太重**：每 10 秒跑一次的东西，别去 `SELECT` 全表，那是自残。
> - **别太轻**：只检查"进程在不在"是没意义的——进程在但死锁了、连接池满了，照样不能用。
>
> `mysqladmin ping` 正好卡在中间：它**真的走了一遍网络连接和认证**（所以要带密码），证明"我能接客"，但又不碰任何业务数据。这就是探活命令的标准姿势。

### 3.3 看看效果

```bash
cd deploy
docker compose ps
```

你会在 `STATUS` 列看到类似这样的东西：

```
NAME           STATUS
rbac-mysql     Up 2 minutes (healthy)      ← healthcheck 说它能用
rbac-redis     Up 2 minutes (healthy)
rbac-backend   Up 2 minutes                ← 没配 healthcheck，只有 Up
```

三种状态要分清：

| 状态 | 含义 |
|---|---|
| `Up` | 容器进程活着。**仅此而已**，能不能用不知道 |
| `Up (healthy)` | 配了 healthcheck，而且**探活通过**了 |
| `Up (health: starting)` | 配了 healthcheck，还在探，**没通过也没判死**（宽限期内） |
| `Up (unhealthy)` | 配了 healthcheck，**连续失败超过 retries 次**了 |

**注意 `Up (unhealthy)` 这个组合**——容器还在跑，Docker 不会因为不健康就把它杀了。healthcheck 只负责**报告状态**，不负责处置。至于谁会看这个报告并采取行动，就是下一节的事了。

## 四、`depends_on`：等谁、等到什么程度

### 4.1 两种写法，天差地别

本项目里 `depends_on` 出现了两次，**写法完全不同**，这个对比是本节最值钱的地方。

**写法一：`backend` 等 mysql/redis（第 81-85 行）**

```yaml
    depends_on:
      mysql:
        condition: service_healthy
      redis:
        condition: service_healthy
```

**写法二：`frontend` 等 backend（第 99-100 行）**

```yaml
    depends_on:
      - backend
```

差别在哪？

| | `- backend`（不带 condition） | `condition: service_healthy` |
|---|---|---|
| 等到什么时候 | 等 backend 容器**启动**了就走 | 等 mysql **healthcheck 通过**了才走 |
| 保证了什么 | 只保证**启动顺序** | 保证**真的能用了** |
| 前提 | 无 | 被等的服务**必须配 healthcheck** |
| 相当于 | "他人到了" | "他能出菜了" |

> 🔑 **不带 condition 的 `depends_on` 只管顺序，不管死活。**
>
> `depends_on: [backend]` 的含义仅仅是"**backend 先启动，我后启动**"。至于 backend 启动完的下一毫秒就崩了，它不管——顺序满足了，任务完成。
>
> 这是新手最大的误解："我都写 `depends_on` 了，为什么还是连不上数据库？"——**因为你只排了队，没等人家准备好。**

### 4.2 为什么本项目要这么区别对待

这不是随便写的，是想清楚过的：

**`backend` 必须用 `service_healthy`**，因为它一启动就要连 MySQL 和 Redis（Spring Boot 启动时初始化连接池、跑 MyBatis 配置）。MySQL 没准备好，Spring Boot 直接启动失败退出。这是硬依赖，**必须等到真能用**。

**`frontend` 用普通的 `depends_on` 就够**，因为它是 nginx——nginx 启动时并不需要立刻访问 backend，它只是在那儿等着请求。等真有用户来访问 `/api` 的时候，backend 早就好了。就算那一瞬间 backend 没好，nginx 也只是返回一个 502，重试一下就行，**不会像 Spring Boot 那样直接死掉**。

而且 `frontend` 想用 `service_healthy` 也用不了——**backend 压根没配 `healthcheck`**（你可以翻回去看第 65-86 行，确实没有）。没有 healthcheck，就没有"健康"这个状态可等。

### 4.3 完整的启动时序

把这一节学的东西拼起来，`docker compose up -d` 那一刻实际发生的事：

```
  t=0    mysql、redis 同时开始启动
         │                          （backend 在等，什么都不做）
  t=1s   两个容器都 Up 了
         │  但 healthcheck 说：health: starting
         │
  t=10s  第一次探活：mysqladmin ping → 失败（还在初始化）
  t=20s  第二次探活 → 失败
  t=30s  第三次探活 → 成功！✅
         │  mysql 状态变成 (healthy)
         │  redis 也 (healthy) 了
         ▼
  t=30s  ★ 条件满足，backend 才开始启动
         │  Spring Boot 起来，连 mysql:3306 —— 一次就连上 ✅
         ▼
  t=45s  backend Up
         ▼
  t=45s  frontend 开始启动（它只等 backend "Up"，不等健康）
         ▼
  t=50s  caddy 启动（depends_on: frontend）
```

对比一下没有 healthcheck 的世界：`t=1s` 时 backend 就冲上去连 mysql，撞个头破血流，然后死掉。

> **这就是那个"让无数人加班到半夜"的 bug。** 它最阴险的地方在于：**在你本地不复现**。你本地 MySQL 早就跑着呢，一直是 healthy，backend 上来就能连；一到全新部署的服务器上，所有容器同时冷启动，MySQL 要初始化 30 秒——啪，挂了。

### 4.4 一个重要的边界

> 🔑 **`depends_on` 只在"启动那一刻"起作用，之后就不管了。**
>
> 如果 mysql 跑到半夜挂了，`depends_on` **不会**把 backend 也停掉、也不会等 mysql 回来再重启它。它管的是**启动时序**，不是**运行时依赖**。
>
> 运行期间数据库断了怎么办？那是**应用自己的事**——连接池要有重连机制、要有超时和熔断。容器编排能帮你解决"启动顺序"，但**解决不了"运行时容错"**，别指望错了对象。
>
> 兜底的是 `03` 学过的 `restart: unless-stopped`：backend 真的因为连不上数据库而崩了，Docker 会把它重启，重启后 mysql 可能就好了。**这是补救，不是解决方案。**

**再看一眼细节**：

```bash

```

这会吐出 healthcheck 的**完整历史**：当前状态、连续失败次数、最近几次探活的输出和退出码。排查"为什么一直 unhealthy"的时候，这条命令是第一现场。

### 练习 2：手动执行一次探活命令

`healthcheck.test` 里那条命令，你可以自己在容器里跑一遍——这能让你彻底相信它没有魔法：

```bash
docker exec rbac-mysql mysqladmin ping -h localhost -prbac_root_123
echo "退出码：$?"
```

应该看到 `mysqld is alive`，退出码 `0`。

**再故意让它失败**，把密码写错：

```bash
docker exec rbac-mysql mysqladmin ping -h localhost -pwrong_password
echo "退出码：$?"
```

退出码变成非 0 了——**这就是 Docker 判定"不健康"的全部依据**。healthcheck 不看你输出了什么漂亮的文字，**只看退出码**。

> 提示：`docker exec` 是 `01` 学过的"钻进容器里执行命令"。

### 练习 3：验证服务名 DNS

钻进 backend 容器，用服务名去 ping mysql：

```bash
docker exec rbac-backend getent hosts mysql
```

你会看到类似 `172.18.0.2   mysql`——**服务名被解析成了容器 IP**，这就是 Docker 内置 DNS 干的活。

再试试解析一个不在网络里的名字，比如 `docker exec rbac-backend getent hosts kafka`（kafka 在 `full` profile 里，默认没起），应该什么都返回不了。

**思考题**：如果你把 `mysql` 服务的 `networks: [rbac-net]` 这一行删掉，`backend` 还能连上它吗？

<details>
<summary>点开看答案</summary>

**连不上。** 服务名解析的前提是**两个容器在同一个网络里**。删掉之后 mysql 会被扔到默认网络，跟 `rbac-net` 上的 backend 互不相识，DNS 解析直接失败——报错大概是 `UnknownHostException: mysql`。

这也解释了为什么本项目**每个服务都老老实实写了 `networks: [rbac-net]`**：漏掉一个，那个服务就成了聋子。

（严格说，Compose 在你完全不写 `networks` 时会自动建一个默认网络并把所有服务塞进去，所以"全都不写"反而能跑。但只要你显式声明了网络，就必须**每个服务都写全**，写一半是最糟的情况。）
</details>

## 附：答案与解析

> 建议先自己想一遍再点开。想不出来不丢人，但直接看答案，这节就白读了。

### 自检问题

<details>
<summary><b>1. 为什么选 `bridge`？改成 `host` 还成立吗？</b></summary>

选 `bridge` 是因为它是**唯一同时满足**这四条的驱动：

1. **单机部署** → 用不上 `overlay`（那是跨主机的）。
2. **容器之间要能通** → 排除 `none`（没网）。
3. **要端口隔离和映射灵活性** → 排除 `host`。
4. **容器不需要直接暴露在局域网** → 用不上 `macvlan` / `ipvlan`。

**改成 `host` 之后，`backend` 的设计直接崩掉。**

`backend` 现在的设计是"不映射 8080 到宿主机，只让 frontend 走内网反代"——这个设计的**前提就是容器有自己独立的网络空间**，8080 是"容器的 8080"，外界够不着。

`host` 模式下没有"内外"之分，容器监听 8080 **就是**宿主机的 8080，全世界都能访问。`ports` 写了也会被忽略，你**没有任何办法把它藏起来**。

一句话：**`host` 模式把隔离墙拆了，而 `backend` 的安全设计恰恰建立在那堵墙上。**

顺带，`host` 还会连累另外两件事：容器之间开始抢端口（`01` 那个"端口已被占用"会天天见），以及服务名 DNS 失效（大家都在宿主机网络上，没人认识 `mysql` 这个名字）。
</details>

<details>
<summary><b>2. 内置的 `bridge` 网络 和 `rbac-net`（也用 bridge 驱动）最关键的区别是什么？</b></summary>

**只有自定义网络才有内置 DNS——也就是"服务名即域名"这个能力。**

| | 内置的 `bridge` 网络 | 自定义网络（`rbac-net`） |
|---|---|---|
| 容器之间走 IP 能通吗 | 能 | 能 |
| **能用服务名互访吗** | **❌ 不能** | **✅ 能** |

在 Docker 内置的那个 `bridge` 网络里（`01` 你手动 `docker run` 的容器就在那儿），容器之间只能靠 IP 互相访问，写 `mysql` 是解析不出来的。老教程里那个已废弃的 `--link` 参数，就是为了绕开这个限制才存在的。

所以本项目费劲声明 `rbac-net`，**换来的就是 `DB_HOST: mysql` 这种写法能成立**。

**"用 bridge 驱动" ≠ "在内置的 bridge 网络里"**——同名不同物，这是 Docker 的历史包袱，也是最容易看混的地方。
</details>

<details>
<summary><b>3. `DB_HOST: mysql` 指的是服务名还是 container_name？</b></summary>

**服务名**，也就是 `services:` 下面那一级的 key。

本项目正好是个绝佳例子：`mysql` 服务的 `container_name` 是 **`rbac-mysql`**，但 `backend` 里写的是 **`mysql`**。如果 Docker 认的是 `container_name`，这套配置根本跑不起来。

（补充：Compose 也会给 `container_name` 建解析记录，所以写 `rbac-mysql` 通常也能通。但**别依赖它**——`container_name` 是给人看的名字，随时可能改；服务名才是编排里的正式身份。）
</details>

<details>
<summary><b>4. 删掉 `ports: "3306:3306"`，backend 还能连上 mysql 吗？</b></summary>

**能，完全不受影响。**

`ports` 是**宿主机 ↔ 容器**的映射，管的是"外面怎么进来"。而 backend 连 mysql 走的是 `rbac-net` **内部网络**，压根不经过宿主机。

**最有力的证据就在本项目里**：`backend` 服务自己根本没有 `ports` 字段（还专门写了注释"不映射 8080 到宿主机"），但 `frontend` 照样能反代到它。

删掉 `ports` 唯一的影响是：**你在 Mac 上用 Navicat 连不上 3306 了**。容器之间该怎么通还怎么通。

一句话：**`ports` 是对外开窗户，不是对内开门。**
</details>

<details>
<summary><b>5. healthcheck 根据什么判断"健康"？看输出内容吗？</b></summary>

**只看退出码（exit code）。0 = 健康，非 0 = 这次探活失败。**

**完全不看输出内容。** `mysqladmin ping` 打印的那句 `mysqld is alive` 是给人看的，Docker 一个字都不读。

练习 2 就是验证这一点：密码写错时，输出变了、退出码也变成非 0——**判定依据是后者**。

这也意味着你可以用任何命令做 test，只要它"成功时退出 0、失败时退出非 0"就行。
</details>

<details>
<summary><b>6. 最坏情况多久被标记成 unhealthy？</b></summary>

大约 **100 秒**（10 次 × 10s 间隔）。

严格说要看失败方式：
- 如果每次都是**快速失败**（比如立刻 connection refused），那就是 10 × `interval` ≈ **100 秒**。
- 如果每次都**卡到超时**，每轮要花 `timeout` 5s + 等 `interval` 10s，会更长一些。

所以 `retries: 10` 不是拍脑袋定的：它给了 MySQL **约 100 秒**的冷启动宽限。首次初始化数据目录（建系统表、跑初始化 SQL）几十秒很正常，retries 给小了，好好的服务会被冤枉成 unhealthy，`backend` 就永远等不到它。
</details>

<details>
<summary><b>7. 两种 depends_on 分别保证什么？为什么区别对待？</b></summary>

- `depends_on: [backend]` —— **只保证启动顺序**："backend 先启动，我后启动。" backend 启动完下一毫秒就崩了它也不管。
- `condition: service_healthy` —— **保证真的能用**：等到 mysql 的 healthcheck 通过才启动。前提是 mysql **必须配了 healthcheck**。

为什么区别对待：

**`backend` 必须用 `service_healthy`**：Spring Boot 启动时就要初始化数据库连接池，MySQL 没准备好 → 直接启动失败退出。**硬依赖**。

**`frontend` 用普通的就够**：nginx 启动时不需要访问 backend，它只是在那儿等请求。真有请求来的时候 backend 早好了；就算没好也只是返回 502，重试即可，**不会像 Spring Boot 那样直接死掉**。

而且 `frontend` 想用 `service_healthy` 也**用不了**——backend 压根没配 healthcheck，没有"健康"状态可等。
</details>

<details>
<summary><b>8. 半夜 mysql 挂了，depends_on 会把 backend 也停掉、等 mysql 好了再启动吗？</b></summary>

**不会。`depends_on` 只在"启动那一刻"起作用，之后完全不管。**

它管的是**启动时序**，不是**运行时依赖**。跑起来之后，两个容器就是各过各的日子了。

运行期间数据库断了，是**应用自己的事**：连接池的重连机制、超时、熔断降级。**容器编排解决不了运行时容错**，别指望错了对象。

兜底的是 `03` 学的 `restart: unless-stopped`：backend 真崩了 Docker 会重启它，重启时 mysql 可能就好了。但那是**补救，不是解决方案**。
</details>

<details>
<summary><b>9. 看到 `Up (unhealthy)`，Docker 会自动杀掉重启吗？</b></summary>

**不会。healthcheck 只负责"报告状态"，不负责"处置"。**

容器该跑还跑着，Docker 只是在状态栏上挂了个 `unhealthy` 的牌子。

那这个牌子有什么用？**给别人看的**：
- `depends_on: condition: service_healthy` 会看它，决定要不要放行；
- 你的监控系统可以看它、告警；
- Docker Swarm / Kubernetes 这类真正的编排系统会看它，做自动替换。

单机 Compose 的场景下，它主要就是**给 `depends_on` 用的，外加给你 `docker compose ps` 时提供诊断信息**。
</details>

### 练习 4（启动顺序）

<details>
<summary><b>对照答案</b></summary>

```
第 1 批：mysql、redis          —— 并行启动，谁也不等
         ↓（等两者 healthcheck 都通过）
第 2 批：backend               —— 等 mysql + redis 都 service_healthy
         ↓（等 backend 容器 Up 即可，不等健康）
第 3 批：frontend              —— depends_on: [backend]
         ↓（等 frontend 容器 Up 即可）
第 4 批：caddy                 —— depends_on: [frontend]
```

关键点：

1. **`mysql` 和 `redis` 是并行的**——它们互相之间没有 `depends_on`，Compose 会同时启动，不会排队。
2. **只有 `backend` 用了 `condition`**，所以只有它在"等健康"；后面 `frontend`、`caddy` 都只是"等 Up"，链条一节比一节松。
3. 这条依赖链的形状是有道理的：**越靠近数据的服务，依赖越硬**；越靠近用户的服务（nginx、caddy），越是"先起着，请求来了再说"。
</details>
