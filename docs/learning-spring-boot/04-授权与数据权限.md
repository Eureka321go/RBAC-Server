# 阶段 4 — 授权与数据权限【核心吃透 2】

> 阶段 3 解决了「**你是谁、你登没登录**」；阶段 4 解决「**你能干什么、你能看到哪些数据**」。
> 这是全项目**最难、也最能体现专业度**的一块——尤其是数据权限。读完你要能讲清「一次带数据权限的列表查询」是怎么被收窄的。

## 零、先建立「三层鉴权」的总心智模型

本项目的安全不是一道墙，而是**三道纵深防线**，一层比一层细：

```
①  Spring Security 登录判定          ← 阶段 3 已讲：没登录/令牌失效 → 401
        │ 已登录，进得来
        ▼
②  @PreAuthorize 权限码判定           ← 本阶段：没有 system:user:delete 这个权限 → 403
        │ 有权限，能调这个接口
        ▼
③  Service 层业务二次校验（红线）      ← 本阶段：就算有权限，也不许删超管/删自己
        │ 过了红线
        ▼
④  数据权限过滤                        ← 本阶段最难：能查用户列表，但只能看到你管得着的那些部门
```

**为什么要三层？记住一句安全红线**：
> 前端隐藏按钮只是「体验」，真正的安全必须在后端一层层再判。

- 第 ① 层挡「陌生人」；
- 第 ② 层挡「登录了但不该碰这功能的人」；
- 第 ③ 层挡「有权限但想干越界的坏事」（比如删掉超管、删掉自己）；
- 第 ④ 层挡「能用这功能、但想看不该看的数据」（越权查看别的部门）。

## 一、第二层：`@PreAuthorize` 权限码鉴权

### 1.1 长什么样（UserController）

```java
@GetMapping
@PreAuthorize("hasAuthority('system:user:list')")     // 要有"查看用户列表"权限
public Result<PageResult<UserVO>> page(UserQuery query) { ... }

@PostMapping
@PreAuthorize("hasAuthority('system:user:add')")      // 要有"新增用户"权限
public Result<Long> create(@Valid @RequestBody UserCreateRequest request) { ... }

@DeleteMapping("/{id}")
@PreAuthorize("hasAuthority('system:user:delete')")   // 要有"删除用户"权限
public Result<Void> delete(@PathVariable Long id) { ... }
```

- `@PreAuthorize` = 「**调这个方法之前**，先检查括号里的条件成不成立，不成立直接拒（403），根本进不了方法体」。
- `hasAuthority('system:user:delete')` = 「当前用户的权限集合里，**有没有** `system:user:delete` 这个权限码」。

### 1.2 它凭什么能判断？——串起阶段 3

还记得阶段 3 吗？三步就闭环了：

```
① 登录时 LoginUserAssembler 顺着"用户→角色→菜单"链路，
   查出这个用户的所有 permission_code，塞进 LoginUser.permissions
        ↓
② 每次请求，JwtAuthenticationFilter 把 LoginUser 写进 SecurityContext，
   LoginUser.getAuthorities() 把 permissions 变成 Security 的"权限对象"
        ↓
③ @PreAuthorize("hasAuthority('system:user:delete')") 就是去这个权限对象集合里找有没有这一条
```

- **能生效的总开关**在 `SecurityConfig` 上的 `@EnableMethodSecurity`（阶段 3 见过）——没有它，`@PreAuthorize` 就是废注解。
- **超管为什么啥都能点？** 阶段 3 讲过：超管登录时 `selectAllPermissionCodes()` 拿了全站权限码，所以任何 `hasAuthority(...)` 对它都成立。

### 1.3 权限码的命名规律

`system:user:delete` 这种三段式：`模块:资源:操作`。项目里成套出现：
`system:user:list / add / edit / delete / reset-password / assign-role`……前端按钮的显隐、后端接口的鉴权，用的是**同一套**权限码——这就是「一处定义，前后端共用」。

> ⚠️ 安全红线复习：前端可以靠权限码隐藏按钮（体验），但**后端这层 `@PreAuthorize` 才是真的拦截**。绕过前端直接调接口？没权限照样 403。

### 1.4 完整闭环：`@PreAuthorize("hasAuthority('system:user:add')")` 从数据库到放行的一生 ⭐

1.2 的「三步」是骨架，这里把每一环拆到真实代码，走一遍**新增用户**接口。串起来你就彻底通了。

```
┌────────────────────────────────────────────────────────────────────────┐
│  准备期（跟这次请求无关，是数据早就配好的）                                │
│  ① 数据库：sys_menu 有一行 permission_code = 'system:user:add'            │
│     （menu_type=BUTTON），并通过 sys_role_menu 挂给了某个角色              │
│  ② 这个角色又通过 sys_user_role 挂给了张三                                 │
└────────────────────────────────────────────────────────────────────────┘
                              │  张三登录时……
                              ▼
┌────────────────────────────────────────────────────────────────────────┐
│  登录期（每次登录跑一次）                                                  │
│  ③ LoginUserAssembler.assemble：                                          │
│     menuMapper.selectPermissionCodesByUserId(张三id)                      │
│     顺「用户→角色→菜单」JOIN 查出张三所有 permission_code                   │
│     → new HashSet<>(perms) → loginUser.setPermissions(...)               │
│     （若是超管：走 selectAllPermissionCodes() 拿全站，所以超管啥都有）      │
│  ④ issueTokens：把这个 LoginUser 以 jti 为 key 存进 Redis 会话            │
└────────────────────────────────────────────────────────────────────────┘
                              │  张三点「新增」，带 token 发 POST /users……
                              ▼
┌────────────────────────────────────────────────────────────────────────┐
│  请求期（每次请求跑一次）                                                  │
│  ⑤ JwtAuthenticationFilter：验签 → 用 jti 查 Redis 拿回 LoginUser         │
│     → new UsernamePasswordAuthenticationToken(loginUser, null,           │
│                                        loginUser.getAuthorities())        │
│     → SecurityContextHolder.getContext().setAuthentication(...)          │
│     ★ getAuthorities() 把 Set<String> permissions 逐个包成                 │
│       SimpleGrantedAuthority("system:user:add") —— 变成 Security 认得的对象│
└────────────────────────────────────────────────────────────────────────┘
                              │  请求进到 UserController.create 之前……
                              ▼
┌────────────────────────────────────────────────────────────────────────┐
│  判定期（方法调用被拦截的一瞬间）                                          │
│  ⑥ @EnableMethodSecurity 让 Spring 给 UserController 生成了一个 AOP 代理   │
│     调 create() 前先被切面拦下，读到方法上的 @PreAuthorize                  │
│  ⑦ 解析表达式 hasAuthority('system:user:add')：                            │
│     去 SecurityContext 当前 Authentication 的 authorities 里找             │
│     有没有一条等于 "system:user:add"                                       │
│        ├─ 有 → 放行，真正进入 create() 方法体                              │
│        └─ 没有 → 抛 AccessDeniedException                                 │
│               → RestAccessDeniedHandler 返回 403（方法体一行都没执行）      │
└────────────────────────────────────────────────────────────────────────┘
```

**逐环对应的真实代码：**

| 环 | 文件 · 方法 | 关键代码 |
|----|-------------|----------|
| ③ 查权限码 | `LoginUserAssembler.assemble` | `menuMapper.selectPermissionCodesByUserId(user.getId())` → `loginUser.setPermissions(...)` |
| ⑤ 转成权限对象 | `LoginUser.getAuthorities` | `permissions.stream().map(SimpleGrantedAuthority::new)` |
| ⑤ 写入上下文 | `JwtAuthenticationFilter` | `new UsernamePasswordAuthenticationToken(loginUser, null, loginUser.getAuthorities())` |
| ⑥ 总开关 | `SecurityConfig` | 类上的 `@EnableMethodSecurity` |
| ⑦ 声明拦截点 | `UserController.create` | `@PreAuthorize("hasAuthority('system:user:add')")` |
| ⑦ 拒绝出口 | `RestAccessDeniedHandler` | 已认证但无权限 → 403 |

**三个最容易被忽略、但正是「闭环」关键的点：**

1. **`hasAuthority` 比的是「字符串完全相等」**。`getAuthorities()` 把权限码原样包成 `SimpleGrantedAuthority`，没有加 `ROLE_` 前缀（那是 `hasRole` 的事）。所以 `system:user:add` 这串在 DB、在 `LoginUser.permissions`、在 `@PreAuthorize` 里必须**一模一样**，错一个字符就 403。
2. **判定读的是「当前线程」的 SecurityContext**（阶段 3 的 ThreadLocal 口袋）。所以它天然只认「这次请求的张三」，不会串到别人——功能鉴权和数据权限都建立在这个基础上。
3. **`@PreAuthorize` 是「Pre」——方法体一行都不会执行**就被挡。它靠 AOP 代理实现，所以只有被 Spring 管理的 Bean（Controller/Service）上的注解才生效；类内部方法自己调自己（不走代理）不触发，这点进阶了解即可。

> 🔑 一句话闭环：**权限码在 DB 定义 → 登录时顺 JOIN 查进 `LoginUser.permissions` 存 Redis → 每次请求过滤器把它转成 authorities 写进当前线程上下文 → `@EnableMethodSecurity` 的 AOP 代理在进方法前用 `hasAuthority` 做字符串比对 → 命中放行、缺失 403。** 全程「一处定义（DB），处处比对（`@PreAuthorize`）」。

## 二、第三层：Service 业务红线（有权限也不许乱来）

有 `system:user:delete` 权限的管理员，是不是就能删任何人？**不行**。看 `UserService.delete`：

```java
public void delete(Long id) {
    requireUser(id);                                   // 用户得存在
    if (id.equals(SecurityUtils.getUserId())) {        // ① 不能删自己
        throw new BusinessException("user.cannotDeleteSelf");
    }
    if (isSuperAdmin(id)) {                             // ② 不能删超级管理员
        throw new BusinessException("user.superAdminUndeletable");
    }
    userMapper.deleteById(id);
    // 顺带清理该用户的角色、岗位关联
    userRoleMapper.delete(...);
    userPostMapper.delete(...);
}
```

**为什么权限之外还要这层？** 因为「有删除权限」是**功能级**的判断，但有些操作**无论谁都不能做**：

| 红线 | 代码位置 | 防止 |
|------|----------|------|
| 不能删自己 | `delete` | 管理员手滑把自己删了 |
| 不能删超管 | `delete` | 系统失去最高权限账号 |
| 不能禁用超管 | `updateStatus` | 变相锁死超管 |
| 不能禁用自己 | `updateStatus` | 把自己锁在门外 |
| 非超管不能改超管 | `update` / `resetPassword` | 越权篡改最高账号 |
| 超管角色不可被改/分配 | `update` / `assignRoles` | 有人偷偷给自己塞超管角色 |

这些叫**业务二次校验**，是 RBAC 系统的「安全红线」，`@PreAuthorize` 管不了这么细，必须写在 Service 里。注意它用 `SecurityUtils.getUserId()` 拿「当前操作人」——从阶段 3 的线程口袋里取。

## 三、第四层：数据权限（本项目最难点）

### 3.1 先讲清「数据权限」到底是什么

前三层管的是「**能不能用某个功能**」；数据权限管的是「**同一个功能里，你能看到哪些行数据**」。

举例：销售部经理张三和市场部经理李四，**都有** `system:user:list` 权限（都能打开「用户管理」页面），但：
- 张三只该看到**销售部**的人；
- 李四只该看到**市场部**的人；
- 超管能看到**所有人**。

同一个列表接口，**返回的数据因人而异**——这就是数据权限。它是通过在 SQL 的 `WHERE` 里**动态加部门过滤条件**实现的。

### 3.2 五种数据范围

每个**角色**上挂一个 `data_scope`（阶段 3 装配时读过），共 5 种，范围由大到小：

| 数据范围 | 含义 | 能看到 |
|----------|------|--------|
| `ALL` | 全部 | 所有数据（超管、总监） |
| `CUSTOM_DEPT` | 自定义部门 | 手工指定的若干部门（存在 `sys_role_dept`）|
| `OWN_DEPT_CHILD` | 本部门及子部门 | 自己部门 + 下面所有层级子部门 |
| `OWN_DEPT` | 仅本部门 | 只有自己所在部门 |
| `SELF` | 仅本人 | 只有自己创建的数据 |

> 一个人可能有多个角色，取的是**并集里范围最大的**（阶段 3 `mergeDataScope` 讲过优先级）；只要有任一角色是 `ALL`，就直接放行全部。

### 3.3 计算数据范围：`DataScopeService.calculate()`

这是把「角色的 data_scope」翻译成「一份可查询的部门/用户 id 清单」的地方：

```java
public DataScopeQuery calculate() {
    LoginUser loginUser = SecurityUtils.getLoginUserOrNull();
    if (loginUser == null) return new DataScopeQuery();     // 未登录：什么都看不到
    if (SecurityUtils.isSuperAdmin()) return DataScopeQuery.all();  // 超管：全部放行

    List<SysRole> roles = roleMapper.selectRolesByUserId(loginUser.getUserId());
    Set<Long> deptIds = new HashSet<>();     // 收集"可见部门 id"
    boolean includeSelf = false;             // 是否额外放行"本人创建的"
    Map<Long, List<Long>> childrenIndex = null;

    for (SysRole role : roles) {             // ★遍历用户每个角色，取并集
        switch (role.getDataScope()) {
            case "ALL" -> { return DataScopeQuery.all(); }        // 任一角色 ALL → 直接全放行
            case "CUSTOM_DEPT" -> {                               // 自定义：查 sys_role_dept
                List<SysRoleDept> customs = roleDeptMapper.selectList(...按 roleId...);
                for (SysRoleDept rd : customs) {
                    deptIds.add(rd.getDeptId());
                    if (rd.getIncludeChildren() == 1)             // 勾了"含子部门"就递归收集
                        collectDescendants(rd.getDeptId(), childrenIndex, deptIds);
                }
            }
            case "OWN_DEPT_CHILD" -> {                            // 本部门 + 所有子部门
                deptIds.add(loginUser.getDeptId());
                collectDescendants(loginUser.getDeptId(), childrenIndex, deptIds);
            }
            case "OWN_DEPT" -> deptIds.add(loginUser.getDeptId()); // 仅本部门
            case "SELF" -> includeSelf = true;                     // 仅本人
        }
    }

    DataScopeQuery query = new DataScopeQuery();
    query.setDeptIds(deptIds);
    query.setSelfUserId(includeSelf ? loginUser.getUserId() : null);
    return query;
}
```

产出的 `DataScopeQuery` 是个「结果说明书」，告诉 Service 层该怎么过滤：

```java
public class DataScopeQuery {
    private boolean all;         // true = 不加任何限制（超管/ALL）
    private Set<Long> deptIds;   // 允许看的部门 id 集合
    private Long selfUserId;     // 非空 = 额外放行"本人创建"的数据
}
```

### 3.4 部门树递归：`collectDescendants`（面试常考）

`OWN_DEPT_CHILD` 和「自定义含子部门」都要「找出一个部门下面的所有子孙部门」。部门是一棵树（`parent_id` 指向上级），要**递归**往下收集：

```java
// 先把所有部门按"父id → 子id列表"建成索引，避免反复查库
private Map<Long, List<Long>> buildChildrenIndex() {
    List<SysDept> all = deptMapper.selectList(null);
    return all.stream()
            .filter(d -> d.getParentId() != null)
            .collect(Collectors.groupingBy(SysDept::getParentId,          // 按父id分组
                    Collectors.mapping(SysDept::getId, Collectors.toList())));
}

// 递归：把 deptId 的所有子孙 id 塞进 acc
private void collectDescendants(Long deptId, Map<Long, List<Long>> idx, Set<Long> acc) {
    List<Long> children = idx.get(deptId);          // 直接子部门
    if (children == null) return;                   // 没有子部门 → 递归到底，返回
    for (Long child : children) {
        if (acc.add(child)) {                        // add 返回 true 说明是新加的（防环/防重复）
            collectDescendants(child, idx, acc);     // ★对每个子部门再往下钻
        }
    }
}
```

**递归怎么理解**：处理「部门A」= 「记下 A 的直接子部门」+「对每个子部门再重复同样的动作」。一层层往下,直到某部门没有子部门(`children == null`)就停。比如：

```
总公司(1)
├─ 华东(2)          collectDescendants(1) 会依次收进 2,3,4,5,6...
│   ├─ 上海(4)
│   └─ 杭州(5)
└─ 华南(3)
    └─ 广州(6)
```

`collectDescendants(1)` → 收 2、3 →（对 2）收 4、5 →（对 3）收 6 → 都到底 → 最终 `{2,3,4,5,6}`。

> `if (acc.add(child))` 这句一箭双雕：`Set.add` 如果元素已存在会返回 `false`,所以它既去重、又**防止部门数据成环时无限递归**(健壮性)。

### 3.5 把数据范围翻译成 SQL：`UserService.page`

计算好的 `DataScopeQuery` 最终在这里变成真实的 `WHERE` 条件：

```java
public PageResult<UserVO> page(UserQuery query) {
    DataScopeQuery scope = dataScopeService.calculate();   // ① 先算当前用户能看的范围
    var wrapper = Wrappers.<SysUser>lambdaQuery()
            .like(...username...).like(...nickname...)     // 普通搜索条件（阶段2讲过）
            .eq(query.getDeptId() != null, SysUser::getDeptId, query.getDeptId())
            .eq(...status...);

    // ② ★数据权限过滤
    if (!scope.isAll()) {                                   // 超管/ALL 跳过，不加限制
        if (scope.hasDeptScope() && scope.hasSelfScope()) {
            // 又有部门范围、又有本人范围 → (部门 IN (...) OR 本人创建)
            wrapper.and(w -> w.in(SysUser::getDeptId, scope.getDeptIds())
                    .or().eq(SysUser::getCreatedBy, scope.getSelfUserId()));
        } else if (scope.hasDeptScope()) {
            wrapper.in(SysUser::getDeptId, scope.getDeptIds());       // 只按部门
        } else if (scope.hasSelfScope()) {
            wrapper.eq(SysUser::getCreatedBy, scope.getSelfUserId()); // 只看本人创建
        } else {
            wrapper.apply("1 = 0");   // ★什么范围都没有 → 恒假条件 → 查出空
        }
    }

    IPage<SysUser> page = userMapper.selectPage(Page.of(...), wrapper.orderByDesc(SysUser::getId));
    // ...转 VO、填部门/角色名、返回分页...
}
```

**几个关键点：**
- **`!scope.isAll()`**：超管/ALL 范围**不加任何过滤**，能看全部。
- **`.in(deptId, deptIds)`**：生成 `AND dept_id IN (2,3,4,5,6)`——只查可见部门的用户。这就是数据权限落到 SQL 的样子。
- **`1 = 0` 恒假条件**：如果一个用户算下来啥范围都没有,不能「不加条件=查全部」(那就漏权了!),而要**主动查出空**。这是**安全兜底**——数据权限的默认必须是「看不到」,不是「都能看」。
- **`SELF` 用 `created_by` 判断**：本人范围 = 「这条数据是我创建的」，靠 `created_by` 字段（阶段 2 的审计字段,由 `AuditMetaObjectHandler` 自动填）。

### 3.6 一次带数据权限的列表查询·全流程

```
张三(销售部经理, 角色数据范围=OWN_DEPT_CHILD) 打开用户管理页
   │  GET /api/system/users
   ▼
① @PreAuthorize('system:user:list')  → 张三有此权限，放行
   ▼
② UserService.page:
     dataScopeService.calculate()
        → 非超管 → 遍历角色 → OWN_DEPT_CHILD
        → 收集 销售部 + 其所有子部门 id = {10, 11, 12}
        → DataScopeQuery{ deptIds={10,11,12} }
   ▼
③ 拼 SQL：... WHERE deleted=0 AND dept_id IN (10,11,12) ORDER BY id DESC LIMIT ...
   ▼
④ 只返回这三个部门的用户 —— 张三看不到市场部、财务部的人
```

**安全红线复习**：数据权限（`dept_id`/`created_by` 过滤）**不可绕过、不可漏接列表接口**。任何返回列表的接口，都必须像 `page` 这样接上 `dataScopeService.calculate()`，否则就是数据越权漏洞。

## 四、动态菜单与按钮权限（回顾 + 补充）

授权除了「拦接口」，还要「**控制前端显示什么**」。这部分阶段 3 的 `AuthController` 见过接口，这里点透关系：

- `GET /auth/menus`（`currentUserMenus`）：返回当前用户可见的**菜单树**（超管全量 / 普通用户按链路查 `DIR/MENU`）。前端据此**动态生成路由和左侧菜单**——你没权限的模块，菜单根本不显示。
- `GET /auth/permissions`（`currentUserPermissions`）：返回当前用户的**权限码集合**。前端用它做**按钮级显隐**（`v-permission` / `PermissionButton`）——没 `system:user:delete` 就不渲染「删除」按钮。

> 但记住：这只是**体验层**。真正的安全是后端的 `@PreAuthorize` + Service 红线 + 数据权限。前端隐藏 ≠ 安全。

```
   │
   ▼ 全部通过 → 真正执行删除
```

**1.** ① Spring Security 登录判定（挡没登录/令牌失效的陌生人 → 401）；② `@PreAuthorize` 权限码（挡登录了但没这功能权限的人 → 403）；③ Service 业务二次校验（挡有权限但想干越界事的人，如删超管/删自己）。（数据权限可算第四层，挡越权看数据。）

**2.** 方法**执行前**判断（Pre）。依据是 `LoginUser.permissions` 里的权限码——登录时 `LoginUserAssembler` 顺「用户→角色→菜单」链路查出并装进去，每次请求由过滤器写入 SecurityContext，`getAuthorities()` 转成 Security 权限对象供 `hasAuthority` 比对。

**3.** 因为 `@PreAuthorize` 只是**功能级**判断（能不能用删除功能），而删超管/删自己是**无论谁都不允许**的业务红线。这属于**第三层**（Service 业务二次校验）。

**4.** 功能权限=「能不能用某功能」（如能否打开用户管理、能否点删除）；数据权限=「同一功能里能看到哪些行」（如同样能看用户列表，张三只看销售部、李四只看市场部）。

**5.** ALL=全部；CUSTOM_DEPT=手工指定的部门（sys_role_dept）；OWN_DEPT_CHILD=本部门+所有子部门；OWN_DEPT=仅本部门；SELF=仅本人创建。多角色取**并集里范围最大的**，任一角色 ALL 即全放行。

**6.** 因为部门是树（parent_id），要拿到「本部门下所有层级的子孙部门」必须一层层往下钻 → 递归。`if (acc.add(child))`：① `Set.add` 天然去重；② 已存在返回 false 就不再往下递归，**防止部门成环时无限递归**（健壮性）。

**7.** 若「不加条件」就等于查全部，那没有任何范围的人反而能看到所有数据 → 严重越权。`1 = 0` 是恒假条件，强制查出**空结果**。体现的原则：**数据权限默认必须是「看不到」（安全兜底 / 默认拒绝），不是「都能看」**。

**8.** 靠 `created_by` 字段过滤（`created_by = 当前用户id`）。该字段在插入数据时由 `AuditMetaObjectHandler` 自动填入「当时的登录用户 id」（阶段 2 审计字段）。

**9.** 前端隐藏只是体验，能被绕过（直接调接口、改前端代码）。真正的安全必须在后端：绕过前端直接调 `DELETE` 接口，后端 `@PreAuthorize` 照样 403。这是核心安全红线。
