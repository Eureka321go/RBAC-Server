# 阶段 7 · Spring Boot 进阶知识缺口与学习路线

完成前面的 00～06 章后，你已经能读懂并开发一个基于 Spring Boot 的 RBAC 系统：请求如何进入 Controller、如何完成登录认证和权限校验、Service 如何组织业务、MyBatis-Plus 如何访问数据库，以及异常和响应如何统一处理。

接下来缺少的不是“再学几个注解”，而是理解框架在复杂场景和生产环境中怎样工作。

## 2. 第一优先级：项目已经用了，但还没有系统学习

### 2.1 事务原理与并发控制

项目中已经多次使用 `@Transactional`，工作流实体还使用了 `@Version`。但仅知道“加上注解就有事务”是不够的，还要学习：

- 事务为什么依赖 Spring AOP 代理；
- 同一个类内部调用为什么可能导致事务失效；
- `REQUIRED`、`REQUIRES_NEW` 等传播行为；
- 读未提交、读已提交、可重复读和串行化的差异；
- 哪些异常默认回滚，为什么项目常写 `rollbackFor = Exception.class`；
- 乐观锁、悲观锁和数据库唯一约束分别解决什么问题；
- 两个人同时审批同一任务时，如何避免重复处理。

建议实践：以工作流“同一待办被并发审批”为案例，写一个并发测试，观察版本号冲突，并给前端返回明确的业务错误。

### 2.2 异步任务与线程池

项目已经使用 `@EnableAsync` 和 `@Async` 处理部分日志逻辑。还需要补充：

- 默认线程池为什么不适合直接用于生产；
- 核心线程数、最大线程数、队列容量和拒绝策略；
- 异步方法的异常为什么不会自动返回给调用者；
- 事务提交前启动异步任务可能产生什么问题；
- `SecurityContext`、日志追踪 ID 等上下文如何在线程间传递；
- 应用停止时怎样等待队列中的任务完成。

建议实践：为操作日志配置独立线程池、线程名和异常处理器，再验证应用关闭时是否会丢日志。

### 2.3 配置体系与多环境管理

当前配置集中在 `application.yml`，已经用环境变量覆盖 JWT 密钥，但还未形成完整的配置管理知识：

- 配置文件、环境变量和命令行参数的优先级；
- `application-dev.yml`、`application-test.yml`、`application-prod.yml`；
- `@Value` 与 `@ConfigurationProperties` 的取舍；
- 配置校验、默认值和类型安全；
- 密码、Token 密钥等敏感配置如何与代码仓库分离；
- 测试环境怎样覆盖 MySQL、Redis 和日志配置。

建议实践：将 `rbac.jwt` 改造成类型安全的配置类，并拆分开发、测试、生产三套配置。

### 2.4 自动配置、Bean 生命周期与代理

前面的章节介绍过 IoC 和自动配置的概念，但还需要继续回答：

- 一个 Starter 为什么只加入依赖就能工作；
- `@Configuration`、`@Bean`、组件扫描分别何时使用；
- `@ConditionalOnClass`、`@ConditionalOnMissingBean` 如何决定 Bean 是否创建；
- Bean 从实例化、依赖注入到销毁经历哪些阶段；
- 循环依赖为什么发生，为什么不应该依赖框架“帮忙解决”；
- Spring AOP 为什么通常只能拦截经过代理的公开方法；
- 如何查看自动配置条件报告，排查 Bean 冲突或缺失。

建议实践：写一个小型审计日志 Starter，并允许业务项目覆盖其默认 Bean。

### 2.5 Spring MVC 完整执行链

目前已经会写 Controller，但还可以继续向下学习：

- Filter、Interceptor、Controller Advice 和 AOP 的执行顺序与职责边界；
- 参数解析、JSON 反序列化和响应序列化；
- Jackson 的日期、枚举、空值和未知字段策略；
- 分组校验和自定义校验注解；
- 404、参数格式错误、业务异常如何形成统一错误协议；
- 文件上传、下载、流式响应和大请求限制。

建议实践：画出一次工作流审批请求的完整时序，并为所有失败情况定义统一的错误码和 HTTP 状态码。

## 3. 第二优先级：生产项目应补齐的能力

### 3.1 自动化测试体系

这是当前最明显的工程缺口。需要建立四层测试：

1. 纯 Java 单元测试：测试条件判断、审批人解析等无框架逻辑；
2. Web 切片测试：使用 MockMvc 测试参数校验、权限和响应结构；
3. 数据层测试：验证 SQL、逻辑删除、乐观锁和事务回滚；
4. 集成测试：启动 Spring 上下文，并连接隔离的 MySQL、Redis 环境。

需要学习 `JUnit 5`、Mockito、`@WebMvcTest`、`@SpringBootTest`、Spring Security Test 和 Testcontainers。

建议实践：先覆盖“登录成功/失败”“无权限访问”“审批并发冲突”三条关键链路。

### 3.2 数据库版本迁移

当前项目通过 `schema.sql` 和 `data.sql` 初始化数据库，适合学习和首次启动，但不适合持续升级生产数据库。需要学习 Flyway 或 Liquibase：

- 每次表结构变化生成不可变迁移脚本；
- 记录已执行版本；
- 区分结构迁移与演示数据；
- 失败后的修复和回滚策略；
- 多实例启动时如何避免重复迁移。

建议实践：将现有建表 SQL 设为基线，再增加一个工作流字段迁移版本。

### 3.3 可观测性与健康检查

只看控制台日志无法判断线上系统是否健康。需要学习：

- Spring Boot Actuator 的健康、信息和指标端点；
- readiness 与 liveness 的区别；
- Micrometer 如何统计请求耗时、错误率、连接池和 JVM 指标；
- 结构化日志、请求追踪 ID 和脱敏；
- 告警应围绕什么指标建立；
- 管理端点本身如何鉴权，避免泄露配置和环境信息。

建议实践：增加健康检查，并为“审批成功、审批失败、审批耗时”建立指标。

### 3.4 缓存设计

项目已经直接使用 Redis 保存登录状态，但尚未学习 Spring Cache 抽象和通用缓存设计：

- `@Cacheable`、`@CachePut`、`@CacheEvict`；
- Cache Aside 模式；
- 缓存穿透、击穿、雪崩和热 Key；
- 数据更新时如何保证缓存失效；
- 哪些权限数据可以缓存，哪些必须实时校验。

建议实践：缓存角色权限集合，并在角色授权变化后准确清理缓存。

### 3.5 定时任务与可靠后台任务

项目暂时没有 `@Scheduled`，但实际系统常见超时审批、过期 Token 清理和统计任务。需要学习：

- `@Scheduled` 的固定频率和 Cron 表达式；
- 多实例部署时为什么会重复执行；
- 分布式锁、任务幂等、失败重试和执行记录；
- 何时应该从简单定时任务升级到调度平台或消息队列。

建议实践：实现一个幂等的“超时待办扫描”任务，并确保两个应用实例不会重复处理。

### 3.6 API 文档与兼容性

需要补充 OpenAPI/Swagger、接口版本、字段兼容和弃用策略。重点不是生成一个页面，而是让接口契约可以被验证，并避免后端改字段导致前端静默出错。

建议实践：为工作流定义、发起、审批接口补齐 OpenAPI 描述和统一错误响应示例。

### 3.7 稳定性设计

调用数据库、Redis 或外部服务时，需要明确：

- 连接超时、读取超时和总超时；
- 哪些操作允许重试，哪些重试会造成重复写入；
- 幂等键、唯一约束和防重复提交；
- 限流、熔断、降级和隔离；
- 优雅停机如何停止接收请求并完成进行中的事务。

建议实践：为“发起流程”和“审批”设计幂等机制，而不是只在前端禁用按钮。

## 4. 第三优先级：按项目需要选择

这些内容不必一次性学完：

| 主题 | 适用场景 |
| --- | --- |
| Spring 事件、`@TransactionalEventListener` | 事务成功后发送通知、记录审计或刷新缓存 |
| RabbitMQ / Kafka | 任务需要可靠异步处理、削峰或跨系统通信 |
| OAuth2 / OIDC | 接入统一身份认证、第三方登录或微服务资源服务器 |
| WebFlux | 大量长连接或高并发 I/O；普通管理系统继续使用 MVC 即可 |
| 多模块与模块化单体 | 业务边界增多，需要隔离依赖和领域 |
| AOT / Native Image | 对启动速度和内存占用有明确要求 |
| Java 21 虚拟线程 | 存在大量阻塞 I/O，并经过压测证明值得引入 |

不要因为它们“高级”就立即加入项目。先由真实问题驱动技术选择。

## 5. 推荐学习顺序

### 阶段 7A：事务与工作流并发

目标：能解释每个事务边界，并保证同一任务不会被重复审批。

### 阶段 7B：配置、自动配置与 Bean 生命周期

目标：能独立排查“配置没有生效”“Bean 没创建”“AOP 没拦截”等问题。

### 阶段 7C：MVC 深入与统一接口契约

目标：能画出完整请求链路，并让所有错误都以一致格式返回。

### 阶段 7D：测试体系

目标：关键业务修改后，不依赖手工点页面确认是否回归。

### 阶段 7E：数据库迁移与可观测性

目标：系统可以安全升级，并能从指标、日志和健康检查定位线上问题。

### 阶段 7F：缓存、任务与稳定性

目标：面对高并发、重复请求和多实例部署时，仍能保证数据正确。

## 6. 学完后的自测清单

如果下面的问题都能结合当前项目回答，说明 Spring Boot 核心能力已经从“会使用”进入“能维护”：

- 为什么 `@Transactional` 加在某些方法上不生效？
- 两个请求同时审批一条待办，最终会发生什么？
- `Filter`、`Interceptor`、AOP 和 Controller Advice 应该分别处理什么？
- 为什么开发、测试、生产不能共用一份数据库和密钥配置？
- 怎样测试一个带 JWT 和权限注解的 Controller？
- 表结构升级时，怎样知道生产环境已经执行到哪个版本？
- Redis 不可用时，登录和权限校验会怎样失败？
- 应用显示“进程还活着”是否就代表它能正常提供服务？
- 一次审批耗时突然升高，应该查看哪些指标和日志？
- 应用重启时，异步日志和正在执行的请求会不会丢失？

## 7. 边界说明

MyBatis-Plus、JWT、MySQL、Redis、Flyway、消息队列并不都属于 Spring Boot 本身。Spring Boot 的核心价值是提供自动配置、依赖管理、配置体系、应用生命周期和生产运行支持，并把这些组件组合成一个可启动、可测试、可运维的应用。

下一步最值得先写的是“事务、乐观锁与工作流并发审批”。它既是当前代码已经存在的真实问题，也是从普通 CRUD 进入可靠业务系统的关键一步。
