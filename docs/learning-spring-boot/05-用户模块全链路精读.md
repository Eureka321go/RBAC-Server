## 零、先建立一个总心智模型：数据在「七件套」间怎么流动

一个请求进来，数据像在流水线上被逐层「换壳」：

```
       前端 JSON                                        前端 JSON
          │                                                ▲
          ▼                                                │
   ┌─────────────┐   DTO      ┌──────────┐  Entity  ┌──────────┐
   │ Controller  │ ────────▶ │ Service  │ ───────▶ │  Mapper  │ ──▶ MySQL
   │ 收请求/发响应 │           │ 业务逻辑  │           │ 只管 SQL │
   └─────────────┘ ◀──────── └──────────┘ ◀─────── └──────────┘
          ▲          VO           │  Entity ▲
          │                       ▼         │
      Result 包一层            Entity ⇄ VO 转换（UserVO.from）
```

**每层只干一件事，各司其职（这是能"类推"的根本原因）：**

| 层 | 职责一句话 | 绝不该干的事 |
|----|-----------|-------------|
| **Controller** | 收 HTTP 请求、做鉴权注解、调 Service、把结果用 `Result` 包好返回 | 不写业务逻辑、不碰 SQL |
| **DTO**（入参） | 接住前端传来的字段 + `@Valid` 校验格式 | 不是数据库表结构 |
| **Service** | **业务逻辑的唯一归属地**：校验、红线、事务、编排多个 Mapper | 不关心 HTTP、不拼 JSON |
| **Mapper** | 只管「一张表怎么增删改查」，MyBatis-Plus 生成大部分 SQL | 不写业务判断 |
| **Entity** | 和数据库表**一一对应**（字段=列） | 不直接返回给前端（含 password 等敏感字段） |
| **VO**（出参） | 返回给前端的「安全视图」，挑字段、拼展示名（deptName/roleNames） | 不含敏感字段 |

> 🔑 **DTO / Entity / VO 三个模型为什么要分开？**
> - **Entity** 有 `password`，直接返给前端就泄密 → 所以要 **VO** 挑字段。
> - 前端**新增**用户传的字段（含 `password`、`roleIds`）和数据库表结构不一样 → 所以要 **DTO** 接参 + 校验。
> - 一句话：**入口用 DTO 防脏数据，出口用 VO 防泄密，中间 Entity 贴着数据库。** 三层解耦，各自演进互不影响。

## 一、Controller：只做「收 / 转 / 包」

看 `UserController`，每个方法都是同一个套路，极其规整：

```java
@RestController
@RequestMapping("/system/users")           // 该模块统一前缀（再叠加 context-path /api）
public class UserController {

    private final UserService userService;  // 构造器注入（全项目统一风格）
    public UserController(UserService userService) { this.userService = userService; }

    @PostMapping                                        // POST /api/system/users
    @PreAuthorize("hasAuthority('system:user:add')")    // ← 第二层：功能权限（阶段 4）
    public Result<Long> create(@Valid @RequestBody UserCreateRequest request) {
        return Result.success(userService.create(request));   // 调 Service → 用 Result 包住
    }
}
```

**读 Controller 只需盯三样：**
1. **URL 与 HTTP 方法**：`@GetMapping`(查) / `@PostMapping`(增) / `@PutMapping`(整体改) / `@PatchMapping`(局部改，如改状态/密码) / `@DeleteMapping`(删)。
2. **鉴权注解** `@PreAuthorize(...)`：这个接口要什么权限码（阶段 4 已吃透）。
3. **入参 / 出参类型**：进来是什么 DTO、出去是什么 `Result<VO>`。

> Controller 里**几乎没有逻辑**——每个方法就一两行：调 Service、`Result.success(...)`。这正是「瘦 Controller、胖 Service」的分层原则。看懂一个方法，其余 9 个方法一眼就懂。

## 二、DTO 与 `@Valid`：把好入口第一道关

`UserCreateRequest`（新增用户的入参）：

```java
@Data
public class UserCreateRequest {
    @NotBlank(message = "{valid.username.notBlank}")     // 不能为空白
    @Size(min = 2, max = 32, message = "{valid.username.size}")   // 长度 2~32
    private String username;

    @NotBlank(message = "{valid.nickname.notBlank}")
    private String nickname;

    private String password;   // 可空：为空则用系统默认密码
    private Long deptId;
    // ...
    @Pattern(regexp = "ENABLED|DISABLED", message = "{valid.status.pattern}")  // 只允许这两个枚举值
    private String status;

    private List<Long> roleIds = new ArrayList<>();
    private List<Long> postIds = new ArrayList<>();
}
```

**关键机制：`@Valid` + Bean Validation**

- Controller 方法参数上写 `@Valid @RequestBody UserCreateRequest request` → Spring 在**进方法体前**自动按注解校验。
- 校验不过 → 抛 `MethodArgumentNotValidException` → 被 `GlobalExceptionHandler` 统一接住转成 400（见第四节）。**方法体一行都不执行**（和 `@PreAuthorize` 一样是「前置拦截」）。
- `message = "{valid.username.notBlank}"` 里的 `{...}` 是**国际化 key**，不是写死中文——中英错误提示同一套代码（见第六节）。

> 📌 对照法预告：其余模块的 DTO 也是这套 `@NotBlank / @Size / @Pattern`，只是字段不同。会读这一个就会读全部。

## 三、Service：业务逻辑的唯一归属地（本模块重头戏）

`UserService` 是整个模块最"厚"的一层。挑几个代表方法看透套路。

### 3.1 `create`：新增用户（事务 + 唯一性校验 + 加密 + 编排关联表）

```java
@Transactional                                   // ① 事务：下面多步要么全成功、要么全回滚
public Long create(UserCreateRequest req) {
    if (existsUsername(req.getUsername(), null)) {   // ② 业务校验：用户名不能重复
        throw new BusinessException("user.usernameExists");   // 抛国际化 key
    }
    SysUser user = new SysUser();                // ③ DTO → Entity 手工搬字段
    user.setUsername(req.getUsername());
    String raw = StringUtils.hasText(req.getPassword()) ? req.getPassword() : defaultPassword;
    user.setPassword(passwordEncoder.encode(raw));   // ④ ★密码一定 BCrypt 加密后才落库
    user.setStatus(req.getStatus() == null ? "ENABLED" : req.getStatus());  // ⑤ 缺省值兜底
    userMapper.insert(user);                     // ⑥ 插主表 sys_user（回填自增 id 到 user）
    replaceRoles(user.getId(), req.getRoleIds());    // ⑦ 编排关联表 sys_user_role
    replacePosts(user.getId(), req.getPostIds());    //    编排关联表 sys_user_post
    return user.getId();
}
```

**四个必须记住的点：**
- **`@Transactional`**：一个方法里改了 3 张表（sys_user / sys_user_role / sys_user_post），必须同生共死。中途抛异常 → 全部回滚，不会留下「有用户没角色」的脏数据。
- **密码永远加密**：`passwordEncoder.encode(raw)`，明文绝不落库（安全红线）。
- **DTO→Entity 手工 set**：本项目不搞自动映射，字段一个个搬，虽啰嗦但清晰可控。
- **关联表用「先删后插」**：`replaceRoles` = 先 `delete` 该用户所有旧角色关系，再按新 `roleIds` 逐条 `insert`。这是「多对多重新赋值」的通用写法，`update` 和 `assignRoles` 都复用它。

### 3.2 `page`：分页列表（数据权限 + 动态条件 + Entity→VO）

这段在阶段 4 已精读过数据权限部分，这里补它作为「查询模板」的骨架：

```java
public PageResult<UserVO> page(UserQuery query) {
    DataScopeQuery scope = dataScopeService.calculate();          // ① 算当前人能看哪些数据（阶段4）
    var wrapper = Wrappers.<SysUser>lambdaQuery()
        .like(StringUtils.hasText(query.getUsername()), SysUser::getUsername, query.getUsername())  // ② 动态条件
        .eq(StringUtils.hasText(query.getStatus()), SysUser::getStatus, query.getStatus());
    // ...（阶段4 讲过的数据权限 SQL 收敛，含 1=0 兜底）
    IPage<SysUser> page = userMapper.selectPage(Page.of(query.current(), query.size()),  // ③ 分页查
        wrapper.orderByDesc(SysUser::getId));
    List<UserVO> vos = page.getRecords().stream().map(UserVO::from).collect(Collectors.toList());  // ④ Entity→VO
    fillDeptAndRoles(vos);                                        // ⑤ 补展示字段：部门名/角色名/岗位名
    return PageResult.of(vos, page.getTotal(), page.getCurrent(), page.getSize());       // ⑥ 包成统一分页
}
```

- `.like(条件, 字段, 值)` 的 **3 参重载**：第一个参数为 `false` 时这个条件**不拼进 SQL**（阶段 2 讲过）——实现「填了才筛，没填就不筛」的动态查询。
- `fillDeptAndRoles`：Entity 里只有 `deptId`（一个数字），前端要显示「技术部」这种**名字**，所以查一次部门/岗位表做 id→name 映射，再逐个 VO 填上 `deptName / roleNames / postNames`。**这就是 VO 存在的意义：拼装「给人看」的展示数据。**

### 3.3 业务红线：有权限也不许乱来（第三层鉴权落点）

`@PreAuthorize` 只管「能不能用这个功能」，管不了「这次操作的对象合不合规」。后者写在 Service：

| 方法 | 红线 | 抛出的 key |
|------|------|-----------|
| `delete` | 不能删自己 | `user.cannotDeleteSelf` |
| `delete` | 不能删超管 | `user.superAdminUndeletable` |
| `update` | 非超管不能改超管 | `user.superAdminImmutable` |
| `updateStatus` | 不能禁用超管 / 不能禁用自己 | `user.superAdminUndisable` / `user.cannotDisableSelf` |
| `resetPassword` | 非超管不能重置超管密码 | `user.superAdminPwdImmutable` |
| `assignRoles` | 不能改超管角色 | `user.superAdminRoleImmutable` |

```java
public void delete(Long id) {
    requireUser(id);                                  // 不存在 → user.notFound
    if (id.equals(SecurityUtils.getUserId())) {       // ★ 当前操作人=被删对象？
        throw new BusinessException("user.cannotDeleteSelf");
    }
    if (isSuperAdmin(id)) {                            // ★ 被删的是超管？
        throw new BusinessException("user.superAdminUndeletable");
    }
    userMapper.deleteById(id);                         // 逻辑删除（@TableLogic，deleted 置 1）
    // 连带清理关联表 sys_user_role / sys_user_post
}
```

- **「当前操作人」哪来的？** `SecurityUtils.getUserId()` —— 从阶段 3 讲的「当前线程的 SecurityContext 口袋」里取。红线判断都建立在这个基础上。
- **`deleteById` 是逻辑删除**：`SysUser` 的父类 `BaseEntity` 有 `@TableLogic` 的 `deleted` 字段，MyBatis-Plus 把 `DELETE` 自动翻译成 `UPDATE ... SET deleted=1`，数据不真删（阶段 2）。

## 四、横切三件套：统一响应 / 统一分页 / 统一异常

这三个是**全模块共用**的地基，不属于 user，但每个接口都在用。

### 4.1 `Result<T>`：统一响应结构

```java
public class Result<T> {
    private int code;       // 200 成功；400 业务错；403 无权限；500 服务器错
    private String message; // 提示文案（国际化）
    private T data;         // 真正的数据
    public static <T> Result<T> success(T data) { ... }   // 成功
    public static <T> Result<T> error(int code, String message) { ... }  // 失败
}
```

前端永远收到 `{code, message, data}` 这**同一个信封**，不管成功失败——前端拦截器只需看 `code` 就知道怎么处理。

### 4.2 `GlobalExceptionHandler`：把各种异常统一成 `Result`

```java
@RestControllerAdvice   // 全局兜住所有 Controller 抛出的异常
public class GlobalExceptionHandler {

    @ExceptionHandler(BusinessException.class)       // 业务异常（我们主动抛的）
    public Result<Void> handleBusiness(BusinessException e) {
        return Result.error(e.getCode(), e.getMessage());   // → {code:400, message:"用户名已存在"}
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)  // @Valid 校验失败
    public Result<Void> handleValidation(...) { return Result.error(400, 第一条错误提示); }

    @ExceptionHandler(AccessDeniedException.class)   // @PreAuthorize 没通过 → 403
    public Result<Void> handleAccessDenied(...) { return Result.error(403, ...); }

    @ExceptionHandler(Exception.class)               // 兜底：没预料到的异常 → 500
    public Result<Void> handleException(Exception e) { log.error(...); return Result.error(500, ...); }
}
```

**闭环理解：Service 里 `throw new BusinessException("user.usernameExists")`，为什么前端能收到规范的 400 JSON？**
> 因为异常一路往上抛，**不会**在 Controller 里被 try-catch，而是冒泡到 `@RestControllerAdvice` 这个全局网兜，由它统一翻译成 `Result`。**所以业务代码里只管「大胆抛」，不用each处处 try-catch**——这是「异常驱动」的整洁写法。

### 4.3 `PageResult<T>`：统一分页信封

`{records: [...], total, page, pageSize}`——所有列表接口返回结构一致，前端分页组件通用。

## 五、操作日志 AOP：`@Log` + `OperationLogAspect`（无侵入记录）

回看 Controller，`update / delete / assignRoles` 上多了个 `@Log`：

```java
@DeleteMapping("/{id}")
@PreAuthorize("hasAuthority('system:user:delete')")
@Log(title = "用户管理", businessType = "DELETE")   // ← 只是打个标记
public Result<Void> delete(@PathVariable Long id) { ... }
```

**方法体里完全没有「写日志」的代码，日志是怎么记的？——靠 AOP 切面。**

```java
@Aspect @Component
public class OperationLogAspect {
    @Around("@annotation(logAnno)")     // 拦截所有带 @Log 的方法
    public Object around(ProceedingJoinPoint point, Log logAnno) throws Throwable {
        long start = System.currentTimeMillis();
        // 记录：模块标题、业务类型、方法名、请求URI/IP、操作人（从 SecurityUtils 拿）、参数
        log.setParams(safeParams(point.getArgs()));
        try {
            Object result = point.proceed();      // ★ 放行执行真正的业务方法
            log.setStatus("SUCCESS");
            return result;
        } catch (Throwable ex) {
            log.setStatus("FAILURE"); log.setErrorMsg(ex.getMessage());
            throw ex;                             // 异常照常往上抛，不吞
        } finally {
            log.setCostMs(System.currentTimeMillis() - start);   // 耗时
            logService.recordOperation(log);      // 落库（写失败也不影响业务）
        }
    }
}
```

**要点：**
- **`@Around` 环绕通知**：在业务方法「前后」都插一脚——前面记开始时间、后面记耗时和结果。`point.proceed()` 那一行就是「真正去执行 `delete()`」。
- **无侵入**：业务代码干干净净，加不加日志只由一个注解决定。想给别的方法记日志？加个 `@Log` 就行。这就是 AOP（面向切面）的威力：**把「与业务无关但到处都要」的横切关注点抽出来**。
- **安全**：`safeParams` 对参数做序列化容错；写日志失败被 catch 掉「不影响主流程」——日志是辅助，绝不能因为记日志失败把用户的正常操作搞挂。（对照安全红线：日志参数需限长、不能出现密码/Token。）

## 六、国际化 `MessageUtils`：为什么抛的是 `"user.usernameExists"` 而不是中文？

你一定注意到了：全项目抛异常、写校验消息，用的都是 `user.usernameExists`、`{valid.username.notBlank}` 这种 **key**，从不写死中文。

```java
public class MessageUtils {
    public static String get(String key, Object... args) {
        // 按「当前请求的语言」去 i18n/messages_xx.properties 里查这个 key 对应的文案
        return messageSource.getMessage(key, args, key, LocaleContextHolder.getLocale());
    }
}
```

- `BusinessException("user.usernameExists")` 构造时就调 `MessageUtils.get(...)`，按**当前请求语言**翻译：中文请求 → 「用户名已存在」，英文请求 → 「Username already exists」。
- **一处 throw，中英双语自动适配**——语言不写进代码，而是放在 `i18n/messages*.properties` 里。切语言只改配置、不改 Java。
- 兜底很稳：key 查不到就**原样返回 key**，绝不因为少配一条文案而抛异常打断响应。

> 🔑 记住这条因果：**「抛 key 不抛中文」= 为了国际化**。这也是为什么小测里问「为什么不直接 throw 中文」。

## 七、模板对照法：这一份如何"套"到其余 7 个模块

掌握 User 后，读 role/menu/dept/post/config/dict/log **只需问 3 个问题**：

1. **它的七件套长啥样？** —— 一定还是 controller/service/mapper/entity/dto/vo，字段换一批而已。
2. **它的权限码是哪套？** —— `system:role:*`、`system:menu:*`……命名规律完全一致（阶段 4）。
3. **它有什么「特色点」？** —— 这才是阶段 6 要讲的：

> 一句话：**结构 90% 相同，差异只在「业务特色」那 10%。** 所以阶段 6 会飞快。

8. `replaceRoles(userId, roleIds)` 为什么是「先全删、再逐条插」，而不是「算差集增量更新」？（提示：想想哪个更简单可靠）

<details>
<summary>👉 点击展开参考答案</summary>

**1.** DTO=接前端入参并 `@Valid` 校验；Entity=贴数据库表（一列一字段，含 password 等敏感列）；VO=返给前端的安全视图（挑字段、拼 deptName/roleNames）。不能合一：Entity 直接返前端会泄露 password；前端新增传的字段和表结构也不一致。**入口用 DTO 防脏、出口用 VO 防泄密、中间 Entity 贴库**，三层解耦各自演进。

**2.** 去掉后三次写表（sys_user / sys_user_role / sys_user_post）不再是一个整体。坏情况：主表 `insert` 成功、插角色关联时抛异常 → 用户建出来了但没有任何角色/岗位，留下脏数据且无法回滚。

**3.** 由 `@RestControllerAdvice` 标注的 **`GlobalExceptionHandler.handleBusiness`** 转换。异常从 Service 一路**冒泡**（Controller 不 try-catch），到全局网兜被捕获 → `Result.error(400, 已本地化的 message)` → 序列化成 JSON。

**4.** `@PreAuthorize` 是**第二层**（功能权限：能不能用删除功能）；「不能删自己」是**第三层**（Service 业务红线：针对本次操作对象的规则）。不能做成权限码：它不是「某类人有/没有的功能」，而是「任何人对某个特定对象（自己）都不许做」的动态规则，依赖运行时的「当前操作人 id == 被删 id」，权限码是静态的、表达不了。

**5.** 在 Service `page` 的 `fillDeptAndRoles(vos)` 一步填的。做法：查部门表得到 id→deptName 的 Map，再遍历每个 VO 用它的 deptId 取出名字 set 进去（角色名、岗位名同理）。

**6.** 靠 **AOP 切面** `OperationLogAspect`：`@Around("@annotation(logAnno)")` 拦截所有带 `@Log` 的方法，在 `point.proceed()`（执行真正业务）前后记录模块/操作人/耗时/结果并落库。术语叫**面向切面编程（AOP）**，处理「横切关注点」。

**7.** 为了**国际化**。key 在 `MessageUtils.get` 里按当前请求语言去 `messages_xx.properties` 翻译，中文请求出中文、英文请求出英文，一处 throw 自动双语；语言放配置不进代码。写死中文就没法多语言了。

**8.** 「先删后插」实现简单、语义明确、绝对可靠（结果一定等于目标集合），且在 `@Transactional` 里是原子的。增量算差集要比对新旧两个集合、分别处理新增/删除项，代码复杂、易漏边界，收益（少几条 SQL）在这种低频后台操作里不值得。**简单可靠 > 微优化**。

</details>
