# IM 客户端消息撤回设计

## 背景与目标

服务端已经支持通过 WebSocket `RECALL` 操作撤回消息，并通过 `PUSH type=RECALL` 向会话成员扇出控制消息。客户端协议类型、本地消息表和 REST 消息模型也已有 `RECALL` 与 `recalled` 字段，但当前客户端没有撤回入口、没有处理实时撤回控制消息，也没有渲染撤回占位。

本阶段只闭合客户端消息撤回链路：用户长按消息气泡后可以撤回符合条件的消息；服务端确认后，所有在线与离线设备最终显示一致的撤回占位和会话摘要。

后续按照消息撤回、@ 提及、富媒体、链接卡片的顺序分别实施。本阶段不提前混入后三项能力。

## 已确认的产品规则

- 撤回入口使用“长按消息气泡 → 底部操作面板”。
- 底部面板本期只提供“撤回”，但组件边界允许后续增加复制、转发等消息操作。
- 客户端只对当前判断为可撤回的消息展示入口；服务端始终是权限和时间窗的最终事实源。
- 单聊只能撤回本人消息。
- 群聊中，成员可以撤回本人消息；群主和管理员可以撤回其他成员消息。
- 客户端根据消息的服务端时间戳预判默认 120 秒窗口，超过窗口不展示入口。
- 已撤回消息、待发送消息、发送失败消息、`SYSTEM` 和 `RECALL` 控制消息不展示撤回入口。
- 点击“撤回”后不再增加二次确认；面板关闭并进入处理中状态。
- 同一会话一次只处理一条撤回，防止重复发送。
- 断线状态不发送撤回请求，直接提示用户连接恢复后重试。

## 方案选择

采用“服务端确认后更新本地”方案：客户端发出 `RECALL` 后不乐观删除正文，只有收到服务端 `PUSH type=RECALL` 或后续 REST 同步确认 `recalled=true` 时才改变本地消息。

没有采用立即乐观撤回，因为当前撤回错误帧没有独立请求 ID；并发情况下无法可靠关联和回滚。没有采用每次撤回后强制 REST 同步，因为正常成功路径已经有实时 PUSH，固定同步会增加冗余请求。

## SDK 与数据流

### 发起撤回

`ChatService` 新增 `recall(cid, targetSeq)`：

1. 校验会话 ID、目标 seq 和连接状态。
2. 同一 cid 已存在待确认撤回时拒绝重复发起。
3. 记录该 cid 当前待确认的 `targetSeq`。
4. 发送 `{ op: "RECALL", cid, body: { targetSeq } }`。
5. 若收到对应撤回控制 PUSH，则结束等待并通知页面成功刷新。
6. 若收到无 `clientMsgId`、cid 与待确认撤回一致的 ERROR，则作为撤回失败事件通知页面。

发送消息的 ERROR 继续通过 `clientMsgId` 进入现有失败重发链路，不与撤回错误混用。

SDK 新增 `recallResult` 事件，载荷固定为 `{ cid, targetSeq, status, reason? }`，其中 `status` 为 `succeeded`、`failed` 或 `timeout`。成功 PUSH、服务端 ERROR 和本地确认超时分别产生对应状态；页面通过这一事件清理处理中状态和显示反馈。`ChatService.stop()` 必须同时清除撤回等待计时器，避免旧账号实例继续发事件。

### 应用撤回控制消息

`SyncEngine` 收到 `PUSH type=RECALL` 后，在同一个 SQLite 事务中：

1. 校验 `body.targetSeq` 是有效正整数。
2. 保存 RECALL 控制消息，保留其 seq，保证本地同步位点连续。
3. 将相同 cid、seq=`targetSeq` 的原消息更新为 `recalled=true` 并清空 `body_json`。
4. 将会话摘要推进为 `[消息已撤回]`。
5. 推进 `syncedSeq`。
6. 事务提交后发出消息与会话刷新事件。

正常 WebSocket 帧由现有串行队列按到达顺序处理。若控制消息先于目标消息落库，控制消息仍会被保存；后续原消息落库时检查已存的 RECALL 控制消息并补做撤回标记，避免迟到消息恢复正文。

### 离线与重连

REST 增量同步继续复用 `applyRestMessage`：

- 服务端返回原消息 `recalled=true` 时，本地直接保存撤回状态和空正文。
- REST 返回 RECALL 控制消息时，走与实时 PUSH 相同的本地协调逻辑。
- SQLite 是页面唯一数据源，页面不维护独立的永久撤回副本。
- 如果客户端发起撤回后 10 秒内未收到 PUSH 或 ERROR，ChatService 发出 `recallResult: timeout` 并释放待确认状态；页面随后同步当前会话并以 REST 结果为准，避免永久处于处理中。

## 本地存储边界

不修改数据库表结构。`messages.recalled`、`messages.body_json` 和已有 RECALL 消息行足以表达撤回状态。

`MessageStore` 新增聚焦的方法：

- 按 cid 和 targetSeq 原子标记目标消息已撤回并清空正文。
- 查询某条原消息是否已有对应 RECALL 控制消息，用于处理控制消息先到的时序。

上述方法不包含 UI 文案、权限判断或网络行为。

## 页面交互

### 可撤回判断

聊天页基于当前消息和会话上下文计算是否允许打开操作面板：

- 必须有服务端 seq，且状态为已发送。
- 消息尚未撤回，类型不是 `SYSTEM` 或 `RECALL`。
- 当前时间与消息服务端 `ts` 的差值不超过 120 秒。
- 单聊中 `senderId` 必须等于当前用户。
- 群聊中 `senderId` 等于当前用户，或当前用户在已加载群成员中的角色为 `OWNER`/`ADMIN`。

时间和角色判断只负责减少无效入口；点击后的结果仍完全服从服务端校验。

### 消息操作面板

新增可复用的消息操作底部面板，接收选中的消息和操作列表，不直接调用 SDK。聊天页负责：

- 长按气泡时选择消息并打开面板。
- 点击撤回时关闭面板、设置当前待处理 seq，并调用 `sdk.chat.recall`。
- 操作完成、失败、超时或页面切换时清理本地处理中状态。

### 撤回占位

聊天消息列表不渲染独立 RECALL 控制消息。它根据控制消息的 `targetSeq` 和 `senderId` 为目标消息构建撤回操作者映射，在原消息位置显示：

- 操作者是当前用户：`你撤回了一条消息`。
- 能解析其他操作者姓名：`{姓名}撤回了一条消息`。
- 缺少控制消息或姓名：`消息已撤回`。

占位不显示原正文、头像、发送状态、已读状态或重试按钮。实时 PUSH 和 REST 拉取采用同一渲染规则。

## 错误处理

客户端将服务端撤回错误转换为中文提示：

| 服务端原因 | 客户端提示 |
| --- | --- |
| `RECALL_WINDOW_EXPIRED` | 消息已超过可撤回时间 |
| `RECALL_NO_PERMISSION` | 你没有权限撤回这条消息 |
| `RECALL_TARGET_NOT_FOUND` | 消息不存在或已被处理 |
| `NOT_RECALLABLE` | 这条消息不能撤回 |
| `NOT_MEMBER` | 你已不在当前会话中 |
| 断线 | 当前离线，连接恢复后重试 |
| 确认超时 | 撤回结果确认超时，已刷新会话 |
| 其他 | 撤回失败，请稍后重试 |

失败时保留原消息。页面顶部沿用现有状态提示组件，不新增全局通知系统。

## 变更范围

主要修改范围：

- `im-sdk-core`：ChatService、SyncEngine、SDK 事件和 MessageStore。
- `app-mobile`：ChatScreen 和一个可复用的消息操作底部面板。
- 不修改后端、网关协议、SQLite migration、导航路由和账号隔离逻辑。
